# 대시보드 퍼플 화면 개편 분석 및 설계

- 작성일: 2026-11-12 (Asia/Seoul, 한국시간)
- 상태: 검토용 설계안. 사용자 검토·수정 후 별도 구현 요청 시 착수한다.
- 대상: `hams-matrix`의 `/dashboard` 본문
- 참고: 사용자 첨부 이미지, `hams-onedoc/components/dashboard/dashboard.tsx`
- 이번 작업: 이 문서 작성과 `HISTORY.md` 링크 추가만 수행한다. 애플리케이션 소스·의존성·설정·DB는 변경하지 않는다.
- 문서의 파일 경로는 별도 표기가 없으면 `hams-matrix/` 기준이다. 아래 신규 API·타입·UI는 향후 구현 제안이며 현재 존재하는 기능으로 해석하지 않는다.

## 1. 요구사항과 적용 범위

현재 프로젝트 목록 중심 대시보드를 첨부 이미지의 문서 작업 흐름 중심 화면으로 개편한다. 참고 컴포넌트의 배치와 시각적 위계를 활용하되 링크·데이터·상태·권한 처리는 Matrix의 실제 기능에 맞춘다.

화면은 다음 순서로 구성한다.

1. 대시보드 제목·설명, 전체/개별 프로젝트 선택, 프로젝트 생성 및 RFP 진입 동작
2. RFP → 요구사항 → 설계 → 변경·추적 → 산출물의 5단계 안내 배너
3. 프로젝트·관리 항목·검토·최근 변경을 보여 주는 요약 카드 4개
4. 프로젝트 카드 목록: 상태, 설명, 진행 막대, 작업 현황
5. 최근 산출물 표와 변경 영향 안내 카드
6. 다음 설계 작업으로 이동하는 하단 안내

기존 프로젝트 생성, 플랜 한도 확인, guest 제한, workspace 격리, 오류 재시도 기능을 보존한다. 사이드바·공통 헤더·프로젝트 내부 탭의 전면 개편과 새로운 문서 생성 엔진은 범위에 포함하지 않는다.

첨부 이미지는 어두운 바탕과 분홍/보라 계열 강조를 사용한다. 본 설계의 기본안은 **이미지의 배치·카드·강조 방식은 적용하고 색상은 기존 개인 테마를 따른다**는 것이다. 대시보드만 퍼플 색상을 고정하거나 퍼플 프리셋을 추가할지는 별도 결정 사항이다.

## 2. 현재 구조와 확인 근거

### 2.1 Matrix 진입과 조회

| 파일 | 확인한 현재 동작 | 설계에 주는 영향 |
| --- | --- | --- |
| `app/page.tsx` | 로그인·온보딩 상태에 따라 `/dashboard`, `/onboarding`, `/login`으로 이동 | 참고 소스의 `/?projectId=...`를 그대로 사용하면 안 됨 |
| `app/(workspace)/dashboard/page.tsx` | `WorkspaceSection section="dashboard"`에 `DashboardPage` 전달 | 인증·workspace 셸은 유지하고 본문을 교체 |
| `components/pages/dashboard/dashboard-page.tsx` | 사용자 이름 제목, 통계 6개, 내 프로젝트 목록, 최근 활동, 생성 다이얼로그 | 현재 개편의 주 대상 |
| `components/workspace-section.tsx` | 인증·온보딩 검사와 대시보드 `/api/projects` SSR 프리패치·hydration을 담당 | 새 요약 조회와 서버/클라이언트 캐시 키를 함께 맞춰야 함 |
| `app/api/projects/route.ts` GET | 현재 workspace에서 사용자가 배정된 프로젝트·멤버·통계와 최근 활동 반환 | 관리자라고 전체 팀 프로젝트가 자동 노출되는 구조가 아님 |
| `lib/project-types.ts` | `Project`, 멤버, 요구사항·화면·프로그램·WBS·DB·검수 통계 정의 | 문서 승인율·고객사·작업 단계 필드는 없음 |
| `components/pages/dashboard/create-project-dialog.tsx` | 팀원 선택, 프로젝트 POST, 생성 후 `onCreated(project)` 실행, 목록·구독 캐시 무효화 | 신규 생성 후 RFP 이동에 반환된 실제 ID 사용 가능 |
| `lib/query/keys.ts`, `components/query/workspace-query-runtime.tsx` | 사용자/workspace별 Query scope와 조회 정책 | 새 조회도 같은 정책 적용 |

현재 대시보드는 `/api/projects`를 `matrixKeys.projects(scope)`로 조회한다. 생성 전 `/api/me/subscription`을 `staleTime: 0`, `retry: false`로 확인하고, `user.accountRole !== "guest"`인 경우 생성 버튼을 노출한다. 서버 POST에서도 정원·팀 공유 조건을 검증한다.

GET `/api/projects`는 내부에서 배정 프로젝트의 삭제되지 않은 `project_artifacts`와 참조 링크를 읽고 `acceptanceReport()`를 계산하지만, 응답에는 전체 산출물 목록을 싣지 않는다. 현재 공개 통계는 종류별 개수, 요구사항 완료 수, WBS 진척/공수, 검수 준비 여부·이슈 수 등이다.

최근 활동은 `artifact_revisions`를 전체 배정 프로젝트에서 최신 10건 조회한 뒤 `projectHistoryEnabled()`를 통과한 프로젝트만 응답한다. 따라서 다음에 유의한다.

- 활동의 `snapshot`은 당시 상태이며 현재 산출물과 다를 수 있다. 삭제 이력도 포함한다.
- `activities.length`는 변경 전체 건수도, 최근 7일 변경 건수도 아니다.
- 전체 최신 10건을 받은 뒤 브라우저에서 특정 프로젝트만 고르면 그 프로젝트의 실제 최신 목록을 보장하지 못한다.
- 이력 플랜 필터가 LIMIT 뒤에 적용되므로 결과가 10건보다 적을 수 있다. 새 조회는 권한·플랜·프로젝트 조건을 먼저 적용하고 정렬·제한한다.

### 2.2 실제 탭·산출물 구조

`lib/project-tabs.ts`와 `components/project-workbench.tsx`에서 확인한 탭은 `overview`, `rfp`, `wbs`, `architecture`, `requirement`, `screen`, `database`, `program`, `test`, `trace`, `acceptance`, `history`, `export`, `documents`의 14개다. URL은 `/projects/{id}?tab={ProjectTab}`이다. 참고 소스의 `generate`, `changes`, `artifacts`는 유효한 Matrix 탭이 아니다.

`lib/artifact-types.ts`의 관리 항목은 WBS·아키텍처·요구사항·화면·DB·프로그램·검증의 7종이다. 상태는 `초안`, `검토 중`, `승인`, `진행 중`, `완료`, `보류`이고 버전은 숫자다. 파일을 관리하는 문서함과 RFP는 이 7종 항목과 별도다.

`components/pages/deliverables/deliverables-page.tsx`의 산출물 탭은 문서 목록 화면이 아니라 Excel 통합 문서 다운로드 안내다. `history`는 최근 100건의 스냅샷을 표시하며, 현재 임의의 `doc`, `artifactId` 파라미터로 특정 항목 상세를 여는 계약은 확인되지 않았다. 이번 기본안은 **항목 종류에 해당하는 탭까지만 이동**한다.

`lib/integration.ts`에는 `referencesFor`, `upstreamArtifacts`, `baselineCurrent`, `acceptanceReport`가 있다. 기존 관계·버전 비교는 재사용할 수 있지만, 퍼플 샘플의 `changes` 목록과 동일한 독립 변경 영향 데이터는 없다. `acceptanceReport().issues`는 미작성·미연결·미승인·재검증 등 다양한 문제를 포함하므로 전부 변경 영향이라고 표시하면 안 된다.

### 2.3 참고 퍼플 소스의 차이

`hams-onedoc/components/dashboard/dashboard.tsx`는 `lib/mock/fixtures.ts`의 `projects`, `projectDocuments`, `changes`, `projectHref`와 전용 `DocumentTable`, UI primitives를 사용한다. 실제 DB 연동 화면이 아니라 1차 퍼블리싱 샘플이다.

| 참고 화면 | Matrix와의 차이 | 반영 원칙 |
| --- | --- | --- |
| `/?projectId=...` | Matrix의 메인은 `/dashboard` | `/dashboard?projectId=...`로 필터 상태 유지 |
| 문서 `승인 완료`, `검토 필요` | Matrix 상태는 `승인`, `검토 중` 등 | 원래 상태 유지, 지표 정의 별도 명시 |
| 프로젝트 `stage`, `client`, `initials`, `color` | Matrix Project에 해당 필드 없음 | 상태·멤버 등 실데이터로 대체, 이름에서 약자 생성 |
| 문서 `v1.2`, 이름·담당자·수정일 | Matrix Artifact는 `title`, 정수 `version`, `fields.owner`, `updatedAt` | `v{version}` 표기, 누락 담당자는 `미지정` |
| 샘플 `REQ-002 → FUNC-002` | Matrix 코드·관계는 실제 Artifact 기반 | 고정 문구·ID·관계 복사 금지 |
| 세 번째 흐름 단계 강조 | 참고 CSS의 `nth-child(3)` 강조는 실제 진행 상태가 아님 | 안내 강조로만 사용하거나 모두 중립 표시 |
| 첫 프로젝트 자동 선택 | 전체 보기에서도 첫 프로젝트로 링크됨 | 프로젝트 선택이 필요한 동작을 명시적으로 처리 |

참고 소스는 `projects[0]`, `visibleChanges[0]`에 의존하고 승인율 분모가 0일 수 있다. 이 방식은 복제하지 않으며 프로젝트 없음·변경 없음·항목 없음 상태를 각각 처리한다.

### 2.4 CSS와 테마

현재 `DashboardPage`는 공통 `styles/project-workbench.css`를 import한다. `styles/pages/dashboard/dashboard-page.css`는 존재하지만 대시보드에서 import되지 않으며, 예전 welcome 배너·sparkline·목록용 선언을 포함한다. 파일이 존재한다는 이유로 현재 적용된 스타일로 간주하지 않는다.

`styles/workspace.css`는 셸·공통 UI·표·다이얼로그·개인 테마 등을 로드한다. Matrix의 주요 토큰은 `--canvas`, `--surface`, `--line`, `--ink`, `--muted`, `--primary`, `--primary-soft`다. 참고 `hams-onedoc/app/globals.css`의 Tailwind 클래스와 `--brand` 계열은 통째로 이식하지 않는다.

## 3. 화면 수정 방향

### 3.1 배치·반응형

큰 화면에서는 배너와 통계 4개를 전체 폭에 놓고, 프로젝트 카드는 3열로 배치한다. 하단은 최근 산출물 표가 넓은 왼쪽, 변경 영향 카드가 좁은 오른쪽인 2열로 구성한다. 화면 폭뿐 아니라 AI 채팅 패널이 열린 상태의 실제 본문 폭도 고려한다.

- 넓은 본문: 통계 4열, 프로젝트 최대 3열, 표/영향 카드 2열
- 중간 본문: 통계·프로젝트 2열, 하단 1열
- 좁은 본문: 통계·프로젝트 1열, 제목 작업 버튼 줄바꿈, 단계 배너 세로 배치
- 표는 전용 가로 스크롤 영역을 두고 페이지 전체 가로 넘침은 방지한다.
- 이미지의 9~10px 텍스트 크기를 그대로 고정하지 않는다. 기본 정보는 읽을 수 있는 크기로 조정하고 긴 이름·설명은 말줄임/줄바꿈과 접근 가능한 원문을 제공한다.

대시보드 전용 선택자는 `.matrix-dashboard` 아래로 한정하고 전용 CSS를 명시적으로 import한다. `.panel`, `.stat-card`, `.progress-track` 등 공통 이름을 전역 재정의하지 않는다. 미사용 CSS 전체를 활성화하기보다 새 마크업에 필요한 선언만 전용 파일에서 정리한다.

### 3.2 프로젝트 선택과 CTA

초기값은 전체 프로젝트다. URL `projectId`는 로그인 사용자에게 실제 배정된 프로젝트 목록에서 검증한다. 존재하지 않거나 접근할 수 없는 ID는 동일한 일반 안내를 표시하고 `전체 프로젝트 보기`로 복구한다. 다른 프로젝트로 조용히 대체하지 않는다.

프로젝트를 바꾸면 통계·프로젝트 카드·최근 산출물·변경 영향이 모두 같은 범위로 갱신되어야 한다. URL 뒤로/앞으로 가기와 새로고침도 같은 선택을 복구한다. 전환 중 이전 프로젝트의 데이터에 새 프로젝트 제목을 붙이지 않도록 로딩/이전 데이터 표시를 구분한다.

상단에는 기존 `새 프로젝트` 동작을 유지하고 `RFP로 시작하기`를 추가하는 안을 권장한다.

- 개별 프로젝트 선택 상태: 해당 프로젝트의 `rfp` 탭으로 이동한다.
- 전체 상태: 프로젝트 선택 UI를 연 뒤 선택한 프로젝트의 `rfp` 탭으로 이동한다. 첫 프로젝트를 임의 선택하지 않는다.
- 프로젝트가 없는 생성 가능 계정: 기존 생성 다이얼로그를 열고, RFP 시작 의도로 생성한 경우에만 `onCreated(project)`의 ID로 `rfp` 탭에 이동한다.
- guest: 생성 버튼을 숨기되 배정 프로젝트의 읽기 권한에 따른 탐색은 유지한다.
- 생성 실패·플랜 한도 초과 시 다이얼로그/안내 정책을 유지하고 RFP로 이동하지 않는다.

배너와 하단 링크도 프로젝트를 정해야 하는 경우 같은 선택 절차를 사용한다. 단순 탐색 버튼 클릭만으로 RFP 분석·문서 생성·AI 요청을 실행하지 않는다.

### 3.3 요약 카드 4개와 데이터 정의

아래는 검토를 위한 권장 정의다. 참고 화면과 수치 의미가 다른 항목은 명칭·보조 설명을 함께 바꾼다.

| 카드 | 권장 표시·계산 | 제외/주의 |
| --- | --- | --- |
| 참여 프로젝트 | 현재 필터의 배정 프로젝트 수 | 진행 상태만 세지 않는다면 `진행 프로젝트`라고 표기하지 않음 |
| 관리 항목 | 삭제되지 않은 7종 Artifact의 수 | RFP·문서함 파일·Excel 파일 개수를 섞지 않음. 보조 설명 `WBS·요구사항·설계·검증 항목` |
| 검토 중 | 현재 상태가 정확히 `검토 중`인 Artifact 수 | 검수 이슈 수와 다름. `검토 필요`를 유지하려면 별도 정의 결정 필요 |
| 최근 변경 | 한국시간 오늘을 포함한 최근 7개 달력 날짜의 `UPDATE` revision 수 | 생성·삭제 제외, 동일 항목 반복 수정은 각각 집계, 이력 권한·플랜 적용 |

최근 변경의 기간은 KST 오늘 00:00에서 6일 전부터 다음 날 00:00 미만이다. 조회 시점까지 저장된 이력만 세고 기간 범위를 보조 설명으로 표시한다. 해당 이력 기능을 사용할 수 없는 경우 `0`으로 오해시키지 않고 `이력 기능 제한` 또는 `—`로 표시한다. 일부 프로젝트만 집계 가능하면 `이력 제공 프로젝트 기준`을 명시한다.

### 3.4 프로젝트 카드

현재 모든 배정 프로젝트를 유지하고 제목은 `참여 프로젝트`로 한다. 완료/보류 프로젝트를 임의로 누락하지 않는다. 실제 진행 중인 프로젝트만 표시할지 여부는 결정 사항으로 남긴다.

- 약자는 프로젝트 이름에서 생성하고 색상은 이름/ID에 따른 일관된 장식으로만 사용한다.
- 상태 배지는 `Project.status`를 표시한다. `설계서 작성`, `요구사항 분석` 같은 업무 단계를 추정해 저장하거나 표시하지 않는다.
- 진행 막대는 기존 `completed / requirements`에 따른 **요구사항 완료율**을 기본안으로 한다. 분모 0은 `요구사항 없음`, 막대 0%로 처리한다.
- 참고 이미지의 고객사 대신 `참여자 N명`을 표시한다. 고객사 필드를 신설하지 않는다.
- 요구사항·화면·프로그램·DB 수, WBS 진척·계획/실제 공수, 검수 확인 이슈는 보조 정보 또는 펼침 영역으로 유지할 수 있다. 기존 정보를 숨기거나 줄이는 범위는 검토 시 확정한다.
- 카드의 주 링크는 프로젝트 개요다. 내부에 검수/탭 링크를 추가하면 카드 전체를 `<a>`로 감싸지 않고 링크 중첩을 피한다.

### 3.5 최근 산출물 표

현재 상태의 Artifact를 `updatedAt DESC, id DESC`로 정렬해 최신 4개를 보여 준다. 기본안은 7종 전체를 대상으로 하고 유형·프로젝트명을 함께 표시해 WBS 항목과 설계 문서의 차이를 알린다. 설계 문서만 포함할지는 결정 사항이다.

열은 문서명/관리번호·유형, 버전, 상태, 담당자, 최근 수정일, 열기 순으로 구성한다. 담당자는 `fields.owner`를 사용하며 최근 수정자와 혼동하지 않는다. 날짜는 `Asia/Seoul`, 버전은 `v1`처럼 실제 정수 버전을 표시한다.

삭제된 항목, 삭제 이력의 스냅샷, RFP 원본, 문서함 파일은 이 표에 혼합하지 않는다. 문서함 파일까지 포함하는 통합 문서 목록이 필요하면 별도 데이터 모델 설계가 필요하다.

개별 행은 해당 프로젝트의 `tab={artifact.kind}`로 이동한다. 현재 상세 선택 URL이 없으므로 `doc={id}`를 붙여 상세가 열린다고 가정하지 않는다. 정확한 항목 자동 선택은 별도 요구로 확정될 때 ArtifactList와 URL 계약을 함께 확장한다.

`전체 보기`는 개별 프로젝트에서 `export` 탭으로 가되 실제 목적에 맞게 `통합 산출물 보기`로 표기한다. 전체 프로젝트 상태에서는 먼저 프로젝트를 고르게 한다. 최신 4개 표의 전체 목록 화면이 필요하다면 신규 목록 기능으로 별도 확정한다.

### 3.6 변경 영향 카드와 하단 안내

실데이터로 확인할 수 있는 관계만 표시한다. 기본안은 **승인된 통과 검증 항목의 baseline 버전과 현재 연결 항목 버전의 불일치**를 후보로 삼는다. 이는 변경 영향 전체를 탐지하는 기능이 아니라 재검증이 필요한 일부 사례다.

- `test`의 `fields.result === "통과"`, 상태 `승인` 또는 `완료`, 저장 baseline이 있는 항목을 대상으로 한다.
- baseline에 기록된 연결 항목의 현재 버전과 저장 버전이 다르면 원본/검증 항목의 실제 코드·제목을 표시한다.
- 누락 baseline·연결 삭제·일반 미승인은 확정된 버전 변경으로 표현하지 않는다. 필요하면 별도 `검수 확인` 안내로 구분한다.
- 후보가 여러 개면 관련 항목 최신 수정일, ID 기준으로 한 건을 일관되게 선택한다.
- 후보 없음은 `확인된 재검증 후보가 없습니다`로 표시한다. 모든 변경이 안전하다고 단정하지 않는다.
- `영향 후보 확인`은 `trace`, 재검증 점검은 `acceptance`, 버전 이력은 `history`로 구분한다. 기존 추적표가 임의 후보 항목을 자동 선택하지는 않는다.

원본과 대상 중 권한 없는 항목이 있으면 제목·코드·관계를 노출하지 않는다. 필터가 제한되어 전체 관계를 확인할 수 없으면 불완전한 결과를 0건으로 단정하지 않고 `확인 범위 제한`을 표시한다.

하단 `문서 생성` 링크는 기본안에서 `설계 작업 이어가기`로 바꾸고 `screen` 탭으로 연결한다. Matrix의 AI 작업은 기존 프로젝트 화면·챗봇의 대상 선택/권한 검증 흐름을 따른다. 대시보드 전용 `generate` 탭이나 자동 생성 실행은 새로 만들지 않는다.

## 4. 링크 매핑

모든 프로젝트 ID는 URL 인코딩하고 실제 `ProjectTab`에 포함된 값으로 링크를 구성한다. 아래 `{id}`는 선택/카드/행에 해당하는 프로젝트의 ID다.

| 위치/참고 링크 | Matrix 링크·동작 | 문구/설명 |
| --- | --- | --- |
| 프로젝트 필터 `/` | `/dashboard`, `/dashboard?projectId={id}` | 다른 검색 파라미터 처리 정책도 구현 시 일관되게 적용 |
| RFP로 시작하기 `rfp` | `/projects/{id}?tab=rfp` | 전체/없음은 3.2절 선택·생성 절차 |
| 배너 RFP 분석 | `/projects/{id}?tab=rfp` | 탐색만 수행 |
| 배너 요구사항 구조화 `requirements` | `/projects/{id}?tab=requirement` | 복수형 `requirements`를 탭으로 쓰지 않음 |
| 배너 설계서 초안 생성 `generate` | `/projects/{id}?tab=screen` | `설계 작업`으로 변경. WBS·아키텍처·DB·프로그램은 프로젝트 내부 탭 사용 |
| 배너 변경 영향·버전 관리 `changes` | `/projects/{id}?tab=history` | `변경 이력`으로 변경. 영향 추적은 별도 카드의 `trace` 사용 |
| 배너 산출물 통합관리 `artifacts` | `/projects/{id}?tab=export` | `산출물 통합`으로 변경 |
| 프로젝트 카드 | `/projects/{id}?tab=overview` | 각 카드의 실제 ID |
| 최근 산출물 행 | `/projects/{id}?tab={kind}` | kind는 7종 ArtifactKind |
| 통합 산출물 보기 | `/projects/{id}?tab=export` | 전체 목록이 아닌 통합 다운로드 안내임을 명시 |
| 영향 후보 확인 | `/projects/{id}?tab=trace` | 요구사항 추적표 |
| 재검증 확인 | `/projects/{id}?tab=acceptance` | 통합 검수 |
| 변경 이력 보기 | `/projects/{id}?tab=history` | 이력 플랜·READ 권한 적용 |
| 하단 설계 작업 이어가기 | `/projects/{id}?tab=screen` | 존재하지 않는 generate 탭 사용 금지 |

상단 프로젝트 선택은 조회 필터이고 개별 행·카드 링크는 해당 데이터의 프로젝트로 이동한다. 전체 상태에서도 행 A를 클릭하면 A 프로젝트로 이동해야 한다.

## 5. 데이터 연동과 영향 범위

### 5.1 구현 방식 비교와 권장안

| 방식 | 장점 | 제약/영향 |
| --- | --- | --- |
| 기존 `/api/projects` 응답만 활용 | UI 변경이 작음 | 현재 문서 표·검토 중 개수·기간별 변경·영향 후보를 정확히 만들 수 없음 |
| 프로젝트별 `/artifacts`를 모두 조회 | 기존 API 재사용 | 프로젝트 수만큼 요청 증가, 전체 상세/이력 과다 전송, 전환 시 응답 경쟁 |
| 대시보드 전용 요약 GET 추가 | 집계 정의와 권한 적용을 한곳에서 처리, 기존 프로젝트 목록 계약 유지 | 새 route·조회 함수·DTO·캐시 키 및 검증 필요 |

**이미지의 모든 영역에 실제 데이터를 연결하려면 전용 요약 GET 방식을 권장한다.** 기본안은 `GET /api/dashboard?projectId={id}`이며 미지정 시 전체 배정 프로젝트를 집계한다. 이는 향후 구현 대상이다. 이번 문서 작업에서 API를 만들거나 DB에 접속하지 않는다.

기존 `/api/projects`는 다른 셸·프로젝트 선택 UI에서도 사용하므로 응답의 의미를 바꾸지 않는다. 조회가 중복되는 부분은 공유 가능한 읽기 함수로 추출할 수 있지만 이 개편에 불필요한 대규모 리팩터링은 피한다. 기존 `projectData()`를 프로젝트마다 호출해 상세와 최근 100건 이력을 모두 불러오는 방식도 피한다.

### 5.2 제안 응답 계약

최종 명칭은 구현 전 확정하되 다음 정보를 최소 DTO로 제공한다.

| 필드 | 내용 |
| --- | --- |
| `selectedProjectId` | 검증된 선택 ID 또는 null |
| `projectOptions` | 접근 가능한 선택 목록의 ID·이름. 선택 프로젝트가 있어도 전체 옵션은 보존 |
| `projects` | 현재 범위의 카드 정보·실제 상태·멤버 수·기존 통계·링크 표시용 권한 |
| `summary` | 프로젝트 수, 관리 항목 수, 검토 중 수, 최근 변경 수와 집계 가능 여부 |
| `recentArtifacts` | 최대 4개의 ID·projectId/이름·kind·code·title·version·status·owner·updatedAt |
| `impactPreview` | 후보 없음/확인 범위 제한/확인된 후보 상태, 실제 원본·대상 코드·제목·버전 |
| `recentActivities` | 기존 최근 활동 보존 시 최대 10개. 기존 이력 접근 조건 적용 |
| `range` | 최근 변경 기간의 KST 기준 시작/끝과 조회 기준 시각 |

관리 항목 본문 `fields` 전체, 구조 JSON, 이력 snapshot 전체는 요약 응답에 실지 않는다. 기간별 변경 개수와 최신 활동 목록 개수는 별도로 계산한다.

### 5.3 서버 범위·권한·성능

- `requireUser()` 후 현재 workspace와 프로젝트 배정을 함께 검증한다. 권한 없는 ID와 존재하지 않는 ID는 구분되는 프로젝트 정보를 응답하지 않는다.
- 새 대시보드가 항목 제목·담당자·관계를 노출하므로 `projectPermissionAccess()`의 탭별 READ 권한을 조회·집계에 반영한다. 기존 프로젝트 GET의 배정 기준 필터만으로 충분하다고 가정하지 않는다.
- `history`와 원본 항목 READ, `projectHistoryEnabled()`를 모두 반영해 이력 카드·최근 활동을 구성한다. 일부만 허용되는 경우 집계 범위를 명시한다.
- 영향 분석에서 전체 관계가 필요한 경우 서버 내부 검증과 응답 노출을 구분한다. 부분 데이터로 `acceptanceReport()`를 계산해 잘못된 미연결 이슈를 만들지 않는다. 관련 자료를 읽을 수 없으면 기능 제한 상태로 응답한다.
- 현재 행을 대상으로 하는 목록은 `deleted_at IS NULL` 조건을 적용한다. 활동에는 삭제 이력을 포함할 수 있지만 현재 산출물 표와 구분한다.
- 필터·권한·플랜 확인 뒤 최신순 정렬/LIMIT을 적용한다. 프로젝트별 조회 반복 대신 배정 프로젝트를 묶어 읽고 집계한다.
- 여러 표/통계는 가능한 동일 읽기 트랜잭션 또는 동일 조회 기준으로 구성한다. 응답에 다른 시점의 프로젝트·문서를 혼합하지 않는다.
- 캐시 헤더는 기존 인증 API처럼 `no-store`를 유지하고 사용자/workspace 범위 없는 전역 서버 캐시를 추가하지 않는다.

### 5.4 Query와 생성 후 갱신

`matrixKeys.dashboard(scope, projectId 또는 전체 식별자)`를 추가하고 목록 키와 분리한다. 일반 조회는 `useWorkspaceQueryPolicy()`를 구독하고 AbortSignal과 `RequestError` 처리·현재 workspace 오류 문구를 유지한다.

현재 `WorkspaceSection`은 dashboard일 때 `/api/projects`를 서버에서 미리 조회한다. 권장안에서는 대시보드 경로가 받은 `searchParams.projectId`를 정규화해 같은 scope/필터의 요약 GET을 프리패치하고 클라이언트와 같은 키로 hydrate하도록 이 경계를 함께 조정한다. 다른 섹션의 공통 인증·감사·플랜 동작은 유지한다. 기존 프로젝트 목록 프리패치를 계속 남길지는 셸의 실제 소비 여부에 따라 결정하고, 사용하지 않는 목록과 요약을 대시보드 진입마다 중복 조회하지 않는다. 서버 QueryClient는 현재처럼 요청별로 생성한다.

프로젝트 생성 성공 시 기존 프로젝트 목록·구독 키와 함께 해당 scope의 대시보드 키들을 무효화한다. 프로젝트 편집·삭제·AI 변경 후 돌아왔을 때도 통계가 갱신되도록 기존 무효화/버전 이벤트 연결 지점을 구현 단계에서 확인한다. 권한 조회는 기존 방침대로 진입/작업 직전 확인하며 10초 access 폴링을 재도입하지 않는다.

### 5.5 DB·의존성

권장안은 기존 프로젝트·Artifact·링크·revision·권한/플랜 정보를 읽어 구성한다. 신규 테이블·상태 코드·고객사 컬럼·저장된 진행 단계·마이그레이션이 필요하지 않다. 아이콘은 이미 설치된 `lucide-react`를 사용할 수 있다. 참고 프로젝트의 Zustand 샘플 store, fixture, Tailwind 전체 스타일을 가져오지 않는다.

향후 서버 GET에서 기존 조회 감사 기록 정책을 적용할지는 기존 API 지침에 맞춰 정한다. 이번 조사에서는 GET도 실행하지 않았으며, 소스 읽기만 수행했다.

## 6. 향후 변경 대상 파일

## 7. 상태·오류·접근성

| 상황 | 처리 |
| --- | --- |
| 첫 조회/필터 전환 | 영역별 로딩 표시, 전환 전후 데이터 혼동 방지, `aria-busy` 적용 |
| 프로젝트 0개 | 안내·생성 가능 계정의 생성 CTA, 프로젝트 링크 미생성 |
| 유효하지 않은 선택 ID | 일반 안내와 `/dashboard` 복귀, 타 프로젝트 자동 선택 금지 |
| 항목 0개 | 통계 0, 표 빈 상태, 진행률 분모 0 처리 |
| 영향 후보 0개 | 재검증 후보 없음 표시, 샘플 관계 생성 금지 |
| 이력 플랜/READ 제한 | 제한 안내 또는 액션 숨김, 실제 0건과 구분 |
| API 오류 | workspace 오류 문구와 수동 재시도. 정상 빈 데이터처럼 보이지 않게 함 |
| 생성 권한/한도 변경 | 작업 직전 재확인, 서버 거절 전달, 중복 제출 방지 |

프로젝트 select에는 label을 제공하고 표에는 caption·열 제목을 둔다. 진행 막대는 이름·현재 값·최댓값을 제공한다. 아이콘만 있는 열기 버튼은 항목명을 포함한 접근 가능한 이름을 갖는다. 상태는 색상과 텍스트를 함께 사용한다. 키보드 포커스, 모달 Escape·포커스 복귀, 모션 감소, 라이트/다크 대비를 검증한다.

## 8. 검증 방법

### 8.1 이번 문서 작업

- 읽기만으로 현재 컴포넌트·API·타입·탭·CSS·권한/플랜 흐름을 확인한다.
- 기존 `HISTORY.md` 내용을 보존하고 이 문서의 상대 링크와 한국시간 작성일만 추가한다.
- 작업 전후 파일 해시와 변경 내역을 비교해 이번 변경이 설계 문서와 이력 파일에 한정되는지 확인한다. 기존 사용자 변경은 보존한다.
- 앱 실행·빌드·마이그레이션·DB 조회/수정은 수행하지 않는다. 다음 항목은 구현 후 수행할 검증 계획이며 완료 결과가 아니다.

### 8.2 향후 구현 검증

1. **정적 검사:** `pnpm lint`, `pnpm typecheck`, `pnpm test:query-audit`, `pnpm build`. 기존 실패와 신규 실패를 구분해 기록한다.
2. **집계/API:** 프로젝트 0/1/다수, 상태별 항목, 삭제 항목, 종류별 개수, 검토 중 수, 반복 수정, 생성·삭제 제외, KST 자정과 7일 경계, 동일 수정일 정렬을 검증한다.
3. **격리:** 다른 workspace·미배정·탈퇴/배정 해제 프로젝트, 변조된 projectId, 탭 READ 제한, 이력 플랜 제한에서 목록·개수·코드·제목·관계가 노출되지 않는지 확인한다.
4. **영향 후보:** 최신 baseline, 버전 불일치, baseline 없음, 삭제된 연결, 순환 참조, 권한으로 일부 연결이 가려진 상태를 검증한다. 일반 검수 이슈가 전부 변경 영향이 되지 않아야 한다.
5. **탐색:** `/dashboard` 직접 진입·새로고침·필터·뒤로/앞으로 가기, 전체 상태의 프로젝트 선택, 모든 배너/행/카드/하단 링크가 유효한 Matrix 탭으로 이동하는지 확인한다.
6. **생성 회귀:** 일반 새 프로젝트 생성과 RFP 시작 의도의 생성 후 이동을 구분하고, guest·한도 초과·서버 거절·중복 클릭·취소 후 포커스 복귀를 확인한다.
7. **갱신:** 프로젝트 생성·수정·삭제 및 AI 변경 후 대시보드 복귀 시 통계/목록이 갱신되는지, 사용자/workspace 전환과 빠른 필터 전환에서 이전 응답이 섞이지 않는지 확인한다.
8. **화면:** 1440px·1024px·768px·390px 및 AI 패널 열림 상태에서 줄바꿈·그리드·표 스크롤·긴 이름·많은 프로젝트를 확인한다. 기존 라이트/다크 프리셋과 custom 색상을 확인한다.
9. **접근성:** 키보드만으로 select·CTA·카드·표·다이얼로그 사용, 포커스 표시, 상태 안내, 대비, 200% 확대를 확인한다.

API/브라우저 회귀는 합성 계정·임시 SQLite·모의 외부 AI로 수행한다. 운영 DB에 테스트 데이터를 만들거나 실제 AI 생성 비용을 발생시키지 않는다.

## 9. 결정이 필요한 사항

사용자는 아래 권장안을 문서에서 직접 수정할 수 있다. 표의 권장안은 승인된 최종 요구로 간주하지 않는다.

| 결정 항목 | 권장안 | 다른 선택 시 영향 |
| --- | --- | --- |
| 퍼플의 의미 | 이미지 구조 적용 + 기존 개인 테마 색상 존중 | 퍼플 고정 또는 새 프리셋은 개인 설정/테마 정책 추가 검토 |
| 요약 카드 명칭 | 참여 프로젝트 / 관리 항목 / 검토 중 / 최근 변경 | `전체 문서`·`검토 필요` 유지 시 파일·원본 포함 범위와 지표 정의 필요 |
| 최근 변경 기간 | 오늘 포함 KST 최근 7개 달력 날짜의 UPDATE 횟수 | 24시간·전체 이력·고유 항목 수는 집계/문구 변경 |
| 프로젝트 표시 범위 | 모든 배정 프로젝트, 실제 상태 배지 | 진행 중만 표시하면 완료/보류 접근 동선 필요 |
| 진행 막대 | 기존 요구사항 완료율 | 문서 승인율은 승인/완료 인정 범위·분모를 별도 결정 |
| 설계서 생성 CTA | `설계 작업`/`설계 작업 이어가기` → screen | 별도 생성 마법사·AI 자동 실행은 추가 기능 설계 |
| 전체 상태의 프로젝트 CTA | 프로젝트를 먼저 명시적으로 선택 | 첫 프로젝트 자동 선택은 대상 오해 가능성이 있어 비권장 |
| 최근 산출물 범위 | 7종 Artifact 최신 4개 | 설계 문서만/RFP·문서함까지 포함은 조회·DTO 재설계 |
| 전체 보기의 의미 | `통합 산출물 보기` → export | 전체 문서 목록을 원하면 신규 목록 화면 필요 |
| 변경 영향 범위 | baseline 버전 불일치의 재검증 후보만 표시 | 요구사항 변경의 전체 전파 탐지는 규칙·정확도·UI 별도 설계 |
| 기존 상세 통계·활동 | 카드 보조/펼침 영역으로 유지 권장 | 완전 제거하면 기존 정보 접근 경로 확인 필요 |
| 데이터 연동 수준 | 전용 요약 GET으로 전체 영역 실제 연동 | UI만 먼저 바꾸면 미지원 지표/영역을 명확히 축소해야 함 |
| 정확한 항목 상세 이동 | 해당 종류의 탭까지만 이동 | 특정 항목 자동 선택은 URL·ArtifactList 동작 추가 필요 |

## 10. 구현 착수 조건과 완료 기준

구현 요청을 받으면 사용자가 수정한 이 문서를 다시 읽고 9절의 선택을 반영한다. 최종 선택에 맞춰 API/DTO·Query/무효화·UI/CSS 순서로 적용한 뒤 임시 환경에서 검증한다.

완료 기준은 첨부 이미지의 영역 구성이 Matrix 데이터로 동작하고, 모든 링크가 실제 프로젝트/탭으로 연결되며, 샘플 데이터·임의 고객사·가짜 변경 관계 없이 빈 상태·권한 제한·테마·반응형이 정상 처리되는 것이다. 구현 결과와 DB 변경 여부는 그 구현 작업의 별도 기록에 남긴다.
