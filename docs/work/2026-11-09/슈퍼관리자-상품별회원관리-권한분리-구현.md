# 슈퍼관리자·상품별 회원 관리 권한 분리 구현

- 작성일: 2026-11-09 (Asia/Seoul)
- 기준: `docs/history/2026-11-09/슈퍼관리자-계약별회원관리-권한분리-설계.md` 최신 내용을 다시 읽고 구현했다.
- 기존 미커밋 변경은 보존했다. 설계 문서는 수정하지 않았다.
- 사용자 추가 결정: 결제사는 미정이므로 결제 연동 인터페이스와 미설정 안내까지 제공한다.

## 주요 변경사항

1. 설정은 개인용, 관리자설정은 자기 상품의 biz_admin/team_admin용, 슈퍼관리자설정은 단일 master용으로 분리했다. 메뉴 표시, 직접 페이지 접근, API 권한을 함께 검사한다. 기존 admin 역할은 관리 우회 권한을 갖지 않는다.
2. 요금제 정책 화면·컴포넌트·API를 `/super-admin/settings?tab=plans`, `/api/super-admin/plans`, `components/super-admin/`으로 이동했다. 기존 요금제 API는 master 검사하는 새 구현을 재사용한다. 도움말 아래 슈퍼관리자 메뉴에 요금제·Business·Team 탭을 제공한다.
3. 공통 상품 유형과 업체/팀별 개별 상품 ID를 분리했다. Business A/B는 같은 business 유형이어도 다른 관리 범위다. 상품·유효 계약·계정 역할·활성 소속을 서버에서 함께 확인한다.
4. master는 Business 상품을 생성하고 그 안에서 신규 biz_admin 계정을 생성한다. 기존 이메일의 계정을 덮어쓰거나 자동 승격하지 않는다. Business 신청은 DB에 저장하고 master에게 읽음 상태가 있는 내부 알림을 남긴다. 검토→계약→승인·상품 연결을 지원하며 신청·승인 자체는 구독이나 역할을 바꾸지 않는다.
5. 일반 가입은 user/Free를 유지한다. Team 주문·서버 검증 어댑터·결제 이벤트 재처리와 중복 방지·갱신·환불 상태 처리를 구현했다. 검증된 신규 Team 구매자만 team_admin이 된다. 지원받는 일반 회원은 user를 유지한다. 결제사가 연결되지 않은 현재 상태에서는 안내와 503 응답을 제공하며 결제나 승격을 수행하지 않는다.
6. 고객 관리자는 자기 상품의 회원·프로젝트 필터·가드레일·이력만 관리한다. 목록·총건수·상세·기존 회원/이력 API도 같은 범위를 사용한다. 일반 회원 추가는 가입 이메일 전체로 조회하고 확인 후 지원한다. Business는 무제한, Team은 관리자를 포함한 활성 사용자 20명을 공유 정원으로 계산하며 트랜잭션에서 동시 요청을 제한한다.
7. 워크스페이스는 생성 시 상품 유형과 상품 ID를 보관한다. 구독 변경으로 기존 공간을 바꾸지 않는다. 정책 사용 시 유형과 상품 ID, 소속·계약 유효성을 검사한다. 불일치는 알림 모달과 요금제 화면으로 연결한다. 개인 설정·관리 복구 화면은 접근할 수 있다.
8. 프로젝트 양도를 UI·API·DB 트리거에서 금지했다. 워크스페이스 양도는 프로젝트 소유자를 바꾸지 않으며 대상의 동일 상품·플랜을 검사한다. 프로젝트를 소유한 회원의 상품 지원 회수는 소유권을 자동 이전하지 않고 거부한다.

## DB 변경 여부

- **실제 연결 DB에 041 마이그레이션 적용 완료.** 다른 미적용 마이그레이션을 일괄 실행하지 않고 041만 적용했다.
- 역할 CHECK 확장을 위해 기존 역할 컬럼을 `previous_account_role`로 보존하고 새 `account_role`에 현재 값을 복사했다. 기존 `legacy_account_role`은 변경하지 않았다. 단일 master 인덱스와 master 보호 트리거를 다시 구성했다.
- 신규 테이블: `plan_products`, `contracts`, `product_members`, `business_requests`, `notifications`, `payment_orders`, `payment_events`, `product_events`.
- `user_subscriptions.product_id`, `workspaces.product_id`와 관련 인덱스·공간 상품 고정·프로젝트 소유권 고정 트리거를 추가했다.
- 적용 트랜잭션에서 기존 계정 역할·사용자 구독 유형·공간 소유자/플랜·프로젝트 소유자가 동일한지 비교했다. 전부 보존됐다. 외래키 검사와 `integrity_check`도 통과했다.
- 기존 Business/Team 데이터는 임의 상품에 자동 매핑하거나 관리자 승격하지 않았다. 실제 계약 확인 후 상품을 만들고 소속을 설정해야 한다. master의 기존 공간 연결 기능도 소유자의 상품 소속·고정 플랜이 일치하는 공간만 허용한다.
- 적용 스크립트 재실행도 `applied:false`로 통과했다. 데이터 보존·외래키·무결성을 다시 확인했으며 중복 변경은 없었다.

## 적용한 기본값과 후속 사항

- Team 기본 정원은 구매 관리자 포함 20명, Business 회원 지원은 무제한이다. 사업자 관리자 개수의 별도 제한은 현재 기본값을 두지 않았다.
- 일반 회원 지원은 원래 요구한 관리자 직접 변경 방식으로 구현했다. 정확한 가입 이메일 조회와 확인 절차를 제공한다. 초대 수락/만료·메일 발송 흐름은 별도 도입하지 않았다.
- 사용자당 활성 상품 소속은 하나다. 다른 상품 소속을 자동 해제하거나 이동시키지 않는다. 상품 지원 회수 시 이전 개인 요금제 유형을 복원하며 과거 결제 기간이나 청구를 자동 복구하지 않는다.
- **결제사 선정 및 실제 어댑터 연결은 후속 작업**이다. `lib/team-payments.ts`의 서버 전용 인터페이스를 구현·등록하고 결제사의 서명/조회 검증, 취소·환불 정책을 확정해야 실제 Team 결제가 가능하다. 클라이언트 값이나 단순 구독 PATCH로 Team/Business 승격을 허용하지 않는다.
- 기존 유료 계정·기존 admin의 실제 계약별 전환은 운영자가 확인해 진행해야 한다. 임의 업체 생성·회원 연결은 수행하지 않았다.
- 비밀번호·API 키·토큰은 기록하지 않았다.
