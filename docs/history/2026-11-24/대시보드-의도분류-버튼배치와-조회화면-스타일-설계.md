‘의도분류 페이지’는 `/projects/[projectId]/intent-classifications`의 독립 조회 화면을 뜻한다. 대시보드 버튼이 먼저 여는 기존 벡터화 설정 모달은 기능 개편 대상이 아니며, 새창 이동 및 재열기와 연결된 배치만 검토한다.

좁은 카드에서 긴 버튼 문구까지 항상 한 행에 유지할지는 제7절의 결정 사항이다. 일반 카드 폭에서는 같은 행·오른쪽 끝 배치를 필수로 하고, 좁은 폭의 예외 기준은 검토 후 확정한다.

현재 배치:

```text
프로젝트 카드
  [의도분류]  검색본 모델·발행 시각·자료 변경·작업 상태 ...
  [의도분류 새창 다시 열기 ↗]  ← 요약 길이와 카드 폭에 따라 위치가 바뀜
```

현재 상태 전이는 다음과 같다.

1. 의도분류 버튼을 누르면 `open=true`가 되어 기존 `RagDialog`를 열고 RAG 요약을 명시 재조회한다.
2. 모달 footer의 새창 이동 버튼은 최신 owner 권한을 확인한다. 새창 열기를 시도하면 `onOpened`에서 `moved=true`, `open=false`로 전환한다.
3. 카드의 재열기 버튼은 `moved && !open`일 때만 나타난다. 처음부터 항상 노출하는 구조가 아니다.
4. `moved`는 컨트롤의 메모리 상태다. 새창이 실제 표시되었는지나 닫혔는지를 추적하지 않으며 전체 페이지 새로고침 뒤 유지되지 않는다.
5. `ConsoleWindowButton`은 확인된 권한이 준비되면 문구를 ‘권한을 확인했습니다. 새창 열기 ↗’로 바꾼다. 이 긴 문구와 재클릭 안내도 좁은 카드 배치에 영향을 준다.

따라서 CSS에서 순서만 바꾸거나 재열기에 `margin-left:auto`만 추가하면 요약·상태 안내가 같은 행을 계속 점유한다. **버튼 전용 행과 요약 영역을 나누는 구조 변경**이 필요하다.

## 3. 수정 방향: 프로젝트 카드 버튼

### 3.1 권고 구조

```text
프로젝트 카드
  [의도분류]                       [의도분류 새창 다시 열기 ↗]
                                  권한 확인·재클릭 안내(필요 시)
  검색본 모델 · 발행 시각(KST) · 자료 변경 · 작업 상태
  요구사항 완료율 ...
```

1. `ProjectRagControl`에 `.project-rag-actions` 등 버튼 전용 래퍼를 만들고, 첫 버튼과 조건부 재열기 컴포넌트를 같은 래퍼에 넣는다. 검색본 요약은 래퍼 다음에 두어 별도 행을 점유한다.
2. 첫 버튼에 `button small`을 적용한다. 재열기도 기존 `button`을 유지하면서 `small`을 추가한다. 색상·테두리·hover·disabled는 기존 공통 스타일을 사용한다.
3. 대시보드에서는 액션 행을 카드 가용 폭 전체로 넓힌다. 첫 버튼은 왼쪽, `.console-window-entry`는 오른쪽으로 정렬한다. 상태 안내는 재열기 아래에서 줄바꿈하고 두 실제 버튼의 윗변을 맞춘다.
4. 요약에는 `min-width:0`, 긴 문자열 줄바꿈을 적용해 검색본 모델명·작업 상태가 카드 밖으로 넘치지 않도록 한다. 빈 재열기 자리를 고정 폭으로 예약하지 않는다.
5. 카드용 레이아웃은 `.matrix-dashboard .dashboard-project` 하위로 제한한다. 작업 화면은 같은 공통 버튼을 사용하되 카드 전체 폭·양끝 정렬을 강제하지 않는다.
6. `RagDialog`는 버튼 행 밖에 유지한다. 기존 모달 footer의 왼쪽 이동 버튼과 오른쪽 닫기·벡터화 시작 배치를 유지한다.

재열기에 `small`을 주는 방법은 공통 `ConsoleWindowButton`에 선택적 `buttonClassName`을 추가하는 안을 권고한다. 기본 `.button`은 컴포넌트가 유지하고 호출자가 보조 클래스만 전달한다. 기본값은 빈 문자열로 두어 가드레일 설정·모달의 기존 버튼 크기를 바꾸지 않는다. 스타일 확장 외에 권한 확인·열기 로직을 변경하지 않는다.

### 3.2 노출·권한·새창 동작 유지

- 재열기는 기존 `moved && !open` 조건을 유지한다. 창 닫힘 감지나 재열기 상태 영구 저장은 추가하지 않는다.
- RAG 관리의 owner/admin 권한과 독립 새창의 실제 owner 전용 권한을 구분한다. 첫 버튼을 owner 전용으로 제한하지 않는다.
- 최신 권한 확인 전 빈 창을 열지 않는다. `noopener,noreferrer`, 현재 최대 1440×960 및 화면 크기 제한, 직접 재클릭 지원을 유지한다.
- `window.open()`의 반환 handle만으로 팝업 성공·차단을 판정하지 않는다. 현재 `onOpened`는 열기 시도 시 호출된다는 점을 보존한다.
- 최초 문구, ‘권한을 확인했습니다. 새창 열기 ↗’ 문구, 권한 확인 중·거부 안내 및 팝업 재클릭 안내가 모두 나타나는 상태를 검증한다.
- 접근 권한 폴링, 새 API, DB 필드, 브라우저 저장소를 추가하지 않는다.

## 4. 수정 방향: 의도분류 조회 화면

### 4.1 화면 구성 권고안

‘같은 스타일’의 기본안은 관제센터의 좌측 탐색·상단 헤더·카드형 본문까지 맞추는 것으로 제안한다. 새 업무 화면이나 통계는 추가하지 않는다. 탐색 영역 범위는 제7절에서 최종 결정한다.

```text
┌─────────────────┬─────────────────────────────────────────────────┐
│ Intent Console  │ 의도분류 조회 / workspace       [새로고침] [테마] │
│ 분류 이력(현재) ├─────────────────────────────────────────────────┤
│                 │ workspace · 조회 프로젝트 · 처리 계획 안내       │
│                 │ 현재 검색본 상태 카드                            │
│                 │ 검색 필터 카드                                   │
│                 │ 분류 이력 목록 카드       │ 분류 상세 카드        │
│ workspace       │ 표 · 이전/다음            │ 메타데이터 · 검색 참조 │
│ 프로젝트        │                           │                       │
└─────────────────┴─────────────────────────────────────────────────┘
```

- 제목 ‘의도분류 조회’를 유지하고 헤더 오른쪽에 기존 새로고침·`ThemeToggle`을 둔다. 헤더에 workspace를 표시하고 본문 범위 안내에서 조회 프로젝트를 명확히 구분한다.
- 좌측 탐색에는 현재 제공되는 ‘분류 이력’만 둔다. 가드레일의 승인 메뉴·건수·정책 링크를 복사하지 않는다. 좁은 화면에서 메뉴를 접을 경우 기존 상태를 잃지 않는 단순 UI 상태만 추가한다.
- 설명과 현재 검색본 상태는 목록·상세 데이터와 구분된 안내/상태 영역에 둔다. 전체 분류 건수나 성공률로 해석될 숫자는 새로 만들지 않는다.
- 필터를 관제센터와 같은 surface 카드로 감싼다. 검색 항목·값·제출 동작은 유지한다.
- 목록과 상세를 각각 카드로 만들고 제목·본문·페이지 이동 영역을 정돈한다. 상세는 계속 선택한 이벤트를 보여주는 패널로 유지한다. 가드레일처럼 별도 승인 상세 화면으로 전환하지 않는다.
- 선택 행은 `aria-selected` 상태를 유지하면서 `--primary-soft` 배경으로 강조한다. 기록 시각 버튼은 키보드 선택 가능한 현재 방식을 유지한다.
- 상세의 `dl`은 라벨과 값의 계층을 관제센터와 맞춘다. 긴 ID·코드·버전·참조 문자열은 잘리지 않도록 줄바꿈한다.
- 목록 로딩·오류·빈 결과·상세 미선택·상세 로딩·오류는 각각 해당 카드 안에서 표시한다. 권한 차단은 기존 boundary의 데이터 숨김 동작을 우선한다.

### 4.2 CSS 적용 전략

권고안은 **의도분류 전용 클래스와 기존 전용 CSS 안에서 관제센터의 시각 규격을 맞추는 것**이다. 예를 들어 `intent-console-nav`, `intent-console-header`, `intent-card`처럼 화면 소유 클래스를 사용한다.

- `styles/pages/projects/intent-classifications/intent-classifications.css`를 계속 사용하고 새 규칙은 `.intent-classifications` 하위로 범위를 제한한다. 기존 `.intent-table`, `.intent-columns`, `.intent-detail` 등 의미 있는 훅은 가능한 한 유지한다.
- `--canvas`, `--surface`, `--ink`, `--muted`, `--line`, `--primary`, `--primary-soft` 등 기존 토큰과 `ThemeToggle`·`PreferencesRuntime`을 재사용한다. 독립 테마 상태나 별도 storage 리스너는 만들지 않는다.
- 제2.4절의 셸·헤더·본문·카드·필터·표 규격을 가져오되 가드레일 전용 차트·승인·대기열 상태 CSS는 가져오지 않는다.
- 관리자 설정 CSS나 가드레일 페이지 CSS 전체를 의도분류 페이지에 import하지 않는다. 전역 `.button`, `table`, `header`, `.console-window-entry`를 새 규칙으로 덮어쓰지 않는다.
- 이번에는 공통 셸 추출을 필수로 하지 않는다. `GuardrailControlTower`에는 메뉴 전환·URL·승인·집계 상태가 결합되어 있어 추출 시 영향 범위가 커진다. 향후 공통화가 필요하면 표현 전용 셸/CSS만 분리하는 별도 범위로 검토한다. `styles/pages/_shared`는 만들지 않는다.
- 기본안에서는 독립 route group의 공통 layout과 가드레일 소스를 변경하지 않는다. 두 화면이 같은 업무 컴포넌트를 공유해야 스타일을 맞출 수 있는 것은 아니다.

### 4.3 반응형·상태 보존

- 관제센터의 1439/1100/1023/640px 기준에 맞춰 폭·간격·탐색·목록/상세를 전환한다. 기존 의도분류의 950px 규칙을 중복 유지하지 않고 새 기준과 충돌하지 않도록 정리한다.

- 리사이즈·메뉴 전환·테마 변경 시 필터 초안, 적용 조건, 커서, 선택 이벤트와 Query 캐시를 초기화하지 않는다. 레이아웃별 별도 조회 컴포넌트를 중복 mount하지 않는다.
- `from`, `to`, `intent`, `clarification`, `fallback`, `cursor`, `eventId` URL 및 직접 진입을 보존한다. 새 탐색을 위해 가드레일의 `view`·`approvalId` 계약을 도입하지 않는다.
- 조회 새로고침과 권한 검사 정책을 유지한다. 관제센터의 15초 조회를 스타일과 함께 가져오지 않는다.

### 6.3 후속 구현의 실행 항목

- 정적 검사: `pnpm typecheck`, 변경 파일 대상 ESLint, `pnpm build`.
- 기본 회귀: `pnpm test:intent-classifications`, `pnpm test:dashboard`, `pnpm test:project-rag`.
- 빌드 후 UI 회귀: `pnpm test:intent-classifications-browser`, `pnpm test:dashboard-browser`.
- 공통 새창 컴포넌트 변경 시: `pnpm test:ai-guardrail-approvals` 및 `pnpm test:ai-guardrail-approvals-browser`로 기존 진입·권한 흐름을 확인한다.
- 개인 테마의 공통 코드까지 변경하는 경우에만 기존 personal-preferences 검증 범위를 추가한다. 기본안은 테마 코드를 수정하지 않는다.

DB를 사용하는 후속 회귀는 기존 스크립트의 임시 SQLite·합성 계정 환경에서 실행한다. 구성 DB의 데이터나 스키마를 수정하는 검증은 이 UI 작업에 포함하지 않는다. 실제 실행 결과와 기존 실패는 구현 기록에서 구분한다.

## 7. 결정이 필요한 사항

이번에는 아래 항목의 선택을 문서에 남기며 구현을 진행하지 않는다.

| 항목 | 선택지·쟁점 | 권고안과 영향 |
| --- | --- | --- |
| ‘같은 스타일’의 범위 | 좌측 탐색을 포함한 독립 콘솔 전체 / 헤더·본문 카드 중심 | 전체 셸까지 맞추는 안을 권고한다. 탐색은 현재 기능인 ‘분류 이력’ 하나만 제공한다. 메뉴 하나가 불필요하다고 판단하면 헤더·본문만 맞추되 이 선택을 구현 전에 확정한다. |
| 좁은 카드에서도 반드시 같은 행인지 | 기존 긴 문구 유지·부족한 폭에서 재열기를 오른쪽 다음 줄로 이동 / 문구 축약으로 같은 행 우선 | 일반 폭에서는 같은 행을 필수로 한다. 기존 문구 유지와 부족한 폭에서만 오른쪽 다음 줄을 허용하는 안을 권고하되, 이는 같은 행 요구의 예외이므로 사용자 검토가 필요하다. 절대 한 행이 필수라면 ‘새창 다시 열기 ↗’ 등 문구 축약과 긴 권한 확인 문구의 별도 상태 안내 전환을 함께 확정해야 한다. 글자 강제 줄바꿈·가로 넘침은 피한다. |
| 버튼 크기 | 기본 `.button` 42px / `.button.small` 34px | 카드의 두 버튼은 `button small`을 권고한다. 독립 조회 페이지는 관제센터의 32px 보정을 따라 카드와 구분한다. |
| 공통 셸 추출 | 의도분류 전용 CSS로 규격 일치 / 두 콘솔의 표현 셸 추출 | 이번에는 전용 CSS로 맞추는 안을 권고한다. 공통화 선택 시 가드레일 JSX·CSS와 새 공통 파일이 변경 범위에 들어가며 회귀 부담이 커진다. |
| 상태 화면 스타일 범위 | 조회 화면 내부 상태 / 서버 접근 거부·boundary 상태까지 포함 | 목록·상세 내부 상태를 우선 포함한다. 공통 boundary를 바꾸면 가드레일에도 영향을 주므로 접근 거부 스타일 확장이 필요하면 별도 범위를 확정한다. 데이터 숨김 로직은 유지한다. |

## 8. 구현 순서 제안

1. 사용자 검토본에서 제7절의 셸 범위·좁은 카드 정책·버튼 크기를 확정한다.
2. 버튼 행과 요약을 분리하고 공통 버튼 스타일 및 대시보드 범위 정렬을 적용한다.
3. 기존 조회 상태·URL 로직을 유지하면서 의도분류 화면의 셸·필터·카드·표 스타일을 바꾼다.
4. 구조에 의존하는 기존 브라우저 선택자를 정리하고 실제 카드 정렬·반응형·권한 흐름을 확인한다.
5. 검증 결과와 최종 변경 범위를 별도 구현 기록에 남긴다.
