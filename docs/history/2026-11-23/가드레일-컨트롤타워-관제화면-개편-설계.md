# 가드레일 컨트롤타워 관제 화면 개편 설계

- 작성일: 2026-11-23 (한국시간)
- 상태: 검토용 설계. 이번 작업은 본 문서와 HISTORY.md만 작성하며 소스·DB는 수정하지 않는다.
- 기준: 사용자가 첨부한 관제 대시보드·승인 대기열·상세 검토 이미지 3장과 현재 구현 소스.
- 연계 문서: [최초 화면 설계](Guardrail_Control_Tower_화면설계.md), [승인·재개 구현 기록](../../work/2026-11-23/가드레일-컨트롤타워-승인재개-구현.md), [프로젝트 관리자 자기 요청 승인 변경](../../work/2026-11-23/가드레일-프로젝트관리자-자기요청승인.md).
- 우선 적용 기준: 기존 설계의 미구현 표기·자기 승인 금지 설명보다 현재 소스와 후속 사용자 요구사항을 우선한다.

## 1. 요구사항과 적용 범위

1. 첨부 이미지처럼 전용 좌측 메뉴, 얇은 상단 헤더, 카드 기반 관제 대시보드, 넓은 승인 대기열과 상세 검토 화면으로 UI를 개편한다. 요청의 ‘퍼플’은 화면 개편 취지로 해석하며 별도 보라색 테마를 강제하지 않는다.
2. 승인 대기열에서 요청을 확인하고 승인·반려하는 현재 업무 기능을 유지한다. 요청 선택 → 상세 검토 → 필수 의견 → 승인 범위 확인 → 승인 확정 흐름을 보존한다.
3. 공통 `ThemeToggle`을 화면 상단 우측 끝에 배치한다. 메인 화면과 컨트롤타워가 동일한 개인 테마 설정·저장 API·색상 토큰을 사용한다.
4. 새 창 진입, 관리자·슈퍼관리자 URL 분리, 상품/workspace 관리 범위, 상세 직접 링크, 사용자 명시적 재개, 프로젝트 관리자 자기 요청 승인 규칙을 유지한다.
5. 이미지의 무역·제재 업무 데이터, 지역/APAC·EMEA·AMER, R1~R4, 2인 승인, 컷오프·당직·에이전트 제어 등을 현재 기능으로 오인하게 표시하지 않는다. 현재 데이터와의 대응 및 추가 범위를 아래에서 명시한다.

후속 구현의 기본안은 **관제 대시보드 + 승인 대기열 + 기존 상세 검토의 시각 개편 + 공통 테마 버튼/창 간 동기화**다. 승인 상태 머신·승인 권한·AI 실행 경로의 확장은 포함하지 않는다.

현재 `ai_guardrail_events`는 workspace·사용자·request_id·정책 버전·검사 단계·decision·findings·소요시간·생성시각을 저장한다. severity는 medium/high/critical이며 R1~R4 대응표가 없다. 검사 이력은 AI 실행 1건에서 여러 건 발생하므로 검사 건수를 실행 횟수라고 표시하면 안 된다.

현재 `GET /api/{admin,super-admin}/ai-guardrails`는 정책 초안·발행 이력과 최신 검사 100건을 함께 반환한다. 이 최근 100건을 클라이언트에서 합산해 ‘오늘 전체’ 통계로 쓰거나 관제 화면 때문에 정책 초안을 반복 조회하지 않는다.

## 4. 수정 방향: 전용 셸과 화면 전환

### 4.1 공통 셸

```text
┌─────────────────┬──────────────────────────────────────────────────────┐
│ Control Tower   │ 현재 화면 / 상품 · workspace    갱신시각 [테마버튼] │
│                 ├──────────────────────────────────────────────────────┤
│ 관제 대시보드   │ 화면별 본문                                          │
│ 승인 대기열 [N] │                                                      │
│ 처리 이력       │                                                      │
│ 가드레일 정책 ↗ │                                                      │
└─────────────────┴──────────────────────────────────────────────────────┘
```

- 데스크톱 사이드바 폭 약 200px, 헤더 최소 높이 56px, 본문 패딩 16~24px, 카드 간격 12~16px를 제안한다. 현재 max-width 1800px의 단일 본문을 전용 셸 내 가용 폭 구조로 바꾼다.
- 헤더 좌측은 현재 메뉴/상세 breadcrumb, 중앙은 상품·workspace 범위, 우측은 마지막 갱신·새로고침·테마 순서다. 사용자 표시가 필요하면 서버에서 최소 이름/역할만 전달한다.
- 상단 우측 테마 버튼은 대시보드·목록·상세에서 동일 위치에 유지한다. 좁은 화면에서도 메뉴/제목/테마 버튼이 가려지지 않게 하고 범위 설명과 갱신시각은 다음 줄로 배치한다.
- 사이드바 메뉴는 관제 대시보드, 승인 대기열, 처리 이력, 가드레일 정책으로 구성한다. 감사 추적·에이전트 관리·기준 데이터·리포트의 빈 메뉴를 만들지 않는다.
- 정책 메뉴는 기존 관리자설정을 명시적 새 창 링크로 열어 현재 승인 의견 초안을 유지한다. 정책 편집 기능을 컨트롤타워 내부에 복제하지 않는다.
- ‘정상 운영’ 같은 상태는 현재 건강도 API가 없으므로 표시하지 않는다. 대신 ‘관제 데이터 갱신 시각’과 조회 실패/일부 데이터 조회 실패를 표시한다.

### 4.2 URL과 초기 진입

- 기존 경로와 `workspaceId`, `approvalId`를 유지하고 읽기 화면 구분용 `view=dashboard|queue|history`를 제안한다. 업무 API의 tab 파라미터와 화면 메뉴 view는 구분한다.
- 기존 링크 호환을 위해 view 없는 기존 진입은 승인 대기열로 유지한다. 관제 대시보드는 전용 메뉴로 진입한다. 대시보드 기본 진입으로 바꾸려면 10절에서 결정한다.
- approvalId가 있으면 view가 없거나 dashboard여도 요청 상세를 우선 복원하고 목록 복귀 위치는 승인 대기열로 정규화한다. 필터 밖의 요청은 기존처럼 상세 직접 조회로 연다.
- 목록 행 선택은 우측 미리보기를 바꾸며, ‘상세 검토’는 같은 창의 상세 화면으로 전환한다. 새 창을 중복 생성하지 않는다.
- 목록→상세→목록 이동 시 필터·탭·커서·선택 행·스크롤을 유지한다. 브라우저 뒤로/앞으로로 화면 이동을 복원하고 불필요한 요청 간 의견 초안 혼합을 방지한다.
- 승인 의견이 있는 상태에서 다른 건/메뉴로 이동할 때 초안 유실 확인을 제공한다. 확정 취소는 초안을 유지하고 처리 성공 시에만 의견을 비운다. 저장되지 않은 의견을 URL/localStorage에 넣지 않는다.

## 5. 관제 대시보드 설계

### 5.1 실제 데이터 기반 카드

상단은 아래 6개 카드로 구성한다. 1440px 이상 6열, 중간 폭 3열, 좁은 폭 2열/1열로 재배치한다.

| 카드 | 집계 정의 | 기준 |
| --- | --- | --- |
| 오늘 검사 | 오늘 생성된 ai_guardrail_events 건수 | KST 당일 00:00 이상, 익일 00:00 미만 |
| 오늘 차단 | 위 이벤트 중 decision=block 건수 | 검사 단위. 고유 AI 실행 건수와 구분 |
| 승인 대기 | requested_at이 있고 미만료 pending | 기존 count와 같은 workspace 전체 기준 |
| 승인 후 재개 대기 | requested_at이 있고 미만료 approved | 관리자 승인과 실제 실행을 구분 |
| 만료 임박 | 미만료 pending 중 expires_at까지 2시간 이하 | 이미지의 컷오프 대신 실제 승인 요청 유효시간 사용 |
| 재개 실행 중 | resuming 상태 건수 | 현재 count 기준, lease 종료 정리 결과와 일치 |

- 승인 관련 현재 건수와 오늘 검사 지표는 기준이 다르므로 카드 보조 문구에 ‘현재’ 또는 ‘오늘 KST’를 명시한다.
- 임박 2시간은 제안값이다. ‘30분 이하’ 보조 강조는 가능하되 SLA 위반/에스컬레이션으로 해석하지 않는다. 경과된 건은 만료 처리되며 pending 임박 건수에서 제외한다.
- 관리자 정책 테스트도 같은 이벤트 저장소를 사용한다. 첫 구현에서 테스트 제외가 정확히 보장되는 식별자를 확인하지 못하면 지표에 ‘정책 테스트 포함’을 표기한다. 추정 규칙으로 제외하지 않는다.

### 5.2 중간·하단 패널

| 영역 | 내용 | 동작 |
| --- | --- | --- |
| 최근 검사 이벤트(약 2/3 폭) | 최근 20건의 KST 시각·검사 단계·결정·탐지 정책·정책 버전 | 화면 이름은 ‘최근 검사 이벤트 / 15초 갱신’. 승인 요청과 연결된 건만 승인 상세 링크 제공 |
| 만료 임박 승인(약 1/3 폭) | pending 5건, 만료 빠른 순, 요청자·프로젝트·정책·만료시각/남은 시간 | 선택 시 기존 상세 검토로 연결. 검토 없이 바로 승인하는 버튼은 두지 않음 |
| 오늘 차단 정책 분포 | block 이벤트의 findings.rule별 고유 이벤트 건수, 상위 5개 | 막대와 숫자/텍스트 함께 표시. 한 이벤트의 여러 정책 때문에 합계가 차단 건수보다 클 수 있음을 설명 |
| 검사 단계 분포 | input/context/tool/tool-result/output별 오늘 이벤트 건수 | 읽기 전용 요약 |
| 현재 승인 현황 안내 | 승인 대기·승인 후 재개 대기·재개 실행 중 및 정책 화면 링크 | 실제 데이터가 없는 에이전트 상태/기준 데이터 최신성 카드의 대체 영역 |

검사 이벤트의 request_id가 승인 행의 event_id와 연결되지 않을 수 있다. 연결되지 않은 검사에서 임의 승인 요청을 생성하지 않는다. 목록/대시보드는 마스킹된 프롬프트 본문도 반환하지 않고 상세에서만 기존 허용 범위로 제공한다.

### 5.3 조회 API와 집계 영향

- 기존 승인 count/list/detail/decision 계약을 유지한다. 대시보드에는 최소 읽기 모델을 반환하는 신규 `GET /api/{admin,super-admin}/ai-guardrail-control-tower/overview?workspaceId=...`를 제안한다.
- 응답 제안: `asOf`, `timeZone: Asia/Seoul`, `todayRange`, `inspectionCounts`, `approvalCounts`, `expiringSoonCount`, `recentEvents`, `expiringApprovals`, `blockedRules`, `stageCounts`. 승인 요약에는 기존 DTO의 최소 필드만 포함한다.
- 두 관리자 경로는 기존 `guardrailAdminUser`와 상품/workspace 검증을 사용한다. 슈퍼관리자 주소라는 이유로 workspace 조건을 제거하지 않는다. 응답은 private, no-store다.
- 서버에서 날짜 경계·JSON 정책 분포·만료 기준을 집계한다. 클라이언트는 최신 20건/현재 목록 페이지만으로 통계를 계산하지 않는다. 집계의 기준 시각 asOf를 하나로 고정하고 필요한 경우 읽기 트랜잭션으로 일관성을 확보한다.
- 기존 count의 만료/abandoned lease 정리 동작과 의미를 재사용한다. overview 구현 시 대량 쓰기 정리나 중복 정리를 새로 만들지 않는다.
- 새 Query key는 사용자/workspace/관리자 경로를 포함한다. overview는 대시보드 표시 중에만 15초 갱신하고 탭 비표시·메뉴 이동 시 중단한다. 승인 완료 후 목록·count·overview를 필요한 범위에서 무효화한다.
- 기존 인덱스 `ai_guardrail_events(workspace_id,created_at DESC)`와 승인 인덱스로 실행 계획을 확인한다. 본 설계 기본안은 DB 마이그레이션 없음이다. 대량 이력에서 추가 인덱스가 필요하면 실측 근거와 별도 migration 범위를 검토한다.

## 6. 승인 대기열과 상세 검토 설계

### 6.1 대기열

- 기존 상태 탭은 승인 대기 / 승인 후 재개 대기 / 처리 이력으로 유지한다. 별도 처리 이력 메뉴는 같은 history 표시를 여는 바로가기다.
- 기존 기간(KST), 요청자 이름/이메일, 프로젝트(없음 포함), 정책, 검사 단계, 이력 상태 필터 및 검색·초기화를 모두 유지한다. 이미지처럼 필터 바를 정돈하되 기능을 삭제하지 않는다.
- 표 컬럼은 요청 시각·요청자/프로젝트·정책/검사 단계·상태·만료시각/남은 시간으로 구성한다. 폭이 허용되면 짧은 요청 ID를 보여주고 전체 ID는 상세에서 복사한다.
- 우측 미리보기에는 요청자·프로젝트·정책·단계·상태·만료와 ‘상세 검토’만 제공한다. 현재 목록 DTO에 없는 promptExcerpt·inspectionExcerpt를 미리보기 때문에 목록에 확장하지 않는다.
- 20건 커서 페이지, 기존 정렬, 빈 목록과 필터 결과 없음의 구분, 오류/로딩 상태를 보존한다. 선택 시 행 강조와 키보드 접근·명확한 링크 이름을 제공한다.
- 이미지의 선택 박스/선택 건 일괄 승인/내 승인함/R등급 필터/2차 승인 상태는 제공하지 않는다. 전체 건수와 검색 결과 건수도 혼동하지 않게 표시한다.

### 6.2 상세 화면

```text
[승인 대기열로]  요청 ID · 정책 · 상태                    만료시각
┌──────────────────────────────────┬──────────────────────────────┐
│ 사용자가 요청한 작업             │ 처리 의견 (필수)             │
│ 요청자 · 프로젝트 · 대상         │ [의견 입력]                  │
├──────────────────────────────────┤ [반려] [이 요청 승인]        │
│ 가드레일 탐지 근거                │ → 기존 승인 범위 확인        │
│ 마스킹 내용 · 단계 · 정책 버전    │ → [승인 확정]                │
├──────────────────────────────────┼──────────────────────────────┤
│ 처리 이력 (시각 · 처리자 · 의견) │ 승인 시 적용 범위/미저장 건수│
│                                  │ 사용자가 이어서 진행해야 실행│
└──────────────────────────────────┴──────────────────────────────┘
```

- 기존 `GuardrailApprovalDetail`을 업무 로직 소유자로 유지하고 카드 배치를 변경한다. 승인/반려 POST URL, expectedVersion, comment, decision 값과 오류 후 재조회 동작은 유지한다.
- 처리 권한은 `canDecide`를 따른다. 해당 프로젝트 owner/admin이 자기 요청을 처리할 수 있는 후속 변경도 그대로 유지한다. 자기 요청이라는 이유로 버튼을 다시 일괄 숨기지 않는다.
- 승인 확인 화면에 사용자·프로젝트·정책 및 이 검사에 한정된 예외라는 내용을 유지한다. 관리자 승인 직후 AI 실행·저장 API를 호출하지 않는다.
- 현재 제공하는 마스킹된 요청/탐지 발췌·미저장 변경안 수·첨부 개수·정책 버전·검사 단계·처리 이력을 재배치한다. 개인 전체 대화·첨부 원본·암호화 checkpoint·실제 도구 인자를 추가 노출하지 않는다.
- 이미지의 ‘실행 미리보기’는 **승인 시 적용 범위**라는 업무 안내로 대응한다. 아직 생성되지 않은 결과를 완성된 실행 결과처럼 표시하지 않는다.
- 정책 버전/검사 단계/판정 강도는 실제 문자열을 사용한다. R3·AI 유사도·1차/2차 승인 등의 값을 생성하지 않는다.
- 폴링 중 승인/만료/조건 변경/권한 변경이 발생하면 기존 오류 처리와 최신 상태 확인을 보존한다. 전송 중 중복 클릭을 막고, 버전 충돌 후 자동 재전송하지 않는다.

## 7. 공통 테마 및 창 간 동기화

### 7.1 버튼과 테마 적용

- `components/theme-toggle.tsx`의 `ThemeToggle`을 셸 헤더 우측 마지막 동작으로 재사용한다. role=switch, aria-checked, 라이트/다크 변경 title, 저장 중/편집 중 비활성화를 유지한다.
- 테마는 사용자별 공통 개인 설정이다. workspace나 컨트롤타워 전용 설정을 생성하지 않는다. 공통 6개 프리셋과 custom, 강조색·명암 전환 규칙은 현재 `/api/me/preferences`의 동작을 따른다.
- CSS는 `--canvas`, `--surface`, `--ink`, `--muted`, `--line`, `--primary`, `--primary-soft`, `--on-primary` 등 공통 토큰을 사용한다. 명도·위험 색도 기존 의미 토큰을 우선하고 화면에만 고정된 보라/남색 팔레트를 만들지 않는다.
- 공통 테마 초기화 경로를 유지해 새 창 진입·새로고침 시 저장된 개인 설정을 복구한다. 별도 테마 선택 모달이나 프리셋 편집 기능은 추가하지 않는다.

### 7.2 열린 창 사이 반영

공통 테마를 쓰더라도 각 창의 Zustand/QueryClient는 독립이다. 따라서 같은 사용자로 열린 메인 화면과 컨트롤타워의 변경 반영을 공통 PreferencesRuntime에서 보완하는 안을 제안한다.

1. 이미 저장 시 발생하는 `matrix-preferences:<현재 사용자 ID>` storage 이벤트를 수신한다. payload를 최종 설정으로 신뢰하지 않고 기존 preferences Query/API를 다시 조회한다.
2. 성공적으로 받은 더 최신 version을 현재 사용자·generation·owner 범위에서 병합한다. 다른 사용자 이벤트나 오래된 응답은 무시한다. 연속 이벤트는 불필요한 중복 조회를 합친다.
3. 개인 설정 화면에 저장 전 초안이 있거나 저장 중이면 초안을 덮어쓰지 않는다. 기존 saved/current 병합·version 충돌 처리를 보존하고 저장 완료/초안 종료 시 최신 설정을 반영한다. 수신한 이벤트로 PATCH를 반복 호출하거나 이벤트를 재발행하지 않는다.
4. localStorage가 차단된 환경에서는 현재 창의 DB 저장과 테마 전환은 정상 동작하고 다른 창은 다음 설정 조회/새로고침 시 반영된다. 즉시 동기화 보장이 필요한 추가 수단은 별도 결정한다.
5. 이벤트 리스너는 공통 runtime에서 한 번만 등록·해제한다. 컨트롤타워별 listener를 복제하거나 focus/visibility 프로젝트 접근 폴링을 도입하지 않는다.

이 변경은 메인 화면·문서 뷰어 등 동일 runtime 소비 화면에 영향을 줄 수 있으므로 테마 저장 실패 복원, 편집 초안 보호, 사용자 전환 회귀가 필요하다.

## 8. 반응형·접근성·상태 표현

- 1440px 이상: 전용 사이드바 + 넓은 본문. 대기열 약 2:1, 상세 약 3:2, 대시보드는 카드 grid를 사용한다.
- 1024~1439px: 사이드바 축약 가능. 표의 가독성을 확보하고 상세/미리보기를 같은 창에서 전환한다. 현재 1279px 상세 전환 규칙과 새 셸 폭을 함께 조정한다.
- 1023px 이하: 내비게이션을 접이식 메뉴로 바꾸고 본문 1열. 선택한 상세에 집중하며 목록 복귀 동작을 제공한다. 390px에서도 테마 버튼과 주 동작이 화면 밖으로 밀리지 않아야 한다.
- 표는 의미 있는 table 헤더와 가로 스크롤을 제공한다. 페이지 전체의 불필요한 가로 스크롤을 방지한다.
- 선택/위험/만료 상태는 색과 텍스트로 함께 표현한다. 막대/아이콘만으로 상태를 구분하지 않는다. 포커스 이동·ESC/키보드 이동·접근 이름을 검증한다.
- 갱신 실패 시 기존 값을 최신 정상값으로 오인하게 하지 않는다. 마지막 성공 시각과 오류를 표시하고 수동 재시도를 제공한다. 0건·미집계·조회 실패를 구분한다.
- 남은 시간은 로컬 표시용 타이머로 갱신하며 초 단위 서버 폴링을 추가하지 않는다. 처리 가능 여부·만료 확정은 서버 판정을 따른다.

| `styles/README.md`, `README.md`, `AGENTS.md`, `CLAUDE.md`, 작업 기록/WORK_HISTORY | 후속 구현 완료 시 변경 기준 기록 | 이번 설계 단계에서는 수정하지 않음 |

`app/(control-tower)/layout.tsx`, 공통 ThemeToggle·테마 API·기존 승인 서비스는 기본적으로 재사용 대상이다. 승인 서비스는 새 통계에서 공통 로직 추출이 꼭 필요할 때만 변경하고 승인 업무 규칙은 바꾸지 않는다. DB 기본안은 변경 없음이다.

## 10. 결정이 필요한 사항

| 항목 | 제안 기본안 | 대안/추가 결정 |
| --- | --- | --- |
| 초기 진입 화면 | 기존 링크 호환을 위해 승인 대기열 유지 | 새로 여는 창부터 관제 대시보드 우선으로 변경할지 검토 |
| 화면 개편 범위 | 이미지 구조를 반영한 실제 데이터 기반 대시보드·대기열·상세 | 대시보드 제외, 기존 대기열 중심 외형 개편만 먼저 할 수 있음 |
| 만료 임박 기준 | pending 잔여 2시간, 30분 이하 강조 | 24시간 승인 유효시간과 운영 업무에 맞춰 기준 조정 |
| 검사 통계의 테스트 포함 | 동일 저장소의 검사 이력 전체, 테스트 포함 문구 | 실행/테스트 구분 요구 시 확실한 식별 방법과 과거 데이터 처리 정의 필요 |
| 추가 내비게이션 | 실제 제공 화면만 표시 | 이미지의 감사 추적·에이전트·기준 데이터·리포트는 별도 요구사항/데이터/API 필요 |
| 테마 공통 범위 | 같은 사용자의 저장 설정 공유 + 열린 창 storage 이벤트 동기화 | 모든 사용자/workspace에 일괄 테마 적용은 현 요구의 범위로 보지 않음 |
| 상세 화면 방식 | 같은 창의 전체 상세 카드 화면 + 목록 우측 미리보기 | 현재 목록/상세 동시 패널을 계속 유지할 수 있음 |

현재 승인은 단일 관리자 승인이고, 승인자 자동 배정·2인 승인·등급별 승인·제재 업무 판정은 미지원이다. 이미지의 해당 기능까지 필요하면 기존 승인 상태 머신과 DB 변경을 포함하는 별도 설계가 필요하다.

## 11. 후속 구현 검증 방법과 수용 기준

### 11.1 기존 승인 기능 회귀

1. 사용자 예/아니요, 전송 전 관리자 목록 비노출, 승인 대기·승인 후 재개 대기·처리 이력, 상세 직접 URL 복원을 검증한다.
2. 필수 의견·반려·승인 확인/확정, 동일 건 동시 처리 충돌, 만료/조건 변경·권한 변경, 요청 처리 이력과 목록 갱신을 검증한다.
3. 해당 프로젝트 owner/admin의 자기 요청 승인 허용과 프로젝트 없음/member/viewer의 자기 처리 차단을 API에서 재확인한다. 관리 범위 밖 상품/workspace 조회·결정 거절도 유지한다.
4. 관리자 승인만으로 실행되지 않으며 사용자가 이어서 진행해야 재개되는지, 재개 중복 방지와 기존 사용자 변경안 HITL이 유지되는지 확인한다.

### 11.2 화면·데이터 검증

1. 관제 카드의 실제 DB 집계, KST 자정 경계, 테스트 포함 표기, 만료 경계, 다중 findings 중복 집계 정의를 임시 DB로 검증한다.
2. 최신 20건 이벤트/5건 임박 목록, 승인 연결 없음, 빈 데이터·일부 조회 실패·접근 거절·느린 응답을 검증한다.
3. 날짜/정책/프로젝트 등 모든 기존 필터와 이전/다음 커서가 유지되고, 미리보기→상세→뒤로 이동 시 목록 조건과 초안 보호가 동작하는지 확인한다.
4. 1440/1280/1024/768/390px와 라이트/다크·공통 프리셋/custom에서 카드·표·상세·사이드바·헤더 테마 버튼을 확인한다. 키보드/포커스·색 대비·상태 텍스트도 확인한다.
5. 활성 메뉴에서만 조회가 갱신되고 비표시 창/탭에서 폴링이 중지되는지, 승인 처리 후 필요한 Query만 무효화되는지 검사한다.

### 11.3 공통 테마 검증

1. 메인 화면과 컨트롤타워 두 창을 열어 어느 창에서 변경해도 같은 사용자 테마가 반영되는지, 새로고침 후 DB 설정으로 복원되는지 검증한다.
2. 개인 설정 편집 초안·저장 중·저장 실패·오래된 version·다른 사용자 이벤트·localStorage 차단에서 초안/계정 경계를 보존하는지 확인한다.
3. 테마 전환이 승인 의견·선택 건·필터·생성/재개 상태를 초기화하거나 승인 요청을 발생시키지 않아야 한다.

후속 구현 시 `pnpm test:ai-guardrail-approvals`, 빌드 후 `pnpm test:ai-guardrail-approvals-browser`, 관련 테마/overview 검증, 변경 파일 ESLint·타입 검사·빌드를 수행한다. 테스트는 합성 계정·임시 SQLite·모의 AI로 수행하며 실행 결과를 별도 작업 기록에 남긴다.
