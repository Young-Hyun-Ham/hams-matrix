# AI 챗봇 승인 요청 대화 통합·문맥 분리 설계

- 작성일: 2026-11-23 (Asia/Seoul, 한국시간)
- 상태: 검토용 설계 초안. 사용자 검토·수정 후 별도 구현 요청으로 진행한다.
- 분석 기준: 현재 작업 디렉터리의 소스. 이미 수정되거나 미추적 상태인 승인·컨트롤타워 구현도 포함해 확인했다.
- 이번 작업: 이 설계 문서와 `HISTORY.md` 링크만 작성한다. 소스·마이그레이션·설정·DB는 변경하지 않는다.

## 1. 요구사항

| 번호 | 요청 | 완료 기준 |
| --- | --- | --- |
| R1 | 입력 영역 아래 승인 요청 레이어를 대화 내용 영역으로 이동하고 챗봇 안에서 HITL 처리 | 정책 안내·예/아니요·승인 상태·이어서 진행·취소가 해당 질문의 AI 응답 위치에 나타난다. 기존 변경안 검토도 해당 답변 안에서 수행한다. |
| R2 | 승인 대기 중에도 다른 질문 가능 | 승인 요청 여부 선택 중·관리자 승인 대기·승인 후 재개 대기 상태는 새 질문의 입력과 전송을 막지 않는다. 다른 질문에는 대기 중인 질문/응답을 제외한 기존 대화 문맥으로 답한다. |
| R3 | 승인된 대화 선택 후 이어서 진행 시 당시 문맥 사용 | 선택한 질문 이전의 유효 문맥과 원래 질문·첨부로 재개한다. 대기 중 나눈 후속 대화와 현재 입력 초안을 섞지 않는다. |
| R4 | 답변 작업 버튼 정렬·크기 통일 | HITL 선택 버튼은 답변 하단 왼쪽부터, `결과 크게 보기`·`다시 사용`은 오른쪽 끝에 배치한다. 승인 카드의 큰 기본 버튼을 챗봇 공통 버튼 크기로 맞춘다. |

여기서 **관리자 정책 승인**은 차단된 작업의 제한된 실행 허용이고, **사용자 변경안 HITL**은 생성한 변경안을 실제 자료에 적용하기 전 검토다. 관리자 승인이 완료되어도 변경안 HITL은 생략하지 않는다. 새로운 HITL 설정 스위치를 추가하는 요청으로 해석하지 않는다.

### 1.1 문맥 적용 예

| 순서 | 대화 | 상태 및 모델에 전달할 내용 |
| --- | --- | --- |
| 1 | A 질문/답변 | 정상 완료 |
| 2 | B 질문 | 가드레일 탐지 → 승인 요청 → 대기 |
| 3 | C 질문 | A + C로 답변. B 질문·차단 내용·승인 카드·첨부는 제외 |
| 4 | D 질문 | A + C + D로 답변. B는 계속 제외 |
| 5 | B 승인 후 `이어서 진행` | B 시작 시 고정한 A + 원래 B 질문/첨부로 실행. C·D와 현재 입력 초안은 제외 |

문맥의 `+`는 모든 원문을 무제한 전달한다는 의미가 아니다. 기존 이력의 건수·용량·첨부 제한을 유지한다. 과거 대화 선택은 선택 상태·정책 상세를 보여 주는 동작이며, `이어서 진행` 클릭이 실행 동작이다. 승인이나 카드 선택만으로 자동 실행하지 않는다.

### 2.1 화면·상태 구조

`다시 사용`은 현재 질문·이미지·모델을 입력 영역에 복원하는 기능이다. 과거 문맥으로 재개하는 기능은 아니다. 두 동작을 같은 버튼으로 처리하지 않는다.

### 2.2 서버 실행·저장·재개

1. `app/api/ai/chats/route.ts`는 요청 초기에 `assertNoPendingReview()`와 `assertNoGuardrailWait()`를 호출한다. 대화 lease 획득 뒤에도 `assertNoGuardrailWait()`를 다시 호출한다. 화면만 활성화하면 새 질문은 서버에서 거절된다.
2. `lib/ai/guardrail-approvals.ts`의 `assertNoGuardrailWait()`는 같은 방의 `awaiting_choice/pending/approved/resuming` 중 하나라도 있으면 다른 요청을 차단한다. 현재 재개 중인 승인 ID만 예외다.
3. `db/migrations/051_ai_guardrail_approvals.sql`의 `idx_guardrail_approval_active`는 사용자·workspace·방마다 활성 승인 1건만 허용한다. 따라서 다른 질문도 가드레일에 걸리는 경우 UI/서버 조건 해제만으로 처리할 수 없다.
4. `userApprovals()`는 방의 승인 중 최신 1건(`LIMIT 1`)만 반환한다. DTO에는 원래 질문의 turn ID와 최종 chat ID 연결이 없다.
5. 차단 시 암호화 checkpoint에 원래 요청 입력과 실행 journal을 저장하고 generation을 `paused`로 종료한다. HTTP·모델·대화 lease·쓰기 트랜잭션을 승인 대기 동안 유지하지 않는다.
6. 재개 API는 `claimApproval()`로 선점한 checkpoint를 복호화하고, 저장된 입력으로 기존 채팅 POST를 다시 실행한다. 완료한 모델·미리보기 도구 응답은 `lib/ai/execution-journal.ts`의 입력 해시 기반 journal로 복원한다.
7. `chatScopeHash()`는 정책 외에 권한·구독·자료·대상 정보와 **방의 전체 저장 대화 ID/시간**, `title_source`를 포함한다. 새 대화 추가나 첫 정상 답변에 따른 자동 제목 상태 변경이 기존 승인을 무효화할 수 있다.
8. 재개가 진입한 채팅 POST도 `conversationHistory()`를 다시 호출한다. 현재 방의 최신 이력을 읽기 때문에 단순히 해시의 전체 이력 항목만 제거하면 대기 중 추가한 질문이 재개 문맥에 섞인다. journal 입력 해시도 달라져 완료한 모델을 다시 호출할 수 있다.
9. 승인 유효성은 관리자 처리/재개 선점, 실제 채팅 진입, 최종 저장 단계에서 확인한다. 문맥 경계를 바꿀 때 모든 검증 지점을 동일한 기준으로 맞춰야 한다.

### 2.3 대화 이력과 별도의 HITL 제약

- `lib/ai/conversations.ts`의 `conversationChats()`는 현재 저장 결과를 `rowid` 기준 최신 10건 + 다음 페이지 확인 1건으로 조회한다. 커서도 `rowid`다. 재개 결과는 완료 시 INSERT되므로 그대로 두면 원래 질문 위치가 아니라 맨 뒤에 나온다.
- `conversationHistory()`는 최신 최대 20건 후보와 60,000자 예산으로 이력을 선택하고, 선택된 대화의 최근 캡처 최대 3개를 서버에서 복호화한다. 공유 답변 재검증 및 변경안 상태 정보도 처리한다. 표시용 페이지와 모델 문맥은 별개다.
- 현재 대기 질문은 `ai_prompt_chats`에 저장되지 않아 새 모델 이력에 들어가지 않는다. 대화 안에 표시하기 위해 저장 구조를 바꿀 때 대기 질문이 이력에 들어가지 않도록 명시적인 필터가 필요하다.
- `lib/ai/change-reviews.ts`의 `assertNoPendingReview()`와 `046_ai_project_analysis_reviews.sql`의 `idx_ai_review_pending`도 방 단위 검토 대기 1건을 강제한다. 가드레일 대기 해제와 별개다. 사용자 검토 대기 중 다른 질문 허용까지 요구하는지는 9절의 결정 사항으로 구분한다.

### 2.4 버튼 크기 원인

- `styles/globals.css`: `.button`은 최소 높이 42px, padding 11px 17px이고 `.button.small`은 최소 높이 34px, padding 7px 11px, 글자 12px다.
- `styles/ai-chatbot.css`: 대화 작업 버튼은 글자 11px, padding 6px 8px, 모서리 6px이며 별도 42px 최소 높이가 없다.
- 승인 카드 버튼은 `className="button"`이고 전용 CSS는 margin만 추가해 큰 기본 크기를 그대로 사용한다. 문맥에 맞는 크기 규칙을 명시해야 한다.

## 3. 수정 방향

### 3.1 대화의 표시 단위와 실행 결과 분리

**권고안: 질문별 안정적인 turn 식별자와 순서를 도입하고, 승인 상태와 최종 결과를 같은 turn에 연결한다.** 승인 데이터를 정상 AI 답변 문자열로 만들어 저장하거나, 브라우저에만 임시 카드를 두는 방식으로 처리하지 않는다.

- turn: 사용자 질문 1건의 표시 위치. 일반 질문·대기 질문·재개 결과의 공통 기준이다.
- logical request: 최초 실행부터 재차단·재개까지 동일한 작업의 식별자. 기존 `logical_request_id`를 활용한다.
- attempt: 실제 HTTP 실행 시도. 기존 `requestId`·`attempt_request_id`로 중복 실행·중지를 관리한다.
- approval: 특정 검사 단계/operation/hash의 관리자 승인. 재차단 시 같은 turn의 새 approval로 연결한다.
- chat: 정상 완료한 답변과 첨부·근거·사용자 변경안 검토의 기존 저장 단위다.

표시용 타입은 `AiChat`의 필수 `result`에 가짜 응답을 넣지 않고, 완료 결과 또는 승인 상태를 갖는 turn DTO로 확장한다. 승인 대기 카드에는 마스킹된 질문 요약·정책명·상태 등 허용된 표시 정보만 제공한다. 차단 원문·도구 결과·checkpoint는 그대로 노출하지 않는다.

### 3.2 대화 영역 안 HITL

`AiConversationMessages`가 각 turn의 사용자 질문과 AI 영역을 렌더링한다.

```text
나: 질문 B의 허용된 표시 내용
AI: 가드레일 정책으로 관리자 승인이 필요합니다.
    [정책 상세] [관리자 처리 의견/만료 안내]
    [예, 승인 요청] [아니요]                  ← 선택 단계
    [관리자 승인 대기] [취소]                 ← 요청 후
    [이어서 진행] [취소]                     ← 승인 후

AI: 실행 결과 및 변경안 상세
    [승인하고 적용] [거절] [수정 요청]    …    [결과 크게 보기] [다시 사용]
```

- `AiGuardrailApproval`은 입력 카드 하단에서 제거하고 해당 turn의 AI 영역에 배치한다. 관리자 컨트롤타워에서 처리하는 권한과 흐름은 유지한다.
- 관리자 정책 승인과 사용자 변경안 검토의 상태·버튼 이름을 구분한다. 하나의 `승인`으로 합치지 않는다.
- 관리자 승인 후에는 카드 상태만 바뀐다. 사용자가 해당 대화의 `이어서 진행`을 눌러야 실행한다.
- 완료·반려·취소·만료·재차단 이력을 해당 질문에서 확인한다. 종료 카드의 `닫기`는 상세 접기로 바꾸는 것을 권고하며 질문 자체를 지우지 않는다.
- 상태 변화는 `role="status"/aria-live`로 알리고, 키보드로 상세·선택 버튼에 접근할 수 있게 한다.

### 3.3 승인 상태와 생성 중 상태 분리

| 상태 | 새 질문 입력/전송 | 해당 turn의 동작 | 모델 이력 포함 |
| --- | --- | --- | --- |
| `awaiting_choice` | 허용 | 예/아니요 | 제외 |
| `pending` | 허용 | 대기·취소 | 제외 |
| `approved` | 허용 | 이어서 진행·취소 | 재개 완료 전 제외 |
| `resuming` | 입력 초안 작성 허용, 같은 방 전송은 실행 종료까지 보류 | 실제 attempt 중지 | 제외 |
| 정상 실행 중 | 입력 초안 작성 허용, 같은 방 전송은 실행 종료까지 보류 | 현재 실행 중지 | 완료 전 제외 |
| 관리자 반려·사용자 거절·취소·만료·무효화·실패 | 허용 | 상태/재질문 안내 | 미완료 turn 제외 |
| 재개 정상 완료 | 허용 | 결과·필요한 변경안 HITL 표시 | 일반 이력 정책에 따라 포함 |
| 사용자 변경안 검토 `pending` | 별도 결정 필요 | 승인하고 적용·거절·수정 요청 | 미적용 사실과 상태를 보존; 세부 정책은 9절 |

승인 조회의 로딩/오류는 해당 카드의 상태와 결정 버튼에만 적용한다. 새 질문 자체의 권한·대상·모델 검증이 정상이라면 승인 목록 조회 실패만으로 전송을 막지 않는다. 서버는 요청마다 실제 권한과 정책을 검증한다.

대기와 별개로 **동일 방의 실제 모델 실행은 1건**을 유지한다. 기존 대화 lease와 generation의 실행 중 상태를 재사용하고, 두 브라우저 탭의 동시 실행도 서버에서 막는다. 대기 요청은 이 실행 자리를 점유하지 않는다.

### 3.4 새 질문 문맥 선택

1. 새 질문을 수락하고 실제 실행 자리를 확보한 뒤 서버가 turn 순서를 배정한다.
2. 그 이전의 완료한 turn 중 접근 가능한 대화를 서버가 선택한다. 승인 여부 선택·승인 대기·재개 대기·실패 등 미완료 turn은 **질문과 응답을 한 쌍으로 제외**한다.
3. 제외 대상에 연결된 이미지·근거·도구 결과·미적용 변경안·승인 의견·자동 생성 요약도 모델 문맥에 섞지 않는다. 화면에는 카드가 남아 있어도 모델 이력에는 넣지 않는다.
4. 필터 적용 후 기존 최대 20건/문자 예산/이미지 제한을 적용한다. 대기 카드가 조회 한도를 소모해 정상 이력이 사라지지 않게 한다.
5. 선택된 질문의 원래 prompt와 첨부를 현재 요청으로 전달한다. 승인 요청 내용에 무조건 답하는 고정 모드 없이 기존 의도 분류·조회·실행 흐름을 적용한다.
6. 이력은 클라이언트의 로딩된 10건이나 `excludeIds` 주장에 의존하지 않는다. 사용자·workspace·프로젝트·방 범위를 검증한 서버 데이터로 결정한다.

다른 질문도 가드레일에 탐지되면 별도의 turn/approval로 보관한다. 기존 요청의 ID·카드·checkpoint를 덮어쓰지 않는다.

### 3.5 승인된 질문 재개의 문맥 고정

**문맥은 차단 시점이 아니라 최초 요청 시작 시 고정한다.** 입력 검사에서 차단되어도 이전 이력 경계를 복원할 수 있어야 한다.

- 기존 실행 journal/암호화 payload의 새 포맷에 turn ID, 최초 경계, 선택된 이력 식별자·해시 및 복원에 필요한 문맥을 저장한다.
- 원래 질문과 원래 첨부는 현재 질문 입력으로 쓰고, history에는 그 질문 이전에 선택한 대화만 넣는다. 원래 질문을 history에 중복 삽입하지 않는다.
- 재개는 `/resume`의 ID와 버전으로 서버가 저장 payload를 선택한다. 현재 입력창의 prompt·이미지·모델·후속 이력은 재개 요청 입력이 아니다.
- 예시의 B를 재개하면 처음 선택한 A만 복원한다. 이후 C·D뿐 아니라 B 시작 때 대기 중이었다가 나중에 완료된 다른 turn도 새로 끼워 넣지 않는다.
- `conversationHistory()`를 재호출해 최신 목록을 선택하지 않는다. 고정된 문맥을 복원한 뒤 현재 접근 권한·공유 원문 유효성·자료 상태를 재검증한다.
- 문맥 원문이 변경되거나 삭제되었거나 공유 근거가 무효화되면 새 이력으로 조용히 대체하지 않고 재개 불가/새 요청 필요로 처리한다.
- 완료한 모델·조회·pending 변경안의 journal 입력이 유지되도록 한다. 후속 대화가 늘었다는 이유로 완료 단계의 모델 호출이나 쓰기를 반복하지 않는다.
- 재차단 시 turn과 logical request는 유지하고 approval 이력만 추가한다. 기존 승인 범위를 새로운 검사 객체에 확장하지 않는다.

### 3.6 승인 유효성 해시 조정

현재 `chatScopeHash()`의 방 전체 이력 검증을 다음 두 기준으로 분리한다.

| 기준 | 검증 대상 | 변경 시 처리 |
| --- | --- | --- |
| 고정 문맥 | 선택된 이전 대화/첨부/공유 참조와 원래 질문·원래 첨부, 해당 요청 경계 | 변경·삭제·접근 불가 시 재개 무효화 |
| 현재 실행 조건 | 정책 버전, 현재 사용자·workspace·프로젝트 권한, 대상/버전, 자료·참조 버전 등 기존 안전 조건 | 기존과 같이 무효화 |

후속 정상 대화 추가, 다른 승인 상태 변경, 방의 제목 자동 확정 등 실행 근거와 무관한 변화는 승인 무효화 원인에서 제외한다. `target_page/target_version`과 실제 자료·권한 검증은 유지한다. 다른 질문이 실제 프로젝트 자료를 변경했다면 단순 대화 추가와 다르므로 기존 승인이 무효화될 수 있다.

이 기준을 `validRow()`·관리자 승인 처리·`claimApproval()`·채팅 재진입·최종 저장에 동일하게 적용한다. `source_hash` 비교를 통째로 제거하거나 클라이언트 `approved` 값으로 우회하지 않는다.

### 3.7 재개 결과 표시와 입력 초안 보존

- 재개 결과는 기존 turn의 `finalChatId`에 연결하고 같은 질문의 AI 영역을 갱신한다. 화면 맨 뒤에 동일 질문을 새로 append하지 않는다.
- C·D 등 후속 대화는 삭제·이동·재생성하지 않는다. B는 최초 위치에서 완료 상태로 바뀐다. 완료 시각은 별도로 표시할 수 있다.
- 성공 처리를 일반 질문 제출과 재개로 구분한다. 재개 완료·실패·취소는 현재 작성 중인 새 질문과 첨부를 지우지 않는다.
- 일반 질문도 제출 시점의 초안 세대를 기록한다. 응답 대기 동안 사용자가 작성한 다음 초안은 성공 콜백이 초기화하지 않도록 한다.
- 가드레일 탐지로 질문이 대화 항목에 수락되면 해당 제출본만 입력창에서 정리하고 즉시 다른 질문을 작성할 수 있게 한다. 선택 거절을 누르면 같은 차단 질문이 입력창에 자동 복원되지 않는다.
- 승인 도착·상태 폴링은 스크롤·포커스를 강제로 옮기지 않는다. 사용자가 재개 버튼을 누를 때 해당 답변의 상태를 확인할 수 있게 한다.

### 3.8 버튼 그룹과 공통 크기

- 답변 하단을 왼쪽 `HITL actions`와 오른쪽 `result actions` 그룹으로 구성한다. 오른쪽 그룹에 `margin-inline-start: auto`를 주고 내부 순서는 `결과 크게 보기`, `다시 사용`으로 유지한다.
- 사용자 변경안 검토의 상세·피드백·Mutation/Query 상태는 `AiChangeReview`가 소유한다. 같은 검토 컴포넌트를 두 번 마운트하지 않고, 본문과 하단 actions 슬롯을 제공하거나 상태를 상위 훅으로 분리해 버튼을 배치한다.
- `공유 답변으로 등록`은 기능을 유지하고 오른쪽 보조 작업 그룹에서 두 결과 버튼 앞에 두는 것을 권고한다. 전역 공유 관리 버튼은 기존 대화 footer에 둔다.
- 정책 승인 예/아니요·재개/취소와 사용자 검토 버튼은 동일한 챗봇 compact 버튼 규칙을 사용한다. 기본안은 기존 대화 작업 버튼의 글자 11px/padding 6px 8px/모서리 6px를 재사용하고 42px 최소 높이를 제거하는 것이다. 전사 `.button.small` 34px 적용 여부는 9절에서 결정한다.
- 전역 `.button`을 축소하지 않고 챗봇 안의 공통 작업 버튼 클래스로 범위를 제한한다. hover/disabled/focus와 light/dark 테마를 함께 맞춘다.
- 좁은 화면에서는 왼쪽 HITL 그룹을 첫 줄, 오른쪽 결과 그룹을 다음 줄 오른쪽에 둔다. 각 그룹의 줄바꿈을 허용하고 가로 스크롤·버튼 잘림을 방지한다.
- 패널/팝업, 상하/좌우 분리에서 같은 컴포넌트를 사용한다. 기존 입력 열 386px, 반응형 임계값, 팝업 크기 조절 정책을 버튼 수정으로 변경하지 않는다.

## 4. 데이터·API 설계 영향

다음은 **향후 구현 시 변경안**이며 이번 단계에서 테이블·SQL 파일을 생성하거나 적용하지 않는다.

### 4.1 저장 구조 권고

| 대상 | 변경안 | 이유 |
| --- | --- | --- |
| 새 turn 메타데이터 저장소(가칭 `ai_conversation_turns`) | `turn_id`, 사용자/workspace/프로젝트/방 scope, `turn_seq`, `logical_request_id`, 표시 상태, `final_chat_id`, 표시 가능한 마스킹 요약, 생성/완료 시각, version | 완료 이력과 미완료 승인을 하나의 순서로 표시. 원문은 불필요하게 복제하지 않음 |
| turn 순서 | 방 내부 단조 증가 순서를 트랜잭션에서 할당, scope+seq unique | 동시 탭·같은 밀리초에도 안정적 정렬. `COUNT(*)+1`·클라이언트 시간으로 할당하지 않음 |
| 기존 완료 대화 | 기존 rowid 순서를 유지해 turn과 연결, 기존 chat ID·이미지·review·사용량 보존 | 과거 대화 페이지/재사용/이미지 URL 호환 |
| `ai_guardrail_approvals` | turn 연결 및 최종 결과 연결을 조회 가능하게 확장 | 여러 승인과 재차단이 같은 질문에 귀속 |
| 활성 승인 제약 | 방 단위 unique를 logical request/turn 단위 활성 승인 unique로 대체 | 다른 질문의 승인 대기를 독립적으로 보관 |
| 암호화 checkpoint | 새 포맷에 고정 이력 경계·복원 문맥·검증 해시 포함 | 최초 문맥과 journal 재현성 보장 |

신규 turn의 원문 질문/첨부를 별도 보관해야 한다면 기존 암호화 방식을 재사용하고 보관 목적·만료·삭제 규칙을 먼저 확정한다. 암호화 checkpoint 종료 정리를 중단해 영구 원문 저장소로 전용하지 않는다. 반려·만료 뒤에도 UI에는 허용된 요약과 상태만 남길 수 있다.

기존 051은 이미 적용된 것으로 기록되어 있으므로 원본을 덮어쓰지 않는다. 후속 migration 번호는 구현 시 최신 목록을 확인해 정한다. 기존 대기 요청은 정확한 과거 경계를 추정해 채우지 않는다. 구형 payload의 호환 정책은 9절에서 결정하고 별도 회귀로 검증한다.

### 4.2 API/클라이언트 계약

- `POST /api/ai/chats`: 일반 실행/승인 필요 응답 모두 안정적인 turn 연결을 반환한다. 가드레일 응답의 기존 코드와 상태는 유지하되 `details`와 turn을 연결한다. 클라이언트는 동일 turn을 upsert한다.
- `GET /api/ai/chats`: 완료 결과와 미완료 승인 turn을 같은 기준으로 페이지 조회한다. turn 순서 커서를 도입할 경우 구형 rowid 커서와 구분할 버전을 두고, 페이지 경계 중복/누락을 방지한다.
- `GET /api/ai/guardrail-approvals`: `LIMIT 1` 계약을 복수 요청으로 확장한다. 모든 활성 요청과 현재 표시/선택한 turn의 상태를 조회할 수 있게 하되 무제한 종료 이력 전체 조회는 피한다.
- 승인 목록 캐시는 ID/turn별 병합한다. `receive()`가 다른 요청을 지우지 않게 하고, 같은 ID의 낮은 version 응답으로 상태를 되돌리지 않는다.
- 폴링은 보이는 챗봇에서 **하나라도** 활성 요청이 있을 때 기존 15초 간격을 활용한다. 최신 항목이 종료됐다고 이전 pending 요청의 갱신을 멈추지 않는다. 카드마다 독립 폴링을 만들지 않는다.
- `POST .../{id}/resume`: 기존 ID+`expectedVersion` 계약을 유지하고 서버의 고정 입력을 사용한다. 응답에 turn/최종 chat 연결을 포함한다. 상태 충돌 시 해당 요청을 재조회하고 쓰기/재개를 자동 재시도하지 않는다.
- `.../decision`, `.../cancel`, 관리자 승인/반려: ID와 version으로 해당 요청만 처리한다. 자기 요청 승인 예외는 현재 프로젝트 owner/admin 및 기존 컨트롤타워 권한 규칙을 유지한다.
- `chats/stop`, `chats/usage`: 현재 선택된 카드가 아닌 **실제 실행 중 attempt**에 연결한다. 다른 대기 요청을 잘못 중지하지 않는다.
- Query key는 기존 사용자/workspace/project/conv scope를 유지하고 필요 시 turn 범위를 추가한다. 계정·방 전환 이후 늦게 도착한 응답이 다른 방의 카드나 초안을 바꾸지 않게 한다.

## 6. 영향 범위와 주의할 회귀

- **이력/페이지:** 완료 시각 기준 INSERT에서 최초 turn 위치 갱신으로 바뀐다. 같은 밀리초 요청, 오래된 페이지의 승인 완료, 새로고침, 뒤로 가기에서 누락/중복이 없어야 한다.
- **자동 제목/최근 활동:** 대기 질문 표시와 첫 완료 답변 제목 생성을 구분한다. 자동 제목 확정이 승인 해시를 깨뜨리지 않게 하고 방 활동 시각 정책은 명시적으로 정한다.
- **기존 공유 답변:** 완료 전 turn에는 결과 확대·공유 등록을 제공하지 않는다. 완료 결과는 현재의 공유 적격성·근거 재검증을 거친다. 승인 의견이나 민감한 checkpoint가 공유 원문으로 들어가지 않게 한다.
- **첨부/개인정보:** 대기 요청 원래 첨부와 새 질문 첨부를 분리한다. 노출 가능한 요약만 DTO에 싣고 기존 키·암호문·차단 원문을 URL/목록/문서에 출력하지 않는다.
- **동시성:** 일반 질문 실행과 과거 요청 재개가 경합하면 같은 방의 실제 실행 1건만 통과해야 한다. 재개 선점 후 lease 획득 실패를 무조건 실행 실패로 끝낼지 승인 대기로 돌릴지는 트랜잭션/응답 설계에 포함한다. 실제 도구 실행이 시작된 뒤 자동 복귀·자동 재시도는 금지한다.
- **원자성:** 최종 chat·첨부·검토안·turn 연결·승인 완료를 한 저장 경계로 처리한다. 결과 저장 실패 시 turn만 완료로 남지 않게 한다.
- **대상 전환:** 다른 방 선택은 허용한다. 방 내 AI 대상을 바꾸는 경우 기존 요청의 대상 버전을 현재 값으로 바꾸지 않으며 해당 승인 재개는 조건 변경으로 막는다. 확인 안내 여부는 결정 사항이다.
- **플랜:** 현재 가드레일 승인 기능의 이력 저장 가능한 Team/Business 범위를 유지한다. 이력 미저장 임시 방의 승인 복구는 확장하지 않고 기존 조회/초안 동작을 회귀한다.
- **정리:** 반려·취소·만료·실패·완료 checkpoint 제거와 기존 lease 정리를 유지하고, turn 메타데이터/첨부의 방 삭제 연쇄 정리를 검증한다.

## 7. 검증 방법

아래는 **구현 후 수행할 계획**이다. 이번 문서 작성에서는 앱 서버·모델·DB·마이그레이션·회귀 스크립트를 실행하지 않는다. 임시 SQLite·합성 계정·모의 AI에서 검증하며 운영 DB/유료 AI를 사용하지 않는다.

### 7.1 동작·문맥 검증

모의 공급자에 실제 전달된 모델 입력을 검사한다. 카드가 보이거나 답변이 그럴듯한지만으로 문맥 격리가 통과했다고 판정하지 않는다.

| ID | 시나리오 | 기대 결과 |
| --- | --- | --- |
| V01 | input/context/tool/tool-result/output 각각에서 차단 | 해당 질문의 AI 영역에 정책 카드가 생기며 정상 결과가 저장된 것으로 취급하지 않음 |
| V02 | 예/아니요, pending, approved 각각에서 새 질문 | 입력·첨부·전송 가능. 선택한 질문에 맞는 답변 생성 |
| V03 | A 완료 → B 대기 → C → D | C 입력은 A만, D 입력은 A+C만 이력으로 포함. B 원문·첨부·도구/승인 내용은 없음 |
| V04 | 대기 B와 C를 모두 생성, 상태가 서로 다르게 변경 | 각각의 카드/버전/취소/재개 독립. 최신 카드가 종료되어도 다른 pending 조회 계속 |
| V05 | B 승인 후 선택만 수행 | AI 실행 없음. 명시적 이어서 진행 후 원래 B 질문/첨부 + 고정된 이전 문맥만 사용 |
| V06 | B 대기 후 C·D를 나눈 뒤 B 재개 | C·D가 재개 이력에 없고 완료 journal 모델 호출을 반복하지 않음 |
| V07 | 고정 이력에 포함됐던 대화/공유 참조 삭제·접근권한 변경 | 새 이력으로 대체하지 않고 재개 차단/무효화 |
| V08 | 후속 대화 추가·자동 제목 확정만 발생 | 기존 승인 유지. 자료·정책·대상·권한 변경 시에는 무효화 |
| V09 | 새 질문 실행과 B 재개/같은 B 두 번 재개 경합 | 실제 실행 1회. 충돌한 요청의 안전한 상태/오류와 중복 쓰기 없음 |
| V10 | 재개 중 또 다른 가드레일 탐지 | 같은 turn의 새 승인 이력. 이전 grant가 다른 operation을 허용하지 않음 |
| V11 | 승인된 변경 작업 재개 완료 | 관리자 승인과 별도로 사용자 변경안 검토 표시, 적용 전 자료 불변 |
| V12 | 새 초안·첨부 작성 중 B 재개 완료/중지/실패 | 초안·첨부·모델 선택 보존. 중지는 B의 실제 attempt만 취소 |
| V13 | 새로고침/방 전환/다른 계정/늦은 응답 | 원래 turn 위치와 모든 승인 상태 복원, 계정·방 정보 혼입 없음 |
| V14 | 승인 반려·아니요·취소·만료·실패 | 상태 이력 유지, 미완료 질문은 후속 모델 이력에서 제외, checkpoint 정리 |
| V15 | 10건 경계·이전 페이지·같은 밀리초 turn·재개 완료 | 페이지 중복/누락 없음, 완료 결과는 최초 질문 위치에서 갱신 |
| V16 | 구형 완료 기록/051 대기 checkpoint | 확정한 이관·호환 정책대로 처리, 기존 chat/review/images/usage/FK 보존 |

### 7.2 화면·접근성 검증

- 대화 아래/입력 카드에 승인 레이어가 중복으로 남지 않는지 확인한다.
- HITL 버튼이 왼쪽 시작, 결과 두 버튼이 오른쪽 끝에 있는지 실제 bounding box로 확인한다. HITL이 없는 답변에서도 오른쪽 정렬을 유지한다.
- 승인·변경안 검토·일반 결과 버튼의 computed style을 비교해 공통 크기 준수를 확인한다.
- 좁은 패널·팝업 최소 너비·모바일·상하/좌우 분리·light/dark에서 줄바꿈과 가로 넘침을 확인한다.
- 정책 상세/검토 상세 펼침, 피드백 입력, 키보드 순서·focus 표시·버튼 disabled·상태 알림을 확인한다.
- 이전 대화를 읽는 중 상태 갱신으로 스크롤이 아래로 이동하지 않는지, 이미지 로드·이전 페이지 추가 후 anchor가 유지되는지 확인한다.

### 7.3 실행할 기존 검증

- `pnpm typecheck`, 변경 파일 ESLint, `pnpm build`.
- `pnpm test:ai-guardrail-approvals` 및 빌드 후 `pnpm test:ai-guardrail-approvals-browser`.
- `node scripts/test-ai-chat-pagination.mjs`, `node scripts/test-ai-chat-pagination-browser.mjs`（현재 `package.json`에는 해당 pnpm script 별칭이 없음）.
- `pnpm test:ai-settings-reviews`, `pnpm test:ai-tool-execution`, `pnpm test:shared-answers`, 필요 시 관련 브라우저 회귀 및 `pnpm test:ai-targets-browser`.
- 스키마 검증·외래키 무결성·중복 활성 logical request·turn 순서 유일성·기존 데이터 이관을 임시 DB에서 검사한다.

기존 승인 테스트에는 방 전체 대기를 이유로 새 질문 409를 기대하는 항목이 있다. 요구사항에 따라 기대값을 바꾸되 관리자 승인 전 재개 금지·다른 사용자 접근 차단·같은 요청 중복 실행 차단 검증은 유지한다. 기존 작업 기록의 통과 결과는 이번 설계의 검증 결과로 재사용하지 않는다.

## 8. 구현 순서 제안

1. 9절의 제품 결정과 구형 checkpoint 처리 정책을 확정한다.
2. turn 식별/순서와 기존 이력 이관, 고정 문맥·검증 해시를 먼저 구현해 임시 DB에서 검증한다.
3. 실제 실행 단일성은 유지하면서 방 단위 승인 차단을 제거하고 복수 승인 API·캐시를 연결한다.
4. 승인 카드를 해당 대화로 이동하고 재개 결과 upsert·초안 보존을 적용한다.
5. 기존 사용자 검토 actions와 결과 actions 배치·공통 크기를 적용한다.
6. 문맥 payload·동시성·페이지·브라우저 회귀를 수행하고 구현 결과를 별도 작업 기록에 남긴다.

## 9. 결정이 필요한 사항

아래 권고안은 검토를 위한 제안이며 확정된 사용자 결정으로 취급하지 않는다.

| 항목 | 권고안 | 대안/영향 |
| --- | --- | --- |
| 버튼 공통 크기 | 기존 챗봇 작업 버튼과 같은 compact 규칙 적용 | 전사 `.button.small` 34px를 기준으로 삼으면 결과 버튼까지 같은 기준으로 맞출지 결정 필요 |
| 승인 대기 복수 허용 | 다른 질문도 차단될 수 있으므로 turn별 복수 승인 허용 | 방 단위 1건을 유지하면 두 번째 차단 질문에 별도 제한 UX가 필요하고 자유로운 대화 요구를 일부 제한 |
| 사용자 변경안 HITL 대기 중 새 질문 | 이번 필수 범위는 가드레일 대기 해제. 사용자 검토 대기도 풀려면 별도 합의 후 함께 설계 | 함께 허용하면 `assertNoPendingReview`, `idx_ai_review_pending`, 대상 변경 제약까지 수정. 미적용 답변을 문맥에서 제외할지 상태를 붙일지와 복수 변경안 충돌/버전 검증을 추가 확정해야 함 |
| B 재개 완료 뒤 새 질문 E의 이력 | E가 시작할 때 완료된 B 결과도 최초 turn 순서에 따라 포함. C·D를 소급 변경하지 않음 | B 재개를 별도 분기로 유지하려면 branch/부모 문맥 모델이 추가로 필요. 이번 기본안은 단일 표시 타임라인 |
| 구형 승인 checkpoint | rollout 시 기존 요청을 처리·종료한 뒤 새 포맷 활성화하는 방식 우선 검토 | 무중단 호환이 필요하면 구형 요청은 기존 방 잠금 동작을 유지하는 adapter 필요. 정확한 과거 문맥을 임의 추정하지 않음 |
| 차단 질문 표시 범위 | 대기/종료 turn은 허용된 마스킹 요약으로 복원 | 원문·첨부를 계속 표시하려면 별도 암호화 저장/열람·보관·삭제 정책 필요 |
| 종료 카드 닫기 | 질문/상태를 남기고 상세만 접음 | 카드 전체 숨김을 원하면 대화 선택 시 복원 방식 필요 |
| 방 AI 대상 변경 | 허용하되 기존 요청은 대상 버전 변경 시 재개 불가 안내 | 대기 요청이 있으면 대상 변경 전 안내/확인 제공 가능. 다른 방 이동은 제한하지 않음 |
| 최근 활동 시각 | 새 질문 수락과 재개 완료를 활동으로 반영 | 완료 답변만 반영하는 현행 방식 유지 여부와 방 목록 순서 영향을 확인해야 함 |
