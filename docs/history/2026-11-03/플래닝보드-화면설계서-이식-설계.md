# Planning Board 화면설계서 이식 분석 및 설계

- 작성일: 2026-11-03 (한국시간)
- 분석 원본: `hams-planning-board/app/planning/page.tsx`와 연결된 편집기·미리보기·API·권한·템플릿
- 이식 위치: `hams-matrix/app/(editor)/planning-board/`
- 단계: 사용자 검토용 설계. 이번 작업은 이 문서와 `HISTORY.md`만 작성하며 소스·패키지·DB는 수정하지 않는다.
- 첨부 이미지는 편집기 배치 참고 자료다. 아래 기능과 문제점은 현재 소스에서 확인한 내용을 기준으로 정리했다.

## 1. 요구사항과 권장 설계

1. 원본 `/planning`에 연결된 편집·저장·협업·검토·AI·미리보기·코드 출력 기능을 전체 분석하여 이식한다.
2. 전용 화면과 `components`, `types`, `stores`, `lib`, 스타일, 템플릿, 전용 API를 지정한 `planning-board` 폴더 아래에서 관리한다.
3. Matrix 화면설계서 목록에서 대상 화면을 선택해 새 창으로 연다.
4. Matrix의 로그인 세션, 워크스페이스, 프로젝트 소속과 화면설계서 탭 권한을 사용한다.
5. 기존 화면설계서의 관리번호, 텍스트 필드, 요구사항·DB·아키텍처 연결, 버전과 추적성을 보존한다.
6. 이번 단계에서는 구현·의존성 설치·DB 접속/변경·데이터 이전을 하지 않는다.

### 확정 요구와 제안의 구분

| 구분 | 내용 |
| --- | --- |
| 사용자 지정 | 폴더 위치, 화면설계서 연결, 새 창, Matrix 권한 적용, 이번에는 문서만 작성 |
| 권장 연결 단위 | `screen` 산출물 1건에 보드 1개, 보드 내부에는 여러 페이지 |
| 권장 저장 | Matrix DB의 보드 전용 테이블, 이미지 바이너리는 비공개 R2 자산 |
| 권장 권한 | 기존 화면의 부속 문서인 보드 작성·저장은 `screen.UPDATE`, 화면 산출물 신규 등록은 기존 `screen.CREATE` |
| 결정 필요 | 검토자·공유 정책, 화면 상태 연동, 용량 제한, 이력 보존, 추가 패키지, 기존 Firestore 자료 이전 |

테이블명·API·파일 분리·크기 제한은 구현을 구체화한 **제안**이다. 구현 요청을 받으면 사용자가 수정한 이 문서의 최신 내용을 다시 확인한다.

원본 서비스 홈(`/`), 로그인·프로필·SSO 서버 자체는 복제하지 않는다. 편집기에서 제공하는 문서 열기·최근 문서 선택은 접근 가능한 Matrix 화면설계서/보드 목록으로 대체한다. 이는 편집 기능의 삭제가 아니라 기존 Matrix 서비스 문맥으로의 연결 변경이다.

### 2.2 원본 데이터 구조

- 편집 문서: `title`, `layers`, `sizes`, `positions`, `layerText`, `layerImages`, `layerStyles`, `selected`.
- `Layer.children`가 계층과 형제 순서를 표현하고, 속성 맵은 레이어 ID를 키로 사용한다.
- AI는 `GeneratedDocument.pages[].elements[]` 평탄 구조와 `parentId`를 사용하며, 편집 트리와 왕복 변환한다.
- 원본의 `projectId`는 **보드 문서 ID**다. Matrix의 프로젝트 ID로 단순 치환하면 다른 보드의 저장·코멘트·권한이 섞일 수 있다.
- 원본 저장소는 `planningProjects/{id}`와 하위 `comments`, `memos`, `aiPromptChats`, `approvalHistory` 컬렉션이다.
- 파일 선택/붙여넣기 이미지는 `layerImages`의 data URL에 들어간다. AI 입력에는 이미지 본문 대신 요소 구조를 전달한다.

### 현재 기능으로 오인하면 안 되는 항목

- 우측 ‘사용자 지정 배치/기본 배치’는 현재 상태 문구다. 자동 레이아웃 선택 기능이 구현되어 있지는 않다.
- Pretendard/Bold 표시는 완전한 글꼴 선택기가 아니다. 변경 가능한 굵기는 별도 select로 제공한다.
- 코드 출력은 화면 프로토타입 마크업이다. 예약·매출 등 실제 업무 API나 배포 기능을 생성하지 않는다.
- 실시간 공동 편집/CRDT와 자동 충돌 병합은 없다. 이식의 기본 동시 편집 방식은 버전 충돌 안내다.
- 승인 이력, 메모리 undo, 저장 문서 버전 복원은 서로 다른 개념이다. 원본에 없는 무제한 복원 UI를 필수 기능으로 간주하지 않는다.

## 4. Matrix 현재 구조 및 영향

- `components/pages/screens/screens-page.tsx`는 `<ArtifactList kind="screen" />`를 표시한다.
- 화면설계서는 `project_artifacts.kind='screen'`이다. 화면 개요, 메뉴 경로, URL, 레이아웃, 입력/검증, 출력, 이벤트/흐름, 담당자, 비고를 저장한다.
- `artifact_links`와 `artifact_revisions`가 요구사항·설계·프로그램·검수 추적에 연결된다. 보드를 만들기 위해 기존 화면의 ID/관리번호를 재발급하지 않는다.
- `components/pages/screens/wireframe.tsx`는 표시용 와이어프레임이며 새 편집기의 저장·협업 기능을 대신하지 못한다.
- 현재 독립 편집기인 `app/(editor)/projects/[projectId]/documents/[fileId]/page.tsx`를 진입 구조의 참고로 삼는다.
- `(workspace)/layout.tsx`의 WorkspaceShell과 프로젝트 Context를 독립 창에 그대로 중첩하지 않는다. 전용 Provider에 사용자·프로젝트·화면·권한을 전달한다.

## 5. 경로와 폴더 설계

### 5.1 진입

```text
/planning-board?projectId={matrixProjectId}&screenId={screenArtifactId}
/planning-board/preview?projectId={matrixProjectId}&screenId={screenArtifactId}
```

- `(editor)`는 URL에 포함되지 않는 route group이다.
- `matrixProjectId`, `screenArtifactId`, 서버 발급 `boardId`를 구분한다.
- 목록의 ‘화면 설계 보드’ 링크를 `target="_blank"`, `rel="noopener noreferrer"`로 연다. URL에 토큰·이메일·문서 본문을 넣지 않는다.
- 화면이 아직 등록되지 않았다면 기존 screen 등록을 먼저 완료한다.
- GET 진입은 DB를 변경하지 않는다. 미작성 보드는 조회자에게 빈 상태, 편집자에게 작성 시작 UI를 제공한다.

## 6. 편집 상태와 데이터 검증

### 상태 분리

| 구분 | 내용 |
| --- | --- |
| 저장 문서 | schemaVersion, 제목, 트리, 위치·크기·텍스트·스타일·이미지 참조, activePageId |
| 편집 UI | selectedIds/anchor, 선택 페이지, 도구, 줌·팬, 트리 펼침 |
| 저장 상태 | boardId, version, contentVersion, screenArtifactVersion, dirty, 저장 중, 충돌 |
| 업무 상태 | draft/review/rejected/complete, 검토 대상 본문 버전, 검토자, 권한 |
| 일시 상태 | undo/redo, 코드 출력 캐시, 모달, AI 입력·진행·오류 |

- Zustand는 Provider별 store로 만든다. 전역 단일 store를 서로 다른 프로젝트/화면에 공유하지 않는다.
- 브라우저 persist는 처음에는 비활성화를 권장한다. 도입 시 user/workspace/project/screen/board를 키에 포함하고 로그아웃 후 데이터가 남아 표시되지 않게 한다.
- 문서/AI/미리보기 변환은 단일 codec을 사용해 ID, 부모, 순서, 표시·잠금, 옵션, 아이콘, 이미지 참조를 보존한다.
- 개인의 선택·줌 변경으로 다른 사용자의 선택이 이동하지 않도록 공유 저장 대상은 activePageId 정도로 제한하는 안을 권장한다.

### 검증 규칙

- 수치의 유한성, 크기 양수, opacity 0~1, 열거값, 문자열 길이, ID 고유성, 맵 참조를 검사한다.
- 부모 종류, 트리 순환, 다른 페이지 부모 참조, 존재하지 않는 부모를 거부한다.
- 페이지의 작업 공간 좌표와 요소의 부모 상대 좌표를 구분한다. 수동·AI 조작에 같은 좌표 규칙을 사용한다.
- 삭제 시 자손과 각 맵을 정리한다. undo/저장 이력이 참조하는 이미지는 즉시 물리 삭제하지 않는다.
- 캔버스뿐 아니라 속성 편집·붙여넣기·트리·키보드 경로에도 읽기 전용 및 검토 잠금을 적용한다.
- 레이어 잠금은 편집 UX이며 서버 접근 권한을 대신하지 않는다. 권한 검사는 별도로 수행한다.

## 7. DB와 저장 설계안

### 7.1 테이블

| 테이블 | 주요 열·제약 | 용도 |
| --- | --- | --- |
| `planning_boards` | id, workspace_id, project_id, screen_artifact_id, schema_version, document_json, version, content_version, status, reviewer_user_id, review_content_version, 생성/수정자·시각 | 현재 문서. `UNIQUE(workspace_id,project_id,screen_artifact_id)` |
| `planning_board_revisions` | id, board_id와 범위 열, content_version, snapshot_json, actor_id, created_at | 저장 본문 버전. 불변 이력 정책 검토 |
| `planning_board_comments` | id, board_id와 범위 열, author_id, text, created_at | 코멘트 |
| `planning_board_memos` | id, board_id와 범위 열, text, x/y/w/h, color, opacity, version, 작성/수정자·시각 | 별도 저장 메모 |
| `planning_board_review_history` | id, board_id와 범위 열, action, from/to_status, actor_id/role, reviewer_id, content_version, message, created_at | 저장·신청·반려·완료 이벤트 |
| `planning_board_assets` | id, board_id와 범위 열, draft_id, object_key, mime_type, byte_length, hash, created_by/at, 상태, expires_at | 비공개 이미지. 최초 저장 전 임시 자산은 board_id가 없을 수 있음 |
| `planning_board_ai_requests` | request_id, board/scope/user, input_hash, model, expected_version, status, 결과 버전, error_code, 생성/종료 시각, lease | 중복 생성·과금 방지, 요청 상태 |

- `project_artifacts(id,project_id,workspace_id)`에 복합 외래키로 연결하고, 서비스에서도 `kind='screen' AND deleted_at IS NULL`을 검사한다.
- 모든 하위 리소스는 workspace/project/screen/board 범위를 확인한다. 자원 ID 단독 조회를 하지 않는다.
- JSON 유효성, 버전 양수, 상태 enum, 코멘트 길이·메모 범위를 검증한다.
- 목록/이력에 `(workspace_id,project_id,board_id,created_at,id)` 인덱스를 제안한다.
- 로컬 undo 40건과 DB 저장 revision은 별개다. 포인터 이동마다 DB 이력을 만들지 않는다.

### 7.2 저장 트랜잭션

1. 세션·권한·화면·상태를 확인한다. 최초 저장은 보드가 없는 상태를 기대한다.
2. `expectedVersion`과 `expectedScreenVersion`을 검사한다. 동시 최초 작성이나 이전 버전 저장은409로 반환한다.
3. 본문과 자산 참조의 유효성을 확인한다.
4. 본문 변경 시 contentVersion을 증가시키고 문서·본문 이력·저장 이벤트를 함께 기록한다.
5. screen의 `structure.planningBoard={id,contentVersion}` 같은 **경량 참조**와 화면 version을 갱신한다. 거대한 캔버스 JSON을 기존 layout 필드에 넣지 않는다.
6. 기존 화면 필드·관리번호·연결은 최신 값으로 보존한다. 보드 제목이 바뀌었다고 화면명·URL을 자동 덮어쓰지 않는다.
7. 산출물 변경 이력/감사까지 성공하면 commit하고, 실패 시 전체 rollback한다.

본문 저장이 screen.version에 반영되어야 기존 추적·검증 기준 버전이 설계 변경을 감지할 수 있다. 메모·코멘트만 변경할 때는 화면의 사양 버전을 매번 올리지 않는다. 검토 상태 변경은 board.version만 올리고 contentVersion을 유지한다.

공통 `ArtifactStructure`와 구조 검증에서 경량 참조를 허용·보존해야 한다. 기존 화면 수정/AI 저장이 이 참조를 지우지 않는지 검증한다. 반대로 기존 화면 필드를 다른 창에서 수정하면 보드 저장도 최신 screen.version을 확인해야 한다.

### 7.3 삭제·보존·이전

- screen 논리 삭제 시 보드·이미지·이력의 일반 접근도 차단한다. 과거 자료를 즉시 물리 삭제하지 않는다.
- 페이지 삭제는 본문 수정이므로 UPDATE, 화면 산출물 삭제는 기존 DELETE다.
- 보드 단독 영구 삭제는 원본 필수 기능이 아니다. 추가하면 권한·복구·보존 기간을 별도로 정한다.
- 사용자에게 제공하는 상세 이력은 Matrix의 `historyEnabled`와 맞춘다. 승인 대상 식별을 위한 최소 이벤트·감사와 일반 이력 UI는 구분한다.
- 기존 Firestore 자료 일괄 이전은 별도 작업이다. 필요하면 승인된 JSON 내보내기를 받아 원본 ID·소유자·공유/검토자·이미지·이력을 매핑한다. API를 바꾸는 것만으로 기존 자료가 이전되지는 않는다.

## 8. Matrix 권한·공유 대응

| 작업 | 제안 권한 |
| --- | --- |
| 보드 창, 저장 문서·이미지·코드·허용된 이력 조회 | 유효 세션, 온보딩 완료, 프로젝트 소속, `screen.READ` |
| 보드 최초 작성·저장, 템플릿, 페이지/레이어 변경 | 기존 screen의 부속 내용 수정으로 `screen.UPDATE` |
| 코멘트, 메모, 이미지 첨부 | `screen.UPDATE` 및 대상 리소스 일치 |
| AI 생성·자동 저장 | UPDATE, AI 유효, 토큰 한도, UPDATE 허용 정책, maxChanges≥1, 본문 수정 가능 상태 |
| Matrix 화면 등록/삭제 | 기존 `screen.CREATE`/`screen.DELETE` |
| 검토 요청·직접 완료 | 프로젝트 owner와 UPDATE를 기본안으로 제안 |
| 반려·검토 완료 | 지명된 동일 프로젝트 구성원, UPDATE, review 상태와 대상 버전 일치 |
| 공유 권한 변경 | 기존 Matrix 프로젝트 권한 관리 조건 |

- owner/admin/member/viewer와 탭별 사용자 설정을 그대로 확인한다. 서비스 관리자 계정이라는 이유만으로 보드 편집을 우회 허용하지 않는다.
- URL의 projectId/screenId, 본문의 userId/ownerId, 클라이언트 권한 상태는 신뢰하지 않는다.
- 새 창에서 권한을 읽기 전에는 편집을 허용하지 않는다. 포커스 복귀·권한 통지·저장 직전에 재확인한다.
- 비소속/다른 workspace는 기존 Matrix의404 방침을 따르고, 권한 상실/세션 만료 시 저장을 중단한다.
- viewer는 탐색·선택·미리보기·코드 복사가 가능하지만 내용·이미지·메모·AI로 데이터를 바꿀 수 없다.

### 원본 이메일 공유의 대체

원본은 이메일만으로 edit/view 공유를 부여하고, reviewerEmail 일치에도 조회권을 부여한다. 이 규칙은 Matrix 프로젝트 권한을 우회할 수 있으므로 그대로 이식하지 않는다.

- 공유 UI는 현재 프로젝트 구성원과 탭 권한을 보여주는 UI로 바꾼다.
- 권한 변경은 기존 `ProjectPermissionsDialog`와 권한 API를 사용한다.
- 검토자는 이메일 문자열 대신 같은 프로젝트의 유효한 구성원 userId로 선택한다.
- 비구성원을 지정해도 자동 초대·조회권을 만들지 않는다. 기존 프로젝트 참가 절차를 먼저 수행한다.
- 구성원 제외/UPDATE 회수 후 승인은 차단하며 owner가 검토자를 재지정한다.

## 9. 검토·승인 흐름

아래 상태는 보드 상태다. Matrix 화면이나 프로젝트의 승인 상태를 자동 변경한다는 뜻이 아니다.

```text
draft --검토 요청--> review --반려--> rejected --저장--> draft
draft --검토 요청--> review --검토자 완료--> complete
draft/rejected --owner 직접 완료--> complete
complete --내용 저장--> draft (새 사이클)
```

- 원본 서버의 review 저장 차단은 edit 사용자에게도 적용된다. 이식 시 UI도 동일하게 본문 편집을 잠근다.
- review에서는 본문 저장, AI 덮어쓰기, 템플릿 대체, 중복 요청, owner 직접 완료를 거부한다.
- 코멘트·메모는 별도의 협의 정보로 보고 UPDATE가 있는 사용자에게 계속 허용하는 안을 제안한다. 승인 대상 본문은 바뀌지 않아야 한다.
- 상태 변경과 이벤트 기록을 한 트랜잭션에서 처리하고 board.version과 review_content_version을 검사한다.
- 미저장 변경이 있으면 먼저 저장시키거나 ‘저장 후 검토 요청’을 원자적으로 수행한다. 화면의 편집본과 DB 검토 대상이 달라지면 안 된다.
- 의견은 최대2,000자, 반려/완료 의견 필수와 본인 검토자 지정 금지를 유지한다.
- complete는 영구 잠금이 아니다. 다시 저장하면 새 draft가 된다.
- board.complete를 이유로 Matrix 화면 승인·통합 검수 완료를 자동 선언하지 않는다. 상태 연동은 결정 사항이다.

## 10. API 설계안

`B = /planning-board/api/projects/{projectId}/screens/{screenId}`.

| 경로 | 메서드 | 역할 |

| `/planning-board/api/format-code` | POST | 화면 범위 확인 후 코드 정리, 실행 금지 |

- 조회 응답은 `private, no-store`, 변경은 origin·세션·리소스·권한·상태·기대 버전을 검사한다.
- 400 입력, 401 인증, 403 권한, 404 대상, 409 충돌, 413 크기, 422 정책, 429 한도, 502/504 AI 실패를 구분한다.
- 실제 UTF-8 바이트 수를 확인한다. 공통 `body()`의 기본10,000문자는 보드 저장에 부족하므로 전용 상한을 둔다.
- 목록은 생성 시각+ID 커서로 처리한다. 원본처럼 최근50/100개를 가져온 뒤 권한 필터를 하는 대신 SQL 자체를 소속 범위로 제한한다.
- 같은 requestId·같은 입력 재송신은 기존 결과를 재사용하고, 다른 입력으로 ID를 재사용하면409다.

## 11. AI 생성과 저장

### 원본에서 달라져야 하는 부분

- 원본은 SSO AI 프록시를 사용하며, 클라이언트가 AI 결과를 먼저 표시한 후 문서 저장·프롬프트 기록을 각각 호출한다.
- 원본은 결과를 최대8페이지·페이지당64개 요소로 자른다. 기존 큰 문서가 빠질 수 있어 그대로 저장하면 안 된다.
- AI 페이지 폭은 최소600px로 정규화하지만 수동 Mobile은390px라 서로 맞지 않는다.
- 원본 AI 출력 상한은16,000토큰이다. Matrix `generateAi`는 현재 출력과 예약 계산에6,000을 사용한다. 단순 호출 교체만으로 큰 문서 생성이 안정화되지는 않는다.

### 제안 처리 순서

1. 권한·AI 정책·상태·기대 버전·요청 길이 확인 및 requestId 확보.
2. 저장 버전과 미저장 편집본을 구분한다. 편집본 기반이면 해당 스냅샷 해시도 요청 ID에 결속한다.
3. 현재 문서·대상screen 정의·필요한 동일 프로젝트 관련 요구사항을 구조화한다. 임의 URL/타 프로젝트는 참조하지 않는다.
4. Matrix 모델 목록, activeGuardrailPolicy, token tracker, quota 예약, Responses, 입력/문맥/출력 검사를 재사용한다.
5. 원본의 스키마·부모 상대 좌표·ID 유지·기존 페이지 보존·새 페이지 배치 지침을 이식한다.
6. 결과를 검증하고 완결 여부를 확인한다. 초과 내용을 조용히 slice하지 말고 범위를 줄이거나 실패 처리한다.
7. 권한·버전·review 상태를 다시 확인하고 문서·화면 참조 버전·이력·요청 완료를 한 트랜잭션으로 저장한다.
8. commit된 내용만 UI 저장본으로 반영한다. 실패·중단·충돌은 기존 편집본을 보존한다.

- 이 기능의 AI 변경은 ‘기존screen 아래 보드 UPDATE 1건’으로 계산하는 안이다. 레이어64개를 새 screen64건으로 등록하지 않는다. maxChanges=0이면 자동 저장을 막는다.
- 페이지 범위 지정 생성을 권장한다.16,000 출력을 채택하면 공통 생성기에 기능별 상한 옵션을 추가하고 토큰 예약도 같은 값으로 맞춘다. 다른 기능의 기본6,000을 일괄 변경하지 않는다.
- 원본 `user.aiEnabled`나 SSO 액세스 토큰은 이식하지 않는다. Matrix의 실제 AI 정책·요금제를 따른다.
- AI 요청 상세와 공유 본문 변경 이력을 분리한다. 개인 프롬프트를 모든 프로젝트 사용자의 채팅 기록으로 자동 공개하지 않는다.

## 12. 이미지·템플릿·코드·새 창

### 이미지와 템플릿

- 이미지 data URL 영구 저장을 비공개 asset ID로 대체한다. blob URL은 업로드 전 일시 표시용으로만 사용한다.
- 최초 저장 전에도 파일 첨부와 미리보기가 가능해야 한다. 임시 자산은 사용자·프로젝트·screen·draftId에 결속하고, 최초 보드 저장 트랜잭션에서 boardId로 연결한다. 그전에는 업로드한 사용자만 접근하며 만료된 임시 자산은 지연 정리한다. 첨부만 했다고 GET 과정에서 보드를 생성하지 않는다.
- PNG/JPEG/WebP를 기본안으로 하며 MIME·실제 데이터·용량을 검증한다. 임의 SVG/외부URL은 당초 범위에서 제외한다.
- 이미지 첨부는 screen.UPDATE, 조회는 READ다. 문서함 자동 등록은 별도 결정이 필요하다.
- DB 실패 시 새 객체의 보상 삭제, 미참조 객체 지연 정리를 설계한다. undo나 저장 이력이 참조하는 자산은 즉시 삭제하지 않는다.
- 코드에 비공개 인증 URL만 복사하면 다른 서비스에서 이미지를 볼 수 없다. 자산 동봉·임베딩·참조표 중 방식을 확정해야 한다. 객체 키나 장기 공개URL을 그대로 내보내지 않는다.
- 세 템플릿은 허용 목록으로 조회하고 기존 문서를 대체하기 전에 확인한다. ID·부모·activePageId를 재매핑한다.
- 템플릿 적용이 Matrix 화면 산출물을 추가로 생성하지 않도록 한다. 저장 전까지 미저장 상태를 표시한다.

### 코드 출력

- DOM/CSS 캡처는 해당 편집 영역 ref만 대상으로 한다. document 전체의 고정 선택자에 의존하지 않는다.
- 선택 테두리·핸들·편집 속성·코멘트/메모 UI를 제외하고 숨김과 폼 상태를 반영한다.
- 원본은 코드 탭 전환 시 주로 생성한다. 이식 후에는 문서 revision 변경에도 최신 코드가 반영되어야 한다.
- CSS/HTML5/React/Astro/Svelte와 일반/한 줄 복사를 유지한다.
- Prettier 및 Astro/Svelte 플러그인은 런타임 의존성을 명시한다. Matrix의 전이 의존성에 우연히 존재하는 패키지를 사용하지 않는다.
- 포맷 실패는 경고와 함께 정리 전 코드로 대체한다. 생성 코드를 서버에서 실행하지 않는다.

### 새 창과 미리보기

- Matrix 목록→편집 창은 URL과 기존 세션으로 진입한다. 부모 창에서 인증 정보를 넘기지 않는다.
- 편집 창→미리보기는 미저장 스냅샷 표시를 유지한다. ready/document 메시지를 사용할 때 origin 외에 source 창·nonce·workspace/project/screen/board 범위를 검증한다.
- 이 메시지 방식의 미리보기에는 필요한 opener 통신을 유지해야 한다. 모든 새 창에 같은 noopener를 적용해 통신을 끊지 않는다. 대안은 범위/nonce가 있는 BroadcastChannel이다.
- 미리보기 자체에도 인증·READ를 적용하고, 저장본 재조회와 임시 전송 연결 끊김 안내를 제공한다.
- 원시 HTML 실행 대신 검증된 문서 타입을 렌더링한다. 같은 origin의 다른 창이 보낸 메시지를 무조건 수용하지 않는다.
- 저장 후 원래 목록에 변경 통지를 보내더라도, 통지를 저장 데이터나 권한의 근거로 삼지 말고 재조회하도록 한다.

## 13. 스타일·패키지·호환성

- 원본 Next16.3.1/React19.2.8과 Matrix Next16.4.2/React19.3.0 차이를 확인한다. 원본 lockfile·root layout·SSO Provider를 통째로 복사하지 않는다.
- Matrix의 cacheComponents·Suspense 규칙에 맞춰 인증/searchParams 등 동적 처리를 구성한다.
- 편집기/미리보기 CSS는 Modules 또는 전용 root에 한정한다. Portal 메뉴도 별도 클래스로 감싸 전역 button/input/workspace 충돌을 막는다.
- 편집기 외곽은 Matrix 테마·강조색·공통 모달을 쓰고, 사용자가 설계한 화면의 색·글자는 문서 데이터로 유지한다.
- MUI 원본 아이콘 유지 시 @mui/icons-material과 관련 MUI/Emotion 의존성을 함께 확인해야 한다. lucide로 이름만 치환해 기존 아이콘 ID를 깨뜨리지 않는다.
- 아이콘 선택 패널 지연 로딩을 권장한다. MUI 의존성 추가와 로컬 SVG 어댑터 중 선택은 결정 사항이다.
- Pretendard 표시만 복사하지 말고 실제 폰트 로딩을 확인한다. 첨부 화면의 예약·매출 데이터는 프로토타입 예시이며 해당 업무 API 이식 범위는 아니다.

1. 문서 검토와 결정 사항 확정 후 최신 문서를 다시 읽는다.

7. Matrix AI 정책·모델·토큰·요청ID·원자적 저장을 연결한다.
8. 권한·상태·복수 창·실패·용량 검증과 작업 기록을 작성한다.

단계적으로 구현하더라도 완료 기준은 제3장의 구현된 원본 기능 전체다. 이메일 공유를 프로젝트 권한으로 대체하는 항목은 단순 생략하지 말고 Matrix에서 대응 동작을 실제로 사용할 수 있어야 한다.

## 17. 검증 방법

### 편집·문서

- 모든 요소/옵션/아이콘/이미지/중첩의 저장→조회→미리보기 일치.
- 페이지/레이어 이름·추가·부모 이동·순서·삭제와 마지막 페이지 보호.
- Ctrl/Shift 선택, 중복ID·순환·잘못된 부모·맵 참조 거부.
- 10/100/300% 이동/리사이즈, 팬, 선택 박스, 부모 상대 좌표.
- 860/650/390px, 빈 페이지 조건, AI/템플릿 후 Mobile390 유지.
- undo/redo40건, 입력 묶음, 문서 로딩 후 초기화, 이미지 삭제 undo.
- 세 템플릿, 미저장 대체 확인, 다섯 코드 형식과 한 줄 복사, 수정 후 코드 갱신.

### API·DB·권한

- 401, guest/온보딩, 타 프로젝트·workspace, screen이 아닌ID, 삭제 화면, 이미지 ID 교체 공격.
- owner/admin/member/viewer와 탭 사용자 설정. READ 전용도 링크로 열리지만 저장/paste/메모/AI는 불가.
- 구성원 제외·권한 회수·세션 만료 이후 저장/조회 처리.
- 동시 최초 저장, 다른 창과의 expectedVersion 충돌, 기존 화면 편집과의 충돌, 전체 rollback.
- 화면 필드·링크 보존, 화면 버전/보드 참조 변경이 기존 추적/검증에 반영되는지 확인.
- 원본 Firebase/SSO 설정 없이 동작하고 서버의 비밀 정보가 브라우저에 전달되지 않는지 확인.

### 협업·검토·AI·UI

- draft→review→rejected→저장→재요청→complete→새draft의 전체 순환.
- review 본문 수정·AI·템플릿·owner 직접 완료 차단, 검토자·대상 버전 검증, 이벤트 원자성.
- 코멘트/메모의 범위·상한·버전·페이지 처리, 작성자·시각, 권한 회수.
- 플랜별 이력, 개인 프롬프트와 공유 변경 이력의 조회 범위.
- AI 초기/기존 수정/페이지 추가/ID 유지/좌표/상한, 가드레일 거부, maxChanges=0, 토큰 소진, 미완료/시간 초과.
- 요청 재송신의 중복 과금·저장 방지, 기록/DB 실패 시 부분 성공 방지.
- 목록→독립 창→미저장 미리보기, 페이지·키 이동, 팝업 차단 안내.
- 잘못된 origin/source/nonce 무시, 재로딩·송신 창 종료·인증 만료.
- 공통 모달, 포커스, 좁은 창, 밝은/어두운 테마, 다른 Matrix 화면 CSS 영향 없음.
- 구현 단계에서 타입 검사·변경 파일 ESLint·빌드·전용 API/브라우저 테스트와 기존 화면 CRUD/추적/AI 회귀를 수행한다.

**이번에는 소스 읽기와 구조 분석만 수행했다. 위 구현 후 검증을 실행했다는 의미가 아니며 DB 접속·migration 적용도 수행하지 않았다.**

## 18. 결정이 필요한 사항

| 항목 | 권장안 | 대안·영향 |
| --- | --- | --- |
| 연결 단위 | screen1건=board1개, 내부 다중 페이지 | 페이지마다 screen이면 채번·추적·저장·이동 설계 변경 |
| 최초 보드 작성 | 기존 화면의 UPDATE | CREATE도 요구하면 권한 조합별 UX 추가 |
| 신청/직접 완료 | 프로젝트 owner | admin 위임 또는 담당자 제도 여부 |
| 검토자 | 동일 프로젝트의 UPDATE 사용자 | READ 특례는 별도 업무 권한·감사 필요 |
| 공유 | 프로젝트 소속·탭 권한 | 보드별 추가 제한은 별도ACL, 이메일로 기존READ 확대 금지 |
| 화면 상태 연동 | 본문 버전 연동, 승인 상태 독립 | screen 승인/완료 자동 전환은 명시적 검수 규칙 필요 |
| 이력 보존 | 일반 이력은 플랜, 승인 식별·감사는 별도 | 전체 스냅샷 상시 보관 시 기간·용량·삭제 정책 확정 |
| AI 프롬프트 | 본인 요청 상세, 공유는 변경 개요 | 원본처럼 문서 조회자에게 전체 프롬프트 공유할지 결정 |
| 크기 제한 | 잠정 JSON5MiB, 이미지8MiB/개·50개/보드, 수동30페이지·2,000요소·깊이12 | 원본900KB, AI8페이지/64요소와 다름. 운영량·플랜 기준으로 확정, 초과 무음 삭제 금지 |
| AI 출력 | 범위 지정과 필요 시 전용16,000 | 공통6,000 유지 시 작은 범위 필요, 예약·비용·시간 반영 |
| 이미지 문서함 연계 | 전용 비공개 자산 | 문서함 등록 시 documents권한·삭제 보호·중복 정책 필요 |
| 코드 이미지 배포 | 동봉/임베딩/참조표 중 확정 | 인증URL만 복사하면 외부 표시 불가, ZIP 출력은 추가 설계 |
| 아이콘 | 원본ID/표시 유지, 지연 로딩 | MUI/Emotion 의존성 또는 로컬 SVG 어댑터 |
| 첫 화면 | 빈 페이지, 템플릿은 직접 선택 | 첨부 업무 예시를 기본값으로 쓰려면 데이터 지정 |
| 기존 자료 이전 | 신규 이용 우선, 별도 이전 | Firestore 소유자·공유·이미지·이력 매핑 필요 |
| 장시간 생성 중지 | 구현 전 Matrix 중지 기능 재사용 여부 확정 | 원본은 생성 대기 중심, 추가 시 요청 상태·저장 경쟁·과금 확정 포함 |

## 19. 이번 작업의 변경 범위

- 본 문서와 `hams-matrix/HISTORY.md` 링크 추가만 수행한다.
- 원본/Matrix 소스, 패키지, 인증 설정, DB, 스토리지 데이터는 변경하지 않는다.
- 제18장의 권장안은 사용자 검토 대상이며 구현 승인이나 DB 변경 실행을 의미하지 않는다.
- 후속 구현 시 이 문서의 최신 내용을 다시 읽고, 기존 미커밋 변경을 보존한다.
- AI는 인증 및 사용 권한은 hams-matrix의 로그인 사용자 정책에 따른다.
