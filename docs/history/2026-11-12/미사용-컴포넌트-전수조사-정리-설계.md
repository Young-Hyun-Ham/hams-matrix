- 작성일: 2026-11-12 (한국시간, Asia/Seoul)
- 상태: 사용자 검토·수정용 설계. 구현은 별도 요청 후 진행한다.
- 조사 기준: hams-matrix의 현재 작업 트리. 기존 관리자 API 분리·CSS 경로 정리 등 미커밋 변경을 포함한다.
- 이번 단계의 변경: 본 문서 작성과 HISTORY.md 링크 추가만 수행한다. 소스 삭제·수정, 설정·의존성 변경, DB 접근·변경, 서버·테스트 실행은 하지 않는다.

## 1. 요구사항

1. 현재 애플리케이션 소스를 전수 조사하여 사용하지 않는 컴포넌트와 관련 소스를 식별한다.
2. 직접 import뿐 아니라 라우트에서의 간접 연결, 재수출, 동적 import, 타입 참조, JSX·컴포넌트 레지스트리, 테스트의 직접 파일 읽기를 확인한다.
3. 미사용 파일은 기능별로 묶어 삭제 후보로 제시하고, 공유 의존성과 공개 URL·API는 유지한다.
4. 삭제에 수반되는 전용 CSS·보조 소스·현재 안내 문서 수정 범위를 구분한다.
5. 요구사항·현재 구조·수정 방향·변경 파일·검증 방법·결정 사항을 문서화한다. 기존 이력 목록은 보존한다.
6. 사용자 검토 전에는 구현하지 않는다. 현재 단계에서 조사용 코드는 메모리에서만 실행하며 저장소에 분석 도구나 결과 JSON을 추가하지 않는다.

### 1.1 범위

- 대상 저장소는 hams-matrix다. 같은 workspace의 hams-planning-board 등 형제 프로젝트는 변경·삭제 대상으로 삼지 않는다. Matrix 안에 이식된 planning-board 소스는 조사에 포함한다.
- UI뿐 아니라 app·components·lib·stores 전체의 import 관계를 확인하고, scripts의 참조와 styles·공개 자원 사용 가능성을 교차 확인한다.
- node_modules, .next, .auth-tests 등 의존성·빌드·테스트 복사본은 제품 소스 목록에서 제외한다. 과거 docs/history·docs/work는 실행 사용처로 계산하지 않되 근거와 과거 기능의 확인에 사용한다.
- 사용 중인 파일 안의 컴포넌트 선언도 심볼 참조와 레지스트리를 확인했다. 사용되지 않는 export 지정이나 내부 전용 타입 자체를 이번 정리의 필수 삭제 대상으로 확대하지 않는다.
- 일반 미사용 CSS 선택자 전수 삭제, 라이브러리 정리, API 폐기, DB 마이그레이션은 별도 작업이다.

## 2. 조사 방법과 결과

### 2.1 판정 방법

1. rg 파일 목록과 현재 소스를 확인했다. 프로젝트 AGENTS.md의 Query·workspace·권한·CSS 경로 규칙을 기준으로 삼았다.
2. 설치된 TypeScript Compiler API로 소스를 파싱하고 tsconfig.json의 @/* 별칭과 bundler 모듈 해석 설정을 사용하여 로컬 참조 그래프를 구성했다.
3. import, export-from, import type, import()·require()의 문자열 리터럴을 확인했다. 타입 전용 연결도 보존해야 하는 연결로 계산했다.
4. app의 page·layout·route·loading·error·not-found 등 특수 파일을 진입점으로 잡았다. Next 설정도 별도 진입점으로 포함했다. 다른 파일의 import가 없는 라우트 파일을 미사용으로 오판하지 않는다.
5. 진입점에서 도달하지 않는 파일을 추출하고 후보의 export·파일명·사용 심볼을 app·components·lib·stores·scripts 및 현재 안내 문서에서 재검색했다. 후보 내부 내용과 실제 대체 화면을 확인했다.
6. TypeScript 심볼 확인과 소스 재검토로 객체 레지스트리·컴포넌트 맵 사용을 확인했다. JSX 태그 검색만으로 미사용을 확정하지 않았다.
7. scripts의 맞춤 load(resolve(...))·readFileSync 등 AST import 그래프에 포함되지 않는 참조를 별도 확인했다. 테스트가 사용하는 파일은 제품에서 연결되지 않아도 무조건 삭제하지 않는다.

**진입점 연결은 보수적인 유지 기준이다.** 정적 연결이 있다는 것만으로 모든 분기가 실제 실행된다는 뜻은 아니다. 반대로 후보 목록은 조사 시점의 저장소 안에서 실행·타입 소비자를 찾지 못한 결과이며, 외부 배포본·저장소 밖 소비자까지 부재를 증명한 것은 아니다. 구현 직전에 사용자가 수정한 최신 문서와 소스를 다시 대조한다.

## 4. 수정 방향

### 4.1 기본 제안

**D01~D18을 파일 단위 삭제 후보로 제안한다.** 기존 화면으로 재연결하거나 다른 공통 컴포넌트로 다시 추상화하지 않고 현재 동작을 유지하는 방향이다. 각 후보의 실제 import·export·타입·테스트 참조를 구현 직전에 다시 확인한다.

추가로 전용 CSS 2개와 보조 소스 2개를 함께 정리하는 안을 권장하되, 8절에서 사용자 검토가 필요한 범위로 구분한다. 이를 모두 선택하면 예상 삭제 파일은 **22개(컴포넌트 관련 18 + 전용 CSS 2 + 보조 소스 2)**다. lib/admin-history.ts는 이 수량에 포함하지 않는다.

삭제 후보 대부분은 이미 제품 진입점에서 연결되지 않으므로 주효과는 유지보수 혼란·과거 계약·검사 대상 소스의 감소다. 실제 번들 크기·로딩 속도 개선량은 측정하지 않았으며 보장하지 않는다.

### 4.2 CSS와 자원

- styles/pages/onboarding/registration.css는 D10이 유일하게 import한다. 가입 UI 묶음 삭제 후 소스·CSS @import·테스트 파일 읽기 참조가 없는지 다시 확인하여 삭제한다.
- styles/pages/projects/tabs/wbs/wbs-schedule-image.css는 D07만 import한다. 이전 로컬 이미지 출력 UI와 함께 삭제한다.
- 이번 기본안에서는 architecture-page.css·screens-page.css 안의 이전 UI 선택자, 공통 CSS의 유사 선택자를 함께 줄이지 않는다. 일반 CSS는 전역 공유될 수 있으므로 별도 선택자 조사가 필요하다.
- 기존 CSS 정리에서 미import로 기록한 dashboard-page·requirements-page·specifications-page·history-page·deliverables-page CSS 5개는 이번 컴포넌트 삭제 목록과 구분한다. 페이지 자체는 사용 중이므로 함께 삭제하거나 import를 추가하지 않는다.
- public 파일이나 JSON·문서 템플릿은 문자열·저장 데이터·다운로드 경로로 사용될 수 있다. 후보 18개 삭제만으로 자원 전체를 연쇄 삭제하지 않는다.
- CSS를 이동하거나 shared 폴더를 새로 만들지 않는다. 현재 styles/ 및 styles/pages/ 배치 기준을 따른다.

## 7. 검증 방법

### 7.1 이번 설계 단계에서 수행한 확인

- 소스 파일 목록과 설정·현재 안내 문서·관련 작업 기록을 읽었다.
- 528개 파일의 AST 참조 그래프와 진입점 도달성을 메모리에서 분석했다. 제품 코드에 비리터럴 import/require가 없는지 확인했다.
- 삭제 후보 18개 각각의 소비자·타입 연결·현재 대체 화면과 scripts의 직접 문자열 로더 참조를 확인했다.
- JSX 태그뿐 아니라 ProjectWorkbench의 동적 탭 맵과 플래닝보드 아이콘 레지스트리를 확인하여 유지 대상으로 분류했다.
- 빌드·타입 검사 CLI·ESLint·브라우저·회귀 테스트·마이그레이션·운영 DB 조회는 실행하지 않았다. 아래 목록은 구현 후 수행할 검증 계획이며 통과 결과가 아니다.
- 이번 변경 범위와 HISTORY 기존 내용 보존은 문서 작성 후 diff·파일 해시로 확인한다.

### 7.2 구현 직전·정리 직후의 정적 확인

1. 대상 경로·export·컴포넌트명과 별칭/상대 경로를 app·components·lib·stores·scripts·설정 파일에서 다시 검색한다. 남은 참조가 있으면 삭제 목록을 수정한다.
2. 진입점 그래프를 재구성한다. 미사용 묶음 내부의 타입 참조가 고아로 남지 않고, 유지 대상 파일이 새로 단절되지 않았는지 확인한다.
3. CSS import·CSS @import·readFileSync·load(resolve(...))와 문서/자원 문자열 경로를 확인한다. 공개 라우트와 저장된 아이콘 이름은 보호한다.
4. pnpm typecheck, pnpm lint, pnpm build를 실행한다. typecheck의 incremental 산출물과 .next 등은 구현 검증 단계에서만 생성하며 설계 단계에서는 만들지 않는다.
5. pnpm test:query-audit로 남은 전송 호출의 분류를 확인한다. 호출 총수는 미사용 파일 삭제로 감소할 수 있으므로 이전 숫자와 무조건 같아야 한다고 판단하지 않는다.
6. git diff --check와 변경 파일 목록으로 채택한 삭제·현재 안내 수정 외 소스·DB·의존성 변경이 없는지 확인한다.

테스트는 구현 시 스크립트의 DB·서비스 격리 여부를 다시 읽은 뒤 임시 SQLite·합성 계정·외부 서비스 대역으로만 수행한다. 운영 DB와 실제 유료 AI·결제 호출을 사용하지 않는다. 문서에 명령을 나열한 것이 전체 스크립트의 현재 통과나 모든 화면 커버리지를 뜻하지 않는다.

현재 [CSS 정리 작업 기록](../../work/2026-11-12/CSS-화면주소별-스타일경로-정리.md)에는 WBS 폼·채팅 독립 fixture의 @tanstack/query-core 모듈 해석 실패와 DB 조회자 fixture의 workspace 불일치가 기록되어 있다. 이는 이번 조사에서 재현한 결과가 아니다. 후속 검증 시 변경 전후 기준선과 신규 실패를 구분하고, 권한을 완화하여 테스트를 통과시키지 않는다.

브라우저 검증은 데스크톱·모바일, 라이트·다크에서 실제 본문 로딩 완료 후 비교한다. 오류 화면이나 로딩 화면만 표시된 상태를 정상 렌더링 통과로 계산하지 않는다.
