# WBS 일정 입력·조회·저장·배포 및 전체 일정 날짜 표시 개선 설계

- 작성일: 2026-10-30 (한국시간)
- 단계: 현재 소스 분석 및 설계. 이 작업에서는 문서와 HISTORY 링크만 수정한다.
- 대상: 프로젝트의 WBS 일정 탭. 기존 다른 작업과 데이터는 보존한다.

## 1. 요구사항

1. 시작일·종료일의 텍스트 직접 입력을 막는다.
2. 상단 작업명·담당자 검색창에서 돋보기와 placeholder가 겹치는 문제를 수정한다.
3. 상태 필터 옆에 `조회`, `저장`, `배포` 버튼을 추가하고 실제 프로젝트 데이터를 저장·재조회할 수 있도록 한다.
4. 전체 일정 모달의 그래프 상단 날짜 표시를 정상화한다.

날짜는 **직접 타이핑·붙여넣기를 제한하되 달력 선택과 간트 드래그는 유지**하는 것으로 우선 해석한다. 날짜 변경 자체를 모두 금지하는 요구인지, 배포가 어떤 상태·대상에 반영하는 행위인지는 아래 결정 사항에서 구분한다.

## 2. 현재 구조와 문제 원인

### 2.1 현재 탭은 DB와 연결되지 않은 편집 화면

- `components/pages/wbs/wbs-page.tsx`는 프로젝트 context에서 artifacts를 받지만 실제 렌더링하는 `WbsComponement`에 전달하지 않는다. 기존 `WbsSchedule`과 `ArtifactList(kind="wbs")`는 주석 처리되어 있다.
- `wbs-schedule-chart.jsx`는 `useState(INITIAL_TASKS)`로 2025년 샘플 데이터를 표시한다. 신규 작업·행 수정·삭제·드래그 모두 로컬 tasks만 변경하며 서버 요청이 없다.
- 신규 ID는 Date.now() 문자열이며 표시용 wbs 번호는 샘플의 `1.0`, `1.1` 방식이다. 실제 산출물 ID 및 서버 발급 관리번호 `WBS-001`과 다르다.
- 현재 화면은 프로젝트 쓰기 권한을 받지 않는다. DB 연결 시 버튼뿐 아니라 행 입력, 추가·삭제·드래그까지 권한 제어가 필요하다.
- 검색은 작업명·담당자·표시 번호를 대상으로 즉시 적용되고, 상태 필터는 `pending/in-progress/completed`를 사용한다. 실제 산출물 status는 초안·검토 중·승인·진행 중·완료·보류다.

### 2.2 날짜 입력

- 등록 영역의 시작일·종료일은 native `input type="date"`이고 onChange에서 tasks를 수정한다. 하위 작업이 있는 부모 행만 disabled다.
- type=date도 브라우저에 따라 키보드로 날짜 부분을 바꿀 수 있어 현재 구현만으로 직접 입력이 차단되지 않는다.
- `components/shared/date-input.tsx`는 연·월·일 텍스트 입력과 native 달력을 함께 제공한다. 요구사항을 맞추기 위해 이를 그대로 교체 사용하면 텍스트 입력이 다시 허용된다. 공통 컴포넌트 전체의 기존 입력 방식도 임의로 바꾸지 않는다.

### 2.3 검색 아이콘 겹침

- 현재 돋보기는 버튼이 아닌 장식용 `Search` SVG이며 absolute left 10px에 배치된다. 입력에는 pl-8, 즉 좌측 32px 여백을 의도했다.
- 차트 CSS에 `.wbs-chart [class~="pl-8"]` 규칙은 이미 존재한다. 누락된 유틸리티를 추가하는 문제로 처리하면 해결되지 않는다.
- `components/project-workbench.css`의 `.matrix-workbench input:not([type="checkbox"])`가 padding 10px 12px을 지정한다. 이 선택자는 차트의 pl-8 규칙보다 우선순위가 높아 아이콘용 여백을 덮어쓸 수 있다.
- 따라서 전용 검색창 클래스와 명시적인 영역 분리 또는 충분한 우선순위의 padding 규칙으로 해결해야 한다.

### 2.4 전체 일정 모달의 날짜 표시

- `renderOverview(expanded)`가 썸네일과 모달을 함께 렌더링한다. 모달은 labelWidth 230, chartWidth=max(1000, totalDays×18), 헤더 높이 32의 SVG다.
- 현재 각 날짜마다 배경 rect → 세로선 → 날짜 text를 그린 뒤 다음 날짜의 배경을 그린다. 모달의 일당 약 18px 영역보다 `10/30` 같은 글자가 넓으면 **뒤에 그린 다음 날짜 배경이 앞 날짜의 글자 뒷부분을 가릴 수 있다.**
- 라벨은 시작점부터 7일마다 M/D만 표시한다. 연도와 월 경계 의미가 약하고 마지막 날짜가 항상 표시되는 구조도 아니다.
- `preserveAspectRatio="none"` 및 외부 width/height 100% 설정으로 축 비율이 변할 수 있다. 작업이 많아 모달 최대 높이에 닿는 경우에는 현재 overflow-y:hidden도 하단 잘림 가능성이 있다.
- 날짜 함수는 실행 브라우저의 로컬 Date를 사용한다. DB 연결 후 윤년·월말·연말·빈 날짜·시간대에 대한 일관된 처리도 필요하다.

### 2.5 기존 서버와 저장 제약

- GET/POST `/api/projects/[projectId]/artifacts`, PATCH/DELETE `/api/projects/[projectId]/artifacts/[artifactId]`가 있다. `lib/artifacts.ts`에서 프로젝트·워크스페이스 권한, version 충돌, 관리번호, 이력 및 감사 기록을 관리한다.
- `project_artifacts`의 fields_json·structure_json, `artifact_links`의 wbs_parent/wbs_dependency, `artifact_revisions`를 기존 WBS 저장소로 재사용할 수 있다.
- `definitions.wbs.fields`는 단계·작업유형·계획 기간·계획/실제 공수·진척률·작업 범위/완료 기준 등을 요구한다. 현재 차트 행에는 이 중 상당수가 없다.
- `prepareStructure`와 `validateProjectGraph`는 요약 부모, 기간 포함, 순환·선행 관계, 마일스톤 조건, 완료 시 100% 진척률 등을 검증한다.
- 차트의 부모 진척률은 단순 평균이지만 `lib/integration.ts`의 taskMetrics는 말단 작업의 계획 공수 가중치를 사용하며 0시간은 가중치 1로 계산한다. DB 연결 시 이 차이를 해소해야 한다.
- 확인한 프로젝트 API·저장 모델에는 WBS의 별도 배포 동작이 없다. 기존 status의 승인/완료나 프로그램 기술 기준선 기능을 일정 배포로 간주해서는 안 된다.

## 3. UI 수정 방향

### 3.1 날짜 선택 전용 컨트롤

- 행에는 날짜를 읽기 전용으로 표시하고, 옆의 `시작일 선택`/`종료일 선택` 버튼으로 달력을 연다. 달력에서 선택한 값만 변경 핸들러에 전달한다.
- type=date에 readOnly만 지정하면 native 달력까지 작동하지 않는 브라우저가 있으므로 그 방식만으로 구현하지 않는다. showPicker 지원 여부와 사용자 클릭 시 호출 가능 조건을 확인하고, 미지원 환경에는 키보드 접근 가능한 달력 팝오버 대안을 제공한다.
- readonly 표시부에서는 타이핑·붙여넣기·드롭으로 값이 바뀌지 않게 한다. 버튼의 Enter/Space와 달력 내부 키보드 탐색은 허용한다. 모든 keydown을 차단하지 않는다.
- 요약 행의 날짜는 하위 항목에서 계산하여 표시한다. 마일스톤은 시작·종료를 함께 변경한다. 읽기 전용 사용자 및 처리 중 상태에는 달력과 드래그를 모두 막는다.
- 공통 날짜 컴포넌트를 확장한다면 opt-in 선택 전용 모드를 추가하고 다른 화면의 기존 텍스트 입력 동작은 유지한다.

### 3.2 검색과 도구 영역

```text
[돋보기 | 작업명, 담당자 검색…] [상태 필터 ▼] [조회] [저장] [배포]
저장 상태: 미저장 변경 N건 / 마지막 저장 시각 / 배포 상태
```

- 검색창을 전용 grid/flex로 구성해 아이콘을 독립된 칸에 두는 방안을 우선 권장한다. 장식 아이콘은 aria-hidden과 pointer-events:none을 사용하고 input에 접근 가능한 이름을 준다.
- 검색은 현재처럼 로컬 필터로 유지하고 `조회`는 서버 새로고침으로 구분한다. Enter 검색 동작을 추가하더라도 저장·배포가 실행되지 않도록 button type을 명시한다.
- 버튼이 늘어나므로 작은 화면에서는 줄바꿈하되 검색·상태·조회/저장/배포 순서를 유지한다. 로딩·실패·빈 결과를 별도로 표시한다.

### 3.3 전체 일정 모달

- SVG의 그리기 순서를 배경/주말 음영 → 눈금·가로세로선 → 작업 막대 → 날짜·작업명·라벨 순서로 분리한다. 날짜 라벨이 후속 배경에 가려지지 않도록 한다.
- 날짜 위치와 막대 위치는 같은 순수 좌표 함수 및 같은 전체 기간을 사용한다. 종료일을 포함한 막대 폭 계산을 유지한다.
- 헤더는 연·월 구간과 일자 눈금을 분리한다. 짧은 기간은 일별, 긴 기간은 주/월별로 간격을 조정하고 최소 라벨 간격을 보장한다. 시작·끝 날짜는 겹치면 정렬·생략 규칙으로 처리하며 전체 YYYY-MM-DD 기간을 헤더 설명에도 표시한다.
- 모달에서는 실제 SVG 폭을 보존하고 가로 스크롤을 제공해 글자와 날짜가 압축되지 않게 한다. 행이 많으면 세로 스크롤도 허용한다. 썸네일은 축약한 라벨 정책을 유지한다.
- 달력 일자 계산은 날짜 전용 YYYY-MM-DD를 기준으로 하고, 오늘/표시 시각은 한국시간으로 정의한다. 날짜만 있는 값을 UTC→로컬로 변환해 하루가 바뀌지 않게 한다.
- 현재 테마, 모달 닫기·포커스 복귀, 분할 화면 및 행 접기 기능은 보존한다. 일간/주간/월간의 의미와 기존 드래그 환산 단위도 회귀 점검한다.

## 4. 실제 데이터 조회·저장 설계

### 4.1 프로젝트 데이터 연결

- WbsPage에서 projectId, WBS artifacts, canWrite, 재조회 콜백을 차트 모델에 전달한다. 현재 context에는 reload가 없으므로 `ProjectContent`의 onReload를 연결하거나 전용 조회 훅을 둔다.
- 샘플 데이터는 실제 프로젝트의 초기값으로 사용하지 않는다. DB에 WBS가 없으면 빈 일정과 추가 안내를 표시한다.
- 프로젝트 전환 시 해당 프로젝트의 초안을 정리하고 로딩 중 추가·저장을 차단한다. 이전 프로젝트의 늦은 응답이 현재 화면을 덮지 않도록 요청 취소/식별자를 사용한다.
- 서버 원본, 편집 초안, 신규 임시 항목, 삭제 목록과 기준 version을 분리한다. 검색/상태 필터/접힘 상태는 표시 상태이며 저장 대상에서 제외한다.
- 저장은 visibleTasks가 아닌 **변경한 전체 tasks와 명시적 삭제 목록**을 대상으로 한다. 필터로 숨긴 작업은 삭제하지 않는다.

### 4.2 필드 매핑 및 기존값 보존

| 차트 값 | 기존 WBS 데이터 | 정책 |
| --- | --- | --- |
| id | Artifact.id | 기존 서버 ID 유지, 신규 임시 ID는 저장 후 서버 ID로 치환 |
| wbs | code 및 계층 표시 번호 | WBS-001은 서버 관리번호. 1.1 등 계층 번호와 분리하고 표시 규칙 확정 |
| title | title | 기존 200자 검증 유지 |
| assignee | fields.owner | 현재 문자열 담당자 보존. 회원 ID로 임의 변경하지 않음 |
| startDate/endDate | fields.startDate/endDate | 날짜 선택과 드래그 결과 저장, 부모 기간·선행 관계 검증 |
| progress | fields.progress | 문자열 직렬화, 0~100. 요약은 공통 가중 집계 |
| parentId | structure.parentId | 같은 프로젝트의 요약 작업만 부모로 허용 |
| status | Artifact.status | 화면의 3개 상태 필터와 원본 status를 분리 |
| 화면에 없는 항목 | phase/taskType/공수/definition/actualStart/actualEnd/notes, links/dependencies 등 | 기존값 병합·보존. 숨긴 필드를 빈값으로 덮어쓰지 않음 |

- 신규 작업에 부족한 필수값은 공통 WBS 등록/상세 편집 모달로 입력하게 하는 방안을 권장한다. 특히 단계·작업 범위는 제목에서 임의 추측하여 저장하지 않는다. 공수는 기존 정의의 0 기본값을 사용할 수 있다.
- 하위 작업 추가 시 기존 실제 작업을 요약으로 바꾸면 연결 산출물·선행 관계 제한이 발생한다. 기존 제약을 안내하고 유효한 요약 항목에만 추가하거나 유형 변경을 명시적으로 처리한다.
- 진행률을 바꿨다고 승인·보류 등을 자동 변경하지 않는다. 완료를 선택할 때 진척률 100을 검증한다. 3개 필터를 진행률 기반으로 유지할지 실제 status 목록으로 바꿀지는 결정 사항이다.
- 요약 집계는 공통 계산 함수를 재사용하고 tasks를 effect 안에서 반복 갱신하는 현재 구조를 정리한다. 원본 작업과 파생 집계를 분리하면 저장 전후 값 차이와 기존 set-state-in-effect lint 오류를 함께 해소할 수 있다.

### 4.3 조회 버튼

- 현재 서버의 WBS 및 버전을 다시 읽는다. 검색/필터 조건은 유지하되 원본·편집 기준은 성공한 응답으로 갱신한다.
- 미저장 변경이 있으면 공통 확인 모달로 폐기 여부를 확인한다. 실패하면 편집 중인 내용을 유지한다.
- 읽기 전용 사용자도 조회할 수 있다. 이력·다른 탭 데이터와 일관되게 프로젝트 데이터를 갱신한다.

### 4.4 저장 버튼과 원자성

- 신규·수정·삭제를 한 번에 제출하는 WBS 전용 batch API를 권장한다. 예: POST `/api/projects/[projectId]/wbs/schedule`에 creates/updates/deletes 및 기준 버전 목록을 전달한다. 경로·계약은 구현 시 확정한다.
- 기존 항목은 version을 요구하며, 새 임시 ID는 중복을 검증하고 서버 ID 매핑을 반환한다. 관계에 쓰인 임시 ID도 같은 트랜잭션에서 치환한다.
- 단일 쓰기 트랜잭션에서 권한 → 입력/버전 → 최종 후보 그래프 → 관리번호/행/관계/이력/감사 기록을 처리한다. 다른 kind 및 다른 프로젝트 항목 변경은 허용하지 않는다.
- 부모 기간과 자식 기간을 동시에 변경하는 경우 개별 PATCH를 순서대로 호출하면 중간 상태가 기간 포함 검증을 통과하지 못할 수 있다. 각 항목의 기본 검증 후 **변경 전체를 반영한 최종 그래프**에 대해 검증하는 일괄 저장 경로가 필요하다.
- 현재 mutateArtifact를 반복 호출하는 것만으로 이 문제를 해결했다고 보지 않는다. 필드·관계 검증과 실제 저장 단계를 분리하여 기존 API와 공유하고, 참조 보호·version·이력 정책을 우회하지 않는다.
- 자식 포함 삭제는 기존 다른 산출물 참조·선행 관계를 검사한다. 필터나 화면에서 보이지 않는다는 이유로 DB 항목을 삭제하지 않는다.
- 일부만 성공하는 저장은 제공하지 않는다. 409 충돌 시 어떤 관리번호가 바뀌었는지 알리고 초안을 보존한다. 저장 성공 후 서버 결과로 원본/초안을 재설정하고 프로젝트 context를 갱신한다.
- 중복 제출을 방지하고 생성/삭제 재시도의 중복 반영을 막을 요청 식별자를 설계한다. 빈 변경 저장은 불필요한 버전 증가를 만들지 않는다.

## 5. 배포의 의미와 DB 영향

배포의 대상·소비 화면이 현재 요구에 정의되지 않았다. 아래는 **검토용 제안**이며 확정된 업무 규칙이 아니다.

### 권장 검토안: 저장본을 프로젝트의 확정 일정 스냅샷으로 발행

- `저장`은 기존 WBS artifacts의 영속화, `배포`는 마지막 저장본의 명시적 확정 버전 발행으로 구분한다. 외부 서비스 배포·이메일/메시지 전송·공개 URL 생성은 포함하지 않는다.
- 미저장 변경이 있으면 배포를 막고 먼저 저장하도록 안내한다. 배포 직전 서버 버전/해시를 검증해 화면에서 확인한 저장본과 다르면 409를 반환한다.
- 요약·작업·마일스톤과 날짜·담당자·공수·선행 관계·원본 ID/version을 포함한 불변 스냅샷, 배포자·배포시각·순번/해시를 기록한다. 작업 진행률 변경 등 후속 저장은 이전 배포본을 덮어쓰지 않는다.
- 배포 전 미리보기/확인 모달에서 대상 프로젝트와 저장본을 제시한다. 동일 저장본 중복 배포의 처리와 조회자가 보는 기본 버전도 확정해야 한다.
- 이 의미를 채택한다면 프로젝트/워크스페이스 범위의 배포 이력 테이블과 최신 배포본 조회 API가 필요하다. 예: `wbs_schedule_publications`. 복합 외래키, 배포 순번/해시 중복 제한, 생성자·UTC 시각, 유효한 JSON 스냅샷을 설계한다. 다음 실제 가용 번호로 마이그레이션을 추가한다.
- 배포본의 소비처는 기존 편집 화면과 별도로 최신 배포 보기 등 명시적 UI가 있어야 한다. 버튼을 누른 기록만 남기고 아무 화면에도 반영되지 않는 구현을 완료로 보지 않는다.

### 대안과 구분

- 배포가 단지 공동 사용자에게 저장 내용을 보이게 하는 뜻이라면, 현재 같은 프로젝트 멤버가 저장 데이터를 공유하므로 별도 저장본 없이 동일 개념의 버튼 두 개가 된다. 이 경우 저장/배포의 업무 차이를 먼저 정해야 한다.
- 승인 상태 전환이 목적이라면 허용 전이·승인자 권한을 별도로 정의한다. 모든 WBS를 일괄 승인/완료로 변경하는 방식은 권장하지 않는다.
- **배포 정책 확정 전에는 신규 테이블의 생성이나 기존 데이터 상태 변경을 확정하지 않는다.** 단순 조회·저장 연결은 기존 JSON/관계/이력 테이블로 가능하다. 별도의 일정 초안 저장소를 중복 생성할 필요는 없다.

## 7. 검증 방법

### 화면·날짜·검색

- 시작/종료일에서 타이핑·붙여넣기·드롭으로 값이 바뀌지 않고 달력·키보드 달력 조작·간트 드래그는 정책대로 동작한다. showPicker 미지원 브라우저도 확인한다.
- 부모/마일스톤/읽기 전용/저장 중 상태에 맞는 날짜 변경 제한과 시작≤종료 검증을 확인한다.
- 프로젝트 작업 공간의 실제 CSS가 적용된 화면에서 placeholder·입력 문자열과 돋보기가 겹치지 않는지 확인한다. 라이트/다크·확대 배율·작은 화면에서 검증한다.
- 전체 일정에서 날짜 글자 잘림·배경 가림이 없는지, 막대와 눈금의 시작/끝이 같은 날을 가리키는지 확인한다. 썸네일도 함께 확인한다.
- 1일·수개월·다년도, 월말/연말·윤년, 작업 없음·많은 작업, 긴 이름·가로/세로 스크롤·접기/검색 조합을 확인한다. 한국시간 오늘 표시와 다른 브라우저 시간대의 날짜 불변성도 검증한다.

### API·DB·회귀

- 임시 테스트 DB에서 저장→새로고침→다른 사용자 조회→프로젝트 재진입 후 같은 데이터가 나온다. 실제 프로젝트에서 샘플 데이터가 자동 생성되지 않는다.
- 신규/수정/삭제와 부모·자식 기간 동시 변경이 전부 성공하거나 전부 취소되는지 검증한다. 임시 ID 치환·관리번호 보존·숨긴 필드/관계 보존도 확인한다.
- 필터된 행·접힌 자식은 저장/삭제 범위에서 누락되지 않는다. 다른 프로젝트·워크스페이스 접근과 읽기 전용 변경을 차단한다.
- 동시 수정, 조회 중 전환, 요청 실패, 저장 성공 응답 유실/재시도, 삭제 참조 충돌에서 초안 보존과 중복 방지를 확인한다.
- 요약의 공수 가중 진척률과 기간, 선행 관계·순환·마일스톤·완료 상태 검증을 기존 화면/API/출력과 비교한다.
- 배포 정책 확정 시 저장본 version 검증, 권한·중복 배포, 이전 스냅샷 불변성, 최신 배포 조회와 실패 롤백을 추가 검증한다.
- `pnpm typecheck`, 변경 파일 lint, `pnpm build`와 관련 WBS/API/AI/이미지 회귀 테스트를 수행한다. 기존 차트의 set-state-in-effect 오류는 새 데이터 흐름에서 해소됐는지 확인한다.

## 8. 결정이 필요한 사항

| 항목 | 제안/확인이 필요한 내용 |
| --- | --- |
| 날짜 입력 제한 범위 | 직접 텍스트 입력만 차단하고 달력·드래그 유지 권장 |
| 배포 의미·소비처 | 저장본 확정 스냅샷 발행 제안. 누가 어디서 배포본을 조회하는지 확정 필요 |
| 배포 권한 | 프로젝트 owner/admin으로 제한할지 canWrite 전체에 허용할지 결정. 현재 규칙으로 추정하지 않음 |
| 신규 작업 필수값 | 기존 공통 등록 모달에서 단계·유형·범위 등을 입력하는 방식 권장 |
| 상태 필터 | 실제 산출물 상태로 확장할지, 진척률 기반 3분류로 유지할지 결정 |
| 표시 번호 | 서버 관리번호와 계층 표시 번호를 병기할지 결정. 서버 ID/code는 변경하지 않음 |
| 저장/배포의 범위 | 필터된 화면이 아닌 전체 변경분 저장, 마지막 저장본 전체 배포 권장 |
| 조회·프로젝트 이동 시 초안 | 미저장 경고 후 명시적 폐기, 실패 시 초안 유지 권장 |
| 부모·자식 집계 | 기존 공통 taskMetrics 기준으로 통일 권장 |
| 날짜 헤더 | 연·월 구간 + 기간별 눈금 간격. 최초 표시 범위와 최대 지원 기간 확정 |
