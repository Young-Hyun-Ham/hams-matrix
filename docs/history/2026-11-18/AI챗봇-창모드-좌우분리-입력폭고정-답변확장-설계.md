- 작성일: 2026-11-18 (한국시간, Asia/Seoul)
- 상태: 사용자 검토용 초안. 사용자가 검토·수정한 최종 문서를 기준으로 별도 구현 요청 시 적용한다.
- 분석 기준: 현재 작업 트리의 실제 소스. 기존 미커밋 변경과 같은 날짜의 창 너비 조절 구현을 포함한다.
- 이번 작업 범위: 이 문서와 `HISTORY.md` 링크만 작성한다. 소스·DB·설정·의존성을 변경하지 않는다.
- 검증 수준: 정적 소스 분석. 앱 실행·빌드·브라우저 테스트·DB 접근은 수행하지 않는다. 아래 수치와 추가 정책은 구현 완료 결과가 아닌 검토용 권장안이다.

## 1. 요구사항

사용자 요청: “AI chatbot 창 모드 좌우 분리일 경우 채팅 영역 패널은 크기에 변경이 없고 답변 영역만 늘어나게 한다.”

현재 UI에는 사용자 질문과 AI 답변이 함께 표시되는 대화 목록과 별도 질문 입력 카드가 있으므로, 본 문서는 다음과 같이 용어를 해석한다. 이 해석은 8절의 검토 항목이다.

| 용어 | 현재 화면·소스와의 대응 | 요구 동작 |
| --- | --- | --- |
| 창 모드 | `floating === true`, 같은 페이지 위의 비모달 팝업 | 이 모드의 내부 배치만 변경한다. |
| 좌우 분리 | `split === true`이며 실제 내부 너비가 좌우 배치를 허용하는 상태 | 왼쪽 답변 영역과 오른쪽 입력 패널을 유지한다. |
| 크기를 유지할 채팅 영역 패널 | 오른쪽 `.matrix-ai-card`, 질문 입력·모델·대상·첨부·실행 버튼을 포함한 카드 | 창 가로 크기를 변경해도 카드의 가로 폭을 일정하게 유지한다. |
| 늘어날 답변 영역 | 왼쪽 `.matrix-ai-conversation-pane`, 질문·AI 답변 목록과 공유 답변 관리 footer | 좌우 배치가 유지되는 범위에서 창 너비 증감분 전체를 반영한다. |

### 1.1 수용 기준

1. 좌우 분리 팝업을 마우스·터치·키보드로 넓히면 오른쪽 입력 패널의 폭은 유지되고 왼쪽 답변 영역만 넓어진다.
2. 좌우 배치를 유지할 수 있는 범위에서 좁힐 때도 입력 패널 폭을 유지하고 답변 영역을 먼저 줄인다.
3. 좌우 배치에 필요한 공간이 부족하면 기존처럼 상하 표시로 전환한다. 이때 입력 카드가 전체 가로 폭을 쓰는 것은 예외로 명시한다.
4. 확대·축소 프리셋과 viewport 변경에도 같은 내부 너비 배분 정책을 적용한다. 외부 창 너비·위치·높이 규칙은 기존 동작을 따른다.
5. 패널 모드와 상하 배치 모드의 현재 배분 정책을 보존한다.
6. 입력 내용·첨부·모델·대상·대화방·진행 중 생성 상태·textarea DOM을 유지한다. 순수 크기 변경은 AI 생성·저장·권한 조회를 발생시키지 않는다.

“크기 유지”는 가로 폭에 대한 요구로 해석한다. 세로 높이는 기존 viewport 반응형 규칙과 독립 스크롤을 따른다. 답변 본문만 별도 패널로 추출하거나 사용자 질문 말풍선을 다른 영역으로 이동하지 않는다.

### 2.2 외부 창 너비와 상태

현재 훅의 핵심 계산은 다음과 같다.

```text
expanded = split ? splitExpanded : stackedExpanded
widthGrowth = expanded || split ? 100 : 0
popupBaseWidth = expanded ? 760 : 460
popupWidth = customWidth ?? (popupBaseWidth + widthGrowth)
displayedWidth = min(popupWidth, max(0, viewportWidth - 24))
```

- 상하 기본 팝업 460px, 확대 팝업 860px, 좌우 분리 진입 860px, 분리 상태 축소 560px가 현재 프리셋이다.
- 수동 조절은 최소 360px이며, 화면이 더 좁으면 viewport 제한을 우선한다. 양쪽 화면 여백은 12px이고 조절 시 반대쪽 창 경계를 유지한다.
- `customWidths.stacked`와 `customWidths.split`은 React 메모리에만 저장된다. 닫기·재열기와 패널 전환에서는 유지한다.
- 확대·축소는 현재 배치의 사용자 지정 너비를 해제한다. 분리 재진입은 split 슬롯을 초기화하고 확대 프리셋을 적용한다.
- 기존 창 높이와 이동·포인터 종료 처리는 내부 열 고정과 별개다. 이 요구만으로 해당 훅의 상태나 조작 수명주기를 바꿀 필요는 없다.

### 2.3 내부 열 계산과 문제 원인

`.matrix-ai`는 `container: ai-chat / inline-size`다. 현재는 **내부 콘텐츠 폭 560px 이상**에서 `.ai-is-split .matrix-ai-panel-content`가 grid가 된다. 팝업 외곽 폭 560px가 기준인 것은 아니다.

`C`를 grid 가용 콘텐츠 폭, `G`를 `--ai-added-width`, 열 간격을 12px로 두면 현재 계산은 다음과 같다.

```text
G = clamp(0px, 표시 팝업 폭 - popupBaseWidth, widthGrowth)
왼쪽 대화 열 = min((C - G - 12px) × 0.6, C - G - 252px)
오른쪽 입력 열 = 남은 폭, 최소 240px
```

- 기존 정책은 추가 100px를 입력 열에 우선 배분하도록 왼쪽 열 계산에서 `G`를 공제한다. 이는 요청의 답변 영역 확장 방향과 반대다.
- `G`는 최대 100px다. 그 이상 수동으로 넓혀도 왼쪽 열 계산에 `C`가 계속 들어가므로 두 열이 함께 커진다.
- 따라서 `--ai-added-width`를 0으로 바꾸거나 100px의 부호만 뒤집어도 입력 열 고정은 성립하지 않는다. **팝업 좌우 배치의 오른쪽 열 자체를 고정 길이로 정의해야 한다.**
- 현재 배분 규칙은 패널과 팝업에서 공유한다. 공통 grid 규칙을 통째로 바꾸면 요청 범위 밖인 패널에도 영향을 준다.

## 3. 수정 방향

### 3.1 입력 열 고정·답변 열 가변

기존 DOM과 grid 영역 이름을 유지하고, 창 모드의 실제 좌우 배치에서만 다음 원칙을 적용한다.

```text
공통 상단: 두 열 전체 사용
왼쪽 답변 열: C - 입력 고정 폭 - 12px
오른쪽 입력 열: 입력 고정 폭
```

권장 grid 형태는 `minmax(0, 1fr) var(--ai-floating-composer-width)`다. `--ai-floating-composer-width`는 디자인 상수로 관리하고, 수동 창 너비·100px 보너스·확대 상태에 따라 재계산하지 않는다. `minmax(240px, 1fr)`처럼 가변 비율을 입력 열에 남겨두지 않는다.

고정 대상은 textarea만이 아닌 입력 카드 전체 border-box다. 모델·대상·첨부·공유 후보·버튼도 같은 열 안에서 줄바꿈·세로 스크롤한다. 열을 늘리지 않도록 `min-width: 0`과 현재 overflow 처리를 보존한다.

### 3.2 고정 폭과 좁은 창 처리 권장안

초안의 권장값은 **입력 열 386px, 답변 열 최소 가용 폭 240px, 간격 12px**다. 386px는 현재 넓은 화면의 분리 진입 팝업에서 입력 카드가 차지하는 폭을 대체로 유지하기 위한 시작값이며, 사용자 요구로 확정된 수치는 아니다.

현 소스의 팝업 860px, 테두리 좌우 각 1px, 내부 padding 좌우 각 16px를 가정하면 다음과 같다.

```text
C = 860 - 2 - 32 = 826px
G = 100px
현재 답변 열 = min((826 - 100 - 12) × 0.6, 826 - 100 - 252) = 428.4px
현재 입력 열 = 826 - 12 - 428.4 = 385.6px
권장 입력 고정 폭 = 386px (정수 반올림)
```

이는 CSS 산식에 따른 추정치이며 브라우저 실측 결과가 아니다. 실제 구현에서는 box sizing, 적용 padding과 렌더링 반올림을 확인한다.

고정 입력 폭과 답변 최소 폭을 동시에 만족하려면 팝업의 좌우 배치 임계값은 콘텐츠 폭 **638px = 386 + 12 + 240**가 된다. 그 미만에서는 상하 배치를 사용하고 `split` 선택은 유지한다.

| 실제 콘텐츠 폭 C | 권장 표시 | 입력 폭 | 답변 폭 |
| --- | --- | --- | --- |
| 637px | 상하 | 기존 상하 카드 규칙 | 기존 상하 대화 규칙 |
| 638px | 좌우 | 386px | 240px |
| 826px | 좌우 | 386px | 428px |
| 966px | 좌우 | 386px | 568px |

위 예시에서 외부 창을 860px에서 1000px로 늘리면 입력 폭은 유지되고 답변 영역이 140px 늘어난다. 기존 분리 축소 프리셋 560px는 내부 폭이 부족하므로 상하로 보이며, 외부 프리셋 수치 자체는 바꾸지 않는다.

CSS custom property를 container query 조건 값에 직접 넣는 방식에 의존하지 않는다. 실제 쿼리 임계값과 고정 폭 상수의 관계를 같은 파일 주석·테스트에 명시하고, 폭을 조정할 때 둘을 함께 갱신한다.

### 3.3 CSS 범위와 우선순위

1. 기존 콘텐츠 폭 560px의 좌우 표시와 입력 우선 배분식은 패널에 유지한다.
2. 팝업은 콘텐츠 폭 638px 이상에서만 별도 고정 입력 열 grid를 적용한다.
3. 공통 `.ai-is-split` 규칙이 팝업의 560~637px 구간을 먼저 좌우로 만들지 않도록, grid 활성화 선택자를 패널과 팝업으로 구분한다. 단순히 638px 쿼리를 뒤에 추가하는 것만으로는 부족하다.
4. heading/messages/composer 영역 지정, 독립 스크롤 등 공유 가능한 선언은 유지하되 두 활성화 조건에서 각각 올바르게 적용되도록 정리한다.
5. 팝업의 `--ai-added-width`는 고정 입력 열 배분식에 사용하지 않는다. 패널에서 사용하는 기존 변수와 외부 창 확대용 `--ai-window-growth`는 보존한다. 기존 100px를 답변 열에 중복 가산하지 않는다.
6. 960px·700px viewport 규칙과 638px 콘텐츠 조건을 구분한다. 작은 화면이라도 실제 팝업 콘텐츠가 충분하면 좌우 배치할 수 있다.

### 3.4 상태·데이터 보존

- 권장안은 CSS 중심 변경으로 신규 React 상태, ResizeObserver, 고정 폭 캡처 로직이 필요하지 않다.
- `useAiWindow`의 수동 너비 슬롯·프리셋 초기화·이동·경계 보정은 유지한다. 창 너비 측정값을 새 채팅 key나 조건부 채팅 인스턴스에 연결하지 않는다.
- 답변 목록과 관리 footer는 같은 왼쪽 pane에 남긴다. 질문 말풍선과 답변 말풍선을 분리하거나 결과 모달 크기를 변경하지 않는다.
- 상하 복귀 때 입력 폭 고정 규칙을 해제해 기존 전체 폭·입력 높이·스크롤 규칙으로 돌아간다.
- DB 스키마·마이그레이션·API·Query key·권한·저장 데이터 변경이 필요 없다. 픽셀 폭을 개인 설정이나 localStorage에 저장하지 않는다.

## 6. 검증 방법

### 6.1 이번 문서 작업의 검증

- 요구사항·현재 구조·수정 방향·변경 대상 파일·검증 방법·결정 사항을 포함했는지 확인한다.
- 새 문서 경로가 `docs/history/2026-11-18/작업명.md`인지, 내부 참고 링크와 HISTORY의 상대 링크가 존재하는지 확인한다.
- 기존 `HISTORY.md` 목록을 바이트 단위로 보존하고 날짜와 링크 한 줄만 추가했는지 확인한다.
- 작업 전후 기존 소스 diff와 기존 미추적 파일 내용이 같고 이번 추가물이 문서에 한정되는지 확인한다.
- 앱 실행·빌드·DB 조회·마이그레이션·DB를 생성하는 회귀 테스트는 실행하지 않는다.

다음 기대값은 입력 386px·답변 최소 240px 권장안 기준이다. 8절에서 수치가 바뀌면 경계와 기대값도 함께 수정한다.

폭은 transition과 레이아웃 반영 후 `getBoundingClientRect()`로 측정한다. 입력 카드와 대화 pane의 border-box 폭, 외곽 폭, 실제 콘텐츠 폭, x좌표·높이를 함께 기록한다. 창 위치가 움직이는 경우에도 너비 차이로 배분을 판단한다. 클래스·CSS 변수 값만 비교하는 검증으로 대체하지 않는다.

### 6.3 향후 실행 계획

- TS/TSX를 변경하는 경우 `pnpm typecheck`와 변경 파일 ESLint를 수행한다.
- CSS와 테스트 변경 후 `pnpm build`, `pnpm test:ai-targets-browser`로 실제 브라우저 geometry와 기존 창 동작을 확인한다. 기존 fixture의 합성 계정·임시 DB를 사용하며 운영 DB를 사용하지 않는다.
- 공유 관리 버튼·후보·근거에 영향이 생기면 `pnpm test:shared-answers-browser`를 추가한다. 서버 로직을 바꾸지 않는 한 실제 AI 호출이나 DB 마이그레이션이 필요한 변경은 아니다.
- 이 절의 명령과 테스트 수정은 향후 구현 계획이며 이번 문서 작업에서는 실행하지 않는다.

## 7. 구현 순서 제안

1. 사용자가 수정한 최종 문서에서 용어, 고정 폭과 좁은 창 정책을 확인한다.
2. 팝업/패널의 grid 활성화 범위를 분리하고 팝업 좌우에 고정 입력 열을 적용한다.
3. 기존 helper에 실제 두 열 폭 측정을 추가하고 팝업·패널별 배분 및 임계값 기대값을 분리한다.
4. 실제 조작·geometry·초안 보존·스크롤 회귀를 실행한다.
5. 현행 안내·유지보수 지침과 구현 기록을 결과에 맞게 갱신한다.

## 8. 결정이 필요한 사항

확정된 요청을 다시 승인받기 위한 목록이 아니라, 사용자가 구현 전 문서에서 선택·수정할 정책이다.

| ID | 결정 사항 | 권장안 | 다른 선택의 영향 |
| --- | --- | --- | --- |
| D1 | “채팅 영역 패널”의 의미 | 오른쪽 질문 입력 카드 전체를 고정하고 왼쪽 질문·답변 목록을 확장한다. | 왼쪽 대화 pane을 고정한다는 의미라면 확장 대상이 별도로 필요하다. 현재 DOM에는 답변만 담은 독립 열이 없다. |
| D2 | 고정 입력 폭 | 모든 팝업 좌우 상태에 디자인 상수 386px를 적용한다. 현재 860px 진입 폭과 거의 같다. | 첫 분리 진입의 실제 폭을 캡처해 유지하려면 별도 상태·측정·초기화 정책이 필요하다. 더 작은 상수를 선택하면 초기 입력 폭도 줄어든다. |

| D6 | 패널 모드 적용 여부 | 이번 요청의 창 모드에만 적용한다. | 패널도 통일하려면 기존 입력 열 추가분 정책과 패널 임계값을 함께 개편해야 한다. |

검토·수정 후 구현 요청을 받으면 최종 문서에 따라 변경 파일·수치·검증 범위를 확정한다.
