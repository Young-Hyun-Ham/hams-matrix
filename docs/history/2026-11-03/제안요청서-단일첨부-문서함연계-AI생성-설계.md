# 제안요청서 단일 첨부·문서함 연계·AI 생성 분석 및 설계

- 작성일: 2026-11-03 (한국시간)
- 대상: `hams-matrix` 프로젝트 상세 > 제안요청서 탭
- 문서 상태: 검토용 설계안. 요구사항으로 확정된 내용과 구현을 위한 권장안을 구분한다.
- 작업 범위: 현재 소스 분석 및 설계 문서 작성만 수행했다. 애플리케이션 소스, DB 스키마·데이터, 스토리지, 환경설정은 변경하지 않았다.

## 1. 요구사항

### 1.1 확정된 요청

1. 제안요청서 탭 상단의 **샘플 불러오기 아래**에 원본 제안요청서 파일을 첨부하는 영역을 추가한다.
2. 제안요청서에 등록할 수 있는 첨부 파일은 **한 개**다.
3. 첨부한 동일 파일을 해당 프로젝트의 **문서함에서도 조회**할 수 있어야 한다.
4. 첨부 완료 후 파일 옆에 **AI로 제안 요청서 생성** 버튼을 표시한다.
5. 버튼을 실행하면 첨부 파일을 분석하여 현재 제안요청서의 입력 구조에 맞게 등록한다.
6. 이번 단계에서는 구현하지 않으며, 사용자가 본 문서를 검토·수정한 뒤 구현을 요청한다.

### 1.2 설계상의 해석과 범위

- 한 개 제한은 **프로젝트별 현재 연결된 제안요청서 원본 한 개**로 해석한다. 문서함 전체의 파일 수를 한 개로 제한하지 않는다.
- 등록은 화면에 문구만 채우는 동작이 아니라 기존 `project_rfp_documents`에 **DB 초안으로 저장**하는 것으로 제안한다. 업무상 최종 검토·승인·배포를 뜻하지 않는다.
- 생성 대상은 제안요청서의 7개 장이다. 기존 요구사항·WBS·아키텍처 탭의 산출물을 자동으로 생성하거나 연결하지 않는다.
- 원본 파일과 구조화된 제안요청서는 별개다. 원본 첨부·교체·해제만으로 작성 중이거나 저장된 제안요청서를 변경하지 않는다.
- 지원 형식·용량, 기존 문서의 재생성 방식, 첨부 해제·교체 정책은 요청에 명시되지 않았다. 아래 권장안을 검토 후 확정해야 한다.

### 2.1 핵심 영향

- 파일 선택 UI만 추가해서는 부족하다. 단일 첨부 관계, 문서함 연계, 서버 문서 추출, 구조화 생성, DB 저장 경로가 함께 필요하다.
- 기존 문서 업로드 API 호출 후 별도 요청으로 첨부를 연결하면, 연결 실패 시 문서함에만 파일이 남는 부분 성공이 발생한다. 전용 업로드 경로에서 파일 메타데이터와 연결을 함께 저장하는 편이 명확하다.
- `project_files`를 파일명으로 찾거나 원본 바이트를 RFP JSON에 넣지 않는다. 파일 ID로 연결하고 R2 객체를 재사용한다.
- 문서함은 20MiB까지 보관하지만 기존 추출기는 4MiB까지만 처리한다. **보관 가능과 AI 생성 가능은 같지 않다.** 이번 기능의 제한을 별도로 정의해야 한다.
- 채팅의 생성 요청 등록·중지 API는 채팅방을 전제로 한다. 전용 생성 버튼에서 이를 그대로 호출하거나 가짜 채팅방을 만드는 방식은 피한다.

## 3. 권장 사용자 흐름과 화면

### 3.1 배치

`rfp-page-header` 다음, 현재 `rfp-summary` 앞에 첨부 영역을 추가한다. 샘플 불러오기가 있는 상단 작업 영역 바로 아래에 해당한다.

```text
제안요청서 작성       [전체 미리보기] [조회] [저장] [샘플 불러오기] ...
원본 제안요청서 파일
  미첨부: [파일 첨부]   1개 / 지원 형식·용량 안내
  첨부됨: 원본.pdf · 크기 · 등록자 · 등록일
          [다운로드] [문서함에서 보기] [AI로 제안 요청서 생성] [교체] [첨부 해제]
저장본/필수 항목 현황
기존 목차 및 작성 영역
```

- 데스크톱에서는 파일명 옆에 생성 버튼을 둔다. 모바일에서는 같은 첨부 영역 안에서 자연스럽게 줄바꿈한다.
- 파일 입력에 `multiple`을 지정하지 않으며 드롭에서도 여러 개면 전체를 거부한다. 임의로 첫 파일만 처리하지 않는다.
- 파일이 있어도 지원 불가·권한 없음·업로드/생성 중이면 생성 버튼을 비활성화하고 이유를 안내한다.
- 업로드 중, 생성 중, 중지 요청 중, 실패, 저장 완료 상태를 구분한다. 성공은 DB 저장 완료 후에만 표시한다.
- 새 확인창이 필요하면 프로젝트의 공통 모달 스타일을 사용한다. 상태 안내는 `role="status"`, 오류는 `role="alert"`로 제공한다.

### 3.2 초기 생성·재생성

1. 사용자가 파일 하나를 업로드한다. 업로드와 관계 저장에 모두 성공하면 첨부 행을 표시한다.
2. 문서함 루트 목록에도 같은 파일 ID가 보인다. 새로고침·재접속 후에도 양쪽에서 확인된다.
3. 사용자가 생성 버튼을 누르면 원본·생성 대상·DB 저장 여부를 확인한다.
4. 저장본이 없으면 CREATE, 저장본이 있으면 명시적인 재생성 확인 후 UPDATE한다. 기존 저장본은 리비전으로 보존한다.
5. 미저장 편집본이 있으면 생성을 바로 진행하지 않는다. 먼저 저장하거나, 사용자가 명시적으로 편집본을 폐기하고 기준 저장본으로 돌아가도록 한다. 확인창 취소·폐기 처리 이전에는 편집본을 제거하지 않는다.
6. 서버가 추출·검사·생성·검증·최종 저장을 완료하면 응답의 저장 문서 ID/version을 기준으로 화면을 갱신한다.
7. 실패·취소·충돌 시 원본 첨부와 기존 DB 저장본을 유지한다. 별도 저장을 요구하는 임시 성공 화면으로 처리하지 않는다.

권장안은 **명시적 실행 후 DB 초안 저장**이다. 생성 결과를 먼저 미리보기하고 별도 승인으로 저장하는 방식은 다른 API·임시 결과 보관 설계가 필요하므로 결정 항목으로 남긴다.

### 3.3 단일 첨부 생명주기

| 동작 | 권장 동작 |
| --- | --- |
| 최초 첨부 | 원본을 문서함 루트에 저장하고 현재 원본으로 연결한다. RFP 저장본이 없어도 가능하다. |
| 두 번째 첨부 시도 | 일반 추가는 409로 거부한다. 별도 교체 동작에서만 현재 연결을 바꾼다. |
| 교체 | 새 파일 업로드와 연결 교체에 성공할 때만 활성 원본을 바꾼다. 실패하면 기존 연결을 유지한다. 이전 파일은 문서함 일반 파일로 남긴다. |
| 첨부 해제 | 연결만 해제하고 원본 파일·기존 생성 문서는 보존한다. 실제 파일 삭제와 다른 동작임을 안내한다. |
| 문서함에서 이름 변경 | 동일 파일 ID의 최신 이름을 표시한다. 활성 원본은 지원 형식을 바꾸는 확장자 변경을 거부하도록 제안한다. |
| 문서함에서 파일 삭제 | 활성 원본이면 파일/R2 삭제 전에 409로 거부하고 RFP 탭에서 먼저 첨부를 해제하도록 안내한다. |
| 문서함에서 DOCX 편집 | 활성 원본이면 문서함 UPDATE와 RFP UPDATE 권한을 모두 검사한다. 생성 중 원본이 바뀌면 완료 저장을 거부한다. |
| RFP 저장 문서 삭제 | 원본 연결·파일은 유지한다. 삭제 이후 같은 원본으로 다시 생성할 수 있다. |

교체 후 문서함에 이전 파일이 남더라도 **활성 원본은 한 개**다. 과거 원본까지 자동 삭제해야 한다면 별도 정책으로 변경해야 한다.

## 4. 데이터 설계안

아래 테이블·필드·API 이름은 구현 제안이며 현재 존재하지 않는다. 마이그레이션은 이번 단계에서 작성하거나 실행하지 않는다.

### 4.1 파일 원본 관계: `project_rfp_sources` 신설

| 필드 | 목적 |
| --- | --- |
| `project_id`, `workspace_id` | 프로젝트별 관계 하나 및 워크스페이스 경계. 프로젝트 범위 외래키 적용. |
| `file_id` (nullable) | `project_files`의 현재 원본. 미첨부/해제 상태는 null. |
| `version` | 연결 변경·교체·해제 시 단조 증가하는 버전. 연결을 해제해도 행을 유지하여 버전 초기화에 따른 충돌 누락을 방지한다. |
| `created_by`, `updated_by`, `created_at`, `updated_at` | 연결 생성·변경 주체와 시각. |

- 프로젝트별 단일 행을 PK/UNIQUE로 보장하고 서버 트랜잭션에서도 확인한다. UI 제한만으로 보장하지 않는다.
- `file_id`는 반드시 같은 프로젝트·워크스페이스 파일을 가리켜야 한다. 이를 위한 `project_files(id, project_id, workspace_id)` 복합 UNIQUE 인덱스와 복합 FK를 검토한다. 현재 파일 테이블에 이 복합 UNIQUE는 없다.
- 연결된 파일 삭제는 RESTRICT로 방어한다. FK 실패에 맡겨 R2를 먼저 삭제하지 않도록 삭제 API에서 관계를 먼저 검사한다.
- 파일 미첨부인 기존 프로젝트는 데이터 백필 없이 빈 상태로 취급한다. RFP JSON 스키마 버전은 변경하지 않는 안이다.

### 4.2 생성 작업: `project_rfp_generation_requests` 신설

전용 버튼의 중복 실행·중지·결과 복구를 위해 프로젝트 범위의 생성 작업을 관리한다.

- 기본 필드: `request_id`, `workspace_id`, `project_id`, `user_id`, 상태, 생성/종료 시각, lease 만료 시각.
- 입력 기준: 원본 `file_id`, 관계 `source_version`, 읽은 `object_key`의 내부 스냅샷, 원본 내용 해시, 파일명, RFP 기준 ID/version 또는 신규 생성 상태.
- 결과: 실제 저장 문서 ID/version, 오류 코드, 모델·정책 버전, 추출 문자/페이지 수 등 최소 메타데이터.
- `running → finalizing → completed`, `running → stop_requested → cancelled`, 실패 시 `failed` 전이를 정의한다. `finalizing` 진입과 저장은 짧은 DB 트랜잭션에서 직렬화한다.
- 프로젝트별 실행 중 작업 한 개를 DB 제약으로 보장한다. 같은 사용자의 더블클릭뿐 아니라 다른 사용자의 동시 생성도 막는다.
- 활성 lease가 만료된 작업은 실패 처리 후 새 작업을 허용한다. 만료된 작업의 뒤늦은 결과는 최종 상태/lease 재검사에서 저장을 거부한다.
- `request_id`를 동일하게 재전송하면 소유권·요청 입력 일치를 확인한 뒤 기존 상태/결과를 반환한다. 다른 입력에 같은 ID를 재사용하면 409를 반환한다.
- 기존 `ai_generation_requests`의 채팅 처리 의미는 유지한다. 전용 작업의 checkpoint/중지 상태를 `generateAi`에 콜백으로 연결하고 토큰 사용량은 동일 `request_id`로 연결한다.
- 상세 오류나 작업 조회는 작업 실행자만 허용한다. 다른 프로젝트 구성원에게는 필요 시 실행 중 여부만 노출한다. 토큰 사용량·개인 오류 내역을 프로젝트 공용 정보로 반환하지 않는다.

### 4.3 생성 출처 보존

- 원본 파일 관계와 별도로 성공한 생성 작업에 `fileId`, 파일명 스냅샷, 내용 해시, 원본 관계 버전, 생성 모델/시각, 결과 RFP ID/version을 남긴다.
- 생성 작업의 파일 참조는 삭제 후에도 남는 출처 스냅샷으로 취급한다. 활성 관계 FK처럼 과거 파일의 영구 삭제를 막지 않는다.
- `project_rfp_revisions`는 기존 불변 규칙을 유지한다. 저장·리비전·생성 성공 상태를 같은 트랜잭션으로 기록한다.
- 감사 로그에는 파일명·ID·크기·해시·문서 버전·요청 ID 등 메타데이터만 기록하고 원본 바이트·추출 본문을 복제하지 않는다.

## 5. 서버 API 및 저장 흐름

### 5.1 제안 API

| API | 요청·역할 |
| --- | --- |
| `GET /api/projects/{projectId}/rfp/source` | 현재 원본 메타데이터, 관계 버전, 실행 가능 권한/사유 반환. R2 키·본문·서버 경로는 반환하지 않는다. |
| `POST /api/projects/{projectId}/rfp/source?name=...` | 원본 바이너리 1개를 등록. 파일명은 기존 방식처럼 URLSearchParams로 인코딩한다. 최초 첨부만 허용한다. |
| `PUT /api/projects/{projectId}/rfp/source?name=...&expectedSourceVersion=...` | 새 바이너리로 원본 교체. 기존 관계 버전 일치 필요. |
| `DELETE /api/projects/{projectId}/rfp/source` | `expectedSourceVersion`으로 연결만 해제. 원본 파일은 유지한다. |
| `POST /api/projects/{projectId}/rfp/generate` | `requestId`, `sourceFileId`, `expectedSourceVersion`, 허용 모델, 대상 RFP ID/기준 version 또는 신규 생성임을 명시. 파일 원문은 브라우저에서 다시 전송하지 않는다. |
| `GET /api/projects/{projectId}/rfp/generate/{requestId}` | 실행자에게 작업 상태와 완료 결과의 저장 문서 참조 반환. 응답 유실 후 중복 생성 없이 상태를 확인한다. |
| `POST /api/projects/{projectId}/rfp/generate/{requestId}/stop` | 실행자의 중지 요청. 이미 완료되었다면 실제 저장 결과를 반환하고 취소되었다고 표시하지 않는다. |

권장 초기 구현은 생성 POST를 기존 채팅과 같은 제한 시간 내 동기 응답으로 처리하되, 중지·상태 복구를 위해 작업 상태를 DB에 남기는 방식이다. 별도 백그라운드 워커나 실시간 진행률 추정은 초기 범위에 포함하지 않는다.

- 파일·목록·작업 응답은 `private, no-store`를 적용한다. 변경 API는 인증 및 `checkOrigin`을 적용한다.
- 오류 구분: 잘못된 입력/지원 불가/손상 400, 미인증 401, 권한·정책 403, 대상 없음 404, 버전·중복·사용 중 충돌 409, 용량 413, 사용량/빈도 한도 429, 공급자·스토리지 장애 및 시간 초과는 원인에 맞는 5xx.

### 5.2 파일 업로드·교체 원자성

1. 인증·RFP 원본 변경 권한·문서함 CREATE 권한·원본 관계 버전을 사전 확인한다.
2. 파일명·허용 확장자·실제 형식·길이와 추출 가능 여부를 서버에서 검증한다. 기존 업로드 읽기 함수는 20MiB 고정이므로 이번 제한을 적용할 수 있는 공통 인자로 확장하거나 별도 상한 검증을 둔다.
3. 새 R2 키로 업로드한다. 교체할 기존 객체를 덮어쓰지 않는다.
4. 짧은 DB 쓰기 트랜잭션에서 권한·원본 관계 버전·생성 진행 상태를 다시 확인한다.
5. `project_files` 생성, 원본 관계 생성/교체, 감사 기록을 함께 commit한다.
6. DB 실패 시 새 R2 객체만 정리하고 기존 연결/파일은 보존한다. 정리 실패는 재처리할 수 있도록 객체 식별 정보가 남는 기록·정리 절차를 둔다.

R2와 DB는 하나의 트랜잭션이 아니므로 보상 정리가 필요하다. 강제 종료로 남는 고아 객체까지 고려한 점검 방법을 구현 시 확정한다. 새 전용 API와 기존 문서함 API가 저장 로직을 중복하지 않도록 공통 서비스 추출을 권장한다.

### 5.3 파일 기반 생성 절차

1. 프로젝트 접근, RFP CREATE/UPDATE, 문서함 READ, AI 활성 상태, 허용 변경 작업, 모델, 사용량·빈도 제한을 확인한다.
2. 원본 연결·파일·RFP 기준 버전을 서버에서 조회하고 요청 기준과 비교한다. 새 문서 생성 요청은 실행 시점에 활성 RFP가 없는지도 확인한다.
3. 생성 작업을 등록하고 중복 요청 및 프로젝트별 동시 실행을 차단한다.
4. 서버가 현재 R2 원본을 읽고 해시와 객체 키를 기록한다. 사용자에게 임의 URL/스토리지 키/추출 본문을 받지 않는다.
5. 제한된 파서로 텍스트를 추출한다. 명령 실행, 문서 속 URL 접근, 외부 개체 로딩을 허용하지 않는다.
6. 실행 요청은 `input`, 원본 추출 내용은 **신뢰하지 않는 `context`**로 가드레일 검사한다. 글로벌 규칙, 정책 버전, 분류기 토큰 집계를 기존 공통 경로로 적용한다.
7. 전용 프롬프트와 JSON Schema로 RFP 구조를 생성한다. 범용 도구·삭제 기능은 제공하지 않는다. 출처에 없는 예산·기한·기관·평가 배점은 임의로 만들지 않고 빈 값/검토 항목으로 남긴다.
8. 구조화 결과를 파싱하고 신뢰 필드인 `projectId`, `schemaVersion`, 문서 ID/version은 서버 기준으로 고정한다. 목록 ID를 서버에서 정규화하고 `validateRfp`로 스키마와 크기를 다시 검사한다.
9. 결과 및 실제 저장 데이터에 출력 검사를 적용한다. `allowedActions`의 CREATE/UPDATE와 `maxChanges`를 서버에서도 검사하여 도구 없는 생성 경로가 정책을 우회하지 않게 한다.
10. 최종 짧은 DB 트랜잭션에서 중지/lease, 현재 권한·AI 활성 상태, 관계 version/file ID, 파일 `object_key`·크기·이름, RFP 기준 ID/version을 다시 확인한다.
11. `mutateRfp(..., tx)`로 문서·리비전·감사 기록을 저장하고, 작업 성공 결과와 문서 참조를 같은 트랜잭션으로 확정한다.
12. 응답의 저장 문서를 클라이언트 상태에 반영하고 AI 변경 알림을 전달한다. 기존 dirty 보호 로직을 무시하는 무조건 reload를 사용하지 않는다.

생성 대기 중 DB 쓰기 트랜잭션을 유지하지 않는다. 원본을 읽는 중 삭제·편집되어 파일을 못 읽으면 실패로 종료하며 자동으로 다른 파일을 대신 사용하지 않는다.

### 5.4 기존 AI 기능과의 관계

- 파일 기반 생성은 `lib/ai/rfp-generation.ts` 등의 전용 서비스로 분리하고 `generateAi`, 가드레일, 토큰 추적, `validateRfp`/`mutateRfp`를 재사용한다.
- 기존 `createRfpAgent`의 UPDATE는 patch만 허용하므로 전체 재생성을 위해 그 제한을 전역 완화하지 않는다. 명시적으로 확인한 전용 API에서 전체 draft를 검증하여 `mutateRfp`에 전달한다.
- 일반 AI 채팅에서 원본을 자동으로 읽거나, 사용자가 버튼을 누르지 않았는데 첨부 즉시 생성하는 기능은 추가하지 않는다.
- 요금 집계에는 `generation`, 가드레일 분류에는 `guardrail` 목적을 유지한다. 논리 `convId`와 고정 작업 제목을 사용하되 채팅 저장 이력이 생겼다고 표시하지 않는다.
- Free 등 `historyEnabled=false`인 경우에도 RFP 저장·리비전·사용량 기록은 채팅 이력과 구분한다. 채팅 이미지용 `attachmentLimit`을 이 문서 첨부의 허용 개수로 그대로 쓰지 않는다. 요금제 적용 여부는 별도 결정이 필요하다.

## 6. 문서 추출·생성 품질과 제한

### 6.1 초기 지원 권장안

| 항목 | 권장 초기값·처리 |
| --- | --- |
| 파일 개수 | 활성 원본 1개. 서버 관계 제약으로 보장. |
| 형식 | `.pdf`, `.docx`, UTF-8 `.txt`, `.md`. 현재 파서가 지원하는 다른 텍스트 형식은 필요 시 확장. |
| 파일 크기 | 4MiB 이하. 문서함의 기존 일반 업로드 상한 20MiB는 유지. |
| PDF 페이지 | 최대 50페이지. |
| 추출 길이 | 최대 100,000자. 길이를 조용히 잘라 일부만으로 성공 처리하지 않는다. |
| 미지원 | HWP/HWPX, 구형 DOC, 이미지 파일, OCR이 필요한 스캔 PDF, 암호화·손상 문서. 변환 방법을 안내하고 저장본은 보존한다. |
| DOCX | 기존 ZIP/XML 내부 개수·압축 해제 크기·DTD 방어를 유지. 문서 내 삽입 이미지는 분석하지 않는다. |

- 최초 첨부 시 추출 가능 여부를 확인하고 생성 시 현재 파일을 다시 검증한다. 문서함 편집으로 내용이 바뀔 수 있으므로 최초 검사 결과를 영구 신뢰하지 않는다.
- `extractGuardrailFiles`는 관리자 테스트의 Base64 입력/3개 제한/파일명 160자 제약까지 묶여 있다. 바이트 기반 추출 함수를 공통 모듈로 분리하고 기존 테스트 래퍼를 유지하는 방향을 권장한다. 파일명은 문서함의 최대 255자와 충돌하지 않도록 공통 계약을 정한다.
- 위 제한은 기술적 초기 권장안이다. 실무 RFP에 HWP/HWPX·50페이지 초과가 많다면 현 범위로는 충족되지 않으므로 별도 파서/OCR/분할 처리 여부를 결정해야 한다.

### 6.2 AI 출력 한계

- DB 스키마상 목록은 최대 200개, 일반 문자열은 최대 10,000자, 전체 JSON 길이는 최대 300,000자다. 화면상 필수값 미충족과 구조 오류를 구분한다.
- 기존 `generateAi`의 6,000 출력 토큰으로 긴 RFP를 모두 복원할 수 있다고 가정하지 않는다. 초기에는 완성된 응답만 허용하고 잘림·누락·목록 초과 시 DB를 저장하지 않는다.
- 추출 길이·모델 입력량·출력 한도·총 처리 기한은 별개다. 모델별 한도와 토큰 예약 결과를 확인하고 초과 시 이유를 안내한다.
- 1차 생성은 추출·매핑 가능한 범위에서 수행한다. 대형 원본 지원이 필수라면 장별 분할 생성, 출처별 누락 검증, 중간 결과 보관, 전체 완료 후 원자적 저장을 추가 설계해야 한다.
- 기존 한도와 타임아웃을 모든 AI 화면에 일괄 확대하지 않는다. 필요하면 RFP 서비스 전용 옵션과 별도 검증을 둔다.

## 7. 권한·경합·오류 처리

### 7.1 작업별 권한 권장안

| 작업 | 서버 확인 |
| --- | --- |
| 첨부 조회·다운로드 | 프로젝트 접근 + RFP READ + documents READ. |
| 최초 첨부 | RFP CREATE + documents CREATE. 구조화 RFP 유무와 별개로 원본 관계의 최초 생성이다. |
| 원본 교체 | RFP UPDATE + documents CREATE. 이전 파일은 삭제하지 않는다. |
| 첨부 해제 | RFP DELETE. 파일 자체를 지우는 documents DELETE는 불필요하다. |
| 원본 이름 변경·편집 | documents UPDATE와, 활성 원본인 경우 RFP UPDATE를 모두 확인. 편집 진입과 저장 callback에서도 재확인. |
| 문서함 실제 삭제 | documents DELETE + 활성 연결 없음. 활성 원본이면 권한과 별개로 먼저 해제 필요. |
| 신규 AI 등록 | RFP CREATE + documents READ + AI/사용량/정책 허용. |
| 기존 문서 재생성 | RFP UPDATE + documents READ + AI/사용량/정책 허용 + 기존 문서 교체 확인. |

현재 RFP 쓰기는 owner에 고정되어 있어 다른 역할에 버튼을 제공하지 않는 것이 기본이다. UI 숨김 외에 서버에서 전 단계와 최종 저장 시 재검사한다. 원본 변경 권한을 RFP 저장본 권한에 종속시키는 다른 정책을 원하면 이 표부터 수정해야 한다.

### 7.2 주요 실패·경합 사례

| 상황 | 기대 결과 |
| --- | --- |
| 동시 최초 첨부·동시 교체 | 한 요청만 commit. 다른 요청은 409, 새 객체는 보상 정리. |
| 생성 중 관계 교체/해제 | UI와 변경 API는 실행 중 변경을 거부. 경합으로 변경이 먼저 완료됐다면 생성 최종 버전 검사에서 409. |
| 문서함 DOCX 저장·이름 변경과 경합 | 현재 `object_key`/메타데이터와 시작 스냅샷이 다르면 생성 저장 거부. `editor_version`만 비교하지 않는다. |
| 다른 탭/사용자가 RFP 수정·삭제·재생성 | 기준 ID/version 불일치로 409. 최신 문서를 자동 덮어쓰지 않는다. 신규 생성끼리의 경합도 활성 문서 제약으로 방어. |
| 생성 중 권한 철회·프로젝트 접근 상실 | 최종 저장 거부. 파일 원문/작업 상세 반환도 차단. |
| 입력/출력 가드레일 차단·모델 오류·파싱 실패 | RFP 변경 없음. 원본 유지. 발생한 AI 사용량은 기존 원칙대로 기록. |
| 스토리지 읽기 실패·형식 위장·지원 제한 초과 | 생성 호출 전 실패를 우선 검출. 기존 저장본 보존. |
| 중지와 저장 완료가 경합 | 서버 트랜잭션에서 이긴 상태만 반환. 완료된 문서를 취소 성공이라고 표시하지 않는다. |
| 브라우저 종료·요청 응답 유실 | 동일 요청 ID로 상태 확인. 완료됐다면 저장 문서 참조를 복구하고 새 생성으로 중복 과금하지 않는다. |
| 파일 삭제 중 관계 생성 시도 | 삭제 경로와 연결 경로를 DB 쓰기 트랜잭션/FK로 직렬화. 삭제 예정 객체에 새 연결이 commit되지 않도록 한다. |

파일 실제 삭제는 기존의 R2 우선 삭제 흐름 때문에 DB 실패 시 메타데이터만 남을 가능성도 검토해야 한다. 이번 관계 추가로 생기는 FK 실패가 파일 본문 유실로 이어지지 않도록 사전 검사와 실패/재시도 테스트가 필수다.

## 9. 검증 방법과 완료 기준

### 9.1 이번 문서 작업 검증

- 참조 경로와 현재 동작을 소스에서 확인한다.
- `HISTORY.md`의 기존 목록을 보존하고 새 문서 상대 경로·한국시간 작성일을 추가한다.
- 문서 링크 존재 및 `git diff --check`를 확인한다.
- 소스·DB를 변경하거나 마이그레이션·AI 유료 호출·스토리지 업로드·통합 테스트를 실행하지 않는다. 아래는 **향후 구현 시 검증 계획**이다.

### 9.2 향후 구현 기능·통합 검증

1. 첨부 하나를 등록하면 RFP와 문서함이 같은 파일 ID를 조회하고, 다운로드 원본 해시가 일치한다. 새로고침·다른 세션에서도 유지된다.
2. 복수 선택·복수 드롭·직접 API 호출·동시 업로드에서도 활성 원본이 두 개가 되지 않는다.
3. 지원 PDF/DOCX/TXT/MD로 7개 장과 목록을 생성하여 실제 RFP GET 응답·리비전·화면 미리보기에 일치하는 저장 결과가 보인다.
4. 원본에 없는 기관·예산·일정이 임의 확정되지 않는다. 필수값이 부족하면 기존 진행률/검토 안내에 반영된다.
5. 파일 교체/해제/원본 파일 삭제/RFP 삭제를 각각 검증한다. 교체 실패 시 이전 원본 유지, 해제 시 문서함 파일 보존, 활성 원본 삭제 차단을 확인한다.
6. 생성 전 dirty 편집본 처리와 취소를 검증한다. 실패 후 사용자 편집본이나 기존 저장본이 사라지지 않는다.
7. owner/admin/member/viewer, 프로젝트 외부 사용자, 다른 워크스페이스, 권한 회수, 문서함 권한만 있는 사용자의 요청을 검증한다. 원본 편집 callback 우회도 차단한다.
8. RFP 수정/삭제와 생성, 다른 사용자 생성, 원본 교체/해제, ONLYOFFICE 일반 저장·강제 저장과 생성의 경합을 검증한다. 충돌 시 문서/리비전/성공 상태가 부분 저장되지 않는다.
9. 동일 요청 ID 재전송·중복 클릭·응답 유실·중지/최종 저장 경합·lease 만료 후 재시도를 검증한다. 완료 요청의 추가 생성 호출과 중복 저장이 없어야 한다.
10. R2 업로드 실패·읽기 실패·DB 실패·객체 정리 실패·파일 삭제 도중 FK/DB 실패를 주입해 원본 유실·깨진 관계·추적 불가능한 고아 객체를 점검한다.

### 9.3 추출·AI·보안 회귀

- 빈 파일, 정확한 용량 경계/초과, 위조 확장자, 긴 한글 파일명, 경로 문자, 비 UTF-8, PDF 50/51페이지, 100,000자 경계/초과, 암호화·손상·스캔 PDF를 검증한다.
- DOCX ZIP 폭탄·내부 파일 과다·DTD·손상 XML·이미지만 있는 문서를 실패 처리한다. 기존 관리자 테스트의 파일 개수·크기 제한과 지원 형식 회귀를 확인한다.
- 원본 내 지시 탈취·비밀 유출 유도, AI 비활성·CREATE/UPDATE 비허용·분류기 장애·출력 차단 시 저장되지 않는지 확인한다.
- 모델의 잘못된 JSON, 잘린 응답, 잘못된 프로젝트/스키마, 목록 초과·중복 ID·잘못된 분류·날짜·배점을 검증한다. 파서나 검증기를 우회해 저장하지 않는다.
- 토큰 예약·확인 사용량·미확인 사용량·가드레일 사용량·취소/실패 정산과 사용자 통계 표시를 검증한다. 채팅 이력 설정 때문에 사용량/문서 리비전이 누락되면 안 된다.
- 6,000토큰으로 부족한 실제 크기의 합성 원본을 사용해 실패 안내와 원자성을 확인한다. 외부 공급자는 모의 응답으로 대체하고 운영 DB·실제 R2를 사용하지 않는다.

### 9.4 UI 및 기존 기능 회귀

- 샘플 불러오기 아래 배치, 파일 옆 생성 버튼, 모바일 줄바꿈, 밝은/어두운 테마, 키보드 접근, 처리 중 중복 동작 방지를 확인한다.
- 첨부 후 문서함 탭 전환 시 새 파일이 즉시 조회되고 원본 표시에 따라 삭제 안내가 제공되는지 확인한다.
- 기존 수동 저장·샘플 불러오기·전체 미리보기·RFP 삭제·채팅 AI 부분 수정·일반 문서함 업로드/삭제·ONLYOFFICE 편집을 회귀 확인한다.
- 구현 후 `pnpm typecheck`, 변경 파일 ESLint, `pnpm test:project-permissions-rfp`, `pnpm test:project-permissions-rfp-browser`, 문서함·가드레일 회귀, `pnpm build`, `git diff --check`를 수행한다. 문서함 독립 스크립트는 현재 `node scripts/test-documents.mjs`로 실행한다.

완료 기준은 **단일 원본의 영속 등록·동일 파일의 문서함 조회·원본 기반 구조화 RFP의 실제 DB 저장·권한/충돌/실패 시 데이터 보존**을 모두 충족하는 것이다.

| 생성 후 저장 시점 | 버튼 실행 확인 후 DB 초안으로 직접 저장 | 먼저 검토 후 저장하려면 임시 생성 결과와 2단계 확정 API가 필요하다. |
| 기존 RFP 재생성 | 확인 후 전체 교체, 기존 리비전 보존 | 신규 생성만 허용하거나 특정 장만 병합할 수 있다. 목록 ID·누락/중복·사용자 수정 보존 정책이 달라진다. |
| 미저장 편집본 | 저장 또는 명시적 폐기 후 실행 | 생성 결과와 자동 병합은 초기 범위에서 제외하는 것을 권장한다. |
| 원본 교체·해제 | 현재 연결만 변경, 과거 파일은 문서함에 보존 | 실제 파일까지 자동 삭제하려면 문서함 DELETE 권한과 스토리지 정리/실패 복구가 추가된다. |
| 원본 편집 | 문서함·RFP UPDATE 권한을 모두 요구하고 본문 변경 검출 | 업로드 당시 원본을 불변으로 보존하려면 활성 원본의 편집 자체를 차단하는 대안이 있다. |
| 저장 위치·기존 파일 선택 | 새 업로드를 문서함 루트에 저장 | 전용 폴더, 문서함 기존 파일을 원본으로 선택하는 기능은 별도 UX·권한·폴더 삭제 정책이 필요하다. |
| 원본 변경 권한 | 7.1의 관계 CRUD 기준 사용 | RFP 저장본 존재 여부에 따라 CREATE/UPDATE를 바꿀지, 별도 첨부 권한을 둘지 검토할 수 있다. 현재 역할별 상한은 유지한다. |
| 모델 선택 | 기존 허용 모델 목록에서 사용자 선택, 선택값 검증 | 관리자 고정 기본 모델이면 비용·재현성·변경 안내 정책을 추가한다. 임의 목록 첫 항목을 품질 기준으로 간주하지 않는다. |
| 요금제 | 단일 원본 규칙과 기존 토큰 할당량을 적용 | Free 허용 여부 및 별도 파일 생성 기능 제한이 필요하면 문서 첨부 전용 정책을 정한다. 이미지 첨부 수 제한을 전용하지 않는다. |
| 생성 결과의 조회 위치 | RFP 화면·기존 리비전·사용량에 기록 | AI 채팅 히스토리에도 표시해야 한다면 채팅방/사용자별 공개 범위·출처·이력 비활성 요금제 처리를 추가 설계한다. |
| 대형 문서·완성도 | 범위 초과/불완전 결과는 실패 처리, 조용한 축약 금지 | 모든 요구사항의 무누락 복원이 필수라면 장별 분할·근거 위치·목록 매핑 검증을 필수 범위로 올려야 한다. |

## 11. 향후 구현 순서 제안

1. 10절의 형식·범위·저장/재생성·보존·권한·요금제 결정을 확정한다.
2. 단일 원본/생성 작업 DB 제약과 업로드·교체·해제·문서함 삭제 보호를 구현한다.
3. 공통 문서 추출 분리와 관리자 테스트 회귀를 완료한다.
4. 구조화 생성·정책·토큰·중지·버전 재검사·원자적 저장을 구현한다.
5. 첨부 영역·생성 확인·dirty 처리·문서함 표시·작업 복구 UI를 연결한다.
6. 격리된 DB/스토리지/모의 AI로 기능·경합·실패·브라우저 검증 후 실제 지원 범위를 안내 문서에 반영한다.

본 문서는 구현 승인을 대신하지 않는다. 검토·수정된 설계에 대한 별도 구현 요청 이후에만 소스 및 DB 작업을 진행한다.
