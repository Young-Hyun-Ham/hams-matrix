# 회원·권한·요금제 개편 분석 및 설계

- 작성일: 2026-10-28 (Asia/Seoul)
- 상태: 구현 전 분석·설계. 이 문서 작성 단계에서는 소스, 마이그레이션, DB 데이터를 변경하지 않는다.
- 대상: 회원가입, 로그인, 게스트 체험, 계정 역할, 프로젝트 권한, 회원별 플랜, 관리자 설정, 사용량 제한, 이력 저장.
- 표기: 아래의 **확정 요구사항**은 사용자 요청이다. **설계안/권장안**은 구현 방향이며, 마지막의 **미확정 정책**과 구분한다.

## 1. 확정 요구사항

| 번호 | 요구사항 | 반영 방향 |
| --- | --- | --- |
| 1 | 가입 역할 선택 제거, 신규 회원은 모두 user | 이메일·소셜 가입 모두 서버에서 계정 역할을 user로 지정 |
| 2 | 계정 역할 master/admin/user/guest, master 1개 | 계정 역할 전용 필드와 DB 제약, 최초 master 생성 절차 |
| 3 | guest는 메뉴 이동과 화면 조회만 가능 | 비로그인 데모, 기능 실행 및 실제 회원 데이터 접근 차단 |
| 4 | Free/Plus/Pro/Business와 관리자 가격·한도 설정 | 플랜 카탈로그·회원 구독·사용량 정책 분리 |
| 5 | 모든 회원의 프로젝트 생성 수 제한 | 회원별 서버 한도 검사, 동시 생성 방어 |
| 6 | 프로젝트 권한 owner/admin/member/viewer | 계정 역할과 별개인 프로젝트 권한 체계 |
| 7 | 생성자가 프로젝트 owner | 생성과 소유자·멤버 등록을 하나의 트랜잭션으로 처리 |
| 8 | 팀공유는 로그인 사용자의 프로젝트 권한 적용 | 선택 프로젝트별 권한 재조회, 화면과 API 판정 통일 |
| 9 | 로그인 우측 상단을 게스트로 시작하기로 변경 | 로그인 없이 데모 화면 진입 |
| 10 | 로그인 버튼 아래 회원등록 버튼 추가 | 별도 /signup 화면으로 이동 |

요금제 명칭의 `Buiness`는 표시명 `Business`, 내부 코드 `business`로 통일한다. Plus에 추천 배지를 표시한다.

## 2. 현재 구현 분석

### 2.1 가입·로그인과 역할

- `components/auth-form.tsx`: 가입 역할 owner/user 선택을 요구하고 `RegistrationChoiceDialog`에서 플랜 또는 팀 가입을 선택한다. 로그인 우측 상단은 현재 `/signup`으로 가는 “무료로 시작하기”다.
- `components/registration/registration-choice-dialog.tsx`, `lib/registration.ts`: owner는 Team/Business, user는 Free와 Guest/팀 신청을 선택한다. 현재의 Guest는 비로그인 체험과 다르다.
- `app/api/auth/[action]/route.ts`, `lib/auth.ts`: 가입 역할에 따라 계정·워크스페이스·소속 역할을 생성한다. user 가입자는 워크스페이스 viewer가 되어 프로젝트 생성 권한과 충돌한다.
- `lib/oauth.ts`, `app/api/onboarding/route.ts`, `app/(auth)/onboarding/page.tsx`: 소셜 신규 가입과 후속 가입 유형 선택도 함께 수정해야 한다. 이메일 가입 화면만 바꾸면 역할 선택이 남는다.
- `lib/types.ts`: `User.accountRole`은 owner/user, `User.role`은 워크스페이스 소속 역할이다. 둘을 계정 역할로 오해하기 쉽다.
- `lib/auth.ts`의 사용자 조회와 세션은 워크스페이스 및 소속 데이터에 의존한다. users에 master 한 행만 넣으면 현재 로그인 조회에서 누락된다.
- `db/migrations/004_registration_teams.sql`: `users.account_role` 기본값이 owner이고 CHECK도 owner/user만 허용한다. UI 수정만으로 master/admin/guest를 저장할 수 없다.

### 2.2 프로젝트·팀공유 권한

- `app/api/projects/route.ts`: 생성자 및 프로젝트 구성원 등록과 owner 지정 흐름은 있으나 회원 플랜별 생성 수 제한은 없다. 승인된 팀 사용자를 새 프로젝트에 자동 포함시키는 로직이 있다.
- `lib/team-permissions.ts`: `projectRoleSql`이 프로젝트 role이 없을 때 워크스페이스 role로 보완한다. 프로젝트별 명시 권한으로 전환할 때 이 상속 규칙을 제거하거나 이관해야 한다.
- `lib/artifacts.ts`: `projectAccess`가 소속 확인과 쓰기 권한 판정의 핵심이다. `projectData.canWrite`도 프로젝트 권한을 사용한다.
- `components/pages/team/team-page.tsx`: 프로젝트별 쓰기 판정이 있으나 프로젝트가 없으면 `user.role`로 돌아가는 부분이 있다.
- `app/api/team/posts/route.ts`: 공유 글 생성은 현재 `member`만 허용한다. 화면은 owner/admin/member를 쓰기 가능으로 보므로 API와 불일치한다.
- `app/api/team/members/route.ts`, `team-membership.tsx`: 프로젝트 owner의 권한 변경·소유권 이전, owner/admin의 구성원 추가와 팀 전체 관리가 섞여 있다. 초대 시 대상 회원의 활성 워크스페이스와 세션까지 변경하는 동작도 재검토해야 한다.
- `019_single_team_owner.sql`은 워크스페이스 owner 중복을 막는다. 서비스 전체 master 1개 또는 프로젝트 owner 규칙을 보장하는 제약과는 별개다.

### 2.3 플랜·AI·이력

- 플랜이 현재 워크스페이스의 `plan`, `subscription_plan`에 나뉘어 있다. 기존 `free/pro/business`와 `free/team/business`가 혼재하고 `auth.ts`에는 team → pro 변환이 있다.
- 회원별 구독과 관리자가 수정할 월간·연간 가격/제공량을 위한 전용 카탈로그는 현재 가입 모델에 없다.
- `lib/ai/token-usage.ts`: 호출 시작·실제 토큰·응답 중복·최종 사용량을 추적한다. 이 측정 기록과 별도로 플랜 한도 예약·차감이 필요하다.
- `lib/ai-image-types.ts`, `lib/ai/chat-images.ts`: 첨부 이미지가 공통 상수 3개로 제한된다. Free 1개, Pro/Business 5개를 지원하려면 클라이언트와 서버 검증을 함께 바꿔야 한다.
- `lib/ai/architecture-images.ts`, `lib/ai/wbs-images.ts`: 개별 생성 잠금과 재사용 흐름이 있다. 회원별 일일 합산 한도는 별도로 적용해야 한다.
- `lib/artifacts.ts`: 산출물 리비전 생성·조회가 있고 AI 채팅은 `ai_prompt_chats`, `ai_conversations`, 첨부는 `ai_chat_images`에 저장된다. Free의 이력 미생성 정책은 각 저장 경로에 반영해야 한다.
- `app_settings`에는 `DB_LOGGING_ENABLED`가 있으며 감사 로그 정책은 플랜의 사용자용 이력 정책과 구분해야 한다.

### 2.4 게스트·관리자 진입

- `app/page.tsx`는 비로그인 사용자를 로그인으로 보낸다. `app/(workspace)/layout.tsx`도 비로그인 진입을 차단하므로 버튼 문구만 바꾸어서는 게스트 진입이 안 된다.
- `components/workspace-shell.tsx`는 워크스페이스 역할과 플랜을 여러 메뉴·편집·관리자 표시 조건에 사용한다.
- 기존 `lib/ai/guardrail-policy.ts`의 관리자는 워크스페이스 owner/admin이다. 이를 전역 플랜 관리 권한과 동일하게 사용하면 안 된다.

## 3. 역할과 권한 설계안

### 3.1 계정 역할

`AccountRole = master | admin | user | guest`로 정의한다. 기존 컬럼 `users.account_role`을 계정 역할의 기준으로 유지하고 CHECK와 기본값을 변경하는 안을 권장한다. API/DTO 명칭은 `accountRole`로 일관되게 사용한다.

| 계정 역할 | 의미 | 전역 관리 |
| --- | --- | --- |
| master | 서비스 최초 관리자, 정확히 1개 | 전체 운영·플랜·일반 계정 역할 관리 |
| admin | 서비스 운영 관리자 | 플랜 가격·한도 관리. master 생성·삭제·강등 불가 |
| user | 일반 가입 회원 | 본인 구독과 참여 프로젝트 범위 |
| guest | 화면 체험 전용 | 없음 |

- 공개 가입 API는 계정 역할 입력을 허용하지 않고 항상 user를 부여한다. 변조된 master/admin/guest 요청은 거부한다.
- 일반 가입은 Free로 시작하는 안을 권장한다. 유료 플랜 선택은 역할 선택과 분리하고 구독 화면에서 처리한다.
- 일반 회원도 프로젝트 owner가 될 수 있다. `accountRole=user`와 `projectRole=owner`는 동시에 성립한다.
- 플랫폼 admin/master라고 다른 회원의 비공개 프로젝트에 자동 참여시키지 않는 안을 권장한다. 운영자 접근이 필요하면 별도 명시 권한과 감사 절차로 정의한다.
- 마찬가지로 master/admin에 프로젝트·AI 한도 면제를 암묵적으로 부여하지 않는다. 모든 회원에 플랜 제한을 적용한다는 요구에 따른다.
- `WorkspaceRole`은 내부 소속/호환용으로 분리한다. 이 값으로 전역 관리자나 프로젝트 권한을 결정하지 않는다.

### 3.2 master 초기 계정

| 항목 | 값/처리 |
| --- | --- |
| 이름 | master |
| 이메일 | master@hamsfam.co.kr |
| 계정 역할 | master |
| 초기 비밀번호 | 이번 요청에서 지정한 값. 이 문서와 SQL·로그에 평문으로 복사하지 않는다. |
| 비밀번호 저장 | 기존 `hashPassword`의 salt 포함 scrypt 형식 |
| 생성 시점 | 역할 스키마 변경 완료 후 최초 부트스트랩에서 삽입. 이번 문서 작업에서는 삽입하지 않음 |

- 요청 비밀번호는 8자로 현재 일반 가입의 최소 10자 검증과 충돌한다. master 부트스트랩에서만 지정값을 직접 해시하고, 일반 회원 비밀번호 규칙을 함께 완화하지 않는 안을 권장한다. 현재 로그인은 가입용 최소 길이 검증을 적용하지 않는다.
- 부트스트랩은 런타임 환경 입력으로 비밀번호를 받아 해시하고 생성한다. 재실행해도 기존 비밀번호를 덮어쓰지 않는다.
- `account_role='master'`에 대한 부분 UNIQUE 인덱스로 최대 1개를 보장한다. 이는 최소 1개 존재를 보장하지 않으므로 초기 생성과 마지막 master 삭제·강등 금지 처리를 함께 둔다.
- 지정 이메일의 계정이 다른 역할로 이미 있거나 다른 master가 존재하면 조용히 변경하지 않고 충돌을 보고한다.
- 현재 인증 의존성을 유지한다면 개인 워크스페이스·소속·활성 워크스페이스까지 원자적으로 생성한다. 계정 인증을 소속과 분리하는 경우에도 실제 master 로그인 경로를 검증한다.
- master의 삭제·강등·이메일 변경 제한과 admin 승격 권한은 별도 서버 가드로 처리한다. 일반 회원 수정 API에 accountRole을 노출하지 않는다.

### 3.3 프로젝트 권한

프로젝트 권한은 `ProjectRole = owner | admin | member | viewer`이며 프로젝트마다 다르게 부여한다.

| 작업 | owner | admin | member | viewer |
| --- | --- | --- | --- | --- |
| 프로젝트·산출물·팀공유 조회 | 허용 | 허용 | 허용 | 허용 |
| 산출물 작성·수정, 공유 글·댓글 작성 | 허용 | 허용 | 허용 | 불가 |
| AI로 프로젝트 데이터 변경, 이미지 생성 | 허용 | 허용 | 허용 | 불가 |
| 구성원 추가 | 허용 | 허용 | 불가 | 불가 |
| 구성원 권한 변경·소유권 이전 | 허용 | 불가 | 불가 | 불가 |
| 프로젝트 삭제 | 허용 | 불가 | 불가 | 불가 |

위 세부 작업표는 기존 동작을 기준으로 정리한 권장안이다. 프로젝트 admin의 관리 범위 등 미확정 항목은 11절에서 별도 확인한다. 로그인 회원 viewer의 조회 보조 기능과 guest의 메뉴 이동 전용 제한은 서로 다르다.

- 프로젝트 생성은 기존 프로젝트 role이 아닌 로그인 계정 역할과 본인의 플랜으로 판정한다. `user`가 개인 워크스페이스 viewer라는 이유로 생성을 막는 기존 흐름을 해소한다.
- 생성자는 `projects.owner_id`가 되고 프로젝트 멤버에 등록된다. owner의 기준은 `owner_id` 하나로 정하고 다른 멤버 role에는 admin/member/viewer를 명시하는 안을 권장한다.
- 각 프로젝트는 반드시 owner 1명을 가지며 owner는 프로젝트 멤버여야 한다. 소유권 이전은 이전 대상 소속·대상 플랜 한도·현재 owner를 검사한 뒤 하나의 트랜잭션으로 반영한다.
- 워크스페이스 owner라는 이유로 프로젝트 owner가 되거나 권한이 승격되지 않는다. role이 누락된 기존 멤버는 명시적으로 이관한다.
- 팀공유의 프로젝트 선택마다 서버가 `projectRole`, `canWrite`, `canAddMembers`, `canManageMembers`, `canTransferOwner`를 반환하고 UI가 이를 사용한다.
- 프로젝트 미선택 시 프로젝트 관리 기능을 표시하지 않는다. 팀 전체 가입 신청 관리가 필요하면 별도 영역에 남기고 프로젝트 권한과 섞지 않는다.
- UI에서 버튼을 숨기는 것과 별개로 모든 API에서 현재 프로젝트 권한을 재확인한다. 공유 글 API의 member 전용 판정도 owner/admin/member로 통일한다.

## 4. 플랜 정책

### 4.1 확정 기본값

금액 단위는 원(KRW)이다. 연간 금액은 월 가격과 별도 저장한다.

| 플랜 | 월간 금액 | 연간 금액 | 프로젝트 | 총 AI 토큰 | 일일 이미지 생성 | 프롬프트 이미지 첨부 | 이력 생성 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Free | 0 | 0 | 1 | 100,000 | 1 | 1 | 안 함 |
| Plus · 추천 | 10,000 | 미정 | 3 | 1,000,000 | 3 | 3 | 함 |
| Pro | 100,000 | 미정 | 5 | 10,000,000 | 5 | 5 | 함 |
| Business | 협의 | 협의 | 무제한 | 무제한·사용량 과금 | 무제한 | 5 | 함 |

- Plus/Pro 연간 가격·할인율을 임의 확정하지 않는다. 관리자가 월간과 다른 연간 금액을 입력한 후 연간 판매를 활성화한다.
- Business는 가격 0원으로 표현하지 않고 “협의”로 표시한다. 자동 무료 활성화나 임의 결제 성공 처리를 하지 않는다.
- 무제한 한도는 `NULL`, 사용 불가는 `0`으로 구분한다. 숫자 필드는 0 이상 정수, 첨부 수는 구현 가능한 범위에서 검사한다.
- 관리자 수정 대상은 월간/연간 가격, 프로젝트 수, 총 토큰, 일일 이미지 수, 첨부 수, 이력 생성 여부다. 추천 표시와 판매 활성화 여부도 카탈로그에 둘 수 있다.
- 가격과 한도는 서버의 동일 정책에서 UI와 API로 제공한다. 클라이언트 요청의 플랜·한도는 권한 판단에 사용하지 않는다.
- 기존 파일 크기·형식·해상도·요청 크기 제한은 유지한다. 첨부 개수가 늘면 전체 요청 크기 계산도 같이 조정한다.

### 4.2 회원별 구독과 공동 프로젝트 적용 기준 — 설계안

플랜의 주체를 워크스페이스에서 회원으로 옮긴다. 팀에 참여하거나 활성 워크스페이스를 변경해도 본인의 구독과 사용량은 바뀌지 않는다.

| 제한/기능 | 적용 주체 권장안 |
| --- | --- |
| 프로젝트 수 | 현재 owner가 본인인 보유 프로젝트 수를 모든 워크스페이스에 걸쳐 합산 |
| 토큰·일일 이미지·프롬프트 첨부 | 요청을 실행하는 로그인 회원 |
| 공동 산출물의 변경 이력 | 프로젝트 owner의 플랜 |
| 개인 AI 대화 이력 | 요청 회원의 플랜 |

참여 초대만 받은 프로젝트는 생성 한도에서 제외하는 안이다. “생성 횟수 누적” 대신 “현재 보유 개수”로 해석하는 정책이므로 최종 확인이 필요하다. 소유권을 넘겨 한도를 우회하지 못하도록 이전 대상의 보유 한도를 함께 검사한다.

- 삭제된 프로젝트는 보유 수에서 제외하고 복원 시 다시 한도를 검사한다. 보관만 한 프로젝트는 포함하는 안을 권장한다.
- 플랜 축소로 기존 보유 수가 한도를 넘더라도 임의 삭제하지 않는다. 신규 생성·추가 소유권 이전·복원을 제한하고 초과 상태를 안내한다.
- 요금제 변경으로 이미 쓴 토큰·당일 이미지 수를 초기화하지 않는다. 가격 변경은 이미 성립한 결제 금액을 소급 수정하지 않는다.
- 명시적인 결제·계약 확정 전에는 유료 플랜을 활성화하지 않는다. 결제 연동 및 수동 부여 권한 범위는 별도 결정한다.

## 5. DB 변경 설계안

기존 `app_settings` 값과 `schema_migrations`를 유지하고 새로운 순번의 마이그레이션을 추가한다. 기존 001~019 파일을 수정하거나 다시 적용하지 않는다.

| 대상 | 변경안 |
| --- | --- |
| users | account_role 기본값 user, master/admin/user/guest CHECK, master 부분 UNIQUE 인덱스 |
| plans | code PK, 표시명, 월간/연간 가격, 가격 방식 fixed/contact, 프로젝트/토큰/일일 이미지/첨부 한도, history_enabled, 추천 여부, 판매 여부, version, 수정자·수정일 |
| user_subscriptions | user_id FK, plan_code FK, billing_cycle(monthly/yearly/contract), 상태, 적용 시작/종료, 정책 버전. 회원별 활성 구독 1개 |
| projects/project_members | owner_id 기준 단일 소유자, 역할 명시, 기존 FK·owner 유효성 제약 보존 |
| quota_reservations | request_id 및 작업 구분 UNIQUE, user_id, 자원 종류, 예약량·확정량, 상태, 만료·확정 시각, 적용 정책 버전 |
| user_usage_counters | 회원·자원·기간 키별 사용량과 예약량. 조건부 갱신으로 한도 초과 경쟁 방어 |
| ai_token_usage | 기존 측정 활용, 사용자 구독·예약과 연결. 프롬프트 본문 저장과 사용량 측정을 분리 |
| plan_change_logs | 관리자 가격·한도 변경의 버전과 전후 값 기록. 필수 운영 기록 여부를 별도 정책으로 정의 |

- `plans`에 4개 기본값을 1회 넣고 이후 재배포 시 관리자 수정값을 덮어쓰지 않는다.
- `user_subscriptions`의 기간은 구독 유효기간이며 토큰 제공량 리셋 주기와 자동으로 같은 의미가 아니다. 토큰 주기를 먼저 확정한다.
- `app_settings`에 모든 플랜을 하나의 JSON으로 넣는 방식보다 타입 검증·참조·버전 관리가 쉬운 전용 카탈로그를 권장한다. 기존 로깅 설정은 유지한다.
- SQLite/libSQL CHECK 변경은 단순 컬럼 추가로 해결되지 않는다. users 테이블 재구성 시 참조 FK·인덱스·트리거와 `app_settings.updated_by`까지 점검하고 원자적으로 이관한다.
- 레거시 계정 owner/user는 계정 user로 이관하고 기존 팀·프로젝트 소유권은 유지한다. 계정 owner를 master로 자동 승격하지 않는다.
- 레거시 team/pro의 신규 Plus/Pro 대응은 확정 전 자동 매핑하지 않는다. 잔여 데이터가 있으면 회원별 이관표를 만들고, 비어 있어도 테스트 fixture를 갱신한다.
- 이번 세션에서 서비스 데이터 초기화를 수행했지만 구현 시점에도 비어 있다고 가정하지 않는다. 신규 가입·기존 구독 데이터 유무를 다시 확인한다.

## 6. 사용량 제한과 저장 정책

### 6.1 공통 서버 판정 순서

1. 세션/계정 역할 확인. guest는 업무 기능 실행을 차단한다.
2. 대상 프로젝트 소속과 작업별 권한 확인.
3. 서버에서 유효한 회원 구독과 최신 적용 정책을 조회.
4. 첨부 개수·자원 한도를 검사하고 원자적으로 사용량을 예약.
5. 실제 작업 또는 AI 호출 수행.
6. 실제 사용량 확정, 예약 차액 정산, 결과·정책에 따른 이력 저장.

프로젝트 수 검사와 프로젝트 INSERT는 같은 쓰기 트랜잭션에서 수행한다. AI 외부 호출 동안 DB 트랜잭션을 열어 두지 않고 짧은 예약·확정 트랜잭션으로 분리한다.

### 6.2 토큰

- 입력+출력의 실제 total_tokens를 기본 차감 기준으로 제안한다. 캐시·추론 토큰은 포함 관계를 확인해 중복 합산하지 않는다.
- 프롬프트·대화 문맥·첨부·출력 상한을 반영해 호출 전 예산을 예약하고, 도구 재호출 등 각 추가 유료 호출 전에도 남은 예산을 검사한다.
- 가드레일 분류 호출과 이미지 생성 토큰을 포함할지 정책을 명시해야 한다. 사용량 형식이 다른 이미지 API 값을 텍스트 API 파서로 강제 처리하지 않는다.
- 응답 중복·재시도·새로고침으로 중복 차감하지 않는다. 기존 request_id/call_index/response_id 중복 방어를 활용한다.
- 제공자 응답이 불명확하거나 usage가 없으면 무료 사용으로 간주해 예약을 즉시 반환하지 않는다. unknown/pending 정산 상태로 남기고 조정한다.
- 총 제공 토큰의 지급·갱신 시점은 미확정이다. 월간/연간 결제 전환이나 플랜 변경 때마다 임의 재지급하지 않는다.

### 6.3 일일 이미지와 첨부

- 일일 경계는 Asia/Seoul 00:00~다음 날 00:00로 권장한다. 저장 시각은 UTC, 집계 날짜는 KST로 명확히 구분한다.
- 아키텍처·WBS 등 모든 생성 경로와 재생성을 회원별로 합산한다. 기존 저장 이미지 조회·재사용은 생성으로 차감하지 않는다.
- 서로 다른 프로젝트에서 동시에 요청해도 `확정 사용량 + 예약량`을 기준으로 한도를 넘기지 못하게 한다.
- 제공자 호출 전 실패는 예약을 반환한다. 제공자 성공 후 결과 저장 실패는 이미 비용이 발생한 상태이므로 재시도 시 같은 생성 결과를 복구하는 방향으로 처리한다. 불명확한 타임아웃은 정산 대기로 남긴다.
- Business 무제한은 플랜상 일일 개수 제한만 제거한다. 서버의 동시 실행·파일 크기·외부 제공자 제한까지 제거하지 않는다.
- 첨부 수는 한 번의 사용자 프롬프트에 첨부한 이미지 수로 제안한다. 이전 대화 이미지 재사용과 전체 문맥 크기는 별도 안전 상한으로 제한한다.

### 6.4 Free 이력 미생성

“이력 데이터”의 범위가 미확정이므로 아래처럼 저장 목적을 나누는 안을 권장한다.

| 데이터 | Free 처리 권장안 |
| --- | --- |
| 현재 산출물·파일·생성 이미지 | 기능 사용 결과로 저장 |
| 사용자용 산출물 변경 스냅샷 | 생성하지 않음. 공동 산출물은 프로젝트 owner 플랜 기준 |
| 개인 AI 대화 목록·프롬프트·응답 본문 이력 | 영구 저장하지 않음. 현재 화면 세션 내 문맥만 사용 |
| AI 첨부 이미지 | Free 대화 이력 저장에 종속되지 않는 임시 처리/만료 삭제 경로 필요 |
| 토큰·이미지 카운터·호출 정산 정보 | 한도 집행에 필요한 최소 데이터 유지 |
| 인증·세션·보안/운영 감사 기록 | 기존 별도 운영 정책 적용. 사용자용 이력 기능과 분리 |

- Free여도 version 갱신과 충돌 검사는 유지한다. 스냅샷 미생성과 데이터 무결성 검사를 혼동하지 않는다.
- `ai_chat_images`의 채팅 참조 등 기존 FK를 검토해야 한다. Free 채팅 INSERT만 생략하면 첨부가 깨질 수 있다.
- Free 전환 뒤 새 이력 생성은 중단하되 기존 이력을 자동 삭제하지 않는 안을 권장한다. 복구·조회 가능 범위는 별도 결정한다.
- 과거 Free 사용 시점의 이력을 Plus 업그레이드 후 소급 생성하지 않는다.

## 7. 게스트 체험 설계안

- 로그인 우측 상단 문구를 “게스트로 시작하기”로 바꾸고 `/guest/dashboard` 등 명시적 데모 경로로 연결하는 안을 권장한다.
- 데모 전용 레이아웃에서 기존 화면 컴포넌트를 재사용하되 익명 `GuestPrincipal`과 고정 샘플 데이터를 제공한다. 실제 회원/워크스페이스/세션을 만들지 않는다.
- guest를 계정 역할 타입에 포함하되 비로그인 방문자마다 users 행을 INSERT하지 않는다. 저장된 guest 계정이 있더라도 동일하게 체험 전용으로 제한한다.
- `requireUser`를 전역적으로 느슨하게 바꾸어 실제 `/api/projects`, `/api/team/*`, `/api/ai/*` 데이터를 공개하지 않는다. 데모는 정적 fixture 또는 별도 데모 조회 경로만 사용한다.
- 허용: 메뉴 이동, 프로젝트 상세 등 화면으로의 이동, 샘플 데이터 표시.
- 제외: 생성·수정·삭제, 팀 초대·승인·권한 변경, 공유 글·댓글 작성, AI 입력·실행·이미지 첨부/생성, 업로드·다운로드·내보내기, 편집기 실행, 결제·플랜 변경·관리자 기능.
- 요구사항의 “메뉴 이동 제외 모든 기능 배제”를 엄격히 적용하여 필터·검색·새로고침·복사 등 보조 기능도 기본 비활성/제거한다. 그래프 선택처럼 추가 상호작용을 허용하려면 별도 확정한다.
- 실제 데이터 요청, 숨겨진 버튼 직접 호출, 문서 편집 URL과 API 우회 접근도 차단한다. 게스트 표시값을 클라이언트에서 user로 바꿔도 권한이 생기지 않아야 한다.
- 로그인·회원등록 이동은 체험 기능과 별개인 인증 진입으로 제공한다. 회원등록 후에만 실제 개인 공간을 생성한다.
- 게스트에서 로그인할 때 fixture와 사용자 데이터를 분리하고, 로그아웃 시 브라우저에 남은 실제 프로젝트 캐시를 제거한다.

| 이미지 | `lib/ai/architecture-images.ts`, `lib/ai/wbs-images.ts` 및 각 API | 통합 일일 한도 예약, 재사용·재생성 구분 |
| 이력·활동 | `lib/artifacts.ts`, `app/api/activity/route.ts`, 프로젝트 목록 최근 활동, history 화면 | history_enabled에 따른 생성·조회 정책 |
| 편집기·AI 자동저장 | `lib/onlyoffice.ts`, `lib/ai/page-tools.ts` | 계정 역할 변환 교체, 프로젝트 권한 재확인, 모든 저장 경로에 이력 정책 적용 |
| 기존 가드레일 관리 | `lib/ai/guardrail-policy.ts`, `app/(workspace)/admin/ai-guardrails/*` | 워크스페이스 정책 관리자와 전역 플랜 관리자 구분 |

신규 경로와 모듈 이름은 설계 예시이며 이번 단계에서 파일을 생성하지 않는다. 프로젝트 역할과 플랜 사용 가능 여부를 합친 capability 응답으로 화면과 서버의 정책 중복을 줄인다.

관리자 플랜 수정은 현재 version을 함께 전달하여 동시 수정 덮어쓰기를 막는다. 일반 user/guest, 프로젝트 owner/admin에게는 전역 플랜 수정 API를 허용하지 않는다. 공개 플랜 조회는 가격·제공량만 반환하고 내부 관리 정보는 제외한다.

## 9. 구현 순서와 배포

1. **정책 확정**: 11절의 연간 가격·토큰 주기·과금/이력 적용 주체·권한표를 결정한다.
2. **DB 준비**: 스키마와 참조 관계를 확인하고 역할 CHECK 변경, master 제약, 플랜·구독·사용량 예약 테이블을 새 마이그레이션으로 추가한다.
3. **데이터 이관·초기화 값**: 기존 역할/구독을 이관하고 플랜 4개를 초기 등록한다. 기존 `app_settings`와 관리자 수정값은 보존한다. master 계정을 한 번만 생성한다.
4. **서버 인증·권한**: 계정/소속/프로젝트 역할을 분리하고 master/admin 관리자 가드, 생성 owner, 팀공유 권한을 적용한다.
5. **가입·게스트 UI**: 역할 선택과 구식 온보딩을 제거하고 회원등록 버튼·독립 데모 경로를 연결한다.
6. **플랜 관리·사용량 집행**: 관리자 가격/제공량 변경, 프로젝트 제한, 토큰 예약·정산, 일일 이미지·첨부 제한을 연결한다.
7. **이력 저장 경로**: 일반 저장·AI 자동저장·문서 편집 콜백 등 모든 경로와 화면 조회에 정책을 반영한다.
8. **검증 후 배포**: 실제 외부 AI 호출 없는 테스트를 우선 수행하고 유료 호출이 필요한 검증은 범위를 분리한다. 스키마/서버 버전 불일치가 없게 순서를 조정한다.

이 문서 작성은 위 구현 단계 실행을 의미하지 않는다. DB 마이그레이션·master INSERT·결제 연동은 후속 구현 작업이다.
