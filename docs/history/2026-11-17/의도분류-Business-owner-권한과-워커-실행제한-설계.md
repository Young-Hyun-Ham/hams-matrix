## 1. 요구사항과 적용 범위

### 1.1 확정 요구사항

1. 의도분류는 Business 플랜의 owner만 사용할 수 있다.
2. 기존 DB 대기열을 유지한다.
3. 실행 제어는 **전용 워커 분리 → 전체 동시 실행 제한 → 공통 API 호출량 제한** 순서로 적용한다.
4. 청크 단위 공정 분배와 전용 큐 도입은 처리량이 증가한 뒤 검토한다.
5. 기존 중지·실패 후 재개·멱등성·권한 재검증·검색본 원자 발행·사용량 기록을 보존한다.

### 1.2 용어와 해석이 필요한 경계

현재 UI의 **‘의도분류’ 버튼은 프로젝트 벡터화 설정·실행 모달**을 연다. 반면 `intent-classifier.ts`는 채팅 질문을 `rag / realtime / execution`으로 자동 분류한다. 동일한 표현이 서로 다른 기능을 가리키므로 버튼만 제한하면 자동 분류와 프로젝트 키를 이용한 검색은 계속 제공된다.

본 문서의 권고안은 요구사항을 넓게 적용하여 Business 프로젝트 owner에게만 의도분류 관리와 자동 분류·RAG 검색을 허용하는 것이다. 다른 사용자는 기존 화면 조회 기반 일반 AI 채팅을 계속 사용한다. 이는 **검토를 위한 제안**이며, 관리만 제한하고 팀원의 검색 사용은 허용할지는 9절에서 결정한다.

`owner`는 우선 **대상 프로젝트의 실제 소유자(`projects.owner_id`)**로 해석한다. 현재 벡터화 권한이 프로젝트 역할을 기준으로 하며 프로젝트 owner와 workspace owner는 별개이기 때문이다. workspace owner를 의미한다면 별도 정책 변경이 필요하다.

`business` 판정은 클라이언트 `user.plan` 문자열만 비교하지 않는다. 서버의 `workspacePlan(user.id, workspaceId, executor)`가 확인하는 현재 workspace 플랜·개인 구독·상품 연결·상품 활성 상태와 소속 검증을 통과해야 한다.

### 2.2 RAG 등록·실행·발행

```mermaid
flowchart LR
  UI[의도분류 모달] --> API[RAG API: 권한·버전·멱등성 검사]
  API --> DB[(project_rag_jobs: queued)]
  DB --> Worker[RAG 전용 프로세스]
  Worker --> Sources[원본 수집·추출·청크 생성]
  Sources --> Embeddings[임베딩 호출·청크 저장]
  Embeddings --> Publish[manifest·권한·완전성 재검증]
  Publish --> Active[트랜잭션으로 검색본 포인터 교체]
```

- `lib/ai/project-rag.ts`: 키를 암호화 저장하고 세대·설정·대기 작업을 생성한다. 모델 목록 확인은 웹 요청에서 외부 API로 수행한다. 시작 전과 쓰기 트랜잭션 안에서 관리 권한을 확인한다.
- `lib/ai/rag-resume.ts`: 실패 작업의 같은 세대·모델과 저장된 청크를 재사용하는 새 작업을 만든다. 기존 실패 작업과 재개 계보를 보존한다.
- `lib/ai/rag-worker.ts`: `created_at` 순으로 회수 가능한 작업을 찾고 조건부 UPDATE로 180초 lease를 획득한다. checkpoint에서 lease 갱신·중지·요청자의 현재 접근·AI 활성 상태를 확인한다.
- 한 프로세스는 작업 하나를 끝까지 처리한다. 소스별로 청크를 순회하며 최대 32개 단위로 누락 임베딩을 호출한다. 기존 청크 재사용과 진행률 저장은 이미 있다. **32개 묶음 호출은 프로젝트 사이의 공정 스케줄링을 의미하지 않는다.**
- 임베딩의 429/503/504에 최대 3회 시도하며 재시도 사이 대기는 1초·2초다. 공통 호출 예산이나 `Retry-After` 반영은 없다.
- 정상 종료 직전 원본 manifest·설정 버전·권한·청크 완전성을 다시 확인한다. 새 세대가 준비된 경우에만 검색본 포인터를 트랜잭션으로 교체한다. 실패한 재벡터화가 기존 검색본을 덮어쓰지 않도록 유지해야 한다.
- `db/migrations/048_project_rag_orchestration.sql`에는 프로젝트별 활성 작업 1개 제약과 대기열 인덱스가 있다. `049_project_rag_resume.sql`은 재개 계보와 불변성 제약을 추가한다. 이 문서는 마이그레이션 파일을 확인했으며 실제 적용 여부는 판정하지 않는다.

### 2.3 전용 워커는 이미 존재한다

| 위치 | 현재 상태 |
| --- | --- |
| `scripts/rag-worker.mjs` | RAG 작업을 하나씩 실행하고 작업이 없으면 1.5초 대기한다. SIGINT/SIGTERM 후 현재 작업이 반환되면 종료한다. |
| `scripts/deliverable-worker.mjs` | 산출물 작업을 로컬 Map으로 제한한다. `DELIVERABLE_WORKER_CONCURRENCY` 기본 2, 범위 1~8이다. |
| `scripts/run-with-deliverable-worker.mjs` | `pnpm dev/start`에서 웹·산출물 워커·RAG 워커를 각각 자식 프로세스로 실행한다. 종료된 워커를 재시작하며 종료 시 5초 후 강제 종료를 시도한다. |
| `package.json` | `worker:rag`, `worker:deliverables` 명령이 이미 있다. |

따라서 ‘전용 워커 분리’는 새로 비동기 대기열을 만드는 작업이 아니다. **이미 분리된 실행 코드를 활용하고 웹 인스턴스 수와 워커 수를 독립 운영하도록 배포 경계를 정리하는 작업**이다. 현재 실행 래퍼를 그대로 여러 웹 인스턴스에서 실행하면 각 인스턴스가 워커를 추가로 실행한다.

RAG의 직렬 실행과 산출물의 로컬 동시성 제한은 전체 배포의 실행 상한이 아니다. 여러 프로세스·서버가 실행되면 총 실행 수가 증가한다. 개별 job lease는 동일 작업의 중복 실행을 막는 장치이며 전체 작업 개수를 제한하는 장치와 다르다.

산출물 대기열은 `project_deliverable_generation_requests`이며 별도 `queued` 상태 대신 `running/validating/stop_requested` 등의 상태와 lease 만료 여부로 회수 대상을 찾는다. `processNextDeliverable()`의 후보 조회 시점과 `continueDeliverables()` 내부의 실제 lease 획득 시점이 다르므로 전역 슬롯 도입 위치를 조정해야 한다.

### 2.4 채팅 자동 분류와 검색

- `app/api/ai/chats/route.ts`는 현재 모든 채팅 처리에서 `orchestrateChat()`을 호출한다. 프로젝트가 없는 채팅도 분류 함수는 호출되며 프로젝트가 있을 때만 RAG 검색과 이벤트 저장이 연결된다.
- `lib/ai/intent-classifier.ts`는 우선 규칙으로 분류하고 모호한 질문에만 LLM을 추가 호출한다. LLM의 execution 판정 자체는 쓰기 권한을 만들지 않는다.
- `lib/ai/orchestration.ts`는 분류 계획에 따라 RAG를 검색하고 분류 이벤트를 저장한다. 채팅 route는 그 결과로 쓰기 허용과 직접 화면 조회 여부를 결정한다.
- `lib/ai/rag-retrieval.ts`는 현재 프로젝트 접근이 있으면 검색을 시도한다. 질문 임베딩에는 프로젝트에 저장된 키를 사용한다. 답변 저장 직전에 원본 manifest를 다시 확인한다.
- 채팅 route와 공통 lib에 결합된 기능이므로, UI와 관리 API만 막으면 자동 분류와 검색 경로는 계속 사용될 수 있다.

### 2.5 API 호출량 제어 현황

`lib/auth.ts`의 `rateLimit()`은 사용자·workspace별 요청 남용을 제한하는 **15분 고정 창**이다. 채팅, 벡터화 시작, 재개, 모델 목록 등의 진입 API에 적용되어 있다. 한 진입 요청에서 발생하는 여러 임베딩 호출·생성 단계·상태 조회를 합산하는 공급자 호출 제한이 아니다.

공통 제어가 필요한 외부 호출 위치는 다음과 같다.

| 파일 | 외부 호출 | 주 사용 키 |
| --- | --- | --- |
| `lib/ai/embeddings.ts` | 모델 목록, 색인 임베딩, 질문 임베딩 | 입력 또는 프로젝트 저장 키 |
| `lib/ai-server.ts` | 모델 목록, Responses 생성, 도구 후속 단계 | 서버 공용 키 |
| `lib/ai/background-response.ts` | Responses 상태 조회와 취소 | 서버 공용 키 |
| `lib/ai/image-generation.ts` | 이미지 모델 목록과 생성 | 서버 공용 키 |

분류 LLM과 가드레일 등 `generateAi()`를 재사용하는 경로도 공용 키 예산을 소비한다. Responses 진행 조회는 현재 500ms 간격이며 워커 여러 개가 합산되면 조회 호출도 늘어난다. `token-usage.ts`와 `quotas.ts`의 회원 사용량·플랜 쿼터는 공급자 RPM/TPM 제한을 대체하지 않는다.

## 3. 권한 수정 방향

### 3.1 단일 서버 정책

의도분류 정책을 공통 함수로 계산하고 관리 API·조회 DTO·채팅·워커가 같은 결과를 사용하도록 한다. 개념적인 결과는 `eligible`, `canManage`, `canUseRetrieval`, `reasonCode`다. 실제 함수명과 DTO 필드는 구현 단계에서 확정한다.

권고하는 허용 조건은 다음 조건의 동시 충족이다.

1. 인증된 비게스트이며 온보딩을 완료했다.
2. 현재 workspace에 소속되고 `workspacePlan()` 검증을 통과했다.
3. 유효한 플랜 코드가 `business`다.
4. 대상 프로젝트에 현재 접근할 수 있다.
5. `projectPermissionAccess()`가 반환한 현재 `ownerId`가 사용자 ID와 일치하고 프로젝트 역할이 owner다.

`master`, `super_admin`, `biz_admin`, workspace owner라는 이유만으로 예외 허용하지 않는다. 이들도 위 조건을 충족할 때만 해당 기능을 사용한다. 일반 채팅과 기존 프로젝트 권한 정책은 각자의 현재 규칙을 유지한다.

| 현재 유효 플랜 | 대상 프로젝트 역할 | 권고안: 관리·자동 분류·RAG 검색 | 일반 AI 채팅 |
| --- | --- | --- | --- |
| Business | 실제 owner | 허용 | 기존 권한대로 허용 |
| Business | admin/member/viewer | 제한 | 기존 권한대로 허용 |
| Free/Pro/Team | owner 포함 모든 역할 | 제한 | 기존 플랜·권한대로 허용 |
| 어느 플랜이든 | 미배정·다른 workspace·게스트 | 기존 접근 오류 유지 | 기존 정책 적용 |
| Business workspace + 다른 구독/상품 | owner라도 | 기존 불일치 오류 유지 | 기존 정책 적용 |

### 3.2 API와 UI

- 직접 접근하는 관리 API는 403과 안정적인 오류 코드(예: `INTENT_CLASSIFICATION_NOT_ALLOWED`)를 반환한다. 외부 모델 조회·키 복호화·사용량 예약보다 먼저 자격을 검사한다. 다른 workspace/프로젝트의 존재를 노출하는 오류로 바꾸지 않는다.
- 시작·재개의 쓰기 트랜잭션과 워커 checkpoint·발행 트랜잭션에서도 최신 권한을 재검증한다. 브라우저에서 받은 `canManage`는 보안 근거로 사용하지 않는다.
- 권고안에서는 RAG 상태·실패 상세 API도 기능 자격을 검사한다. 일반 프로젝트 READ 권한과 의도분류 사용 권한을 명확히 구분한다.
- 대시보드와 프로젝트 화면의 버튼·모달·초기 DTO가 동일한 정책을 사용하게 한다. 미허용 사용자는 전용 컨트롤을 숨기고 RAG 조회·활성 작업 폴링도 시작하지 않는다. 안내 문구가 필요하면 ‘Business 플랜의 프로젝트 owner만 사용할 수 있습니다’를 사용한다.
- 대시보드 전체를 403으로 실패시키지 않는다. 미허용 프로젝트는 최소 capability만 반환하고 키 존재·작업 상세·오류 원문 등 관리 정보를 내려주지 않는 형태를 제안한다. 기존 `rag` 필드의 nullable 여부와 타입 호환성을 함께 정리한다.
- 현재 `ragSummary()`의 단건 응답과 `dashboardData()`의 직접 계산을 공통 정책으로 일치시킨다. 요약 일괄 조회 시 권한 판정 때문에 전체 원본을 수집하거나 프로젝트별 무거운 조회를 추가하지 않는다.
- 권한 확인은 화면 진입·프로젝트 변경·작업 직전·명시적 권한 변경 이벤트에서 수행한다. project access 주기 조회를 재도입하지 않는다. 권한 관련 Query는 staleTime 0/retry 0 정책을 유지하고 자동 focus/reconnect 조회를 추가하지 않는다.

### 3.3 미허용 사용자의 일반 채팅

`orchestrateChat()`을 그대로 호출한 뒤 결과만 숨기면 분류 비용과 검색 사용이 남는다. 자격 판정 후 **호출 전에 분기**한다.

- 허용 사용자: 현재 분류·RAG 경로를 사용한다.
- 미허용 사용자 또는 프로젝트 없는 채팅: 의도분류 LLM·RAG 검색·프로젝트 임베딩 키 사용·신규 분류 이벤트 저장을 생략하고 현재 화면 데이터를 직접 조회하는 일반 채팅 경로로 처리한다.
- 빈 `plan`을 반환하거나 `needsExecution=false`를 일괄 주입하지 않는다. 그렇게 하면 의도분류를 사용할 수 없는 사용자의 기존 AI 작성·수정 기능까지 막힐 수 있다. 일반 경로의 `canWrite`는 대상 탭 권한·플랜 이력 정책·현재 사용자의 명시적 요청·기존 도구 검증으로 계산한다.
- 분류를 건너뛰는 경우에도 `page-tools.ts`, `rfp-tools.ts` 등의 명시 요청 검사, 허용 도구, 가드레일, HITL, 원본 버전·도메인 검증, 원자 저장을 그대로 적용한다. 분류가 실행 권한을 대신하는 구조를 만들지 않는다.
- 오케스트레이션 결과는 사용 여부를 명시적으로 나타내도록 설계하고, 미사용 경로는 RAG context/reference가 빈 값임을 타입으로 처리한다. 기존 참조 footer·출처 검증·이벤트 통계도 이 경우를 처리한다.
- 허용 자격이 답변 도중 회수되면 저장 직전에 다시 검사한다. 이미 검색 근거를 사용해 생성한 답변을 조용히 일반 답변으로 저장하지 말고 재질문 가능한 권한 변경 오류로 종료한다.

### 3.4 기존 작업과 권한 회수

새 정책 적용 전에 admin 또는 비Business 사용자가 등록한 작업이 남을 수 있다. 작업 행·키·청크·이력을 일괄 삭제하지 않는다. 처리 직전 최신 정책으로 부적격을 확인하면 추가 유료 호출과 발행을 중단하고 원인 코드를 남겨 실패로 정리한다. 이전 검색본은 보존하되 이용 자격이 없는 사용자에게 검색을 제공하지 않는다.

현재 owner는 이전 요청자가 시작한 작업도 중지할 수 있게 한다. 요청자의 권한 상실과 별개로 이미 접수된 중지 요청은 안전하게 정리해야 한다. 기존 워커의 권한 검사 순서 때문에 `stop_requested`가 일반 실패로만 끝나지 않도록 취소 처리와 권한 오류 처리를 구분한다. 운영자 내부 정리는 사용자용 API의 예외 권한을 만드는 방식으로 구현하지 않는다.

## 4. 1단계: 전용 워커 운영 분리

### 4.1 적용안

1. 기존 `worker:rag`, `worker:deliverables`와 처리 함수를 재사용한다. 웹 요청에서 전체 벡터화나 산출물 생성을 실행하지 않는다. 요청은 검증·등록·상태 응답 역할을 유지한다.
2. 개발에서는 현재 통합 실행 래퍼를 유지할 수 있다. 운영은 웹만 실행하는 진입점과 별도 상시 워커 실행 구성을 제공한다. 운영 웹 인스턴스가 워커를 자동으로 추가 실행하지 않게 한다.
3. 배포 시스템에서 웹·RAG 워커·산출물 워커의 수와 자원을 독립 관리한다. 서버리스 웹과 함께 사용할 경우에도 워커는 상시 실행 가능한 별도 환경에 둔다.
4. DB 연결과 동일한 자격 증명 암호화 키를 필요한 프로세스에 제공한다. 실제 값은 코드·DTO·로그·문서에 기록하지 않는다.
5. 종료 신호를 받으면 신규 작업 획득을 멈추고 현재 호출·checkpoint를 정리한다. 배포 종료 유예와 기존 래퍼의 5초 강제 종료가 충돌하지 않도록 운영 설정을 분리한다.

### 4.2 완료 기준

- 웹 재시작이 등록된 작업을 삭제하지 않으며, 웹 증설만으로 워커가 늘어나지 않는다.
- 워커가 없어도 등록은 가능하고 작업은 대기 상태를 유지한다. 별도 운영 지표로 워커 미동작과 장기 대기를 탐지한다.
- 워커 장애 시 기존 job lease·청크·응답 ID로 복구하며 새 요청을 중복 생성하지 않는다.

## 5. 2단계: 전체 동시 실행 제한

### 5.1 제한의 단위

최소 필수 범위는 **모든 RAG 워커를 합친 실행 작업 수**다. 권고안은 여기에 산출물 워커까지 포함하는 전체 백그라운드 작업 상한을 두고, RAG와 산출물의 종류별 상한을 함께 두는 것이다. 구체적인 포함 범위와 수치는 9절에서 확정한다.

일반 채팅은 장기 작업 슬롯을 점유시키지 않는다. 대신 3단계의 공통 API 예산을 공유한다. 다음 세 제한은 서로 다르다.

| 제한 | 해결하는 문제 | 제어 위치 |
| --- | --- | --- |
| 프로젝트별 활성 작업 1개 | 같은 프로젝트의 중복 벡터화 | 기존 DB unique index |
| 배포 전체 실행 작업 N개 | 워커 증설에 따른 CPU·메모리·DB 부하 증가 | DB의 전역 실행 슬롯 |
| 공통 API 호출량 | 한 작업의 다수 호출과 여러 기능의 공급자 예산 경합 | 외부 HTTP 호출 직전 |

### 5.2 DB 기반 실행 슬롯

DB 대기열은 그대로 두고 별도의 작은 제어 테이블을 추가하는 안을 권고한다. 테이블명은 가칭 `ai_worker_slots`이며 pool/slot 식별자, 작업 종류·ID, 소유 토큰, 만료·heartbeat를 관리한다. **기존 DB 유지라는 요구는 대기열 저장소 유지이며, 미래 구현에서 보조 테이블 추가까지 금지한다는 뜻으로 해석하지 않는다.** DB 스키마 변경도 불가한 경우 대체 설계를 다시 결정해야 한다.

획득 절차는 하나의 짧은 쓰기 트랜잭션으로 처리한다.

1. 비어 있거나 회수가 확인된 슬롯을 선택한다. 전체 풀과 종류별 상한을 함께 검사한다.
2. 해당 job이 여전히 처리 대상인지와 기존 lease 조건을 재확인한다.
3. 슬롯과 job lease를 동일 소유 토큰에 연결하여 함께 갱신하고 커밋한다.
4. 확보에 실패하면 job을 대기 상태로 두고 경쟁에 진 워커는 짧은 지터 후 다시 조회한다.

`COUNT(running) < N`을 트랜잭션 밖에서 확인하는 구현이나 메모리 Map·환경변수만으로 전역 제한을 구현하지 않는다. RAG는 `processNextRagJob()`의 claim과 결합하고, 산출물은 `continueDeliverables()`의 실제 lease 획득 부분과 결합한다. 후보만 조회하는 `processNextDeliverable()`에서 슬롯을 확정하면 실제 실행하지 못하는 작업이 슬롯을 점유할 수 있다.

### 5.3 갱신·반납·장애 복구

- 작업 checkpoint에서 job과 slot의 소유권을 함께 확인하고 갱신한다. 기존 180초 job lease를 기준으로 시작하되 heartbeat는 만료보다 충분히 짧게 설정한다.
- API 대기·재시도 중에도 heartbeat와 중지 확인을 수행한다. DB 트랜잭션을 연 채 외부 API나 대기를 실행하지 않는다.
- 완료·실패·취소·사용자 검토 대기 전환 시 슬롯을 반납한다. 산출물의 `review_required` 등 사람을 기다리는 상태는 실행 슬롯을 점유하지 않는다.
- 중지 요청 정리는 신규 생성 슬롯 부족으로 무기한 밀리지 않게 한다. 청크 공정 배분을 도입하지 않아도 취소·상태 확인은 별도 제어 경로로 처리할 수 있다.
- lease를 잃은 워커는 다음 유료 호출과 DB 저장·발행을 중단한다. 갱신·저장·반납은 소유 토큰을 조건에 포함해 이전 워커가 새 소유자의 상태를 변경하지 못하게 한다.
- 단순 TTL 만료만으로 외부에서 실행 중인 생성까지 종료되지는 않는다. 산출물은 저장된 Responses ID의 실행 상태를 확인·회수하고, 미확인 활성 응답은 새 생성과 중복하지 않는다. 임베딩처럼 공급자 실행을 취소·확인하기 어려운 호출은 최대 호출 시간과 회수 유예를 반영한다.
- 따라서 슬롯 상한은 정상 소유권 아래의 작업 실행 수를 보장하는 장치다. 네트워크 단절 시 외부 미확인 실행까지 엄격하게 N개로 보장하려면 응답 추적·격리·회수 정책이 추가로 필요함을 운영 한계로 기록한다.
- 상한을 낮췄을 때 기존 작업을 강제 중단하지 않고 신규 획득을 막아 자연스럽게 수렴시키는 방식을 권고한다.

초기 수치를 기존 로컬 기본값에서 그대로 확정하지 않는다. 실제 리소스와 API 예산을 확인한 뒤 RAG·산출물·전체 상한을 정하고 낮은 값부터 조정한다.

## 6. 3단계: 공통 API 호출량 제한

### 6.1 공통 호출 계층

웹과 모든 워커가 같은 외부 호출 제어 모듈을 사용하도록 한다. 가칭 `lib/ai/provider-request.ts`는 admission·HTTP timeout·취소 신호·429 메타데이터 처리를 담당하고, `provider-rate-limit.ts`는 공유 예산 예약과 정산을 담당한다. 업무별 응답 해석과 사용량 기록은 기존 모듈에 남긴다.

호출자 식별에는 자격 증명 범위, 공급자, 제한 그룹, 용도(`orchestration`, `embedding_index`, `embedding_query`, generation, models, poll, cancel)를 전달한다. 저장·생성 API 자체나 업무 트랜잭션을 범용 HTTP 재시도로 감싸지 않는다.

### 6.2 공유 예산 저장과 구분

- 프로세스 메모리 대신 같은 DB의 제어 테이블을 사용한다. 가칭 `ai_provider_buckets`와 호출별 예약 기록을 두고, 짧은 트랜잭션으로 다중 버킷 예산을 원자 예약한다. 신규 전용 큐나 Redis는 이 단계의 필수 조건으로 두지 않는다.
- 호출 횟수 예산(RPM 계열), 토큰 처리량 예산(TPM 계열), 필요 시 공급자 호출 동시성 제한을 분리한다. 구체 알고리즘은 토큰 버킷과 예약량 기반 정산을 권고하며 창 경계의 순간 폭주도 제한한다.
- 서버 공용 키는 채팅·의도분류·가드레일·산출물·이미지 등의 실제 사용처 전체에서 공유한다. 프로젝트 키는 같은 실제 키가 여러 프로젝트에 등록되어도 예산을 합산한다. `credential_id`만 버킷 키로 사용하지 않는다.
- 원문 키 대신 서버에서 계산한 HMAC fingerprint를 내부 식별자로 사용한다. 기존 `credentialFingerprint()` 활용을 검토하되 암호화 키 교체 시 버킷이 초기화되어 상한을 우회하지 않도록 식별·교체 정책을 정한다.
- 서로 다른 키도 동일한 공급자 조직·프로젝트 예산을 공유할 수 있다. 키별 버킷만으로 모든 상위 예산을 보장한다고 간주하지 않는다. 상위 제한 그룹 매핑을 설정으로 지원하고, 정보가 없으면 서비스 전체 보수적 상한을 함께 적용하는 안을 검토한다.
- 모델마다 별도 버킷을 무조건 만들지 않는다. 공급자 설정상 예산을 공유하는 모델은 같은 그룹에 매핑한다. 이미지·목록·상태 조회처럼 토큰 기준이 맞지 않는 요청은 횟수/종류별 예산을 적용한다.
- 실제 RPM/TPM 수치는 이 소스에서 확인할 수 없다. 계정의 실제 제한과 운영 목표를 확인해 설정하고 문서에 특정 공급자 수치를 추정해서 넣지 않는다.

### 6.3 호출 생명주기와 사용량

1. 현재 권한·중지·deadline을 검사한다.
2. 요청 크기와 최대 출력을 기준으로 호출 횟수·예상 토큰 예산을 예약한다. 토큰 추정량이 단일 버킷 용량보다 크면 영원히 기다리지 않고 입력 축소 또는 명시적 오류로 처리한다.
3. 예약 대기 후 권한·중지를 다시 확인한다. 기존 회원 플랜 쿼터 예약과 순서를 정해 미전송 시 두 예약을 모두 정리한다.
4. 외부 호출 직전에 전송 상태를 확정하고 호출한다. 실제 재시도는 각각 별도 호출 예산을 소비한다.
5. 실제 사용량이 확인되면 토큰 예약량과 차이를 정산한다. 요청이 공급자에 도달하지 않은 것이 확실한 경우만 미사용 예약을 해제한다.
6. timeout 등 결과 미확인은 횟수 예산을 되돌리거나 토큰을 0으로 단정하지 않는다. 보수적으로 유지하고, 확인 가능한 Responses ID와 기존 사용량 기록으로 중복 정산 없이 보정한다.

외부 호출 대기 자체를 `ai_token_usage`의 실제 유료 호출 성공으로 기록하지 않는다. limiter의 예약 ID와 기존 `(request_id, call_index)` 사용량 식별을 연결해 재개·poll·재시도에서 이중 과금 집계를 방지한다. 이 제어는 회원의 누적 토큰 알림·플랜 쿼터·일일 이미지 한도와 별개다.

### 6.4 과부하·429·취소

- 백그라운드 작업은 예산 부족을 즉시 실패로 저장하지 않고 제한된 간격으로 대기한다. 각 대기 구간에 job/slot heartbeat와 중지 checkpoint를 실행한다.
- 일반 채팅은 기존 요청 deadline 안에서만 짧게 대기한다. 분류 추가 호출이 예산 내에 완료되지 못하면 허용 사용자에 한해 기존 안전한 확인 질문 fallback을 유지하거나 일반 경로 전환 정책을 명시한다. 권한 제한을 fallback으로 우회하지 않는다.
- 호출 전 예산 부족과 공급자 429를 구분하는 오류 코드·재시도 가능 시각을 제공한다. 공급자 `Retry-After`가 있으면 반영하고 지수 백오프와 지터, 최대 재시도·대기 한도를 둔다.
- 현재 RAG 임베딩 재시도를 공통 정책과 결합하되 이중 재시도를 만들지 않는다. 임베딩의 제한적 재시도와 Responses 생성의 재시도를 동일하게 취급하지 않는다. 새 생성은 기존 응답 ID 확인 없이 자동 반복하지 않는다.
- 상태 조회·취소·복구 호출도 요청 예산을 소비한다. 생성 호출이 예산을 모두 소모해 취소할 수 없게 되지 않도록 제어 호출용 여유를 확보하고, 같은 응답 ID의 불필요한 중복 poll을 억제한다. 모든 요청을 합친 상위 예산도 지킨다.
- 공급자 상태 조회 간격은 공통 예산과 응답 상태에 따라 조정한다. 작업 lease 갱신을 외부 poll 성공에만 의존하지 않는다.
- 공통 예산 DB에 접근할 수 없으면 무제한으로 전송하지 않는다. 백그라운드는 대기·복구하고 대화형 요청은 재시도 가능한 오류로 정리한다.

## 7. 후속 단계: 처리량이 커졌을 때 검토

### 7.1 청크 단위 공정 분배

현재는 작업 하나가 소스와 청크를 끝까지 처리하므로 큰 프로젝트가 슬롯을 오래 점유할 수 있다. 먼저 전체 실행 수와 API 예산을 적용하고 대기시간·프로젝트 크기별 편차를 관찰한다. 작은 프로젝트의 장기 대기가 반복되면 다음을 별도로 설계한다.

- 일정 청크 수 또는 시간 예산마다 진행 cursor를 저장하고 작업을 양보한다.
- 프로젝트·workspace별 라운드로빈이나 가중치로 순서를 정한다.
- 현재의 32개 임베딩 묶음과 ‘스케줄러가 작업을 양보하는 단위’를 구분한다.
- 청크 저장의 멱등성, 같은 세대 이어하기, 누락 검증, 최종 발행 단일 소유권을 유지한다.

이 단계는 checkpoint/cursor·lease·진행률의 의미를 바꾸므로 최초 구현에 끼워 넣지 않는다. 1차 작업에서는 큰 작업의 점유 시간이 길 수 있다는 한계를 명시한다.

### 7.2 전용 큐

DB claim 지연·락 경합, 워커 규모, 지연 재시도·우선순위·운영 도구 요구가 현재 방식으로 감당하기 어려워졌을 때 검토한다. 특정 큐 제품은 지금 확정하지 않는다.

도입 시에도 DB의 작업 상태와 결과는 유지하고 알림/dispatch 역할을 분리하는 방향을 우선 검토한다. DB 커밋과 큐 발행 사이 유실 방지(outbox 등), 중복 전달·재처리 멱등성, 실패 큐와 재개 정책이 필요하다. 큐 변경만으로 공통 API 예산 문제가 해결되지는 않는다.

## 10. 검증 방법과 완료 조건

### 10.1 이번 문서 작성의 검증

- 인용한 함수·경로와 호출 관계를 현재 소스로 확인한다.
- `HISTORY.md`의 기존 목록을 유지하고 이 문서의 상대 링크와 한국시간 작성일을 추가한다.
- Git diff와 작업 전후 상태로 문서 외 소스·DB·설정 변경이 없음을 확인한다. 기존 사용자 변경인 `PROMPT.md`는 보존한다.
- 실행 검증은 후속 구현 계획이며 이번 단계에서는 DB 연결·마이그레이션·애플리케이션 테스트를 실행하지 않는다.

### 10.2 권한 검증: 후속 구현

임시 SQLite와 합성 계정을 사용해 Business/Team/Pro/Free × project owner/admin/member/viewer를 검증한다. workspace owner와 project owner가 다른 경우, 관리자 계정이 프로젝트 owner가 아닌 경우, 다른 상품·workspace·미배정·게스트도 포함한다.

- 단건 RAG API, 모델 목록, 시작, 실패 상세, 재개, 중지의 서버 결과를 확인한다.
- 대시보드 초기 응답과 단건 요약의 capability가 일치하고 미허용 사용자에게 관리 정보가 노출되지 않는지 확인한다.
- 버튼 직접 접근·변조 POST·오래 열린 모달로 권한을 우회할 수 없는지 확인한다.
- 대기/실행/발행 직전에 플랜 하향·소유자 변경·상품 정지·키 폐기를 주입한다. 새 유료 호출과 발행을 중단하고 기존 검색본은 보존해야 한다.
- 기존 admin 요청 작업·중지 대기 작업이 영구 점유로 남지 않고 실패/취소로 정리되는지 확인한다.
- 미허용 사용자의 일반 채팅·기존 명시적 쓰기·HITL·RFP 작성은 유지하면서 classifier/embedding_query 호출이 0회인지 확인한다. 프로젝트 없는 일반 채팅도 포함한다.

### 10.3 동시성·복구 검증: 후속 구현

단일 프로세스의 Promise 병렬 검사만으로 전역 상한을 검증하지 않는다. 같은 임시 DB에 **실제 자식 워커 프로세스 여러 개**를 연결하고 가짜 공급자에서 진행을 멈출 수 있게 한다.

- N=2 예시에서 워커 수와 대기 작업을 늘려도 소유한 실행 슬롯과 정상 실행 작업이 2개를 넘지 않는지 확인한다.
- 같은 job을 동시에 claim해도 한 소유자만 성공하며, 산출물의 후보 조회와 실행 사이 경쟁도 검사한다.
- 작업 중 워커 강제 종료, lease 만료, 이전 워커 재개를 주입한다. 새 소유자의 저장/발행이 이전 토큰으로 오염되지 않아야 한다.
- 진행 중 Responses ID는 재조회하고 생성 POST를 중복하지 않는다. 외부 결과 미확인 상태의 한계와 회수 유예를 검증한다.
- 예산 대기가 lease보다 길어져도 heartbeat와 중지가 동작해야 한다. 중지 요청과 review 대기는 생성 슬롯 부족 때문에 멈추지 않아야 한다.
- 상한 축소·워커 재기동·DB 일시 장애에서 슬롯 누수·무제한 재획득·대기 작업 유실이 없어야 한다.

### 10.4 공통 API 예산 검증: 후속 구현

가짜 시계와 모의 공급자를 사용해 창 경계·burst·토큰 예약/정산을 검증하고, 실제 공유 DB를 사용하는 다중 프로세스 검사도 수행한다.

- 같은 키를 서로 다른 프로젝트에 등록해도 합산한다. 서버 키와 프로젝트 키가 같을 때도 매핑된 동일 범위를 공유한다.
- 공용 키를 쓰는 채팅·분류·가드레일·산출물·이미지와 models/poll/cancel 호출이 공통 제어를 통과하는지 확인한다.
- RPM·TPM 동시 충족과 단일 요청 용량 초과를 검증한다. 공급자 측에서 본 실제 전송 횟수를 기준으로 확인한다.
- 429 + `Retry-After`, 503, timeout, 불완전 사용량, 취소, 재시도를 주입해 이중 재시도·즉시 재폭주·미확인 사용량의 0 정산이 없는지 확인한다.
- poll/cancel을 위한 여유와 일반 채팅 대기 한도를 확인한다. 예산 부족 시 저장·생성 API가 클라이언트에서 자동 재시도되지 않아야 한다.
- 로그·DTO·오류·테스트 결과에 키·암호문·원문 입력이 추가 노출되지 않는지 확인한다.

### 10.5 기존 회귀와 운영 지표

후속 구현에서는 `pnpm test:project-rag`, `pnpm test:ai-settings-reviews`, `pnpm test:ai-tool-execution`, `pnpm test:deliverable-background`, `pnpm test:deliverable-generation`, `pnpm test:dashboard`, `pnpm test:workspace-plan`, `pnpm test:query-audit`를 변경 범위에 맞춰 수행한다. 브라우저 회귀는 기존 스크립트를 활용하거나 필요한 시나리오를 보강한다. 타입·lint 검사도 수행한다. 모든 DB/공급자 검사는 격리 환경을 사용하고 운영 DB를 테스트 대상으로 삼지 않는다.

운영에서는 종류별 대기 건수·최장 대기·대기시간 p95, 실행 슬롯 점유·회수, heartbeat 지연, DB claim 지연/락 충돌, API 예산 대기, 공급자 429·오류율, 호출별 실제 사용량과 미확인 건수를 관찰한다. 현재 사용자 화면에는 ‘대기 중’, ‘벡터화 중’, ‘중지 요청 중’ 등 의미 있는 상태를 제공하고 내부 슬롯·DB 식별자는 노출하지 않는다.

## 11. 구현 순서와 배포 고려사항

1. 9절의 권한 범위·owner 의미와 상한 범위를 확정한다.
2. Business owner 공통 정책과 일반 채팅 분기, 양쪽 UI/DTO를 함께 구현·검증한다.
3. 기존 워커를 운영 웹과 독립 배포하도록 정리한다.
4. 공유 실행 슬롯 스키마와 원자 claim·복구를 추가한다.
5. 공통 API 제어를 모든 실제 공급자 호출에 연결하고 사용량 예약·복구를 검증한다.
6. 낮은 상한으로 시작해 지표를 관찰한다. 청크 공정 배분과 전용 큐는 관찰 결과에 따라 후속 설계한다.

공유 제한을 따르지 않는 구버전 워커가 섞여 있으면 상한을 보장할 수 없다. 구현 배포에서는 기존 워커의 신규 claim을 중지·정리한 뒤 신규 스키마와 모든 호출자 버전을 맞추고 워커를 시작하는 절차를 마련한다. 웹의 직접 호출 경로도 함께 전환한다. 롤백 시 작업·청크·키·검색본·사용량 이력을 삭제하지 않으며, 구버전이 제한을 우회할 수 있으므로 워커와 호출자 트래픽을 제어한 상태에서 진행한다.

이번 단계의 산출물은 이 설계 문서와 이력 링크다. 실제 권한 변경, 워커 실행 구성 변경, API 제한 설정, DB 스키마 추가·적용은 사용자 검토 및 후속 구현 요청 이후의 작업이다.
