# 제안요청서 작성 탭 신설 분석 및 설계

- 작성일: 2026-10-30 (한국시간)
- 상태: 검토용 설계안
- 대상: 프로젝트 작업 공간의 제안요청서 작성 화면
- 이번 작업: 현재 소스 분석, 설계 문서 작성, HISTORY.md 링크 추가
- 소스 변경·DB 변경·마이그레이션·구현은 수행하지 않는다. 사용자가 문서를 검토·수정한 뒤 요청할 구현의 기준으로 사용한다.

## 1. 요구사항과 목표

프로젝트의 `개요` 바로 다음에 `제안요청서` 탭을 추가한다. 탭을 누르면 사업의 배경·범위·요구사항·제안 안내 등을 직접 작성하고 전체 내용을 읽어볼 수 있는 화면을 제공한다.

핵심은 파일을 업로드하는 문서함이나 요구사항 목록을 하나 더 만드는 것이 아니라, **문서의 구성을 보면서 내용을 항목별로 작성하고 완성된 제안요청서를 확인하는 작업 공간**이다.

| 목표 | 화면에서 제공할 방법 | 확인 기준 |
| --- | --- | --- |
| 가시성 | 목차, 현재 작성 위치, 항목별 작성 상태, 미작성 항목 수 표시 | 작성 위치와 남은 항목을 화면에서 확인할 수 있다. |
| 직관성 | 목차 선택 → 해당 내용 작성 → 전체 미리보기의 일관된 흐름 | 별도 사용법 없이 제목·본문·요구사항을 수정할 수 있다. |
| 가독성 | 제목 계층, 적절한 본문 폭과 줄 간격, 표와 목록, 읽기 전용 미리보기 | 긴 문서에서도 제목과 내용을 쉽게 구별할 수 있다. |
| 프로젝트 일관성 | 기존 탭·프로젝트 선택·권한·테마 사용 | 새 탭에서 기존 프로젝트와 다른 데이터가 표시되지 않는다. |

### 범위 제안

우선 샘플 화면으로 작성 경험을 검토한 다음 실제 저장 기능을 붙이는 순서를 권장한다. 샘플 우선 여부는 구현 전 결정 사항이며, 이번 문서 작성으로 구현 범위가 확정되는 것은 아니다.

- 1차 샘플: 탭 연결, 샘플 문서, 목차 이동, 항목별 편집, 작성 현황, 전체 미리보기, 샘플 초기화.
- 후속 실제 서비스: 서버 저장·재조회, 버전 충돌 처리, 변경 이력, 요구사항 연결, 파일 내보내기.
- 별도 확장: AI 초안 생성, 기존 RFP 파일 분석·가져오기, 다중 문서·버전 관리, 검토·승인 절차.

## 2. 현재 소스 구조와 분석 결과

### 2.1 탭 정의와 라우팅

| 현재 파일 | 확인한 구조 | 설계에 미치는 영향 |
| --- | --- | --- |
| `lib/project-tabs.ts` | `ProjectTab` 타입과 `projectTabLabels`에서 탭 정의. 현재 순서는 개요 다음 WBS 일정이다. | `rfp` 타입을 추가하고 라벨의 `overview` 바로 뒤에 `rfp: "제안요청서"`를 배치한다. |
| `components/project-workbench.tsx` | `Object.keys(projectTabLabels)`로 탭을 렌더링하고 `pages: Record<ProjectTab, ComponentType>`로 화면을 선택한다. | 탭 타입·라벨·화면 매핑을 함께 추가해야 한다. |
| 같은 파일 | `?tab=`을 해석하고 `window.history.pushState`로 탭 URL을 변경한다. `ProjectContent`에서 `<Page />`를 렌더링한다. | 기존 패턴대로 `/projects/{projectId}?tab=rfp`를 사용한다. 별도 페이지 라우트는 기본적으로 필요 없다. |
| `app/(workspace)/projects/[projectId]/page.tsx` | 로그인·온보딩 확인 후 `ProjectWorkbench`에 프로젝트 ID 전달. | 새 탭만 추가한다면 이 파일의 변경은 필요하지 않다. |
| `components/workspace-shell.tsx` | 공통 탭 라벨을 이용해 현재 프로젝트 탭과 경로를 해석한다. | 제안요청서 경로·표시가 자연스럽게 반영되는지 확인한다. 탭명 하드코딩을 늘리지 않는다. |

### 2.2 프로젝트 데이터와 편집 권한

- `components/shared/use-project-data.ts`에서 프로젝트 목록과 `/api/projects/{projectId}/artifacts` 응답을 조회한다.
- `components/shared/project-page-context.tsx`의 `useProjectPage()`로 `user`, `data`, `artifacts`, `selectTab` 등을 사용한다.
- `lib/artifacts.ts`에서 프로젝트 역할 `owner`, `admin`, `member`에 대해 `canWrite`를 제공한다.
- `ProjectContent`는 `key={model.projectId}`로 프로젝트별로 구분된다. 프로젝트를 바꾸면 기존 페이지 상태가 유지된다고 가정할 수 없다.
- 제안요청서 화면의 편집 가능 여부는 사용자 전역 역할만으로 판단하지 않고 `data.canWrite`를 따른다.

### 2.3 기존 제안요청서 관련 요소

- `components/pages/project-overview/project-traceability.tsx`에는 `rfp`라는 제안요청서 노드와 WBS·요구사항으로 이어지는 연결이 있다.
- 이 관계도는 파일 안의 고정 노드·연결 데이터를 사용하며, 노드 선택은 관계도 내부 선택 상태를 바꾼다. 실제 RFP 문서나 작성 탭을 조회하는 구조는 아니다.
- `components/pages/project-overview/integration-overview.tsx`가 해당 관계도를 개요에 표시한다.
- `lib/artifact-types.ts`의 요구사항 필드에 `source`와 `sourceId`가 있고, `sourceId`의 라벨은 `원본 요구사항 번호 (RFP)`다.
- 현재 `ArtifactKind`는 WBS·아키텍처·요구사항·화면·DB·프로그램·검증으로 구성되며 RFP는 포함하지 않는다. 확인한 탭·타입 정의에는 제안요청서 전용 구조가 없다.

### 2.4 문서함과의 관계

`components/pages/documents/documents-page.tsx`는 폴더·파일 조회, 업로드, 이름 변경·삭제 등을 처리한다. `onlyoffice-editor.tsx`도 별도 문서 관련 컴포넌트로 존재한다.

제안요청서 작성은 구조화한 사업 정보와 요구사항을 편집하는 기능으로 설계한다. 문서함의 파일 관리 화면을 그대로 재사용하는 방식은 작성 항목 안내·작성률·요구사항 연결을 구현하기에 맞지 않는다. 필요하면 후속 단계에서 작성 결과 파일을 문서함과 연결한다.

편집기 관련 패키지가 설치되어 있다는 사실만으로 현재 재사용 가능한 공통 편집기가 있다고 보지는 않는다. 1차에서는 기존 React 입력 컴포넌트·목록·표 중심으로 구성하고, 리치 텍스트 편집기의 필요성은 별도로 결정한다.

### 2.5 스타일 및 AI 연관 범위

- `components/project-workbench.css`는 탭·입력 컨트롤을 공통 정의하고, 개요 외 탭에는 `matrix-tab-content-compact` 스타일을 적용한다.
- 새 작성 화면은 공통 테마를 따르되 본문·제목의 글자 크기를 독립적으로 정할 필요가 있다. 공통 compact 규칙의 우선순위도 확인해야 한다.
- `lib/ai-context.ts`와 `lib/ai/page-prompts.ts`, `app/api/ai/chats/route.ts`에서도 공통 탭 정의를 참조한다.
- 탭이 추가되어 AI 화면 이름에 노출되는 것과 AI가 RFP 내용을 읽고 저장할 수 있는 것은 별개다. 샘플에서는 RFP 전용 저장 도구나 AI 생성 기능을 추가하지 않는 안을 권장한다.
- `app/guest/[...path]/page.tsx`도 공통 라벨로 게스트 프로젝트 메뉴·유효 경로를 생성한다. 새 탭 라벨 추가만으로 게스트 메뉴가 늘어날 수 있어 표시 정책을 확인해야 한다.

## 3. 화면 설계

### 3.1 기본 배치

```text
프로젝트 선택
개요 | 제안요청서 | WBS 일정 | 아키텍처 | 요구사항 | ...

제안요청서       문서명 / 초안 / 샘플 표시
필수 항목 8 / 12 작성                      [전체 미리보기]
────────────────────────────────────────────────────────
문서 목차                 선택한 항목 작성
1. 사업 개요              1. 사업 개요
   기본 정보              작성 안내 한 줄
   추진 배경              [사업명......................]
2. 추진 범위              [발주기관....................]
3. 세부 요구사항          [추진 배경....................]
4. 수행 및 관리           [............................]
5. 제안 안내
6. 평가 기준              [이전 항목]        [다음 항목]
7. 부록
```

기본 화면은 **왼쪽 목차 + 오른쪽 작성 영역**의 2단 구조로 한다. 작성 화면 옆에 전체 미리보기를 항상 세 번째 패널로 두면 편집 폭이 줄어들기 때문에, 기본안에서는 미리보기를 큰 모달로 연다.

### 3.2 상단 문서 정보와 동작

- 문서 제목, 초안 상태, 필수 항목 작성 수를 표시한다.
- 1차 샘플은 `샘플 · 서버에 저장되지 않습니다`를 명시한다.
- `전체 미리보기`는 실제 입력값으로 조합한 문서를 보여준다.
- 샘플 초기화는 변경이 있을 때 확인 후 초기 데이터로 되돌린다.
- 서버 저장을 구현하지 않은 단계에서 `저장 완료`, 실제 승인 상태, 실제 최종 저장 시각을 표시하지 않는다.
- 실제 서비스 단계에서는 `저장 중 / 저장됨 / 저장 실패 / 변경 사항 있음`을 실제 저장 결과에 따라 표시한다.

### 3.3 왼쪽 목차

- 권장 너비 220~240px. 현재 선택 항목을 배경과 텍스트로 함께 강조한다.
- 장 제목과 하위 항목을 구별하고, `미작성 / 작성 중 / 필수 입력 충족`을 표시한다.
- 상태는 색상뿐 아니라 텍스트·아이콘으로 구분한다. 입력 충족 상태를 검토·승인 완료로 표현하지 않는다.
- 목차 클릭 시 오른쪽 작성 내용이 전환된다. 입력값은 문서 전체 상태에 보존하여 항목 이동으로 사라지지 않는다.
- 1차는 고정 목차를 사용한다. 임의 장 추가·삭제·재정렬은 필요성이 확인된 뒤 확장한다.

### 3.4 오른쪽 작성 영역

- 선택한 장의 제목, 짧은 작성 안내, 라벨이 있는 입력 영역을 제공한다.
- 일반 정보는 짧은 입력, 서술형은 여러 줄 입력, 일정·평가는 행 목록 또는 표를 사용한다.
- 한 화면에 문서 전체의 모든 입력을 펼치지 않는다. 선택한 장의 작업에 집중할 수 있게 한다.
- 서술형 입력은 최소 높이와 적절한 줄 간격을 두고, 내용이 길어지면 확장한다.
- 필수값 표시는 라벨과 연결하고 오류는 해당 입력 가까이에 표시한다. placeholder만으로 라벨을 대신하지 않는다.
- 사업명·발주기관 같은 공통 정보는 문서 상태 한 곳에서 관리하여 표지와 본문에 다르게 반영되지 않게 한다.

### 3.5 권장 목차와 작성 항목

아래는 소프트웨어 프로젝트용 초기 템플릿 제안이다. 공식 양식이나 법적 의무 항목으로 취급하지 않으며 사업 유형에 맞게 사용자가 수정할 수 있다.

| 장 | 주요 항목 | 편집 방식 | 초기 필수값 제안 |
| --- | --- | --- | --- |
| 사업 개요 | 사업명, 발주기관, 사업기간, 예산, 배경, 목표 | 단문·날짜·금액·서술형 | 사업명, 발주기관, 배경, 목표 |
| 추진 범위 | 현황, 대상 사용자, 구축 범위, 제외 범위, 기대효과 | 서술형·목록 | 구축 범위 |
| 세부 요구사항 | 분류, 원본 번호, 제목, 설명, 세부 내용, 산출물, 검수 기준 | 목록 + 선택 항목 상세 | 요구사항 1건 이상 및 각 항목의 번호·제목·내용 |
| 수행 및 관리 | 단계별 일정, 주요 산출물, 수행조직, 품질·보안·위험·운영 지원 | 일정 표·목록·서술형 | 주요 일정, 주요 산출물 |
| 제안 안내 | 제출 문서, 제출 방법·기한, 문의처, 제안서 목차 | 항목형 입력·목록 | 초기에는 선택 |
| 평가 기준 | 평가 항목, 설명, 배점 | 편집 가능한 표 | 초기에는 선택 |
| 부록 | 용어, 참고자료 목록, 추가 설명 | 목록·서술형 | 선택 |

문서 제목은 초기에 `{프로젝트명} 제안요청서`로 제안한다. 사업기간·예산 등 확인되지 않은 사실은 자동 확정하지 않는다. 평가 배점 합계는 표시하되 합계 기준이나 공공 발주 규칙을 임의로 강제하지 않는다.

### 3.6 세부 요구사항 작성

- 장 안에서 요구사항을 추가·선택·수정·삭제할 수 있게 한다.
- 목록에는 원본 번호, 분류, 제목, 작성 상태를 표시한다.
- 상세에는 정의, 세부 내용, 산출정보, 검수 기준을 분리하여 작성한다.
- 기존 `requirementCategories` 분류를 초기 분류 후보로 재사용한다. 별도 분류 체계가 필요하면 명시적으로 매핑한다.
- 요구사항의 내부 고유 ID와 표시 번호를 분리한다. 삭제 후 배열 순서가 바뀌어도 참조 ID가 바뀌면 안 된다.
- `RFP-SFR-001` 같은 샘플 번호는 미리보기용 규칙 예시다. 실제 번호 발급 규칙은 후속 저장 설계에서 결정한다.
- 작성 장 내부에 또 다른 `요구사항` 탭을 만드는 대신, 원본 문서 작성과 기존 요구사항 정의 탭의 역할 차이를 안내한다.

### 3.7 전체 미리보기

- 문서 상태 하나를 공유해 제목·목차·본문·요구사항·표를 순서대로 조합한다.
- 모달 크기는 너비 `min(1100px, calc(100vw - 48px))`, 높이 최대 `calc(100dvh - 48px)`를 초기 기준으로 삼는다.
- 읽기 영역의 본문 폭은 약 760~860px, 본문 14px 안팎, 줄 간격 1.65~1.8을 권장한다. 테마·실제 해상도에 맞춰 조정한다.
- 긴 문서는 세로 스크롤을 허용한다. 읽을 수 있는 크기를 유지하며 문서 전체를 억지로 한 화면에 축소하지 않는다.
- 긴 표만 해당 영역에서 가로 스크롤한다. 화면 전체 가로 스크롤은 피한다.
- 닫기 버튼·Esc·초점 복귀를 지원한다. 모달을 닫아도 작성 중인 내용은 유지한다.
- 필수 항목이 비어 있어도 미리보기는 허용한다. 빈 항목은 미작성으로 표시해 문서 구성을 확인할 수 있게 한다.

### 3.8 반응형·테마·접근성

- 실제 콘텐츠 너비가 충분하면 2단, 좁아지면 목차를 상단 선택 목록이나 접을 수 있는 목록으로 바꾼다. 시작 기준은 콘텐츠 폭 약 900px로 검토한다.
- 작성 본문과 표에 `min-width: 0`을 적용하여 작업 공간을 밀어내지 않게 한다.
- 공통 CSS 변수 `--surface`, `--canvas`, `--ink`, `--muted`, `--line`, `--primary`를 사용한다.
- 새 CSS는 `.rfp-page`, `.rfp-preview` 등의 범위로 제한하고 전역 `button`, `input`, `p`, `table` 규칙을 추가하지 않는다.
- 공통 compact 스타일과 충돌하는 제목·본문·입력 크기만 RFP 범위에서 명시한다. 공통 스타일 전체를 바꾸지 않는다.
- 입력 라벨, 키보드 이동, 포커스 표시, 목차 현재 위치, 모달 제목을 제공한다. 아이콘은 기존 `lucide-react`를 사용한다.

## 4. 상태 및 데이터 설계

### 4.1 샘플 데이터 구조 제안

```ts
type RfpDraft = {
  schemaVersion: 1;
  id: string; // 샘플 내부 식별자. 서버 문서 ID로 취급하지 않는다.
  projectId: string;
  title: string;
  basic: {
    organization: string;
    startDate: string;
    endDate: string;
    budget: string;
    background: string;
    objectives: string;
  };
  scope: {
    currentState: string;
    targetUsers: string;
    included: string;
    excluded: string;
    expectedEffects: string;
  };
  requirements: RfpRequirementDraft[];
  delivery: RfpDeliveryDraft;
  proposalGuide: RfpProposalGuideDraft;
  evaluation: RfpEvaluationItemDraft[];
  appendix: RfpAppendixDraft;
};
```

`RfpRequirementDraft` 등의 하위 타입은 앞 절의 입력 항목에 맞춰 정의한다. 위 코드는 구조 예시이며 완성된 구현 타입은 아니다. HTML 전체를 문자열 하나로 저장하기보다 항목별 검증과 표시가 가능한 구조를 권장한다.

### 4.2 상태 관리와 화면 이탈

- 문서 전체 상태와 현재 선택 항목을 분리한다. 입력 화면·작성 상태·오류 목록·미리보기는 같은 문서 상태에서 계산한다.
- `ProjectWorkbench`는 탭마다 다른 페이지 컴포넌트를 표시하므로 페이지 내부 state만으로는 탭 이탈 시 내용을 유지할 수 없다.
- 초기안은 RFP 전용 메모리 저장소를 `workspaceId + userId + projectId` 단위로 관리한다. 탭을 왕복해도 샘플 편집은 유지하고, 다른 프로젝트 내용과 섞이지 않게 한다.
- 초기안에서는 새로고침·브라우저 종료 이후까지 보존하지 않는다. 보존 범위를 화면에 명시한다.
- `sessionStorage` 활용은 대안이며 키 분리·구조 버전·읽기 실패 처리를 설계한 뒤 채택한다. 브라우저 저장을 서버 저장으로 표시하지 않는다.
- 탭 이동 때마다 초기화되는 일회성 샘플도 가능하다. 원하는 보존 수준을 결정한 뒤 구현한다.

### 4.3 작성 상태와 검증

- `미작성`: 해당 항목에 입력된 내용이 없다.
- `작성 중`: 일부 내용이 있지만 필수값이 부족하다.
- `입력 완료`: 해당 항목의 필수값을 충족한다. 내용 검토나 승인을 의미하지 않는다.
- 작성률은 필수 항목 수를 분모로 계산한다. 공백만 입력한 값은 미입력으로 취급한다.
- 예산은 미정을 허용하고, 입력값이 있으면 음수나 잘못된 숫자를 확인한다. 사업기간 양끝이 입력되면 시작일이 종료일보다 늦지 않은지 확인한다.
- 원본 요구사항 번호 중복, 요구사항 필수값 누락, 잘못된 평가 배점을 확인한다.
- 샘플에서는 미입력 때문에 항목 이동을 차단하지 않는다. 오류 목록에서 해당 입력으로 이동할 수 있게 한다.

### 4.4 실제 저장 기능을 추가하는 경우

아래는 후속 단계의 방향이며 이번에는 테이블 추가나 DB 설계 확정을 하지 않는다.

- 초기 후보는 프로젝트별 독립 RFP 문서 리소스다. 화면 추가만을 위해 `ArtifactKind`부터 확장하지 않는다.
- `ArtifactKind` 추가는 유형별 정의·관리번호·검증·연결·통합 검수·집계·AI·출력에도 영향을 주므로 별도 평가한다.
- 독립 리소스의 API 후보는 `/api/projects/{projectId}/rfp`다. 문서 ID, workspace/project, 구조 JSON, schemaVersion, revision, 수정자·수정 시각을 저장하는 안이다.
- 서버에서도 권한을 검사한다. version/revision으로 충돌을 감지하여 다른 사용자의 수정을 조용히 덮어쓰지 않는다.
- 저장 실패 시 입력값을 유지하고 재시도를 제공한다. 자동 저장을 채택하면 연속 입력 처리, 저장 순서, 이탈 시 미저장 표시도 설계한다.
- 문서 개수, 버전 이력, 기존 변경 이력 통합 방법을 결정한 뒤 저장 구조를 확정한다.

## 5. 기존 기능과의 연계

### 요구사항 탭

RFP 요구사항은 발주 측 원문으로, 기존 요구사항 탭은 설계·구현·검증을 위해 구체화하는 관리 대상으로 구분한다. 후속 연계에서는 RFP 원본 번호를 기존 `sourceId`에 전달하고 `source`에 출처를 기록하는 안을 제안한다.

현재 문자열 필드만으로는 참조 정합성이나 원본 변경 후 미반영 상태를 보장할 수 없다. 실제 서비스에서는 안정적인 RFP 문서·요구사항 ID와 참조 버전 도입을 검토한다. 원문 변경으로 기존 요구사항을 자동 덮어쓰지 않는다. 1차 샘플에서는 기존 요구사항 등록 API를 호출하지 않는다.

### 개요 관계도

RFP 노드 선택과 화면 이동을 구별한다. 기존 선택·연결 관계 표시를 유지하면서, 후속 단계에 상세 영역의 `제안요청서 작성 화면 열기` 버튼을 추가할 수 있다. 1차 필수 변경에는 포함하지 않는다.

### AI·출력·게스트

- AI: 새 탭 라벨이 정상 해석되는지 확인한다. 전용 데이터 조회·저장을 구현하지 않은 단계에서 샘플 내용을 AI가 조회·저장한 것처럼 안내하지 않는다.
- 출력: 1차는 화면 전체 미리보기까지를 기본으로 한다. PDF·DOCX 출력, 기존 산출물 통합, 문서함 저장은 후속 범위다.
- 게스트: 공통 라벨 추가로 메뉴가 늘어나는 영향을 확인하고, 조회 전용 샘플 또는 기존 공통 안내 중 표시 방식을 결정한다. 편집과 데이터 갱신은 허용하지 않는다.

| 필수 항목·작성률 | 3.5절 제안을 초기값으로 사용 | 업무마다 조건이 다르므로 문서에서 항목을 조정한다. |
| 미리보기 | 큰 모달의 읽기 전용 문서 | 상시 나란히 보는 구성을 택하면 좁은 화면 전환도 설계한다. |
| 기존 요구사항 반영 | 1차 샘플에서는 연계하지 않음 | 대상 선택·중복 확인·원본 참조·업데이트 규칙이 필요하다. |
| AI 지원 | 1차에는 RFP 전용 기능 없음 | 부분 생성·교정·전체 생성의 범위와 저장 책임을 결정한다. |
| 출력·첨부 | 1차는 화면 미리보기만 제공 | PDF·DOCX·인쇄·문서함 연계·첨부 보관 위치를 추가 검토한다. |
| 개요 RFP 이동 | 선택적으로 추가 | 추가하더라도 기존 노드 선택 동작은 유지한다. |
| 게스트 표시 | 공통 안내로 조회 경로 유지 | 전용 조회 샘플을 제공하려면 게스트 페이지에도 분기가 필요하다. |

## 9. 권장 구현 순서

1. 사용자가 이 문서의 목차·필수 항목·샘플 보존 범위를 검토하고 수정한다.
2. 탭 정의와 샘플 페이지를 추가하고 개요 직후 표시·URL 전환을 확인한다.
3. 목차·사업 정보·장별 입력·요구사항 편집을 구현한다.
4. 작성 상태·검증·전체 미리보기를 구현한다.
5. 좁은 화면·테마·조회 권한·탭 이탈을 확인하고 샘플을 검토한다.
6. 검토 결과에 따라 실제 저장·버전 관리·기존 요구사항 연계·출력을 후속 단계로 구현한다.

이 문서는 검토용 제안이며 사용자가 수정한 내용을 다음 구현 지시의 기준으로 우선한다.
