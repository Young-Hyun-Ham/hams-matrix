# 요금제 명칭 변경 및 팀공유 옵션 분석·설계

- 작성일: 2026-11-05 (한국시간, Asia/Seoul)
- 상태: 검토용 설계 초안. 사용자 검토·직접 수정 후 별도 구현 요청 시 적용한다.
- 분석 기준: 현재 저장소의 소스와 SQL 마이그레이션. 운영 DB의 실제 값은 조회하지 않았으며, 아래 초기 가격·한도는 마이그레이션의 시드 기준이다.
- 이번 작업 범위: 이 문서 신규 작성과 `HISTORY.md` 링크 추가만 수행한다. 소스, SQL, DB, 실행 환경 설정은 변경하지 않는다.
- 구분: **확정 요구사항**은 사용자 요청이며, **권장안**과 **결정 필요** 항목은 아직 확정되지 않은 구현 제안이다.

## 1. 요구사항

| 구분 | 확정 요구사항 | 완료 기준 |
| --- | --- | --- |
| R1 | 기존 Free / Plus / Pro / Business 중 Plus를 Pro, 기존 Pro를 Team으로 변경 | 사용자에게 보이는 요금제가 Free / Pro / Team / Business 순서로 표시된다. 기존 두 상품의 가격·한도·구독 대응이 서로 뒤바뀌지 않는다. |
| R2 | 관리자설정의 요금제 탭에 요금제별 팀공유 체크 옵션 추가 | 각 요금제에서 독립적으로 체크·해제하고 저장·재조회할 수 있다. |
| R3 | 팀공유 가능한 요금제를 사용할 때만 팀공유 메뉴 표시 | 서버에서 조회한 요금제 옵션을 기준으로 메뉴가 표시되며, 미지원 요금제에서는 메뉴와 메뉴 검색 결과에 나타나지 않는다. |
| R4 | 이번 단계는 분석·설계 문서만 작성 | 구현 파일과 DB 변경 없이 설계 문서 및 HISTORY 링크만 추가한다. |

상품명 변경 자체가 가격, 사용량, 프로젝트 개수, 추천 여부 변경을 의미하지 않는다. 팀공유의 초기 체크 상태, 직접 URL·API 접근 제한 여부, 초대받은 회원의 이용 자격은 사용자 요청만으로 확정할 수 없으므로 8절에서 결정한다.

### 2.4 재사용 API와 레거시 모델

1. `components/pages/dashboard/create-project-dialog.tsx`도 프로젝트 ID 없이 `GET /api/team/members`를 호출한다. 현재 이 API가 실패하면 생성 폼 제출이 막히므로 `/api/team/*`를 일괄 차단할 수 없다.
2. `app/api/projects/route.ts`의 프로젝트 생성은 `memberIds`로 다른 회원을 함께 등록할 수 있다. 팀공유를 실제 협업 기능의 이용 자격으로 제한하려면 이 우회 경로도 범위를 결정해야 한다.
3. `app/api/team/requests/route.ts`는 owner의 승인·거절과 신청자의 상태 조회를 함께 제공한다. 미지원 회원도 신청 상태를 계속 확인하게 할지 별도 결정이 필요하다.
4. 댓글 API에는 `project_id`가 없는 과거 게시글 처리 분기가 있다. 프로젝트 소유자 기준 옵션을 선택한다면 이런 데이터의 판정 기준도 필요하다.
5. `001_identity_audit.sql`의 `workspaces.plan`은 `free/pro/business`, `004_registration_teams.sql`의 `workspaces.subscription_plan`은 `free/team/business`다. 이들은 현재 회원 카탈로그의 코드 체계와 다르다.
6. `lib/registration.ts` 타입과 과거 가입 선택 컴포넌트에 `team`이 남아 있으나, 실제 `registrationChoice()`는 user/Free 신규 가입만 허용한다. `scripts/upgrade-accounts.mjs`도 레거시 유료 워크스페이스를 별도로 검사한다. 기존 `team` 문자열을 새 상품 코드로 일괄 해석하거나 변환하지 않는다.

## 3. 요금제 명칭 변경 방향

### 3.1 권장안 A: 내부 코드를 유지하고 표시명 변경

요청이 “명칭 변경”이므로 `plans.name`만 `plus → Pro`, `pro → Team`으로 변경하는 안을 권장한다. 내부 코드는 계속 `free / plus / pro / business`이며, 사용자 표시는 `Free / Pro / Team / Business`가 된다.

- 적용 대상은 **기존 코드별로** 지정한다. 표시명 문자열을 순차 치환하면 새 Pro까지 Team으로 바뀌는 오류가 생길 수 있다.
- 기존 Plus 구독자는 동일한 `plus` 구독으로 Pro를 이용하고, 기존 Pro 구독자는 동일한 `pro` 구독으로 Team을 이용한다. 월/연 가격, 할인 가격, 제공량, 청구 주기, 추천 표시, 사용량은 유지한다.
- `listPlans()`의 현재 코드별 정렬은 그대로 표시 순서와 맞는다. 외부 요청의 `plan`, `currentPlan`, 관리자 회원 필터 value도 현재 코드를 유지한다.
- 요금제 카드·관리자 요금제 제목 외에 회원 관리의 코드 직접 표시를 제거한다. API가 `plan`(코드)과 `planName`(카탈로그 표시명)을 별도로 제공하고, select는 코드 value/표시명 label을 사용하도록 한다. 옵션 목록은 카탈로그에서 얻어 이름을 여러 곳에 하드코딩하지 않는 안을 권장한다.
- 구독이 없는 회원의 기존 “구독 정보 없음” 처리를 유지한다. 알 수 없는 코드를 임의의 유료 상품으로 매핑하지 않는다.
- 감사 로그의 과거 코드/JSON은 원본을 보존한다. 코드가 남는 운영 이력에는 필요 시 현재 명칭과 코드를 함께 표시하고, 과거 표시명과 현재 표시명을 구분한다.

표시명과 코드가 다른 점은 운영자·개발자 문서에 명시한다. 예를 들어 새 Pro를 선택할 때 API로 `plus`가 전달되는 것은 이 안에서 정상이다.

### 3.2 대안 B: 내부 코드도 free / pro / team / business로 변경

제품·외부 연동에서 코드와 명칭 일치가 필요하다면 별도 데이터 이관 작업으로 선택한다. A와 B를 동시에 적용하는 방식은 아니다.

- 매핑은 **old `plus` → new `pro`**, **old `pro` → new `team`**이다. 현재 `pro` 키와 충돌하므로 단순 UPDATE 두 번으로 처리할 수 없다.
- `plans.code` CHECK를 새 체계로 바꾸고 `user_subscriptions.plan_code` 외래키, 인덱스, 기본 구독 트리거 등 실제 참조를 보존하는 테이블 재구성/이관 절차를 설계한다. 기존 `pro` 구독을 먼저 식별한 원본 매핑으로 변환한다.
- `PlanCode`, `listPlans()` 정렬, 구독 변경 API와 관리자 회원 API의 코드 허용 목록, 관리자 필터·select, 관련 테스트와 fixture를 함께 변경한다.
- 구버전 클라이언트의 `pro` 요청은 기존 Pro인지 새 Pro인지 구분할 수 없다. `pro`를 무조건 호환 alias로 받지 않고, 배포 시 클라이언트 재로딩·버전 확인 또는 명시적인 API 버전 전략을 정해야 한다.
- 과거 로그 JSON은 다시 쓰지 않는다. 필요하면 이관 시점·스키마 버전을 사용해 과거 코드를 설명한다. 레거시 워크스페이스 플랜과 회원 플랜의 매핑도 별개로 취급한다.
- 가격/할인/한도/추천/버전/구독자 수 보존, 외래키 검사, 충돌 시 롤백, 구버전 코드 배제 검증이 추가된다.

**구현 전 A/B 중 하나를 확정한다. 이하 기본 설계는 A를 기준으로 한다.**

## 4. 팀공유 옵션 데이터·관리자 저장 설계

### 4.1 데이터 모델과 초기값

| 계층 | 제안 이름 | 타입·규칙 |
| --- | --- | --- |
| DB `plans` | `team_sharing_enabled` | `INTEGER NOT NULL DEFAULT 0 CHECK(team_sharing_enabled IN (0,1))` |
| `Plan` DTO | `teamSharingEnabled` | 필수 boolean, `toPlan()`에서 DB의 1만 true로 변환 |
| 인증 사용자 DTO | `teamSharingEnabled` | 현재 회원의 실제 구독 카탈로그에서 조회한 boolean. 클라이언트는 표시 용도로만 사용 |
| 관리자 폼 | `teamSharingEnabled` | “팀공유” 체크박스, `defaultChecked`는 저장된 옵션 |
| 관리자 PATCH | `teamSharingEnabled` | JSON boolean만 허용. 문자열·숫자·null·누락은 400 처리하는 엄격 검증안 |

새 순번 마이그레이션을 추가한다. 현재 마지막은 `033_planning_project_templates.sql`이므로 구현 시 다음 사용 가능한 번호를 확인한다. 적용된 `020` 등 과거 마이그레이션은 수정하지 않는다.

권장 초기값 후보는 다음과 같다. **사용자 승인이 필요한 정책이며 이번 단계에서 적용하지 않는다.**

| 새 표시명 | A안 내부 코드 | 팀공유 초기값 후보 |
| --- | --- | --- |
| Free | `free` | 해제 |
| Pro | `plus` | 해제 |
| Team | `pro` | 체크 |
| Business | `business` | 체크 |

옵션은 네 요금제 모두 관리자가 변경할 수 있다. 이름이나 유료 여부로 자동 판정하지 않는다. 현재는 Free도 메뉴·API에 접근할 수 있어 위 후보를 적용하면 기존 일부 사용자의 메뉴가 사라진다. 기존 이용자 예외 유지가 필요한지 먼저 확인한다.

### 4.2 관리자 저장 흐름

1. `PlanAdmin`에 기존 이력 생성/추천 체크와 같은 형태로 팀공유 체크를 추가한다. 폼 전송 시 `form.has("teamSharingEnabled")`로 값을 만든다.
2. 관리자 PATCH의 boolean 검증과 UPDATE에 필드를 포함한다. origin 검사, master/admin 권한, 기존 가격/한도 검증, 충돌 응답은 유지한다.
3. 기존 `version`과 일치할 때만 저장하고 `version=version+1`, 수정자/수정 시각 갱신을 수행한다. 옵션만 바꾸어도 버전을 올려 오래된 요금제 선택 요청을 409로 처리한다.
4. 동일 트랜잭션에 옵션을 포함한 변경 전후 로그를 저장한다. `lib/admin-history.ts`의 허용 키에도 `teamSharingEnabled`를 추가한다. 과거 로그에 값이 없는 경우에는 미기록으로 취급한다.
5. 반환된 `plans`로 관리자 폼을 갱신한다. 기존 `code-version` key에 따라 체크 초기값이 새 서버 값으로 재생성된다.
6. 표시명 변경과 초기 옵션 설정을 수행하는 마이그레이션에서도 대상 요금제의 버전을 갱신한다. 기존 수정자 이력을 임의의 일반 사용자로 덮어쓰지 않고, 배포 변경임을 추적할 방법을 정한다.

엄격 검증안은 구버전 관리자 폼이 새 필드를 보내지 않으면 저장에 실패한다. 배포 후 새로고침 안내가 필요하며, 혼합 버전 운영이 필수라면 “누락 시 기존 값 유지”를 별도 호환 정책으로 선택한다. 누락을 false로 간주해 설정을 지우면 안 된다.

## 5. 팀공유 메뉴와 권한 판정 설계

### 5.1 메뉴 표시 기준과 상태 전달

**권장 기준은 로그인한 회원 본인의 구독 옵션이다.** 현재 구독이 회원별로 관리되고 사용자 요청도 “해당 요금제를 사용할 경우”이므로 이 구조에 맞춘다. 팀/프로젝트 소유자가 유료이면 초대받은 Free 회원도 이용할 수 있어야 한다면 8절의 다른 정책을 선택해야 한다.

```text
user_subscriptions.plan_code → plans.team_sharing_enabled
  ├─ 서버의 현재 사용자 DTO → WorkspaceShell / 메뉴 검색 / 알림 안내
  └─ 서버의 기능 검사 → 직접 화면·API 접근(정책 확정 시)
```

- `lib/auth.ts`의 공통 사용자 조회에서 실제 회원 구독에 대응하는 옵션을 함께 조회하고 `toUser()`/`User`에 포함하는 안을 권장한다. 워크스페이스 전환, 로그인, `/api/me` 조회 등도 같은 DTO를 사용한다.
- `WorkspaceShell`의 공통 필터는 기존 전역 관리자 메뉴 조건에 `team` 항목의 `teamSharingEnabled === true`를 추가한다. 데스크톱/모바일 및 메뉴 검색에 같은 결과를 사용한다.
- 메뉴 정의 자체를 삭제하거나 플랜 이름/코드 비교를 하드코딩하지 않는다. 관리자 체크만으로 Free의 팀공유도 활성화할 수 있어야 한다.
- 별도 `/team` 알림 링크와 viewer 안내는 같은 옵션으로 표시한다. 미지원 상태에서는 접근할 수 없는 메뉴로 안내하지 않는다.
- `master/admin`은 요금제 설정 권한을 유지하되 팀공유 이용 자격은 본인 요금제를 따른다는 안을 권장한다. 운영자 우회는 자동으로 추가하지 않는다.
- 구독 정보 누락·조회 장애 때 true를 추정하지 않는다. API는 기존 오류 정책에 따라 구독 확인 오류를 반환하고, 화면은 오류/재시도 상태를 제공한다.

### 5.2 직접 URL·API 접근: 별도 확정이 필요한 권장 확장

확정 요청은 “메뉴 표시”다. 기능 자체를 요금제로 제한할 목적이라면 메뉴 숨김 외에 다음 서버 검사를 함께 적용하는 안을 권장한다. **직접 접근을 허용할지, 기능도 제한할지는 8절에서 확정한다.**

| 대상 | 기능 제한안의 처리 |
| --- | --- |
| `/team` | 서버에서 현재 옵션 검사. 미지원이면 `/settings/subscription`으로 안내/이동하고 “현재 요금제에서는 팀공유를 사용할 수 없습니다” 표시. 팀 화면을 먼저 렌더링하지 않는다. |
| 팀 게시글·댓글 GET/POST | 기능 검사 후 기존 워크스페이스/프로젝트 역할 검사. 미지원 403, 비로그인 401. 쓰기는 같은 트랜잭션 안에서 현재 옵션 재검사. |
| 프로젝트별 팀원 GET, 구성원 추가·변경/소유권 이전 | 기능 검사와 기존 프로젝트 역할 검사 모두 통과해야 한다. 옵션 true여도 다른 프로젝트나 다른 워크스페이스에 접근할 수 없다. |
| 팀 가입 신청 GET/PATCH | 승인·거절 제한과 신청자 상태 조회 예외를 분리해 결정. 상태 조회를 예외로 둘 경우 요금제와 무관하게 접근할 별도 UI가 필요하다. |
| `GET /api/team/members`의 프로젝트 ID 없는 호출 | 개인 프로젝트 생성과 공유되므로 일괄 403 처리하지 않는다. 기능 제한안에서는 미지원 회원에 본인만 반환하고 `canAdd=false`로 응답하는 예외를 권장한다. |
| `POST /api/projects` | 개인 프로젝트 생성은 허용. 미지원 회원이 본인 외 `memberIds`를 전송하는 것은 기능 제한안에서 403 처리하고 UI에서도 팀원 선택을 숨긴다. |
| `/api/projects/[projectId]/permissions` | 팀 화면 외 직접 호출이 가능하다. 팀 권한 설정까지 기능 제한 대상으로 확정하면 같은 기능 검사 추가. 일반 프로젝트 산출물 접근과는 구분한다. |

공통 서버 검사는 `lib/plans.ts`에 `assertTeamSharingEnabled(userId, executor)` 같은 함수로 모으고 실제 DB를 읽는다. 인증 사용자 DTO나 클라이언트가 보낸 boolean만으로 권한을 승인하지 않는다. `projectAccess()` 등 모든 산출물 경로에 일괄 삽입하지 않는다.

이 표의 멤버 조회 예외·프로젝트 생성 제한은 **API까지 제한하는 안을 선택할 때 필요한 부수 변경**이다. 메뉴 표시만 변경한다면 기존 API·개인 프로젝트 생성 동작은 유지하고, 숨겨진 메뉴의 URL/API를 직접 호출하면 기존 권한으로 접근할 수 있음을 명시한다.

### 5.3 기존 역할, 다른 요금제 회원, 변경 후 데이터

- 팀공유 활성화는 기능 이용 자격이며 기존 프로젝트 역할의 대체가 아니다. viewer는 조회, owner/admin/member는 기존 허용 범위의 작업만 수행한다.
- 본인 요금제 기준에서는 프로젝트 owner가 Team이어도 Free 참여자는 옵션이 false라면 팀 화면을 사용할 수 없다. 반대로 본인이 활성 요금제여도 참여하지 않은 프로젝트에는 접근할 수 없다.
- 옵션 해제/미지원 요금제로 변경해도 게시글, 댓글, 구성원, 프로젝트, 신청, 사용량을 삭제하거나 자동 탈퇴시키지 않는다. 재활성화하면 기존 역할에 따라 다시 접근한다.
- 개인 프로젝트/산출물과 이미 참여한 프로젝트의 일반 작업까지 제한하는 것은 별도 범위다. 이번 요구에서 자동으로 확장하지 않는다. 따라서 기능 제한안을 적용하더라도 “팀공유 화면·관리 기능 제한”인지 “모든 공동 작업 제한”인지 구분해야 한다.
- 프로젝트/워크스페이스 owner 기준을 택하면 프로젝트별 가용성, 메뉴의 “접근 가능한 공유 프로젝트 하나 이상” 기준, 프로젝트 없는 과거 글 및 가입 신청 처리까지 다시 설계해야 한다. 기존 `projectHistoryEnabled()`의 소유자 구독 조회 패턴은 참고할 수 있으나 그대로 혼용하지 않는다.

### 5.4 요금제·관리자 옵션 변경의 반영 시점

- 본인 요금제 변경은 기존 `SubscriptionPlans`의 성공 후 `router.refresh()`를 유지하고, 서버 사용자 DTO와 `stores/workspace.ts` 상태가 함께 갱신되도록 한다. shell의 오래된 사용자 상태로 메뉴가 다시 나타나지 않아야 한다.
- 관리자에 의한 본인/다른 회원 구독 변경과 옵션 저장 후에도 해당 화면의 사용자 DTO를 다시 확인한다. 클라이언트 상태만 변경하고 서버 검사를 생략하지 않는다.
- 다른 세션·탭에서의 관리자 변경까지 즉시 푸시하는 구조는 현재 없다. 권장 기본은 변경 당사자 화면은 저장 직후 갱신하고, 다른 세션은 새 진입/새로고침 및 창 재활성화 시 `/api/me` 재조회로 갱신하는 것이다.
- 기능 제한안에서는 UI가 아직 갱신되지 않았어도 다음 보호 API 호출은 최신 DB로 판정한다. 옵션이 해제되어 403이 반환되면 작성 중 폼의 자동 재전송을 중지하고 요금제 안내와 사용자 상태 갱신을 수행한다.
- 창 재활성화 재조회가 없다면 열린 탭의 메뉴가 오래 남을 수 있다. 이를 허용할지, 주기적 재조회까지 필요한지 반영 시점 요구를 확정한다. 사용자별 응답은 기존 `no-store` 정책을 유지한다.

A안에서는 `PlanCode`, API 코드 허용 목록, 레거시 워크스페이스 플랜, `scripts/upgrade-accounts.mjs`를 명칭 변경 때문에 수정할 필요가 없다. B안 선택 시 이들을 별도 영향 대상으로 다시 확장한다. 아이콘 이름 `plus`, 문장 속 영어 plus 등 상품과 무관한 문자열도 치환하지 않는다.

## 7. 검증 방법 및 향후 적용 순서

### 7.1 인수·회귀 검증표

| 영역 | 검증 시나리오 | 기대 결과 |
| --- | --- | --- |
| 명칭/정렬 | 관리자 요금제, 회원 요금제, 게스트 요금제, 회원 목록·상세·필터·선택/확인 모달 확인 | Free / Pro / Team / Business 표시. 기존 Plus 구독과 기존 Pro 구독이 각각 올바르게 대응 |
| 데이터 보존 | 기존 DB 사본에서 이름·옵션 마이그레이션 전후 비교 | 가격·할인·한도·추천·청구 주기·구독·사용량·이력 보존. 활성 구독자의 의도하지 않은 상품 이동 없음 |
| 옵션 저장 | 4개 요금제 각각 체크/해제 후 저장·새로고침 | 해당 요금제의 옵션만 변경되고 체크 상태 유지 |
| 입력 검증 | boolean 대신 문자열/숫자/null/누락 요청 | 엄격안 400. 호환안 선택 시 누락만 기존 값 유지. 비관리자 403, origin 검사 유지 |
| 동시 수정 | 같은 version으로 관리자 2명이 저장 | 첫 저장 성공, 두 번째 409. 옵션 변경 뒤 오래된 planVersion으로 구독 변경 시 409 |
| 감사 이력 | 옵션만 변경하고 이력 상세 조회 | 변경 전후 boolean과 행위자 확인. 구 로그에 값이 없어도 오류 없음 |
| 메뉴 | 모든 요금제에서 옵션 true/false를 각각 시험 | true만 표시. Free도 true면 표시, Team도 false면 숨김. 모바일·검색·알림 진입점 일치 |
| 사용자 상태 | 본인 요금제 변경, 관리자 구독 변경, 옵션 변경, 다른 탭 복귀, 재로그인 | 정해진 갱신 시점에 메뉴 반영. 활성 워크스페이스 변경으로 본인 옵션이 타인 값으로 바뀌지 않음 |
| 직접 접근 | 미지원 요금제의 `/team` 및 보호 API 직접 호출 | 기능 제한안에서는 화면 안내/이동, API 403. 메뉴만 변경하는 안이면 기존 접근 가능함을 명시적으로 확인 |
| 프로젝트 역할 | 활성 요금제의 owner/admin/member/viewer와 비소속 계정 | 기존 역할 범위 유지. viewer 쓰기 불가, 다른 워크스페이스·비참여 프로젝트 접근 불가 |
| 혼합 구독 | Team owner + Free 참여자, Free owner + 활성 참여자 | 확정한 본인/소유자 기준과 일치. 관리자라는 이유로 기능 우회하지 않음 |
| 개인 생성 회귀 | 옵션 false인 회원의 대시보드에서 프로젝트 생성 | 정상 생성. 멤버 API 차단 때문에 폼이 막히지 않음. 기능 제한안에서 타인 memberIds 전송 차단 |
| 제한 해제/재활성화 | 기존 글·댓글·구성원·신청이 있는 계정의 옵션 off → on | 데이터 삭제·탈퇴 없이 기존 역할과 데이터로 복귀 |
| 가입/게스트 | 이메일·소셜 신규 가입과 게스트 체험 | 신규 user/Free 유지. 게스트 데모 정책과 실제 회원 데이터 접근 경계 유지 |
| 기타 기능 | 프로젝트 한도, 토큰/이미지/첨부 한도, 이력 생성·할인 가격 | 명칭 변경으로 기존 제공량·검증이 바뀌지 않음 |

기능 제한안을 택하면 글/댓글/구성원/승인 각 GET·POST·PATCH별 검사를 확인한다. 프로젝트 없는 과거 댓글 및 프로젝트 ID 없는 멤버 조회의 예외도 빠뜨리지 않는다.

### 7.2 향후 구현 시 실행할 검사

- `pnpm typecheck`, `pnpm lint`, 필요 시 `pnpm build`로 타입·정적 검사·빌드를 확인한다.
- `pnpm test:accounts`, `node scripts/test-subscription-change.mjs`, `pnpm test:plan-quotas`에 명칭과 옵션 검증을 반영한다.
- `node scripts/check-team-collaboration.mjs`, `pnpm test:project-permissions-rfp`, `pnpm test:project-permissions-rfp-browser`에서 기존 팀 역할과 개인 프로젝트 생성의 회귀를 확인한다.
- `pnpm test:migration` 및 새 이관 시나리오로 기존 스키마 업그레이드와 전체 신규 구성을 확인한다. 기존 테스트가 이번 새 필드의 보존을 확인하는지는 보강이 필요하다.
- DB를 사용하는 검증은 테스트 전용 임시 DB와 합성 계정으로만 실행하도록 스크립트의 연결 설정을 먼저 확인한다. 운영 DB용 `db:migrate`/`db:upgrade-accounts`를 테스트로 실행하지 않는다.

**이번 문서 작성 단계에서는 위 실행 검사를 수행하지 않는다.** DB 연결·서버 실행 없이 경로와 소스 근거를 확인하고, 생성 문서/HISTORY 링크 및 문서 외 변경 유무만 검증한다.

### 7.3 구현·배포 순서 제안

1. 8절의 명칭 변경 방식, 옵션 기본값, 자격 기준, 제한 범위와 갱신 시점을 확정한다.
2. 확정된 안으로 새 마이그레이션·DTO·관리자 저장·메뉴 필터 및 필요한 서버 가드를 구현한다.
3. 빈 DB와 기존 DB 사본에서 이관·회귀 테스트를 수행한다. 특히 기존 관리자 설정과 구독자별 매핑을 비교한다.
4. 코드와 스키마의 배포 순서를 정한다. 새 컬럼을 참조하는 애플리케이션은 컬럼 생성 후 기동하고, 구버전 앱이 새 설정을 무시하지 않도록 점검 시간/동시 배포 또는 단계적 전환을 선택한다.
5. 신규 스키마를 유지한 코드 롤백은 구버전 앱의 팀공유 제한이 사라질 수 있다. 옵션 제한을 운영 정책으로 적용한 이후에는 수정 배포나 점검 상태를 포함한 복구 계획을 확정한다. DB 컬럼/기록을 즉시 삭제하는 롤백은 하지 않는다.

## 8. 결정이 필요한 사항

| 번호 | 결정 항목 | 권장안 | 다른 선택 시 영향 |
| --- | --- | --- | --- |
| D1 | 표시명만 변경할지 내부 코드도 변경할지 | A: 기존 코드 유지, 이름만 Pro/Team으로 변경 | B: 코드·제약·구독 이관 및 구버전 클라이언트의 pro 의미 충돌 해결 필요 |
| D2 | 요금제별 팀공유 초기값과 기존 이용자 처리 | Free/Pro 해제, Team/Business 체크를 후보로 검토 | 현재 무료 이용자도 공유에 접근 가능하므로 기존 이용권 유지, 유예 기간, 안내 여부를 결정해야 함 |
| D3 | 누구의 구독으로 자격 판단할지 | 현재 로그인 회원 본인 구독 | 프로젝트 owner/워크스페이스 owner 기준이면 Free 초대 참여 허용 가능하나 메뉴·프로젝트 필터·레거시 글·신청 정책 재설계 필요 |
| D4 | 메뉴만 숨길지 기능도 제한할지 | 기능 이용 자격으로 운영하려면 URL/API도 검사 | 메뉴만 변경하면 직접 URL/API로 기존 기능을 사용할 수 있음. 구현 범위가 크게 달라짐 |
| D5 | 기능 제한 범위 | 팀 화면·게시글·댓글·구성원/권한 관리와 새 공동 멤버 등록 제한, 개인 작업 유지 | 모든 공동 산출물 접근까지 제한하려면 프로젝트·문서·AI 등 별도 범위 확대 필요 |
| D6 | 가입 신청 상태 조회 예외 | 기존 신청자의 조회 필요성을 검토 후 확정 | 예외 허용 시 미지원 회원을 위한 별도 접근 화면/안내 필요. 전면 차단 시 상태 확인 불가 |
| D7 | master/admin의 팀공유 우회 | 본인 요금제와 동일 적용 | 우회 허용 시 메뉴와 서버 정책 모두 명시하고 별도 테스트 필요 |
| D8 | 게스트 팀 데모 표시 | 실제 회원 데이터가 없는 체험 메뉴는 유지하는 안 검토 | “해당 요금제만 메뉴 표시”를 게스트에도 엄격 적용하면 `/guest/team`과 관련 체험 메뉴도 숨김 |
| D9 | 관리자 변경 후 열린 탭 반영 시점 | 본인 변경 직후 및 창 재활성화/새 진입 시 재조회, 보호 API는 매 요청 최신 검사 | 초 단위 메뉴 갱신이 필요하면 폴링/푸시와 추가 운영 비용 필요 |
| D10 | 구버전 관리자 요청의 새 필드 누락 | 엄격 boolean 검증과 새로고침 안내 | 무중단 혼합 버전 운영이면 누락 시 기존 값 유지, 전환 종료 시점 필요 |
| D11 | 요금제 카드의 기능 안내 | 팀공유 지원/미지원 표시 추가 권장 | 요청 필수 사항은 아니며, 생략해도 체크와 메뉴 동작은 구현 가능 |

위 항목은 문서 검토 시 수정·선택한 뒤 구현 요청의 기준으로 사용한다. 미결 정책을 구현 과정에서 임의로 확정하지 않는다.
