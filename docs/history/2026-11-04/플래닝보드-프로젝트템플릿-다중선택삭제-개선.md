# 플래닝보드 프로젝트 템플릿·다중 선택 삭제 개선 설계

- 작성일: 2026-11-04 (한국시간, Asia/Seoul)
- 대상: `hams-matrix/app/(editor)/planning-board`
- 상태: 사용자 검토용 설계. 문서 검토·수정 이후 별도 구현 요청 시 최신 문서를 다시 읽고 구현한다.
- 분석 기준: 작성 시점 작업 디렉터리의 최신 소스와 기존 미커밋 변경.
- 관련 문서: [캔버스 조작·텍스트·이모티콘 개선](플래닝보드-캔버스조작-텍스트-이모티콘-개선.md)
- 이번 단계에서는 이 문서와 `HISTORY.md`만 작성한다. 소스·테스트·패키지·DB·스토리지는 수정하거나 실행하여 변경하지 않는다.

## 1. 요구사항과 범위

| 번호 | 요구사항 | 수용 기준 |
| --- | --- | --- |
| 1 | 프로젝트 master가 좌측 패널 `…` 옵션에서 템플릿 생성 | 권한 있는 사용자만 메뉴를 보고 생성할 수 있다. 생성한 템플릿은 해당 프로젝트의 템플릿 목록에 나타나며 다른 프로젝트에서는 조회·적용할 수 없다. |
| 2 | 다중 선택 우클릭 메뉴에 선택 개수와 삭제 제공 | `N개 요소 선택` 안내 아래 `삭제` 버튼을 표시한다. 메뉴를 열어도 선택 집합을 유지하고 해당 집합을 한 번에 삭제한다. |
| 3 | Delete 키로 다중 선택 요소 삭제 | 캔버스/트리 선택 상태에서 Delete가 같은 일괄 삭제 명령을 실행한다. 입력란의 문자 삭제와 충돌하지 않는다. |
| 4 | 다중 선택 시 우측 옵션 전체 숨김 | 디자인 영역에 `N개 선택 · 옵션은 대표 요소에 적용됩니다.` 문구만 표시하고 모든 속성 옵션을 숨긴다. 단일 선택으로 돌아오면 기존 옵션을 복원한다. |

### 1.1 기본 범위와 가정

- 커스텀 템플릿은 프로젝트 구성원이 여러 화면에서 재사용할 수 있는 스냅샷이다. 원본 화면을 나중에 수정해도 이미 생성한 템플릿은 변경되지 않는다.
- 기존 공통 기본/상세 템플릿은 유지한다. 새 프로젝트 템플릿을 전역 공통 템플릿에 등록하지 않는다.
- 생성 위치는 좌측 `홈` 제목 오른쪽 `.page-more-button`의 `…` 메뉴를 우선 제안한다. 개별 요소 우클릭 메뉴와는 구분한다.
- 생성 대상은 현재 편집 중인 **보드 전체의 문서 스냅샷**을 권고한다. 활성 페이지 또는 선택한 레이어만을 뜻한다면 8절에서 범위를 확정한다.
- 템플릿 이름 변경·삭제·버전 관리 UI, 프로젝트 간 공유, 자동 템플릿 갱신은 추가 요청 전까지 범위 밖이다.
- 기존 로그인·프로젝트 권한·검토 상태·문서 저장·이미지 보호·Undo/Redo·라이트/다크·이모티콘 패널 확대를 보존한다.

## 2. 현재 구조와 확인 결과

아래 기능 경로는 `app/(editor)/planning-board/` 기준이다.

### 2.1 master와 프로젝트 역할은 서로 다른 개념

- `lib/plan-types.ts`의 계정 역할 `AccountRole`은 `master/admin/user/guest`이다. 프로젝트 역할 `ProjectRole`은 `owner/admin/member/viewer`이며 프로젝트 역할 `master`는 없다.
- `lib/team-permissions.ts`의 `projectRoleSql`은 `projects.owner_id === project_members.user_id`인 사용자를 `owner`로 계산한다. `requireProjectOwner()`도 현재 워크스페이스·프로젝트 구성원·소유자를 함께 확인한다.
- `lib/project-permissions.ts`의 `projectPermissionAccess()`는 현재 워크스페이스 안의 프로젝트 구성원과 화면설계 READ/UPDATE 등 정책을 계산한다. 계정 master라는 이유만으로 모든 프로젝트의 owner가 되는 구조가 아니다.
- 플래닝보드의 `projectAccess`는 owner/edit/view로 축약된다. 서버의 화면 `access` 응답과 `stores/editor-provider.tsx`에는 `canUpdate`가 있으나 템플릿 생성 전용 권한은 없다.
- 따라서 요구사항의 '프로젝트 master'를 서버 권한으로 표현하려면 의미를 확정해야 한다. 본 설계의 권고는 **해당 프로젝트 owner**이며, 계정 master 여부만으로 생성 권한을 부여하지 않는다.

### 2.2 좌측 메뉴와 템플릿 불러오기

- `components/left-panel.tsx`의 `.page-menu`에는 새 페이지 추가·저장·검토·완료·페이지 삭제가 있다. 템플릿 생성은 없다. 개별 `.layer-context-menu`는 요소 추가·단일 삭제만 제공한다.
- `components/editor-header.tsx`는 템플릿 select에 `screens-template`, `screens-template2` 두 항목을 하드코딩한다. 프로젝트별 목록 조회가 없다.
- `planning-board-editor.tsx`의 `applyTemplate()`은 `/template-data?template=...`를 호출한다. 여기의 fetch는 전역 fetch가 아니라 `boardFetch` 별칭이다.
- `lib/client-api.ts`가 논리 경로를 `/api/planning/templates/{name}`으로 변환한다. `lib/server/handler.ts`는 정적 `data/screens/*.json` 두 파일을 반환한다. 이 공통 경로는 프로젝트 식별자가 없으며 커스텀 템플릿 저장 경로도 아니다.
- 현재 불러오기는 편집기 전체 문서를 교체하고 Undo를 남긴 뒤 '저장 필요' 상태로 만든다. 템플릿 적용 자체가 보드 DB 저장을 의미하지 않는다.
- `createEditorState()`는 현재 문서 JSON과 AI pages 형식을 처리한다. 텍스트 개행·가로/세로 정렬·배경·번호 이모티콘도 문서 필드에 포함된다.

### 2.3 다중 선택과 우클릭

- 상위 편집기가 `selected` 대표 ID, `selectedIds` 집합, `selectionAnchor`를 관리한다. 캔버스 영역 선택과 트리 Ctrl/Meta/Shift 선택이 이를 공유한다.
- 캔버스의 `openOrderMenu()`는 우클릭 지점의 `data-layer-id`를 찾은 뒤 항상 `onSelect(targetId)`로 단일 선택한다. 메뉴 상태에는 `targetId` 하나만 있다.
- 왼쪽 트리의 `openMenu()`도 항상 해당 ID를 단일 선택한다. 두 메뉴 모두 현재는 선택 집합용 안내/삭제가 없다.
- 캔버스 메뉴는 포털을 `.planning-root` 아래에 만들며 화면 경계 보정·바깥 클릭·Escape 닫기를 제공한다. 다중 선택 경계 `.canvas-multi-selection`은 문서 데이터가 아닌 조작 표시이다.

### 2.4 삭제 처리와 데이터 정합성

- `planning-board-editor.tsx`의 `deleteLayer(id)`는 ID 하나만 받는다. 페이지는 최소 한 개를 남기고, 대상 자체의 잠금과 `canEdit`을 확인한다.
- 트리에서는 하위 요소까지 재귀적으로 제거하지만, `sizes/positions/layerText/layerImages/layerStyles`에서는 지정한 ID만 제거한다. 컨테이너 삭제 시 자손 map 항목이 남을 수 있다.
- 서버 `lib/server/document-validation.ts`는 map의 모든 키가 실제 레이어 ID에 속하는지 확인한다. 따라서 자손 map 정리가 빠지면 이후 저장이 거부될 수 있다.
- `lib/editor-selection.ts`의 `movableSelection()`은 조상 중복 제거에 활용할 수 있으나 숨김 요소도 차단한다. 삭제 정책과 이동 정책을 그대로 동일시해서는 안 된다.
- `commitCanvasChange()`는 작업 단위 이력 기반을 제공하지만 현재 patch 적용에 `layerImages` setter 처리가 없다. 삭제 명령에서 이미지 map까지 갱신하도록 확장해야 한다.

### 2.5 키보드와 우측 패널

- `components/use-canvas-interactions.ts`의 키보드 처리는 캔버스 focus 상태의 방향키와 Escape를 처리한다. Delete/Backspace 삭제는 없다.
- 입력 컨트롤·contenteditable·IME·모달·메뉴·READ 상태를 제외하는 키 가드가 이미 있다. 트리 키보드 삭제는 별도로 연결해야 한다.
- `components/right-panel.tsx`는 `selectionCount > 1`일 때 안내 문구를 추가하지만 그 아래에 대표 요소의 모든 옵션을 계속 렌더링한다.
- 디자인/코드 탭이 별도로 존재한다. 요구사항의 '옵션 전체 숨김'은 디자인 속성 영역을 우선 의미하는 것으로 해석하며 코드 탭 유지 여부는 결정 항목이다.

### 2.6 DB와 이미지 자산 제약

- `db/migrations/032_planning_boards.sql`에는 보드·revision·댓글·메모·이미지·AI 요청 테이블이 있다. 프로젝트 커스텀 템플릿 테이블은 없다.
- 보드 문서는 스키마 버전 1의 `document_json`에 저장된다. 템플릿을 보드 상태나 `project_artifacts.fields_json`에 섞어 저장할 기존 근거는 없다.
- 이미지 URL과 `planning_board_assets`는 워크스페이스·프로젝트·**화면** 범위다. 저장 시 다른 화면의 URL은 거부된다. pending 자산은 생성자와 만료도 확인한다.
- 따라서 원본 화면 이미지 URL을 템플릿에 그대로 넣어 다른 화면에 적용하면 정상 저장되지 않는다. 원본 화면이 삭제되거나 pending 이미지가 만료되는 문제도 고려해야 한다.

## 3. 프로젝트 커스텀 템플릿 설계

### 3.1 권한과 UI

1. 서버에서 로그인·온보딩·현재 워크스페이스·프로젝트 멤버십·화면설계 READ를 확인하고, 생성은 추가로 프로젝트 owner를 확인한다.
2. 화면 `access` 응답에 `canCreateTemplate`을 추가하고 Provider에서 기본 false로 관리한다. UI에 사용자 ID 비교나 계정 master 하드코딩을 중복하지 않는다.
3. 좌측 `…`에 `템플릿 생성`을 추가한다. owner만 표시하고 저장/AI 생성/검토 중 등 사용 불가 상태에는 비활성화와 이유를 제공한다. 서버도 요청 시 상태·권한을 재확인한다.
4. 클릭하면 템플릿 이름 입력 모달을 열고 기본값은 현재 문서 제목으로 제안한다. 이름의 앞뒤 공백을 제거하고 1~80자를 권고한다.
5. 확인한 순간의 현재 편집 문서를 스냅샷으로 보낸다. 미저장 편집도 포함하되 원본 보드의 강제 저장·상태 변경·Undo 항목 생성은 하지 않는다.
6. 성공 시 모달을 닫고 프로젝트 템플릿 목록을 갱신한다. 목록에 `기본 템플릿`/`프로젝트 템플릿` optgroup을 사용한다. 새 템플릿을 자동 적용하여 현재 편집을 덮어쓰지 않는다.

템플릿 생성은 프로젝트 공유 데이터의 실제 저장이다. 실패 시 현재 문서와 선택을 그대로 유지하고 오류를 모달에 표시한다.

### 3.2 프로젝트 범위 API 제안

| Method | 실제 경로 | 목적/권한 |
| --- | --- | --- |
| GET | `/api/planning/projects/{projectId}/templates` | 기본 목록과 해당 프로젝트의 ready 커스텀 목록. 프로젝트 화면설계 READ. |
| POST | `/api/planning/projects/{projectId}/templates` | 이름·문서 스냅샷·sourceScreenId·requestId를 받아 프로젝트 템플릿 생성. 프로젝트 owner 및 원본 화면 READ. |
| GET | `/api/planning/projects/{projectId}/templates/{templateId}` | 해당 프로젝트 템플릿 메타데이터/검증된 템플릿 문서 조회. 원시 object key 등은 응답하지 않음. |
| POST | `/api/planning/projects/{projectId}/screens/{screenId}/templates/{templateId}/apply` | 템플릿 이미지의 대상 화면 복제 및 적용 가능한 문서 반환. 대상 화면 UPDATE·검토 중 아님. 보드 본문은 아직 저장하지 않음. |

- 기존 전역 `/api/planning/templates/{name}`는 **정적 기본 템플릿 전용**으로 유지한다. 프로젝트 템플릿 UUID를 이 경로에서 조회할 수 없게 한다.
- 목록 select 값은 `builtin:screens-template`/`custom:{id}`처럼 종류를 구분하고 표시 이름을 식별자로 사용하지 않는다.
- 새 프로젝트 리소스 분기는 현재 handler의 필수 `screens/{screenId}` 검사보다 먼저 처리해야 한다. 공통 Route Handler 진입점은 유지한다.
- 모든 커스텀 조회는 클라이언트가 보낸 workspaceId가 아닌 세션의 workspaceId와 URL projectId로 DB를 제한한다. templateId 단독 조회나 목록 반환 후 클라이언트 필터링은 금지한다.
- 다른 프로젝트 또는 워크스페이스의 ID 접근은 404, 자기 프로젝트 구성원의 생성 권한 부족은 403으로 처리한다. 생성자 개인 소유 목록이 아니라 프로젝트 공유 목록으로 조회한다.
- POST는 기존 `checkOrigin()`과 제한된 request body 처리를 적용한다. 이름 충돌은 409, 유효하지 않은 문서는 400, 용량 초과는 413으로 구분한다.

### 3.3 클라이언트 호출·오류·동기화

- 정적 2개 옵션을 목록 상태로 바꾸고 최초 진입·프로젝트 전환·focus·생성 성공에 목록을 읽는다. 비동기 응답은 사용자/워크스페이스/프로젝트 식별자가 그대로일 때만 반영한다.
- 원본 화면별 보드 버전 cursor와 템플릿 버전은 분리한다. 템플릿 생성/조회/준비가 기존 board version과 screenVersion을 갱신하거나 화면 목록에 보드 저장 이벤트를 보내면 안 된다.
- 기본 템플릿의 기존 URL 입력 호환은 유지하되 커스텀 적용은 프로젝트 범위 API를 명시적으로 호출한다. 프로젝트 템플릿을 기존 `/template-data`의 전역 이름으로 취급하지 않는다.
- 현재 `planningFetch()`는 모든 planning 요청의 401/403/404를 화면 접근 오류로 전달한다. '템플릿이 없거나 생성 권한이 없음'을 '현재 화면에 접근할 수 없음'과 구분하도록 호출 옵션 또는 전용 helper를 둔다. 401은 로그인 만료 처리하고, 템플릿 403/404는 작업 오류로 표시하며 필요 시 권한을 재조회한다.
- 생성 성공을 같은 프로젝트의 다른 창에 알리려면 `matrix-planning-templates:{workspaceId}:{projectId}` 채널을 제안한다. payload는 목록 갱신 알림만 포함하고 본문·이미지·개인정보는 보내지 않는다. focus 재조회도 유지한다.
- 생성 중 중복 클릭은 막고 requestId와 입력 hash로 재시도를 멱등 처리한다. 프로젝트 전환·늦은 응답이 이전 프로젝트 목록을 새 화면에 넣지 않게 한다.

### 3.4 생성·불러오기 데이터 흐름

```text
프로젝트 owner
  → 좌측 … → 템플릿 생성 → 이름 입력
  → 현재 문서 스냅샷 검증 + 서버 프로젝트 권한 확인
  → 프로젝트 템플릿/전용 이미지 복제·등록 → ready
  → 해당 프로젝트 목록 갱신

같은 프로젝트의 편집 가능한 다른 화면
  → 목록에서 커스텀 템플릿 선택 → 현재 문서 교체 확인
  → 서버가 대상 화면의 이미지 자산 준비
  → 반환 문서로 로컬 편집 상태 교체 + Undo 한 건 + 저장 필요
  → 기존 저장 버튼으로 보드/화면 버전·revision 저장
```

- 문서 제목·페이지·레이어·크기·위치·텍스트·이미지·스타일·활성 페이지를 보존한다. 댓글·메모·검토 상태·리뷰어·변경 이력·화면 고유 ID·원본 보드 버전은 템플릿에 복사하지 않는다.
- 페이지/요소 ID는 템플릿 스냅샷 내부에서 유지해도 보드별로 분리되어 충돌하지 않는다. 단, assetId는 대상 화면용으로 새로 발급한다.
- 적용 취소 확인은 자산 복제 요청 전에 수행한다. 실패하거나 응답 도중 문서를 바꿨다면 기존 로컬 문서를 교체하지 않는다. 사용자 편집 revision token을 잡아 오래된 적용 응답을 폐기한다.
- Undo/Redo가 템플릿 적용 전/후의 이미지까지 복원할 수 있도록 반환된 pending 자산을 즉시 제거하지 않는다. 미저장 자산은 기존 만료 정책을 따르되 만료 후 저장 오류를 안내한다.

### 3.5 이미지 포함 템플릿 처리

**권고안은 템플릿 전용 자산을 보관하고 적용 시 대상 화면으로 복제하는 방식이다.** 원본 URL 유지·외부 URL·공개 이미지 전환으로 기존 화면 격리 검사를 완화하지 않는다.

1. 생성 입력은 기존 `validateDocument(document, sourceScope)`로 검증한다. 실제 이미지 자산의 소속·읽기 권한·pending 생성자·만료·MIME·용량을 확인한다.
2. 이미지 바이너리를 템플릿 전용 object key로 복사하고, 별도 템플릿 자산 row에 등록한다. 템플릿 본문의 `layerImages`는 내부 `template-asset:{id}` 참조 등 화면과 독립된 표현으로 변환한다.
3. 이 내부 표현은 **템플릿 전용 validator/type**으로만 허용한다. 일반 보드 validator에 해당 참조나 다른 화면 URL을 허용하지 않는다.
4. 적용 요청은 같은 프로젝트의 ready 템플릿만 읽는다. 바이너리를 대상 화면의 `planning_board_assets`에 새로운 pending 자산으로 만들고, 현재 사용자를 생성자로 기록한다.
5. 대상 URL로 치환한 문서를 기존 `validateDocument(document, targetScope)`로 검증한 후 반환한다. 이후 일반 저장에서 attached로 전환한다.
6. 생성 후 원본 화면 삭제·원본 수정·원본 pending 만료가 템플릿을 깨뜨리지 않도록 원본과 독립시킨다. 이미지 없는 템플릿은 스토리지 복사 없이 같은 흐름으로 처리한다.

- DB 트랜잭션과 스토리지 쓰기는 하나의 원자적 트랜잭션이 아니다. pending/ready 상태와 작업 ID를 사용하고, 실패 시 생성한 object/row의 보상 정리 또는 만료 정리 경로를 둔다. 목록에는 ready만 표시한다.
- 최종 ready 전환/대상 자산 확정 직전에 프로젝트·화면 권한과 검토 상태를 다시 확인한다. 원본·대상 자산 제한(현재 화면당 50개, 개별 최대 8MiB)과 문서 5MiB 제한도 적용한다.
- 스토리지 설정이나 복사가 실패했을 때 이미지 누락 템플릿을 성공으로 등록하지 않는다. 이미지 포함 생성을 1차에서 제외하려면 사용자 검토로 범위를 확정하고 명시적으로 차단해야 한다.

## 4. 다중 선택 메뉴·일괄 삭제 설계

### 4.1 메뉴와 선택 집합

- 메뉴 상태를 single/multi로 구분하고 multi에는 선택 ID 스냅샷과 선택 개수를 보관한다. 렌더 직전/명령 실행 시 실제 존재하는 ID로 다시 확인한다.
- 선택된 요소 중 하나 또는 공통 선택 경계에서 우클릭하면 집합을 유지하고 다음 메뉴만 표시한다.

```text
4개 요소 선택
────────────
삭제
```

- 해당 메뉴에는 단일 요소의 추가/순서 옵션을 표시하지 않는다. 선택 밖 다른 요소에서 우클릭하면 기존 방식대로 그 요소를 단일 선택하고 단일 메뉴를 연다.
- 캔버스 hit test에서 선택 경계·핸들을 건너뛰되, 공통 선택 박스 안의 빈 공간은 현재 다중 선택 메뉴로 처리한다. 보드 밖 빈 공간은 이전 요소 삭제 메뉴를 열지 않는다.
- 왼쪽 트리도 선택된 행의 우클릭은 집합을 유지하도록 맞춘다. 요구사항을 캔버스로만 제한하려면 결정 항목에서 확정한다.
- 메뉴 표시 수 N은 중복·사라진 ID를 제거한 현재 선택 수다. 조상 삭제에 따라 같이 없어지는 미선택 자손까지 N에 더하지 않는다.

### 4.2 공통 삭제 명령

`deleteLayers(ids)`를 상위 편집기에 두고 캔버스 메뉴·트리 메뉴·Delete 키·기존 단일 삭제가 함께 사용하도록 권고한다.

1. 현재 문서의 선택 ID를 검증하고 중복·미존재 ID를 제거한다.
2. 조상/자손이 함께 선택되면 조상을 삭제 루트로 정규화한다. 각 삭제 루트의 전체 자손 ID를 수집한다.
3. `canEdit`, 대상/조상 잠금, 선택된 컨테이너 내부 잠금 자손, 보호 요소, 남을 페이지 수를 확인한다. 잠긴 자손을 부모 삭제로 우회 제거하지 않는다.
4. `layers`와 삭제 집합에 속하는 `sizes/positions/layerText/layerImages/layerStyles`를 **한 번의 문서 patch**로 반영한다. `commitCanvasChange()`의 layerImages 적용을 함께 보완한다.
5. 살아남은 유효한 부모 또는 페이지를 다음 선택으로 설정하고 대표 선택·선택 집합·앵커·활성 페이지/포커스 대상을 정리한다. 삭제된 ID가 메뉴·선택 보조선·드래그 상태에 남지 않게 한다.
6. 실행 취소 한 번으로 모든 삭제 요소와 자손·이미지·스타일을 복구하고 다시 실행으로 동일하게 삭제한다. 무효 요청은 이력이나 저장 필요 상태를 만들지 않는다.

### 4.3 삭제 제약과 저장

- 권고 정책은 **원자적 일괄 삭제**다. 잠금/권한/마지막 페이지 등 차단 대상이 섞였으면 전체 작업을 거부하고 이유를 안내한다. 일부만 조용히 삭제하지 않는다.
- 페이지가 포함된 트리 다중 선택에서는 삭제 후 최소 한 페이지를 남긴다. 마지막 페이지 삭제를 피하기 위해 임의로 일부 페이지를 고르는 정책은 넣지 않는다.
- 숨김 요소는 트리에서 선택하여 삭제할 수 있게 한다. 이동용 `blocked`를 그대로 재사용하여 숨김이라는 이유로 삭제가 막히지 않도록 삭제 전용 판정을 분리한다.
- 삭제는 현재 로컬 문서 변경이며 DB 보드/revision 반영은 기존 저장 시점에 한다. DELETE 화면 권한이 아니라 기존 본문 편집의 screen.UPDATE 기준을 유지한다.
- 문서에서 이미지 참조를 제거하되 바이너리·asset row를 즉시 물리 삭제하지 않는다. Undo/Redo·기존 revision이 참조할 수 있으므로 별도 자산 수명 정책을 유지한다.
- 삭제 중 활성 포인터 조작이 있으면 먼저 취소/정리하여 이동 리스너가 삭제 전 좌표를 다시 쓰지 못하게 한다.

### 4.4 Delete 키

- 캔버스 및 왼쪽 트리의 선택 영역 focus에서 `event.key === "Delete"`를 공통 삭제 명령에 연결한다. 별도 전역 키 가로채기는 지양한다.
- 입력/textarea/select/contenteditable, 한글 조합, 열린 모달·이모티콘 패널·텍스트 편집, READ/검토/저장/AI 처리 중에는 문서 삭제를 실행하지 않는다.
- Ctrl/Meta/Alt 조합과 `event.defaultPrevented`는 제외한다. repeat 입력은 같은 키 누름에서 후속 선택이 연속 삭제되지 않도록 첫 keydown만 처리한다.
- 삭제를 실제 처리한 경우에만 기본 동작을 막고 전파 중복을 방지한다. 메뉴와 키보드가 동일한 대상·정책·Undo 경로를 사용하도록 한다.
- Backspace 삭제는 이번 요구사항에 포함하지 않는다. 단일 선택 Delete도 같은 명령으로 지원하는 것을 권고한다.

## 5. 다중 선택 우측 패널 설계

- `selectionCount > 1`이면 디자인 속성 분기로 진입하기 전에 안내 전용 화면으로 반환한다. CSS로 흐리게 처리하거나 `disabled`만 적용하는 방식은 사용하지 않는다.
- 본문에는 요구한 `N개 선택 · 옵션은 대표 요소에 적용됩니다.` 문구만 표시한다. 대표 요소 이름/더보기, 콘텐츠, 이미지, 아이콘, 체크 옵션, 레이아웃, 타이포그래피, 모양, 효과 등 속성 전체를 DOM에서 제외한다.
- 원칙적으로 디자인/코드 탭과 패널 외곽은 유지하고 디자인 본문을 안내로 바꾼다. 코드 탭은 전체 문서 내보내기 기능이므로 유지하는 권고안이다. 우측 전체를 문구 하나로 만들려면 코드 탭도 숨기도록 결정한다.
- 안내 문구는 실제로 옵션을 숨기는 동작과 표현상 맞지 않지만 사용자 요청 문자열을 우선 그대로 사용한다. `N개 요소 선택` 등으로 바꾸는 것은 별도 결정 사항이다.
- 한 개 선택으로 돌아오면 그 요소의 옵션을 복원하고 READ/잠금 비활성 처리를 그대로 적용한다. 다중 선택으로 바뀔 때 기존 입력란 focus와 지연 업로드/콜백이 숨겨진 대표 요소를 수정하지 않게 방어한다.
- 공통 `--muted/--ink/--surface` 토큰을 사용하여 라이트·다크의 글자 대비를 유지한다. 안내 표시 자체는 문서 변경·이력을 만들지 않는다.

## 6. DB·타입·서버 영향

### 6.1 신규 테이블 제안

| 테이블 | 주요 필드와 제약 | 목적 |
| --- | --- | --- |
| `planning_project_templates` | id PK, workspace_id, project_id, name, name_key, schema_version, document_json, source_screen_id, created_by, created_at, status(pending/ready), request_id, input_hash | 프로젝트 템플릿 스냅샷과 생성 작업 상태. |
| `planning_project_template_assets` | id PK, template_id, workspace_id, project_id, object_key UNIQUE, mime_type, byte_length, hash, created_at | 원본 화면에서 독립된 템플릿 이미지. |

- 템플릿은 `FOREIGN KEY(project_id, workspace_id) → projects(id, workspace_id)`와 `(id, project_id, workspace_id)` UNIQUE를 둔다. 자산은 동일 범위의 템플릿 복합 FK를 사용한다.
- ready 목록을 위해 `(workspace_id, project_id, status, created_at, id)` 인덱스를 둔다. 이름 정규화는 NFC·trim·대소문자 정책을 정한 name_key로 처리하고 `(workspace_id, project_id, name_key)` 중복을 막는 것을 권고한다.
- `(workspace_id, project_id, created_by, request_id)` 유일성을 두어 중복 생성 재시도를 처리한다. 같은 requestId에 다른 input_hash는 409다. pending 만료/실패 정리에 필요한 시각 또는 만료 필드를 구현 시 함께 확정한다.
- source_screen_id는 출처 메타데이터다. 원본 삭제가 템플릿을 연쇄 삭제하는 FK로 만들지 않는다. 템플릿 사용 권한은 현재 프로젝트 범위로 판단한다.
- 문서 전체 제한은 기존 5MiB·30페이지·2,000요소·깊이 12·텍스트 10,000자 규칙을 재사용한다. 이미지 개별 8MiB·최대 50개를 적용하되 프로젝트 템플릿 총수/총용량은 결정 항목이다.
- 새 migration 파일은 구현 시 최신 migration 다음 번호로 만든다. 현 시점 마지막은 032이나 기존 032 파일을 수정하여 이미 적용된 DB와 불일치시키지 않는다.
- 기존 보드 테이블·문서 schemaVersion 1·revision 스냅샷의 일괄 변환은 필요하지 않다. 다중 삭제와 패널 변경만으로 DB 구조 변경은 없다.

### 6.2 데이터 경계

- 별도 `TemplateSummary`, `TemplateDocument`, 생성/적용 DTO를 둔다. 전용 자산 참조는 일반 `BoardDocument`와 구분한다.
- template document schema와 board schema가 모두 숫자 1이더라도 자산 참조 규칙은 다르므로 validator를 구분한다.
- 사용자 계정/세션과 보드 문서에 템플릿 관리 권한을 저장하지 않는다. capability는 서버가 현재 프로젝트 역할로 매 요청 계산한다.
- 템플릿 이름/본문을 로그·목록 응답에 과도하게 노출하지 않고 object key·내부 오류·인증정보는 UI/문서에 기록하지 않는다.

## 8. 결정이 필요한 사항

| 항목 | 권고안 | 대안의 영향 |
| --- | --- | --- |
| 프로젝트 master 의미 | 프로젝트 owner | 계정 master 또는 admin까지 허용하려면 별도 서버 역할 정책 필요. |
| 생성 메뉴 위치 | 좌측 홈 제목의 … | 개별 레이어 옵션이라면 캡처 대상·생성 위치를 다시 정의. |
| 템플릿 캡처 범위 | 현재 보드 전체, 미저장 내용 포함 | 활성 페이지/선택 요소만이면 부모·좌표·페이지 재구성 규칙 추가. |
| 생성 가능 상태 | 편집 가능하고 검토/저장/AI 처리 중이 아님 | 검토 중 읽기 스냅샷 생성 허용 여부는 보드 편집과 별도 정책 필요. |
| 목록 사용자 | 같은 프로젝트 화면 READ 구성원 모두 | owner 전용 목록은 구성원 재사용 요구 해석을 바꾸게 됨. |
| 이미지 처리 | 전용 자산 저장 후 대상 화면 복제 | 1차 이미지 제외 시 명시적 생성 차단 필요. 원본 URL 재사용은 채택하지 않음. |
| 이름 중복 | 프로젝트 안의 동일 정규화 이름은 409 | 중복 허용이면 목록에서 구별할 보조 정보 필요. |
| 템플릿 총수/보존 | 기존 문서·이미지 개별 제한 유지, 프로젝트 총량은 확정 필요 | 관리/삭제 UI가 없으므로 무제한 생성은 누적 용량 문제. |
| 다중 우클릭 범위 | 캔버스와 트리 모두, 선택 내부는 유지·외부는 단일 전환 | 다중 선택이면 어디서나 집합 메뉴를 열지 여부는 추가 결정. |
| 삭제 제약 혼합 | 하나라도 차단되면 전체 거부 | 일부 삭제라면 삭제 가능 수와 선택 수를 별도로 안내해야 함. |
| Delete 적용 범위 | 캔버스/트리 focus, 단일/다중 공통 | 다중만 허용하거나 손 도구에서도 허용할지는 UI 정책 조정. |
| 우측 코드 탭 | 유지하고 디자인 속성만 안내로 대체 | 전체 패널을 문구 하나로 만들려면 코드 탭/내보내기도 숨김. |
| 우측 문구 | 요청 문자열 그대로 유지 | 옵션이 사라지는 동작에 맞게 'N개 요소 선택'으로 바꿀지는 사용자 확인. |

권고안은 문서 검토를 위한 가정이며 사용자 확정으로 간주하지 않는다. 구현 요청 시 이 문서의 최신 요구사항/수정 내용을 우선한다.

## 9. 검증 방법

### 9.1 프로젝트 템플릿

1. 같은 워크스페이스의 프로젝트 A/B와 다른 워크스페이스 C를 준비한다. A owner·A admin/member/viewer·A 비구성원·계정 master지만 A owner가 아닌 사용자를 분리한다.
2. 권한표대로 생성 메뉴/직접 POST를 확인한다. 메뉴를 숨기는 것만으로 서버 권한 검증을 대신하지 않았는지 검사한다.
3. A에서 생성한 템플릿이 A의 다른 화면/구성원/새 창/새로고침에서 조회되는지 확인한다. B/C 목록에는 이름·ID·본문·이미지가 나타나지 않아야 한다.
4. B/C URL로 A templateId를 직접 조회·적용하는 요청도 404여야 한다. 전역 정적 템플릿 경로에서 커스텀 ID가 조회되지 않아야 한다.
5. 템플릿 생성에 미저장 텍스트·개행·세로 정렬·번호·중첩 요소·숨김/잠금이 포함되는지 확인한다. 원본 저장본/보드 버전/이력은 생성만으로 바뀌지 않아야 한다.
6. 원본과 다른 화면에 적용·저장한 이미지가 대상 화면 자산 URL을 갖는지 확인한다. 원본 수정/삭제/이미지 pending 만료가 이미 만든 템플릿을 깨뜨리지 않아야 한다.
7. 중복 이름·이중 클릭·같은 requestId 재시도·다른 hash·스토리지 실패·일부 복사 실패·만료 pending·권한 변경·원본/대상 삭제·용량 한도를 검사한다. 실패한 템플릿은 목록에 나타나지 않아야 한다.
8. 두 창 목록 갱신·프로젝트 전환 중 늦은 응답·적용 중 편집·취소·Undo/Redo를 확인한다. 템플릿 오류가 현재 화면 전체 접근 오류로 오인되지 않아야 한다.

### 9.2 다중 선택 삭제와 우측 패널

1. 2개/4개 요소 선택 후 선택 내부와 공통 박스 빈 공간에서 우클릭한다. `N개 요소 선택` 아래 삭제만 표시되고 선택 수가 줄지 않아야 한다. 외부 요소 우클릭은 기존 단일 메뉴다.
2. 캔버스/트리 메뉴와 Delete가 동일한 집합을 삭제하고 Undo 한 번으로 전부 복구하는지 확인한다. Redo·길게 누름·더블 클릭도 후속 요소를 추가 삭제하면 안 된다.
3. 부모+자손 중복 선택 및 부모만 선택한 삭제에서 모든 자손 map이 제거되는지 확인한다. 이미지·스타일이 남지 않고 서버 저장 validator를 통과해야 한다.
4. 잠긴 대상·잠긴 조상·잠긴 자손·숨김 요소·삭제 후 마지막 페이지·READ·검토 중을 확인한다. 숨김과 잠금을 혼동하지 않고 혼합 거부 정책대로 동작해야 한다.
5. textarea·콘텐츠·이름 편집·댓글·메모·코드 입력·IME·모달·이모티콘 패널에서 Delete가 문서를 지우지 않아야 한다. 선택 영역 focus를 되찾으면 정상 삭제되어야 한다.
6. 다중 선택의 디자인 본문에는 정확한 N개 안내만 있고 모든 Property/입력/더보기가 없어야 한다. 단일 선택 복원과 코드 탭 정책도 확인한다.
7. 삭제/선택 중 focus·이동/크기 조절·템플릿 적용이 바뀌어도 이전 콜백이 삭제된 요소를 재생성하지 않아야 한다. 저장 후 재조회·미리보기·내보내기도 확인한다.
8. 라이트/다크 메뉴·모달·안내·비활성/포커스·화면 경계, 기존 방향키/영역 선택/리사이즈/이모티콘 패널 회귀를 확인한다.

- 구현 단계 실행 명령: `pnpm typecheck`, 변경 파일 ESLint, `pnpm build`, `pnpm test:planning-board`, `pnpm test:planning-board-browser`.
- DB/스토리지 테스트는 임시 DB·격리된 바이너리 저장소 대역과 가짜 사용자로 실행하고 실사용 데이터나 유료 AI 호출에 의존하지 않는다.
- 이번 문서 단계에서는 정적 소스 분석과 문서/링크 확인만 수행한다. migration·테스트 DB 생성·스토리지 쓰기는 수행하지 않는다.
