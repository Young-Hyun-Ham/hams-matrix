# Guardrail_Control_Tower_화면설계

- 작성일: 2026-11-23 (한국시간)
- 상태: 검토용 화면 설계. 화면/API/DB 미구현.
- 연계 설계: [가드레일 관리자 승인 요청 및 실행 재개](가드레일-관리자승인-요청및재개-설계.md)
- 목적: 관리자가 가드레일로 중단된 요청을 검토·승인/반려하고, 요청자가 직접 실행을 재개하도록 한다.

## 관리자 승인 화면의 위치

**관리자가 사용자의 승인 요청 건을 확인하고 승인하는 화면은 새 창으로 열리는 컨트롤타워 안에 만든다.** 컨트롤타워의 기본 탭인 `승인 대기`가 관리자 승인 요청 목록이고, 목록에서 한 건을 선택하면 같은 화면 오른쪽의 `승인 요청 상세·처리` 영역에서 내용을 확인한 뒤 승인 또는 반려한다. 기존 관리자설정의 정책 편집 화면과 구분되는 요청별 심사 화면이다.

| 구분 | 위치와 역할 |
| --- | --- |
| 관리자 진입 | `관리자설정 → AI 가드레일 관리 → 대상 워크스페이스 선택 → 컨트롤타워 이동` |
| 새 창 URL | `/admin/guardrail-control-tower?workspaceId=<선택값>` |
| 요청 확인 화면 | 컨트롤타워의 `승인 대기` 탭. 사용자가 `예(Yes)`를 선택하여 전송에 성공한 요청을 목록으로 표시한다. |
| 승인 처리 화면 | 목록에서 요청 한 건 선택 → 같은 창 오른쪽의 `승인 요청 상세·처리` 영역. 요청 내용·차단 이유·승인 후 작업 범위를 확인하고 하단의 `이 요청 승인` 또는 `반려`를 누른다. |
| 좁은 화면 | 같은 창에서 목록 대신 요청 상세를 보여준다. `목록으로`로 돌아갈 수 있고 별도 창을 다시 열지 않는다. |
| 상세 직접 열기 | `/admin/guardrail-control-tower?workspaceId=<선택값>&approvalId=<요청ID>`. 서버 권한 확인 후 해당 건을 선택한다. 필터 범위 밖의 건이면 상세 직접 조회로 표시하고, 목록에는 적용 중인 필터를 유지한다. |
| 승인 후 | 해당 건은 `승인 후 재개 대기`로 이동한다. 사용자 화면의 `이어서 진행`이 활성화되며, 사용자가 눌러야 AI가 재개된다. |

### 사용자 요청부터 관리자 승인까지의 화면 연결

1. **사용자 AI 화면:** 가드레일 질문에 `예(Yes)`를 누른다. 서버가 승인 요청 ID를 생성하고 사용자는 `관리자 승인 대기` 카드에서 기다린다.
2. **관리자 컨트롤타워:** 같은 workspace의 `승인 대기` 목록에 요청 ID가 같은 새 행이 나타나고 대기 건수가 증가한다. 컨트롤타워가 닫혀 있으면 관리자가 위 진입 경로로 열어 확인한다. 이미 열려 있으면 상태 조회 또는 새로고침으로 반영한다. 헤더 알림 추가 여부와 관계없이 이 목록에서 조회·처리할 수 있어야 한다.
3. **관리자 승인 요청 상세·처리:** 해당 행을 선택해 요청자, 사용자가 보낸 작업 요청, 어떤 정책 때문에 어느 내용이 차단되었는지, 승인하면 어떤 작업을 이어서 하는지 확인한다. 구체적인 표시 항목은 5.1절을 따른다.
4. **관리자 결정:** 처리 의견 입력 → `이 요청 승인` → 승인 범위 확인 → `승인 확정`. 반려하려면 사유 입력 후 `반려`한다. 결정 결과는 선택한 승인 요청 ID에 저장한다.
5. **사용자 AI 화면:** 같은 승인 요청 ID의 상태를 조회하여 승인 결과를 표시한다. 승인되었으면 `이어서 진행`을 활성화하고, 반려되었으면 사유를 표시한다.

즉, 관리자 승인 UI의 구현 대상은 `guardrail-control-tower.tsx`의 목록과 `guardrail-approval-detail.tsx`의 상세·처리 패널이다. 기존 `guardrail-admin.tsx`에는 새 창으로 가는 진입 버튼을 추가한다. 이 화면들은 후속 구현 대상이며 현재는 문서만 작성한다.

## 1. 요구사항

1. 관리자설정의 AI 가드레일 관리 탭에 `컨트롤타워 이동` 버튼을 추가한다.
2. 버튼은 현재 선택한 workspace를 명시하여 새 창으로 컨트롤타워를 연다.
3. 컨트롤타워는 승인 대기·승인 후 사용자 재개 대기·처리 이력을 구분한다.
4. 관리자는 해당 요청의 차단 정책·검사 단계·작업 범위·마스킹된 근거를 확인하고 승인/반려한다.
5. 승인만으로 AI가 실행되거나 프로젝트 자료가 저장되지 않는다. 실행은 요청자의 `이어서 진행`으로 시작한다.
6. 사용자 화면에는 예/아니요와 요청 후 이어서 진행/취소 상태를 명확히 표시한다.

## 2. 현재 화면 구조와 수정 방향

`app/(workspace)/admin/settings/page.tsx`가 AI 가드레일 관리 탭을 제공하고, `components/admin/product-admin.tsx`가 workspace를 선택하여 `GuardrailAdmin`에 이름과 endpoint를 전달한다. `GuardrailAdmin`에는 정책 설정·글로벌 규제 준수·정책 테스트·적용/검사 이력 탭만 있다.

`/admin/ai-guardrails`는 현재 관리자설정으로 이동시키는 호환 URL이다. 이를 컨트롤타워로 전환하지 않고 별도 `/admin/guardrail-control-tower` 경로를 제안한다. 현재 화면의 초안·선택 탭·테스트 첨부는 새 창 열기로 초기화하지 않는다.

현재 관리자 권한은 상품 및 workspace 범위를 검사한다. 기존 `docs/AI_GUARDRAILS.md`의 과거 owner/admin 설명 대신 실제 `lib/guardrail-admin-access.ts`의 범위를 따른다. 승인자는 일반 프로젝트 관리 역할과 다르다.

## 3. 진입 및 새 창

### 3.1 관리자설정 진입점

```text
관리자설정
[회원 관리] [AI 가드레일 관리] [시스템설정] [이력 관리]

대상 워크스페이스 [개발팀 A ▼]

개발팀 A의 입력·출력과 도구 실행 정책을 관리합니다.
                         [컨트롤타워 이동 ↗] [새로고침]

적용 정책 v12  |  차단 모드  |  초안 수정 4
[정책 설정] [글로벌 규제 준수] [정책 테스트] [적용·검사 이력]
```

- 선택 workspace가 없으면 버튼을 비활성화하고 workspace 생성/선택 안내를 제공한다.
- 버튼 접근 이름: `개발팀 A 가드레일 컨트롤타워 새 창으로 열기`.
- 목적지: `/admin/guardrail-control-tower?workspaceId=<선택값>`. 검색 문자열에 프롬프트·사용자 이메일·승인 토큰을 넣지 않는다.
- super-admin 화면에도 제공하기로 결정하면 `/super-admin/guardrail-control-tower?workspaceId=...`를 별도로 추가한다.
- 클릭 이벤트 안에서 새 창 열기를 시도하고 `noopener,noreferrer`, 예시 크기 1440×960, resize/scroll 가능 옵션을 사용한다. 화면보다 크면 가용 영역에 맞춘다.
- 브라우저 설정에 따라 탭으로 열릴 수 있다. 팝업 차단 시 `새 창을 열 수 없습니다. 아래 링크로 컨트롤타워를 열어 주세요.`와 사용자 클릭용 새 창 링크를 제공한다.
- noopener 환경의 반환값만으로 차단 여부를 단정하지 않는다. 새 창 열기 구현에 맞는 감지 또는 항상 보조 링크를 제공하는 방식을 선택한다.
- 새 창이 열린 뒤 부모에서 workspace를 바꿔도 이미 열린 창의 범위를 자동 변경하지 않는다. 각 창은 상단에 대상 workspace를 명시한다.

### 3.2 페이지 구성

기본안은 전역 프로젝트 사이드바 없이 넓게 사용하는 독립 화면이다. `app/(control-tower)/...` route group을 제안한다. 기존 root layout의 Provider/테마 기반을 사용하되 `(workspace)/layout.tsx`에서 제공하던 인증·온보딩·게스트 제한·WorkspaceQueryBoundary·개인 테마 초기화를 누락하지 않게 별도 layout/boundary에서 재사용한다.

새 창에서 현재 세션을 다시 확인하고 workspace 관리 권한을 서버에서 검증한다. URL 직접 접근·변조도 같은 검사를 거친다. 관리자설정에서 버튼이 보인다는 사실은 접근 권한의 근거가 아니다.

## 4. 컨트롤타워 화면

### 4.1 목록과 상세 배치

```text
Guardrail Control Tower             상품: Team 상품 A / 워크스페이스: 개발팀 A
마지막 갱신 2026-11-23 14:32:10 KST    [새로고침] [관리자설정 열기 ↗]

[승인 대기 8] [승인 후 재개 대기 3] [재개 실행 중 1]

[승인 대기] [승인 후 재개 대기] [처리 이력]
기간 [최근 7일 ▼]  요청자 [이름/이메일]  프로젝트 [전체 ▼]
정책 [전체 ▼]  검사 단계 [전체 ▼]  상태 [전체 ▼] [검색] [초기화]

┌ 요청 목록 ───────────────────────┬ 선택 요청 상세 ───────────────────┐
│ 요청시각  요청자  프로젝트  정책   │ 요청 ID / 상태 / version          │
│ 14:30 김사용 주문관리 차단문구 대기 │ 요청자 · workspace · 프로젝트     │
│ 14:25 이사용 고객포털 외부링크 대기 │ 요청 시각 · 만료 시각 · 검사 단계  │
│ ...                              │ 차단 정책/규칙 및 적용 정책 v12     │
│                                  │ 마스킹 요청 요약 / 실행 예정 범위   │
│ [이전] [다음]                    │ [요청 요약] [차단 근거] [처리 이력] │
│                                  │ 처리 의견 [                     ]  │
│                                  │ [반려] [이 요청 승인]              │
└──────────────────────────────────┴──────────────────────────────────┘
```

왼쪽에서 사용자가 보낸 요청 한 건을 선택하면 오른쪽이 **그 요청 건을 심사하고 승인하는 화면**으로 바뀐다. 상세를 선택하기 전에는 `왼쪽에서 승인 요청을 선택해 주세요.`를 표시하고 승인/반려 버튼을 노출하지 않는다. 정책 설정/정책 테스트의 검사 결과를 승인하는 화면으로 혼동하지 않도록 오른쪽 제목은 `승인 요청 상세·처리`로 표시한다.

수치는 배치 예시이며 실제 데이터나 운영 화면 구현 결과가 아니다. 1280px 이상은 목록/상세 약 55:45, 960~1279px은 목록 선택 시 상세 패널, 960px 미만은 목록→상세 단일 열로 전환한다. 상세의 목록 돌아가기는 필터·스크롤·선택 상태를 보존한다.

### 4.2 요약 및 탭

| 항목 | 내용 |
| --- | --- |
| 승인 대기 | 사용자 예 선택으로 실제 생성된 pending 요청 건수. 차단 이벤트 수나 예/아니요 선택 전 challenge 수가 아니다. |
| 승인 후 재개 대기 | approved이며 미만료·미취소인 요청 수. 승인 건수를 실행 완료 건수로 표시하지 않는다. |
| 재개 실행 중 | resuming인 요청 수. 중지 미확인 상태가 있으면 상세에 구분한다. |
| 승인 대기 탭 | 기본 탭. 오래된 요청 우선, 만료 임박 표시. |
| 승인 후 재개 대기 탭 | 승인 시각·승인자·만료·요청자 재개 대기 표시. 관리자 재실행 버튼은 제공하지 않는다. |
| 처리 이력 탭 | 완료/반려/취소/만료/무효화/재차단/실패와 상태 변화. 최신 처리 우선. |

탭마다 상태 기본값을 정하고 기간/프로젝트 필터와 서버 목록·건수를 일치시킨다. 기본 목록 페이지는 20건 제안이며 cursor 기반으로 조회한다. 기존 정책 관리 API의 최근 검사 100건을 가져와 브라우저에서 승인 목록처럼 가공하지 않는다.

요약은 현재 탭/페이지가 아닌 상단 workspace 전체를 기준으로 하며 그 범위를 라벨에 명시한다. 기간 필터를 요약에도 적용할지 선택하면 API와 라벨을 함께 바꾼다.

### 4.3 필터와 목록 컬럼

| 필터 | 규칙 |
| --- | --- |
| 기간 | KST 기준 최근 7일 기본 제안. 직접 날짜 선택 가능. 서버에서 UTC 경계로 변환하고 종료 다음 날 미만으로 검색. |
| 요청자 | 현재 이름/이메일 검색. 기록된 요청자 이름도 상세에 보존 여부 결정. |
| 프로젝트 | 관리 가능한 선택 workspace 프로젝트만. 프로젝트 없는 dashboard/team 요청은 별도 `프로젝트 없음` 항목. |
| 정책/검사 단계 | 서버 규칙 카탈로그의 표시명과 ID. input/context/tool/tool-result/output 구분. |
| 상태 | 현재 탭에 맞는 상태만 선택. 필터 변경 후 검색에서 첫 페이지로 이동. |

목록 컬럼: 요청 시각, 요청자, 프로젝트/실행 대상, 차단 정책(복수 시 대표명+외 n개), 검사 단계, 상태, 만료/처리 시각. 요청 ID는 상세와 복사 기능으로 제공한다. 프롬프트 원문과 첨부 미리보기는 목록에 넣지 않는다.

## 5. 요청 상세 및 관리자 동작

### 5.1 상세 정보

| 영역 | 표시 내용 |
| --- | --- |
| 기본 정보 | 승인 요청 ID, 원 requestId, 논리 실행 ID, 요청자, 상품/workspace, 프로젝트, 대화 식별자, 실행 대상, 요청/만료 시각. |
| 차단 정책 | 규칙 ID·한국어 정책명, severity, 검사 단계, 정책 버전, 승인 가능 여부와 불가 사유. |
| 요청 요약 | 서버가 제공한 마스킹 프롬프트 발췌, 첨부 개수/형식, 분석/생성/수정/삭제 등 요청 범위. 전체 개인 대화는 기본 비공개. |
| 차단 근거 | 마스킹된 해당 검사 객체의 최소 발췌와 구조화 규칙 설명. 모델 자유 서술을 확정 판정처럼 표시하지 않는다. |
| 실행 예정 | 해당 checkpoint 다음 단계, 이미 검증된 pending 건수/작업 유형, 아직 저장되지 않았다는 안내. 생성 전이면 `아직 생성되지 않음`. |
| 승인 범위 | “이 사용자·이 요청·이 정책 버전의 표시된 검사 대상에 한해 적용됩니다.” |
| 처리 이력 | 요청, 승인/반려, 취소, 만료, 무효화, 재개, 재차단, 완료/실패. 처리자와 KST 시각·사유 표시. |

심사 상세 API도 관리 권한과 보존 정책을 적용한다. 민감 본문을 임의 HTML로 렌더링하지 않고 첨부 원본은 기본 제공하지 않는다. 승인 내용에 참고 자료의 우회 지시가 포함되어도 실행 명령으로 취급하지 않는다.

관리자가 요청 건을 판단할 수 있도록 상세 본문에는 다음 세 가지를 각각 구분해 표시한다.

- **사용자가 요청한 작업:** 예를 들어 “요구사항 문서에 외부 참고 링크를 추가해 주세요.”와 같이 실제 작업 목적과 대상이 드러나도록 표시한다. 민감정보는 마스킹하되 정책명만 보여주고 요청 내용은 생략하지 않는다.
- **가드레일이 탐지한 내용:** 탐지 정책명·규칙 ID·검사 단계와 차단된 링크/문구 등 판단에 필요한 발췌를 표시한다. 입력 이외에 AI 출력이나 도구 인자가 차단되었다면 그 검사 대상을 별도로 구분한다.
- **승인하면 진행할 작업:** 예를 들어 “표시된 외부 링크 검사에 한해 예외 적용 후 해당 요구사항 변경안 생성을 계속합니다.”처럼 해당 요청의 실행 범위를 표시한다. 아직 생성되지 않은 결과를 완료된 작업처럼 표시하지 않는다.

마스킹 때문에 판단 정보가 부족하면 `추가 확인 필요` 안내를 표시한다. 원문 열람 기능과 공개 범위는 결정 사항이며, 구현 시 정책명만으로 승인을 유도하는 화면으로 축소하지 않는다.

### 5.2 승인/반려

pending 상세의 하단에 처리 의견과 `반려`/`이 요청 승인` 버튼을 둔다. 권고안은 양쪽 의견 필수, 공백 제외 1~1000자다. 글자 수는 구현 사양 확정 시 조정한다.

승인 버튼 선택 시 확인 영역에 요청자·프로젝트·정책·승인 범위를 재표시한다.

> 이 요청의 표시된 가드레일 검사에 한해 예외를 승인합니다. 승인 후 요청자가 ‘이어서 진행’을 눌러야 작업이 실행됩니다.

`승인 확정` 이후 서버 성공 시 상태를 `승인됨 · 사용자 재개 대기`로 바꾸고 목록·상세·요약을 무효화한다. 처리 중 버튼을 비활성화하며 승인 확정 요청을 자동 재시도하지 않는다. 반려는 사유를 요청자에게 전달하고 실행을 종료한다.

다른 관리자가 이미 처리했으면 `다른 관리자가 먼저 처리했습니다. 최신 상태를 확인해 주세요.`를 표시하고 최신 상세로 갱신한다. 만료·정책/원본 변경·권한 상실은 해당 사유와 읽기 전용 상태를 표시한다. 클라이언트의 이전 canApprove 값으로 처리를 강행하지 않는다.

일괄 승인, 승인 후 자동 재개, 요청자의 다른 프롬프트까지 승인, 정책 모드 변경은 기본 화면에 포함하지 않는다. 필요하면 각각 별도 요구로 결정한다.

## 6. 사용자 HITL 화면

### 6.1 예/아니요 선택

```text
가드레일 확인
[사용자 지정 차단 문구] 가드레일 정책으로 인해 해당 작업에 대해
관리자에게 승인 요청을 하시겠습니까?

검사 단계: 입력  /  적용 정책: v12
[정책 상세 보기]
[아니요(No)] [예(Yes)]
```

정책 상세는 복수 규칙·검사 단계·요청 범위와 승인 불가 사유를 표시한다. 민감 원문을 다시 노출하지 않는다. 어느 선택도 자동 확정하지 않고 키보드로 접근할 수 있게 한다. 대화 입력 DOM·첨부 초안·현재 창 모드를 유지한다.

예 선택을 전송 중이면 중복 선택을 막는다. 네트워크 실패 시 동일 challenge의 상태를 재조회하고 성공 여부를 확인한 뒤 재시도한다. 아니요는 관리자 요청을 만들지 않고 `승인 요청하지 않음`으로 종료한다.

### 6.2 요청 후 대기 및 종료 상태

```text
관리자 승인 요청을 보냈습니다.
정책: 사용자 지정 차단 문구 / 상태: 승인 대기
요청 ID: ...  /  만료: 2026-11-24 14:30 KST

[이어서 진행 (비활성)] [취소]
관리자 승인 후 진행할 수 있습니다.
```

| 상태 | 사용자 표시 | 버튼 |
| --- | --- | --- |
| pending | 관리자 승인 대기 | 이어서 진행 비활성 / 취소 활성 |
| approved | 관리자가 승인했습니다. 이어서 진행을 눌러 주세요. | 이어서 진행 활성 / 취소 활성 |
| resuming | 승인된 요청을 이어서 실행하고 있습니다. | 이어서 진행 비활성 / 생성 중지 |
| stop unconfirmed | AI 중지를 확인하고 있습니다. | 중지 재시도, 재개 비활성 |
| rejected | 관리자가 반려했습니다. 사유 표시 | 새 요청 안내 / 닫기 |
| cancelled | 요청을 취소했습니다. | 닫기 |
| expired | 승인 요청이 만료되었습니다. | 새 요청 안내 / 닫기 |
| invalidated | 정책 또는 실행 조건이 변경되어 재개할 수 없습니다. | 원인 표시 / 새 요청 안내 |
| reblocked | 다른 검사 대상 또는 정책에 걸려 다시 확인이 필요합니다. | 새 challenge의 예/아니요 |
| completed | 실행 결과 및 저장/사용자 변경안 검토 상태 | 기존 결과/사용자 승인 UI |
| failed | 실행 실패 사유와 저장 여부 | 서버가 허용한 경우에만 명시 재시도 |

새로고침 후 서버에서 같은 대화의 challenge/승인 상태를 복원한다. 다른 workspace나 대화로 이동하면 해당 카드가 섞이지 않아야 한다. 대기 중 프롬프트/첨부/대상 변경은 취소 후 새 요청으로 안내한다. 창을 닫는 동작만으로 서버 요청을 취소하지 않는다.

## 7. 갱신·오류·접근성

- 자동 조회는 승인 대기 또는 실행 중인 화면에서 가시 상태일 때만 15초를 제안한다. 최종 상태에서 종료하고 수동 새로고침을 항상 제공한다. 재개 실행의 진행 조회 간격은 작업 API 설계에 맞춰 별도 설정한다.
- 권한 확인 API의 주기 조회를 새로 추가하지 않는다. 화면/작업 진입과 서버 작업마다 기존 방식으로 검증한다.
- 사용자/workspace 범위 Query key를 사용하고 원문/checkpoint를 key나 목록 캐시에 넣지 않는다. 새 창은 독립 QueryClient일 수 있으므로 한 창의 invalidate만으로 다른 창이 갱신된다고 가정하지 않는다.
- 로딩은 목록/상세 각각 표시한다. 검색 결과 없음과 실제 대기 요청 없음, 조회 실패를 구분한다. 실패 시 기존 목록이 최신이라는 표시를 하지 않는다.
- 인증 만료는 로그인 안내, 관리 권한 상실은 접근 제한, 삭제된 프로젝트/대화는 재개 불가 상세로 처리한다. 다른 workspace 요청의 존재를 오류 메시지로 노출하지 않는다.
- 상태는 색상과 텍스트를 함께 사용한다. 상태 변화는 aria-live로 안내하되 폴링마다 반복 낭독하지 않는다.
- 목록 행 선택은 키보드로 가능하게 하고 상세 제목으로 초점을 옮긴다. 모달은 초점 고정·닫힌 뒤 원위치 복귀를 지원한다. 처리 의견의 오류는 입력과 연결한다.
- 기존 개인 테마를 사용하며 화면 CSS는 `.guardrail-control-tower` 하위에 한정한다. 공통 `workspace-dialog admin-detail-dialog`를 재사용한다.

## 9. 검증 방법

1. 관리자설정에서 선택한 workspace로 새 창이 열리고 기존 초안·정책 테스트 입력이 남는지 확인한다.
2. 팝업 차단/탭 열기/좁은 화면에서도 보조 링크와 화면 접근이 가능한지 확인한다.
3. 비관리자·다른 상품 관리자·workspaceId 변조·직접 URL 접근에서 화면/API·건수 정보가 노출되지 않는지 확인한다.
4. 예/아니요 선택, 예 전송 실패, 중복 클릭, 새로고침, 창 닫기/다시 열기를 검사한다. 아니요는 관리자 목록에 생성되지 않아야 한다.
5. 승인 대기/승인 후 재개 대기/반려/취소/만료/무효화/재차단의 버튼과 안내가 실제 서버 상태와 일치하는지 확인한다.
6. 관리자 승인 후 사용자 클릭 전에는 AI 호출·프로젝트 저장이 없어야 한다. 클릭 후에도 기존 사용자 변경안 승인이 별도로 필요한지 확인한다.
7. 두 관리자 동시 처리와 두 사용자 창의 동시 재개에서 1건만 처리되고 다른 창은 최신 상태를 표시하는지 확인한다.
8. 기간 KST 경계·서버 필터·페이지 이동·복수 규칙·프로젝트 없는 요청·요약 집계 범위를 검증한다.
9. 프롬프트/첨부/키가 URL·목록·알림·로그로 유출되지 않고 상세는 허용된 마스킹 DTO만 렌더링하는지 확인한다.
10. 키보드·스크린리더 상태 안내·초점 복귀·개인 테마·960px 이하/큰 창에서 사용 가능한지 확인한다.

검증은 후속 구현 시 임시 DB·합성 사용자·모의 AI와 브라우저에서 수행한다. 이번 문서 작성 단계에서는 정적 확인과 문서 링크 검증만 수행하며 소스/DB 실행은 하지 않는다.
