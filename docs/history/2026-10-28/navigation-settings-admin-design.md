# 좌측 메뉴·개인 설정·관리자설정 개편 분석 및 설계

- 작성일: 2026-10-28 (Asia/Seoul)
- 상태: 구현 전 분석·설계. 이번 작업은 HISTORY.md만 작성하며 소스·설정 파일·마이그레이션·DB를 변경하지 않는다.
- 기준: 현재 구현된 회원·권한·플랜 구조를 유지하면서 메뉴, 개인 설정, 관리자 화면을 재구성한다.
- [회원·권한·요금제 개편 분석 및 설계](membership-roles-plans-design.md) | [WORK_HISTORY.md](../../../WORK_HISTORY.md)
- 구분: 요청에 명시된 내용은 확정 요구사항, 경로·기본값·세부 동작은 설계안이다. 미확정 항목은 12절에 별도로 표시한다.

## 1. 요청사항과 반영 방향

| 번호 | 확정 요구사항 | 수정 방향 |
| --- | --- | --- |
| 1 | 대시보드·팀공유·AI Chatbot·요금제·설정·도움말을 모든 사용자에게 표시 | 공통 메뉴 정의 통합, 로그인/게스트 화면에 동일한 메뉴 순서 적용 |
| 2 | 설정에 토큰사용량·인터페이스관리·계정설정 3개 탭 | 독립 설정 화면과 탭별 주소/상태 구성 |
| 3 | 기존 계정설정 모달의 토큰사용량 이동 | AiTokenStatistics 재사용, 기존 조회 범위와 필터 유지 |
| 4 | 인터페이스관리에서 토스트 상/하 위치와 기본 테마 설정 | 개인 환경설정 저장과 공통 토스트 표시기 연결 |
| 5 | 기존 모달의 프로필 이동 | 계정설정 탭에 현재 프로필과 저장 흐름 배치 |
| 6 | 관리자에게 요금제 아래 관리자설정 메뉴, 내부 4개 탭 | 계정 역할 master/admin 전용 관리자 화면 구성 |
| 7 | 관리자 요금제 탭에는 기존 플랜 편집 영역만 표시 | 현재 PlanAdmin에서 플랜 편집과 회원 관리를 분리 |
| 8 | 회원 검색·조회·페이징, 페이지 크기 10/20/50/100, 기본 20 | LIMIT 200 고정 조회를 서버 검색·집계·페이지 조회로 변경 |
| 9 | 회원 행 더블클릭 시 상세 정보 및 회원 플랜·역할 영역 표시 | 회원 상세 다이얼로그, 조회와 변경 권한 분리 |
| 10 | AI가드레일관리 탭에 기존 관리 화면 표시 | GuardrailAdmin 재사용, 관리자 진입과 기존 워크스페이스 범위 명시 |
| 11 | 이력 탭 상단 DB_LOGGING_ENABLED 변경, 전체 이력 검색·동일 페이징 | 전역 관리자용 이력 조회 API와 설정 변경 API 신설 |

5번의 “사용자설정”은 2번의 “계정설정” 탭을 가리키는 것으로 해석한다. 실제 화면 명칭은 **토큰 사용량 / 인터페이스 관리 / 계정 설정**, **요금제 / 회원 관리 / AI 가드레일 관리 / 이력 관리**로 통일한다.

## 2. 현재 소스 분석

| 영역 | 현재 구현 | 변경 시 주의점 |

| 테마 | stores/theme.ts, lib/theme.ts, ThemeToggle. light/dark와 브라우저 공통 localStorage 키 사용 | 회원별 DB 설정은 없으며 첫 화면 테마 적용 스크립트와도 동기화 필요 |
| 토스트 | 확인한 소스에서 전역 토스트 저장소·표시기 없음. 성공/오류는 주로 인라인, 알림 벨은 별도 팝오버 | 위치 설정 UI만 만들어도 기존 메시지가 자동으로 토스트가 되지는 않음 |
| 플랜 관리 | /admin/plans와 PlanAdmin에 플랜 편집·회원 플랜/역할 수정 영역이 결합 | 요금제 탭에서 회원 목록 조회와 폼을 제거하고 회원 탭으로 이동 |
| 회원 조회 | /admin/plans 서버 페이지와 /api/admin/members 모두 최신 200명 고정 조회 | 프런트에서 200명을 잘라 페이징하면 전체 회원 검색이 안 됨 |
| 회원 변경 | /api/admin/members PATCH는 플랜 변경, master의 일반 계정 역할 변경, 변경 기록 저장 지원 | 상세 화면으로 이동해도 기존 역할 보호·사용량 보존·세션 취소 규칙 유지 |
| 가드레일 | /admin/ai-guardrails와 GuardrailAdmin. 관리자 판정이 현재 워크스페이스 owner/admin 기준 | 새 관리자설정은 계정 master/admin 기준이므로 메뉴뿐 아니라 API 권한도 검토 필요 |
| 개인 이력 | /api/activity는 현재 회원·워크스페이스의 최근 50건만 반환 | 이 API를 그대로 전역 관리자 이력 조회에 사용하면 누락 발생 |
| 로깅 설정 | app_settings의 DB_LOGGING_ENABLED, getAppSetting/getBooleanSetting 읽기 함수 존재 | 관리자용 안전한 갱신 경로는 새로 필요 |
| 감사 기록 | lib/audit.ts가 SQL 내부에서 로깅 설정 확인. audit_logs는 수정·삭제 방지 트리거 보유 | 설정을 끈 뒤 동일 audit 함수로 변경 사실을 기록하면 그 기록도 빠지는 문제 고려 |
| 다른 이력 | plan_change_logs, artifact_revisions, AI 토큰/가드레일 기록은 별도 저장 체계 | “전체 이력”의 의미와 로깅 스위치 적용 범위를 화면에 명확히 구분 |
| 게스트 | app/guest/[...path]/page.tsx에 독립 메뉴와 정적 샘플 화면 | 공통 6개 메뉴를 추가하되 이전의 메뉴 이동·조회 전용 정책 유지 |

현재 WorkspaceShell은 /admin/ai-guardrails만 별도 관리자 제목으로 인식한다. 새 설정·관리자 경로와 기존 요금제 경로의 제목·현재 메뉴 표시도 함께 정리해야 한다.

## 3. 메뉴와 진입 구조 설계안

### 3.1 좌측 패널 순서

| 순서 | 메뉴 | 로그인 회원 | 게스트 |
| --- | --- | --- | --- |
| 1 | 대시보드 | /dashboard | /guest/dashboard |
| 2 | 팀공유 | /team | /guest/team |
| 3 | AI Chatbot | 기존 AI 대화 패널 동작 | /guest/ai 샘플 화면 |
| 4 | 요금제 | /settings/subscription | /guest/subscription 요금제 안내 |
| 5 | 관리자설정 | master/admin에게만 /admin/settings | 표시 안 함 |
| 다음 | 설정 | /settings | /guest/settings 샘플 화면 |
| 마지막 | 도움말 | 기존 도움말 모달을 공통 컴포넌트로 재사용 | /guest/help 또는 동일한 읽기 전용 안내 |

- 관리자설정은 요청대로 요금제 바로 아래에 배치한다. 일반 사용자에게는 해당 행 없이 공통 6개 메뉴만 표시한다.
- 별도 “요금제·회원 관리”, “AI 가드레일 관리” 메뉴는 관리자설정으로 통합한다. 계정 설정 메뉴의 표시명은 “설정”으로 변경한다.
- 워크스페이스 선택, 사용자 요약, 로그아웃은 메뉴 목록과 구분한 계정 영역에 유지한다. 게스트의 로그인·회원등록 진입도 유지한다.
- 사용자 요약 클릭은 기존 프로필 모달 대신 /settings?tab=account로 연결한다.
- 메뉴 정의는 href를 가진 링크형과 AI/도움말 같은 실행형을 구분한다. 권한 판정, 메뉴 검색, 아이콘, 표시명, 활성 상태는 같은 정의를 사용한다.
- /settings/subscription은 “요금제”만 활성화하고 /settings는 “설정”을 활성화한다. 단순 startsWith('/settings')로 두 메뉴를 동시에 활성화하지 않는다.
- /admin/settings의 모든 탭에서는 “관리자설정”을 활성화하고 상단에 현재 탭 이름을 표시한다.

### 3.2 탭 주소와 이전 경로

- 설정: /settings?tab=usage|interface|account, 기본 usage.
- 관리자설정: /admin/settings?tab=plans|members|guardrails|history, 기본 plans.
- URL 쿼리로 직접 진입·새로고침·브라우저 뒤로가기를 지원한다. 허용하지 않은 tab 값은 기본 탭으로 정규화한다.
- /admin/plans → /admin/settings?tab=plans, /admin/ai-guardrails → /admin/settings?tab=guardrails로 호환 이동한다. 해당 화면을 두 군데에서 따로 유지하지 않는다.
- 탭별 필요한 데이터만 읽는다. 요금제 탭 진입 시 전체 회원·감사 로그를 미리 읽지 않는다.
- 설정·관리자 화면은 AI 산출물 생성 대상 화면으로 등록하지 않는다. 기존 AI 화면 문맥이 남아 다른 프로젝트 작업이 실행되지 않도록 패널 상태/지원 범위를 정리한다.

### 3.3 모든 사용자와 게스트의 의미

“모든 사용자에게 메뉴 표시”에는 기존 guest를 포함하는 것으로 설계한다. 다만 이전 요청의 guest 조회 전용 제한을 폐기하는 요청은 아니므로, guest는 화면 안내와 샘플 탭만 보고 프로필·환경설정 저장, 실제 토큰/회원/이력 조회, AI 실행은 할 수 없다. 관리자설정은 로그인한 계정 역할 master/admin에게만 노출한다.

## 4. 일반 설정 화면 설계안

### 4.1 토큰 사용량 탭

- 기존 AiTokenStatistics를 재사용한다. 기간·프로젝트·채팅방 필터, 통계 차트, 사용량 미확정 표시와 갱신 동작을 유지한다.
- 현재 API는 활성 워크스페이스 내 본인 사용량이다. 이번 UI 이동에서 이를 임의로 전역 전체 계정 사용량으로 확장하지 않는다.
- 요금제 화면의 계정 전체 할당량/잔여량과 조회 범위를 혼동하지 않도록 “현재 워크스페이스의 내 사용량”을 명시한다. 전체 워크스페이스 합산은 별도 정책 확인 대상이다.
- 다른 탭으로 이동하면 통계 폴링과 진행 중 요청을 중단한다. 비활성 탭의 타이머를 계속 실행하지 않는다.
- 기존 계정설정 모달에서 통계를 제거해 같은 컴포넌트가 이중으로 마운트되지 않게 한다.

### 4.2 인터페이스 관리 탭

| 항목 | 입력 | 저장 단위 | 기본값 설계안 |
| --- | --- | --- | --- |
| 토스트 위치 | 상단 / 하단 라디오 선택 | 로그인 회원 개인 | 하단 권장, 최종 확인 필요 |
| 기본 테마 | 라이트 / 다크 선택 | 로그인 회원 개인 | 기존 초기값인 라이트 |

- “상/하 표시”는 표시 위치 선택으로 해석한다. 토스트 표시 끄기 기능이나 시스템 테마 자동 감지는 별도 요청이 없어 추가하지 않는다.
- 개인 선호 설정이므로 app_settings의 전역 설정에 저장하지 않는다. 워크스페이스를 바꿔도 같은 회원의 설정을 유지한다.
- 저장 전 미리보기와 저장·취소를 제공하는 안을 권장한다. 취소/실패하면 저장된 테마와 위치로 돌아간다. 미리보기만으로 DB를 변경하지 않는다.
- 테마는 기존 CSS 변수와 data-theme를 사용한다. 테마 토글과 설정 탭이 같은 상태와 저장 함수를 사용하고 서로 다른 기본값을 갖지 않도록 한다.
- 상단 테마 토글을 유지한다면 토글 변경도 개인 기본 테마에 반영하는 안을 권장한다. 임시 전환과 기본값을 분리할지는 12절에서 확인한다.
- 로그인 시 DB 저장값을 기준으로 적용하고, 브라우저 캐시는 첫 화면 표시 보조로 사용한다. 기존 THEME_INIT_SCRIPT와 연계해 깜빡임과 hydration 불일치를 방지한다.
- 현재 공통 localStorage 키는 계정별 설정이 아니다. 신규 캐시는 회원 ID로 구분하고 계정 전환 시 이전 회원의 선호값을 다른 회원 DB에 자동 복사하지 않는다.
- 저장소 사용이 차단돼도 현재 화면의 테마 적용은 가능하게 하고, 설정 저장 실패는 명확히 표시한다. 서버 저장과 브라우저 캐시 중 두 개가 동시에 원본이 되지 않게 한다.

**토스트 구현 범위**

- 전역 토스트 표시기 1개와 공통 상태/호출 함수를 신설한다. 위치를 저장한 뒤 실제 성공·안내 메시지가 그 위치에 나와야 한다.
- 기존 알림 벨 팝오버는 토스트와 별개로 유지한다. 모든 오류/폼 검증 메시지를 무조건 토스트로 교체하지 않는다.
- 설정 저장, 플랜/회원 수정 등 완료 알림부터 공통 토스트를 사용한다. 입력 필드 오류와 사용자가 조치해야 하는 중요한 오류는 인라인 안내도 유지한다.
- 상단은 헤더, 하단은 모바일 안전 영역과 AI 패널을 가리지 않도록 배치한다. 수평 위치는 중앙을 권장하되 최종 확인한다.
- 연속 알림은 제한된 개수로 쌓고 동일 요청의 중복 표시를 막는다. 성공·안내는 role=status, 중요한 실패는 적절한 alert를 사용하며 포커스를 강제로 이동하지 않는다.

### 4.3 계정 설정 탭

- 현재 모달의 이름·이메일·워크스페이스·계정 역할·플랜 정보를 이동한다. 이름 변경은 기존 /api/me PATCH 흐름을 재사용한다.
- 계정 역할과 프로젝트/워크스페이스 역할을 다른 개념으로 표시한다. user가 프로젝트 owner라는 이유로 서비스 관리자라고 표시하지 않는다.
- master의 고정 이름·이메일과 역할 보호, 소셜 계정의 이메일 없음 표시를 유지한다.
- 본인 설정에는 타인의 역할 변경, 플랜 강제 부여, 비밀번호 해시 조회 기능을 추가하지 않는다.
- 저장 성공 시 전역 사용자 표시와 서버 화면을 갱신해 좌측 사용자 이름에도 반영한다.
- 기존 프로필 모달과 관련 상태를 WorkspaceShell에서 제거한다. 도움말 모달은 별도 컴포넌트로 분리해 계속 사용할 수 있다.

## 5. 관리자설정 권한과 탭 구성

| 항목 | master | admin | user/guest |
| --- | --- | --- | --- |
| 관리자설정 메뉴·화면·조회 API | 허용 | 허용 | 불가 |
| 플랜 가격·한도 수정 | 허용 | 허용 | 불가 |
| 회원 전체 검색·상세 조회 | 허용 | 허용 | 불가 |
| 회원 플랜 변경 | 허용 | 허용 | 불가 |
| 일반 회원의 계정 역할 변경 | 허용 | 조회만 가능 | 불가 |
| master 생성·삭제·강등·고정 신원 변경 | 불가 | 불가 | 불가 |
| 로깅 설정 변경·전역 이력 조회 | 허용 | 허용 | 불가 |

- 관리자 기준은 isPlatformAdmin(accountRole) / requirePlatformAdmin이다. 프로젝트 owner/admin 또는 워크스페이스 owner만으로 전역 관리 권한을 부여하지 않는다.
- 상세 화면에 역할 영역을 표시하는 요구와 역할을 변경할 권한은 별개다. 기존 master 전용 역할 변경 정책을 유지한다.
- 메뉴 숨김뿐 아니라 페이지·API·상세 ID 직접 접근에서도 권한을 확인한다. 비로그인은 401, 로그인 권한 부족은 403을 기본으로 한다.
- 클라이언트가 전달하는 master 여부나 workspaceId로 관리자 범위를 결정하지 않는다. 관리자 목록은 현재 워크스페이스로 암묵 제한하지 않는 전역 회원/이력 조회다.

### 5.1 요금제 탭

- 현재 PlanAdmin을 플랜 편집 컴포넌트와 회원 관리 컴포넌트로 분리한다. 이 탭에는 플랜 편집 영역만 넣는다.
- 월간/연간 가격, 가격 방식, 프로젝트/토큰/이미지/첨부 한도, 이력 생성, 추천 표시, version 충돌 검증을 유지한다.
- 기존 /api/admin/plans를 재사용한다. 화면을 옮기는 과정에서 기본값으로 관리자 수정값을 덮어쓰거나 회원 구독/사용량을 초기화하지 않는다.

### 5.2 AI 가드레일 관리 탭

- 현재 GuardrailAdmin의 정책·초안·게시 버전·복원·시험·기록 UI를 재사용한다. 관리자설정 4개 탭 안에서 기존 가드레일 내부 탭을 유지할 수 있다.
- 새 관리자설정 진입에는 계정 master/admin 검사가 필요하다. 기존 /admin/ai-guardrails 페이지와 /api/admin/ai-guardrails에도 같은 전역 관리자 조건을 적용해 이전 URL로 우회하지 못하게 한다.
- 현재 가드레일 정책은 워크스페이스별 데이터다. 관리자 화면으로 이동했다고 서비스 전체 공통 정책으로 바꾸지 않는다.
- 권장안은 계정 관리자 검사와 기존 대상 워크스페이스 owner/admin 검사를 함께 적용하는 것이다. 화면에 대상 워크스페이스를 표시하고, 권한이 없으면 명확히 안내한다.
- 전역 관리자가 타인의 모든 워크스페이스 가드레일을 조작할지 여부는 별도 확인한다. 단순 통합 과정에서 기존 소속 제한을 제거하지 않는다.
- 이미지 첨부 한도, AI 시험 토큰 차감, 초안 버전 충돌과 정책 변경 기록 등 기존 동작을 보존한다.

## 6. 회원 관리 설계안

### 6.1 검색과 목록

- 기본 검색은 이름·이메일·회원 ID의 부분 일치다. 계정 역할·플랜 필터와 초기화 버튼을 추가하는 안을 권장한다.
- 목록 열: 이름, 이메일, 계정 역할, 플랜, 가입일, 상세 보기. 이름과 별개인 직무 정보는 상세에 표시한다.
- 가입일은 users.created_at, 화면 표시는 KST로 한다. 현재 전용 최근 로그인 컬럼은 없으므로 이를 임의로 만들어 표시하지 않는다.
- users를 기준으로 구독 정보를 결합한다. 구독 데이터가 누락된 회원도 목록에서 사라지지 않도록 조회 구조와 오류 표시를 설계한다.
- 소셜 제공자 정보가 필요하면 회원당 한 행을 유지하도록 집계한다. OAuth 계정 JOIN 때문에 동일 회원이 여러 행으로 페이징되지 않게 한다.
- 서버에서 검색 조건과 전체 건수를 계산하고 LIMIT/OFFSET을 적용한다. 현재 LIMIT 200 방식은 제거한다.

### 6.2 더블클릭과 상세 화면

- 회원 행 더블클릭으로 상세 다이얼로그를 연다. 동일한 동작의 “상세 보기” 버튼과 키보드 진입도 제공해 모바일·키보드 사용자도 접근할 수 있게 한다.
- 상세는 선택한 회원 ID로 새로 조회한다. 목록에 있던 값만으로 편집 폼을 열지 않는다.
- 기본 정보 영역과 “회원 플랜·역할” 영역을 나눈다. 기본 정보는 조회 위주이며 별도 요청 없는 타인 이름·이메일 편집은 추가하지 않는다.
- 기본 정보: 회원 ID, 이름, 이메일 또는 소셜 계정 표시, 직무, 가입/수정 시각. 비밀번호 해시·세션·토큰·암호화 자료는 반환하지 않는다.
- 플랜은 master/admin이 변경할 수 있고 계정 역할은 master만 변경한다. admin에게는 역할을 읽기 전용으로 표시한다. master 계정의 역할은 누구에게도 변경 선택지로 제공하지 않는다.
- 상세를 닫으면 검색어·필터·페이지·페이지 크기를 유지한다. 저장 후 해당 행과 상세를 다시 읽고, 필터에서 제외되거나 마지막 페이지가 비면 유효한 페이지로 보정한다.
- 회원을 빠르게 바꾸면 이전 상세 요청을 취소하고, 다른 회원에게 이전 응답이 표시되거나 저장되지 않도록 ID 기준 응답 검증을 한다.
- 저장은 실제 변경 필드만 PATCH한다. 역할만 바꾸는데 플랜 청구 주기가 초기화되는 식의 부수 변경을 막는다.
- 최신 관리 버전과 기대값을 검사해 다른 관리자의 변경을 덮어쓰지 않는다. 역할 변경 시 기존 세션 취소, master 보호, 플랜 변경 시 사용량 유지 규칙을 보존한다.

## 7. 회원·이력 공통 페이징 규칙

| 항목 | 규칙 |
| --- | --- |
| 페이지 크기 | 10, 20, 50, 100만 허용. 신규 진입 기본 20 |
| 페이지 번호 | 1부터 시작하는 정수 |
| 검색 적용 | 검색 버튼 또는 Enter로 적용하고 1페이지로 이동 |
| 필터/크기 변경 | 1페이지로 이동 |
| 응답 | items, total, page, pageSize, totalPages |
| 정렬 | 회원 created_at DESC, id DESC / 감사 occurred_at DESC, id DESC |
| 빈 목록 | 0건 안내, 이전·다음 비활성, 1/0 같은 잘못된 표시 금지 |
| 범위 밖 페이지 | 최신 건수 기준 유효 페이지로 보정하고 응답의 실제 page 사용 |
| 상태 유지 | URL/탭별 상태에 저장해 새로고침·뒤로가기·상세 닫기 시 복원 |

- 두 목록이 같은 페이징 UI와 검증 함수를 사용하되 검색 조건·현재 페이지 상태는 서로 독립시킨다.
- 검색/개수 조회와 목록 조회에 동일한 WHERE 조건을 사용한다. 가능하면 짧은 읽기 트랜잭션으로 같은 시점의 결과를 반환한다.
- 검색어 길이 제한, 정렬 필드 허용 목록, SQL 파라미터 바인딩과 LIKE 와일드카드 처리 규칙을 둔다. 임의 SQL 조각은 받지 않는다.
- 처리 중 이전 결과를 새 검색 결과처럼 표시하지 않는다. AbortController 또는 요청 키로 오래된 응답의 덮어쓰기를 막는다.
- 이력은 계속 추가될 수 있으므로 페이지 변경을 강제하는 자동 새로고침 대신 명시적 새로고침을 권장한다. 전체를 내려받아 브라우저에서 검색·페이지 분할하지 않는다.

## 8. 이력 관리와 로깅 설정 설계안

### 8.1 상단 DB 로깅 설정

- DB_LOGGING_ENABLED의 현재 boolean 값, 설명, 수정자·수정 시각을 보여준다. true는 DB 감사 기록 생성, false는 생성 중단으로 표시한다.
- boolean true/false만 받고 문자열 "true"/"false"는 거부한다. 수정 가능한 키는 DB_LOGGING_ENABLED 하나로 제한한다.
- 저장 시 app_settings.version을 확인하고 value_json, version, updated_by, updated_at을 같은 트랜잭션에서 갱신한다. 다른 관리자가 먼저 수정하면 409와 최신값을 안내한다.
- 서버의 현재 설정 조회와 audit SQL 판정을 계속 사용하므로 재시작 없이 이후 감사 INSERT에 반영된다. 변경 전에 이미 저장된 이력을 지우거나 과거 기록을 소급 생성하지 않는다.
- 스위치를 끄는 작업 자체가 감사 기록에서 사라지지 않도록 별도 최소 관리자 설정 변경 기록을 같은 트랜잭션에 남기는 안을 권장한다. 일반 audit 함수만 호출하는 방식은 새 값 false에 의해 누락될 수 있다.
- 이 설정은 감사 로그 수집을 제어한다. 플랜/역할 변경 기록, AI 과금 원장, 별도 가드레일/산출물 이력까지 모두 멈추는 전역 스위치로 확대하지 않는다.

### 8.2 “전체 이력”의 범위

확정되는 최소 범위는 **현재 회원·워크스페이스 필터에 묶이지 않는 audit_logs 전체 조회**다. 현재 /api/activity의 본인 최근 50건 조회와 분리한다.

관리 작업 누락을 피하기 위한 권장 기본 구성은 audit_logs, 기존 plan_change_logs, 신규 관리자 설정 변경 기록을 하나의 관리자 이력 목록으로 조회하고 “전체 / DB 감사 / 플랜·회원 설정 / 로깅 설정” 출처 필터를 제공하는 것이다. 이는 DB의 모든 테이블을 그대로 노출한다는 의미가 아니다. 정확한 통합 범위는 12절에서 확인한다.

| 저장소 | 의미 | 기본 통합 설계안 |
| --- | --- | --- |
| audit_logs | 인증·조회·변경 등 DB 감사 | 전체 워크스페이스·회원 범위 포함 |
| plan_change_logs | 플랜/회원 구독·역할 변경 | 운영 변경 이력으로 함께 조회 권장 |
| 관리자 설정 변경 기록 | 로깅 활성/비활성 변경 증적 | 로깅 중단 자체도 남기기 위해 함께 조회 권장 |
| artifact_revisions | 사용자용 산출물 버전 스냅샷 | 기존 프로젝트 이력에 유지. 통합 여부 확인 |
| ai_token_usage / quota_reservations | 사용량 측정·정산 상태 | 토큰 통계/운영 원장에 유지. 일반 감사 로그와 동일시하지 않음 |
| ai_guardrail_events | 보안 정책 검사 결과 | 기존 가드레일 내부 기록 유지. 통합 여부 확인 |

### 8.3 이력 검색·목록·상세

- 필터 권장안: 기간, 출처, 작업 유형, 성공/실패, 회원/행위자, 워크스페이스, 자원 유형, 검색어.
- 기본 전체 범위에서 기간 조건을 추가할 수 있게 한다. 임의로 “최근 50건”만 가져와 전체 목록이라고 표시하지 않는다.
- 검색어는 행위자 이름/ID, 자원 유형/ID, 요청 ID, 경로 등 명시한 필드에서 검색한다. JSON 본문 전체 검색과 포함할 필드는 별도 확정한다.
- 목록은 시각, 출처, 행위자, 워크스페이스, 작업, 대상, 결과를 중심으로 표시한다. 상세에서 변경 필드, 전후 값, 요청 ID와 경로를 조회한다.
- 서로 다른 출처는 source+id를 고유 키로 사용한다. 없는 필드의 정규화 규칙을 정하고 동일 동작에 대한 감사/운영 기록을 이유 없이 중복 제거하지 않는다.
- 행위자는 삭제·이름 변경 후에도 남는 저장된 스냅샷을 우선 사용한다. users와 INNER JOIN해서 기존 기록을 숨기지 않는다.
- 목록 응답에는 큰 전후 JSON을 전부 싣지 않는다. 상세 API에서 허용 필드만 반환하고 화면에서는 텍스트로 안전하게 표시한다.
- 기간 입력과 표시는 KST, DB 저장은 UTC를 유지한다. 마지막 날은 다음 날 00시 미만으로 변환해 누락/중복 경계를 방지한다.
- 이력 화면에 수정·삭제 버튼을 추가하지 않는다. 기존 audit_logs 불변 트리거를 보존한다.
- 설정 읽기와 목록의 반복 조회가 다시 이력 조회를 유발하는 구조를 피한다. 이력 조회 자체의 감사 여부는 별도 정책으로 정하고 자동 재귀 기록을 막는다.

## 9. API와 DB 변경 설계안

아래 경로·테이블은 후속 구현 제안이며 이번 문서 작업에서 만들지 않는다.

| API | 역할/동작 |
| --- | --- |
| GET /api/me/preferences | 본인 토스트 위치·기본 테마·version 조회. 저장 행이 없으면 기본값 반환 |
| PATCH /api/me/preferences | 로그인 본인 설정만 부분 갱신, 값·version 검증 |
| GET/PATCH /api/me | 기존 프로필 조회·이름 변경 재사용 |
| GET /api/admin/members?q=&role=&plan=&page=1&pageSize=20 | 전체 회원 검색, 동일 조건의 total과 페이지 목록 |
| GET /api/admin/members/[userId] | 선택 회원 기본 정보·플랜·역할·변경 가능 권한·관리 버전 |
| PATCH /api/admin/members | 기존 변경 경로를 보완해 변경 필드와 기대 관리 버전만 처리 |
| GET/PATCH /api/admin/plans | 기존 가격·한도 API 재사용 |
| GET/POST /api/admin/ai-guardrails | 기존 정책 API 재사용, 계정 관리자 및 대상 범위 검증 정리 |
| GET/PATCH /api/admin/settings/logging | 로깅 설정 단일 키 조회/변경, boolean·version 검증 |
| GET /api/admin/history | 출처·필터·검색·페이징을 적용한 전역 이력 조회 |
| GET /api/admin/history/[source]/[id] | 출처별 허용 목록과 권한을 검증한 이력 상세 |

개인/관리 데이터 응답은 no-store를 사용한다. 개인 설정 API는 클라이언트의 userId로 대상을 선택하지 않고 인증된 본인을 기준으로 한다. 모든 변경 API는 기존 출처 검증과 권한 재확인을 유지한다.

| DB 대상 | 변경 제안 |
| --- | --- |
| user_preferences 신규 | user_id PK/FK, toast_position(top/bottom), default_theme(light/dark), version, created_at, updated_at |
| users | 회원 플랜·역할 변경의 낙관적 동시성 검사용 management_version 추가 권장 |
| 관리자 설정 변경 기록 신규 | actor_id, 설정 키, 이전/새 boolean 값, 발생 시각, 요청 ID. 업무 비밀/전체 요청 본문 미저장 |
| audit_logs / plan_change_logs | 전역 시간·고유 ID 정렬 및 실제 검색 조건에 맞는 인덱스 검토 |
| users / user_subscriptions | 가입일·역할·플랜 필터와 안정적인 정렬을 위한 인덱스 검토 |
| app_settings | 기존 DB_LOGGING_ENABLED 행과 version 사용. 테이블 초기화나 기본값 덮어쓰기 금지 |

- 신규 개인 설정은 GET 조회만으로 행을 만들지 않고 첫 저장 시 UPSERT하는 안을 권장한다. 이력이 있는 서비스 데이터와 기존 사용자 값을 보존한다.
- 다음 마이그레이션 순번은 현재 021 이후이며 구현 시 실제 최신 순번을 다시 확인한다. 기존 마이그레이션과 master 제약을 수정하지 않는다.
- 부분 일치 검색은 일반 B-tree 인덱스만으로 해결되지 않을 수 있다. 임의 검색 엔진을 먼저 도입하지 말고 실제 조회 계획·건수로 검증한다.

## 11. 구현 순서와 검증 기준
