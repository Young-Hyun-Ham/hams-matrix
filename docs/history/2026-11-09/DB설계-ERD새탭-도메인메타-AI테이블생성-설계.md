# DB설계 ERD 새 탭·도메인 메타 CRUD·AI 테이블 생성 분석 및 설계

- 작성일: 2026-11-09 (한국시간, Asia/Seoul)
- 추가 요구 반영일: 2026-11-09. ERD 캔버스의 테이블별 수정·삭제, 모달 편집, FK 연결 시 삭제 차단을 추가했다.
- 상태: 사용자 검토용 설계 초안. 사용자가 검토하고 직접 수정한 문서를 기준으로, 별도 구현 요청 후 적용한다.
- 분석 기준: 현재 작업 트리의 소스. 커밋되지 않은 AI 대상 선택·DB 일괄 등록 코드도 현재 구조에 포함해 확인했다.
- 이번 단계: 본 문서와 `HISTORY.md` 링크만 작성한다. 소스, DB, 마이그레이션 파일, 패키지, 설정은 수정하지 않으며 DB 접속·마이그레이션·AI 호출도 수행하지 않는다.
- 구분: **요구사항**은 사용자 요청이고 **권장안**은 검토를 위한 제안이다. 정책 결정이 필요한 항목은 9절에 모았다.

## 1. 요구사항과 완료 기준

| ID | 요구사항 | 구현 단계 완료 기준 |
| --- | --- | --- |
| R1 | DB설계 탭의 `ERD · 테이블 관계`를 버튼으로 새 탭에서 볼 수 있게 한다. | 현재 프로젝트를 포함한 URL을 새 브라우저 탭으로 열고, 저장된 테이블·컬럼·PK/UNIQUE/FK 관계를 표시한다. URL 직접 접속과 새로고침도 지원한다. |
| R2 | 도메인 메타 등록 버튼을 만들고 새 탭에서 연다. | DB설계 탭에서 현재 프로젝트의 도메인 메타 관리 화면으로 진입한다. 조회 권한만 있는 사용자는 목록을 볼 수 있고 등록·수정·삭제는 각 권한에 따른다. |
| R3 | 도메인 메타 등록 CRUD를 제공한다. | 논리 명칭, 물리 명칭, 자료형, 길이/정밀도 등을 등록·조회·수정·삭제하고 검색, 중복 검사, 동시 수정 충돌 처리를 제공한다. |
| R4 | AI 테이블 등록 시 도메인 메타로 컬럼 물리명·자료형을 결정한다. | `작업 / job / varchar2(16)` 메타가 있으면 논리 컬럼 `작업_아이디`를 `job_id`, `VARCHAR2`, 길이 `16`으로 저장하고 ERD에서도 `job_id · VARCHAR2(16)`으로 표시한다. 단건·일괄 등록에 같은 규칙을 적용한다. |
| R5 | 이번에는 설계 문서만 작성한다. | 날짜 디렉터리 아래 작업명 문서를 만들고 기존 이력 목록에 링크를 추가한다. 실제 구현과 DB 변경은 수행하지 않는다. |
| R6 | ERD 캔버스의 테이블명 오른쪽에 수정·삭제 버튼을 제공한다. | 각 테이블 카드 헤더에 해당 테이블을 대상으로 한 액션을 배치한다. UPDATE/DELETE 권한을 각각 적용한다. |
| R7 | ERD에서 수정하면 테이블 정보를 모달 팝업으로 열어 편집한다. | 테이블 기본 정보·컬럼·PK/UNIQUE/FK 등을 수정하고 기존 API로 저장한다. 성공 후 ERD의 테이블명·컬럼·관계선을 다시 표시한다. |
| R8 | ERD에서 테이블을 삭제할 수 있게 하되 FK가 걸려 있으면 삭제하지 못하게 한다. | 삭제 확인 후 처리하며, FK가 남아 있으면 화면과 서버에서 차단한다. 참조받는 FK뿐 아니라 자신이 가진 FK와 자기 참조 FK도 포함하는 해석을 기본으로 한다. 저장 직전 최신 관계를 검사한다. |

요구 해석과 권장 범위:

- **새 탭**은 프로젝트 내부 메뉴 탭 추가가 아니라 브라우저의 별도 탭을 의미한다. 최종 탭/창 선택은 브라우저 설정에 따른다.
- **도메인 메타**는 DB 컬럼의 표준 논리 명칭·물리 명칭·자료형 사전이다. 현재 관리자 화면의 AI 가드레일 `허용 도메인`은 URL 호스트 정책으로, 이 사전과 별개다.
- **테이블 등록**은 현재 제품의 테이블 정의서 산출물 저장이다. 실제 업무 DB에 `CREATE TABLE`을 실행하는 기능으로 확대하지 않는다.
- 1차 구현은 프로젝트별 사전과 AI 신규 테이블 생성에 집중하는 것을 권장한다. 기존 테이블 일괄 변환, 메타의 AI CRUD, 사전 엑셀 일괄 입출력, 팀 공통 사전은 별도 범위로 둔다.

## 3. 화면과 새 탭 설계

### 3.1 DB설계 탭

권장 구성:

```text
DB설계 도구
  [ERD · 테이블 관계 ↗]  [도메인 메타 관리 ↗]
데이터베이스설계서 목록                         [테이블 등록]
  기존 검색·상태 필터·상세·수정·삭제
```

- ERD 전체 영역은 새 탭으로 이동하고, 원래 DB설계 탭에는 진입 버튼과 기존 테이블 목록을 남기는 것을 권장한다. 인라인 ERD를 유지할지는 9절에서 결정한다.
- 테이블이 0개여도 두 버튼을 표시한다. 메타를 먼저 등록한 뒤 AI로 테이블을 생성할 수 있어야 한다.
- 버튼 형태의 링크를 사용하고 `target="_blank"`, `rel="noopener noreferrer"`, 새 탭 안내와 키보드 접근성을 적용한다.
- `도메인 메타 관리`를 공통 진입명으로 권장한다. 목록 화면에 `도메인 메타 등록` 버튼을 둔다. 원래 화면의 버튼명을 반드시 `도메인 메타 등록`으로 사용할 경우에도 CRUD 목록 진입 여부를 명확히 안내한다.

| URL | 용도 | 신규 파일 제안 |
| --- | --- | --- |
| `/projects/{projectId}/database/erd` | ERD 조회·테이블 모달 수정·삭제 | `app/(database)/projects/[projectId]/database/erd/page.tsx` |
| `/projects/{projectId}/database/domains` | 도메인 메타 CRUD | `app/(database)/projects/[projectId]/database/domains/page.tsx` |
| 위 두 화면 공통 | 인증·온보딩·테마·스타일 | `app/(database)/layout.tsx` |

- `(database)`는 URL에 포함되지 않는 전용 route group 제안이다. 경로의 `projectId`를 기준으로 조회하고, 브라우저의 마지막 프로젝트 선택값으로 대체하지 않는다.
- 공통 헤더에 프로젝트명, 화면명, `DB설계로 돌아가기` 링크를 표시한다. 돌아가기 URL은 `/projects/{id}?tab=database`다. `window.opener`에 의존하지 않는다.
- 로그인·온보딩·guest 제한과 서버의 프로젝트 소속·워크스페이스·`database.READ` 검사를 적용한다. 인증만 통과한 다른 프로젝트 사용자가 URL로 조회할 수 없어야 한다.
- 새 레이아웃에는 공통 테마·폼·테이블·다이얼로그 스타일을 명시적으로 로드한다. 별도 화면이라는 이유로 개인 설정이 빠지지 않게 한다.
- ERD는 기존 `DatabaseDiagram`을 확장해 재사용하고 빈 상태, 로딩, 실패, 재시도, 최종 조회 시각, 새로고침을 제공한다. 테이블명 오른쪽의 수정·삭제 버튼으로 새 탭 안에서 모달 편집·삭제를 수행한다. 원래 DB설계 목록의 편집 기능도 유지한다.
- 도메인 화면은 논리명/물리명 검색, 목록, 상세, 등록·수정 폼, 삭제 확인을 제공한다. 권한에 따라 각 액션을 표시한다. 저장 중 중복 제출을 막고 실패 시 입력값을 보존한다.
- 독립 화면에는 1차로 AI 패널을 노출하지 않는 것을 권장한다. 원래 프로젝트 DB 탭의 AI가 사전을 사용하는 것으로 R4를 충족한다.

### 3.3 새 탭 데이터 갱신

- 최초 진입·명시적 새로고침·탭 복귀 시 서버에서 다시 조회한다. 네트워크 재조회는 `no-store`로 처리하고 진행 중 조회 취소와 프로젝트별 응답 범위를 확인한다.
- 필요하면 `BroadcastChannel`을 사용하되 채널 범위는 사용자·워크스페이스·프로젝트까지 포함한다. 저장 성공 후에만 변경 사실을 알린다.
- 채널 메시지는 재조회 신호로만 사용하고 전달받은 메타·권한·산출물을 신뢰하여 상태에 직접 반영하지 않는다. 서버 권한 검사를 거쳐 다시 읽는다.
- 메타 편집 폼이나 ERD 테이블 수정 모달이 dirty이면 탭 복귀·외부 통지로 입력을 덮어쓰지 않는다. 최신 버전 알림을 제공하고 저장 시 충돌을 검사한다. 미저장 상태에서 모달을 닫거나 화면을 나갈 때도 보호한다.
- 채널을 사용할 수 없거나 원래 탭이 닫힌 경우에도 조회·저장이 가능해야 한다. 실시간 협업이나 주기적 polling은 필수 범위가 아니다.

### 3.4 ERD 캔버스의 테이블별 수정·삭제

추가 요구에 따른 테이블 카드 헤더 구성:

```text
┌─────────────────────────────────────────────┐
│ DB-001 · job                [수정] [삭제]   │
├─────────────────────────────────────────────┤
│ PK job_id · VARCHAR2(16) NOT NULL            │
│ ...                                         │
└─────────────────────────────────────────────┘
```

- 각 카드의 테이블명 오른쪽에 실제 버튼을 배치한다. 이름 문자열이나 배열 index 대신 해당 테이블의 실제 artifact ID를 액션 대상으로 사용한다.
- `database.UPDATE` 권한이 있을 때 수정, `database.DELETE` 권한이 있을 때 삭제를 제공한다. 권한 확인 중에는 액션을 사용할 수 없게 하고, 클릭·최종 저장 시 최신 권한을 검사한다. 조회 전용 사용자는 ERD를 계속 볼 수 있다.
- 삭제 권한은 있지만 FK가 남은 경우 삭제 버튼을 비활성화하고 `FK 연결을 먼저 해제해 주세요`라는 이유와 관련 테이블·컬럼을 확인할 수 있게 한다. 비활성 버튼의 tooltip에만 이유를 넣지 말고 키보드로도 확인 가능한 안내를 제공한다.
- 현재 카드 너비 330과 헤더 높이 40을 고려해 이름과 액션 영역을 분리한다. 긴 이름은 액션을 덮지 않게 줄임 표시하고 전체 이름을 확인할 수 있게 한다. 헤더 높이를 바꾼다면 카드 높이·컬럼 좌표·FK 시작/끝 좌표도 같은 기준으로 변경한다.
- 현재 그래프는 SVG의 `role="img"`와 `<text>` 기반이다. 텍스트에 클릭 핸들러만 붙이지 말고, SVG `foreignObject` 내부의 HTML 버튼이나 카드 좌표에 맞춘 HTML 액션 레이어를 사용한다. `foreignObject` 방식을 선택하면 상위 `role="img"`가 내부 버튼을 접근성 트리에서 숨기지 않도록 그래프를 그룹으로 구성한다.
- 버튼은 Tab/Enter/Space로 조작 가능하고 대상 테이블을 포함한 접근성 이름을 제공한다. 클릭 이벤트가 향후 카드 선택·캔버스 이동 액션에 전파되지 않게 한다.
- `DatabaseDiagram`에는 `onEdit(table)`, `onDelete(table)`, 수정/삭제 가능 여부와 차단 사유를 props로 전달하는 구성을 권장한다. 그래프 안에서 별도의 저장 API나 모달 상태를 중복 구현하지 않는다. 액션을 전달하지 않는 기존 호출부에서는 조회 표시를 유지할 수 있다.

### 3.5 테이블 수정 모달과 저장 흐름

1. 수정 버튼 클릭 시 해당 프로젝트의 최신 산출물과 권한을 조회하고 artifact ID로 대상 테이블을 다시 찾는다. 삭제됐으면 안내 후 ERD를 재조회한다. 초기 조회가 끝나기 전에는 저장 가능한 모달을 열지 않는다.
2. 기존 테이블 편집 폼과 동일한 모달을 연다. 명칭·상태·테이블 개요·스키마·물리/논리 테이블명·인덱스·제약조건·담당자·비고, 컬럼의 논리/물리명·타입·길이·기본값·NULL·PK·UNIQUE·FK 및 기준 문서 연결을 편집한다.
3. 기존 `useArtifactActions()`와 `ArtifactDialogs`의 폼·검증을 재사용한다. 독립 화면에서 필요한 데이터·권한·액션만 props로 전달할 수 있도록 모달 본체를 분리하고 기존 context 기반 래퍼를 유지하는 방안을 권장한다. 독립 화면에 프로젝트 작업 공간 전체를 중복 렌더링하지 않는다.
4. `PATCH /api/projects/{projectId}/artifacts/{artifactId}`에 기존 artifact version을 포함해 저장한다. 기존 `mutateArtifact()`의 필수값·컬럼 중복·참조·타입·길이·전체 그래프 검증을 그대로 적용한다. ERD 전용 수정 API를 새로 만들지 않는다.
5. 참조받는 컬럼 삭제, 참조 대상 PK/UNIQUE 자격 제거, 연결된 컬럼의 자료형·길이 불일치처럼 FK 무결성을 깨는 변경은 저장을 차단한다. FK가 있다는 이유로 테이블의 모든 수정을 막지는 않는다. 설명·이름 등 관계를 깨지 않는 수정과 FK 연결 해제는 허용한다.
6. 기존 테이블·컬럼 ID를 유지하고 도메인 생성 근거를 보존한다. 이 수정은 6절의 AI CREATE 자동 메타 적용과 구분하며, 메타 변경을 이유로 컬럼을 자동 재명명하지 않는다.
7. 성공 시 모달을 닫고 같은 프로젝트 자료를 재조회해 카드·컬럼·관계선·관계 목록을 함께 갱신한다. 다른 탭에는 저장 성공 후 변경 신호를 보낸다. 저장은 성공했지만 재조회가 실패했다면 저장 실패로 표시하지 말고 갱신 실패와 재시도 방법을 안내한다.
8. 실패 시 입력을 보존하고 모달 안에 오류를 표시한다. version 충돌 409에서는 자동 덮어쓰기나 무조건 재시도를 하지 않는다. 저장 중 중복 클릭을 막고 닫기·취소·미저장 변경 확인, 닫힌 뒤 원래 버튼으로의 포커스 복귀를 지원한다.

기존 모달의 `최신 내용 다시 불러오기`는 모달을 닫고 목록을 재조회하므로 입력을 버릴 수 있다. ERD에서 재사용할 때도 미저장 확인을 거치도록 보완한다.

### 3.6 삭제 확인과 FK 차단 규칙

- 삭제 버튼은 바로 삭제하지 않고 대상 관리번호·물리/논리 테이블명을 표시하는 확인 모달을 연다. 기존 삭제 모달과 `useArtifactActions().remove()` 흐름을 재사용한다.
- `DELETE /api/projects/{projectId}/artifacts/{artifactId}`에 현재 version을 전달한다. 성공 시 기존 산출물의 논리 삭제 정책을 따르며 관리번호·이력을 보존한다. 삭제 후 ERD와 원래 목록을 재조회한다.
- **삭제 차단 기준:** 다른 테이블이 이 테이블을 참조하는 FK, 이 테이블이 다른 테이블을 참조하는 FK, 자기 자신을 참조하는 FK가 하나라도 남아 있으면 삭제할 수 없다. 순환 관계도 동일하게 처리한다. FK를 자동 해제하거나 관련 테이블을 연쇄 삭제하지 않는다.
- 기존 `artifact_links`의 비-FK 연결 차단도 유지한다. 요구사항·WBS·프로그램 테이블 처리 등 기존 연결이 남아 있으면 삭제를 막는다. FK가 없어졌다는 이유로 다른 연결 검사까지 생략하지 않는다.
- 화면은 조회한 전체 프로젝트의 `structure.columns[].reference`에서 들어오는 FK·나가는 FK·자기 참조를 계산해 사유를 안내한다. 현재 그려진 선, 검색 결과나 화면에 보이는 카드만을 기준으로 검사하지 않는다.
- 서버는 같은 write 트랜잭션 안에서 프로젝트·워크스페이스·DELETE 권한·version을 확인하고, 활성 테이블의 저장된 컬럼 구조와 기존 `artifact_links`를 검사한 뒤 삭제한다. 자신이 가진 FK도 구조에서 확인하므로 자기 참조와 연결 인덱스 누락에 대한 검사가 가능하다.
- 이 보완은 공통 `mutateArtifact()`의 DB 테이블 DELETE 경로에 적용한다. ERD만 막고 원래 목록이나 AI 삭제 경로에서 같은 테이블을 삭제할 수 있는 상태를 만들지 않는다.
- 관계가 있으면 409와 이해할 수 있는 사유를 반환한다. 같은 프로젝트에서 조회 가능한 참조 테이블·컬럼을 안내하고, 다른 프로젝트 정보는 노출하지 않는다. 현재 공통 메시지는 유지할 수 있으나 FK와 기타 연결의 차단 이유를 구분할 수 있도록 응답을 보강하는 것을 권장한다.
- 모달이 열린 뒤 다른 사용자가 FK를 추가한 경우에도 최종 서버 검사로 삭제를 막는다. 반대로 FK가 해제된 경우 재조회하면 삭제 버튼이 다시 활성화되어야 한다. 삭제와 관계 추가를 같은 트랜잭션 검증 경계로 처리해 유실된 참조가 남지 않게 한다.

FK의 범위를 참조받는 관계로만 한정하는 방안은 이번 기본 설계에 포함하지 않는다. 사용자의 `FK가 걸려 있으면 삭제 불가`를 들어오는 관계·나가는 관계·자기 참조 모두에 적용하고, 다른 정책을 원할 때 명시적으로 변경한다.

## 4. 도메인 메타 데이터 설계

### 4.1 저장 범위와 모델

**권장안: 프로젝트별 독립 테이블에 저장한다.** 도메인 메타는 테이블 정의서와 성격이 다르므로 `ArtifactKind`를 추가하거나 일반 `database` 산출물로 위장하지 않는다. 별도 메뉴 권한을 신설하는 대신 기존 `database` CRUD 권한을 상속한다.

`project_database_domains` 신규 테이블 제안:

| 필드 | 의미와 제약 |
| --- | --- |
| `id` | 서버 생성 UUID, 기본키 |
| `workspace_id`, `project_id` | 필수 소속. `projects(id, workspace_id)` 복합 외래키로 프로젝트·워크스페이스 일치 보장 |
| `logical_name` | 사용자에게 표시할 논리 명칭. 권장 최대 100자, 예: `작업`, `작업_아이디` |
| `logical_key` | 서버가 정규화한 검색·매칭 키. 클라이언트 입력값을 그대로 신뢰하지 않음 |
| `physical_name` | 영문 물리 명칭 또는 복합 명칭. 소문자 snake_case, 권장 최대 100자. 예: `job`, `job_id` |
| `data_type` | 길이를 제외한 자료형, 권장 최대 80자. 예: `VARCHAR2`, `NUMBER` |
| `length` | 길이/정밀도 문자열, 권장 최대 40자. 예: `16`, `18,2`, 길이 없는 타입은 빈 문자열 |
| `description` | 선택 설명, 권장 최대 1,000자 |
| `version` | 항목 동시 수정 검사용 정수. 최초 1, 변경마다 증가 |
| `created_by`, `updated_by` | 생성·수정 사용자 |
| `created_at`, `updated_at`, `deleted_at` | 생성·수정 시각과 논리 삭제 시각. 저장은 UTC, 화면은 한국시간 |

추가로 `project_database_domain_catalogs`에 `(project_id, workspace_id)`별 `revision`, `updated_at`을 둔다. 항목 신규 등록·수정·삭제마다 같은 트랜잭션에서 revision을 증가시킨다. 항목 version만 비교하면 AI가 조회한 뒤 새 메타가 추가되어 매칭 우선순위가 바뀐 경우를 감지할 수 없다.

인덱스·제약 권장안:

- 활성 항목에 대해 `(workspace_id, project_id, logical_key)` 유일성을 DB의 부분 유일 인덱스로 보장한다. 동일 정규화 논리명의 중복 등록을 막는다.
- 물리명의 중복은 동의어 요구가 있을 수 있어 일괄 금지하지 않고 경고한다. 최종 테이블 안의 컬럼 물리명 중복은 반드시 차단한다.
- 프로젝트별 활성 목록·검색 인덱스를 둔다. `version`, catalog `revision`은 양의 정수로 제한한다.
- 삭제는 `deleted_at`을 설정한다. 삭제된 메타는 신규 AI 매칭에서 제외하지만 기존 컬럼의 생성 당시 정보는 남긴다.
- 신규 마이그레이션은 구현 시점의 다음 번호로 작성한다. 현재 작업 트리에 `036_ai_conversation_targets.sql`까지 있으므로 이 설계에서 번호를 확정하지 않는다.

### 4.2 자료형 입력과 정규화

- 폼은 `논리 명칭`, `물리 명칭`, `자료형`, `길이/정밀도`, `설명`으로 구분한다. 사용자 입력 `varchar2(16)`은 서버 파서가 `dataType="VARCHAR2"`, `length="16"`으로 분리한다.
- 자료형에 `(16)`을 남기면서 길이에도 `16`을 저장하면 현재 ERD가 `VARCHAR2(16)(16)`으로 출력할 수 있으므로 금지한다.
- 길이 칸과 합쳐진 자료형을 동시에 입력했고 값이 다르면 오류를 반환한다. 하나를 임의로 덮어쓰지 않는다.
- `NUMBER(18,2)` 같은 정밀도·스케일과 길이가 없는 타입을 처리한다. 길이 양수 여부, 정밀도/스케일 관계, 불완전한 괄호 등은 서버에서 검사한다.
- 지원 타입과 DBMS별 길이 단위는 구현 전 결정한다. 우선 사용자 예시의 Oracle `VARCHAR2`를 지원하되 앱 저장소의 타입으로 치환하지 않는다. `TIMESTAMP WITH TIME ZONE`, `VARCHAR2(16 CHAR)` 같은 확장 문법은 지원 정책 없이 단순 괄호 분리로 수용하지 않는다.
- 물리명은 규칙을 벗어난 식별자, 빈 값, 과도한 길이를 거부한다. 논리명 정규화는 앞뒤 공백 제거, Unicode NFC, 공백/밑줄 구분자 통일을 기본으로 제안한다. 부분 문자열 포함만으로 매칭하지 않는다.

### 4.3 컬럼 계약 확장과 기존 데이터 호환

`TableColumn` 확장 권장안:

- `logicalName?: string`: 명확한 논리 컬럼명. 예: `작업_아이디`. 신규 AI 테이블 컬럼에는 필수 입력으로 요구하고, 과거 저장 데이터에서는 생략을 허용한다.
- `domainBinding?: { domainId, domainVersion, catalogRevision, ruleVersion, sourceLogicalName, physicalName, dataType, length }`: 서버가 작성하는 적용 근거 스냅샷. `domainId`는 자료형을 제공한 주 메타의 ID이며 복합명 전체 일치 시 해당 항목을 가리킨다. `ruleVersion`은 접미어 등 조합 규칙 변경도 구분한다.
- `description`은 기존 자유 설명으로 보존한다. 논리명을 추출하기 위해 설명 전체를 임의 변환하지 않는다.
- `domainBinding`은 클라이언트나 AI가 원하는 값을 지정하는 계약으로 노출하지 않는다. 서버가 조회한 실제 메타로 만들고, 수정 시 기존 컬럼 ID에 연결된 저장 정보를 검증·보존한다.
- `structure_json`은 선택 필드 추가만으로 확장할 수 있다. 기존 산출물·revision JSON을 일괄 갱신하거나 논리명을 자동 backfill하지 않는다.
- 메타 수정·삭제는 이미 생성된 `name`, `dataType`, `length`, PK/FK를 자동 변경하지 않는다. 생성 당시 버전과 값을 보존한다. 기존 컬럼 수정 시 메타 기준과 달라졌다는 안내는 가능하지만 제목·설명 수정까지 막지 않는다.
- 수동 컬럼 수정으로 물리명/자료형/길이가 바뀌면 binding은 생성 당시 출처로만 취급한다. 현재 사전과 일치하는지 여부와 과거 적용 이력을 구분한다. 재적용은 별도 명시적 작업으로 설계한다.

도메인 참조는 `artifact_links`에 넣지 않는다. 해당 테이블은 산출물 간 연결 모델이므로 별도 메타 테이블 ID를 넣을 수 없다. 메타의 논리 삭제와 컬럼 내 스냅샷으로 과거 정보 보존을 처리한다.

## 5. CRUD API·권한·감사 설계

다음 표는 신규 도메인 메타 API다. ERD 테이블 편집·삭제는 기존 `app/api/projects/[projectId]/artifacts/[artifactId]/route.ts`의 PATCH/DELETE를 재사용하며, 3.5~3.6절의 모달·FK 검증을 연결한다. ERD 액션 자체를 위한 신규 DB 테이블이나 마이그레이션은 필요하지 않다.

| 메서드/경로 | 역할 | 주요 계약 |
| --- | --- | --- |
| `GET /api/projects/{id}/database/domains` | 목록 조회·검색 | `q`, `page`, `pageSize`; `{ items, total, page, pageSize, catalogRevision }`. 기본 20건, 최대 100건 제안. 삭제 항목 제외 |
| `POST /api/projects/{id}/database/domains` | 메타 등록 | 논리/물리 명칭, 자료형, 길이, 설명. 서버가 ID·정규화 키·version 발급. 성공 201 |
| `GET /api/projects/{id}/database/domains/{domainId}` | 상세 조회 | 현재 항목과 version, catalogRevision. 삭제·다른 프로젝트 항목은 404 |
| `PATCH /api/projects/{id}/database/domains/{domainId}` | 메타 수정 | 현재 version과 변경 필드. 성공 시 항목 version 및 catalogRevision 증가 |
| `DELETE /api/projects/{id}/database/domains/{domainId}` | 논리 삭제 | 현재 version 필수. 성공 후 신규 매칭 제외. 기존 테이블 값 보존 |

- 모든 API는 `requireUser()`, 프로젝트 소속·워크스페이스 검사와 `requireProjectPermission(..., "database", action)`을 서버에서 수행한다. 폼의 버튼 표시만으로 권한을 보장하지 않는다.
- 변경 요청은 기존 `checkOrigin()`, 크기를 제한한 `body()`, 파라미터 바인딩, `errorResponse()` 패턴을 따른다.
- 항목 변경·catalog revision 증가·감사 기록은 같은 write 트랜잭션에서 처리한다. 변경 시점에 권한을 다시 확인한다.
- 입력 오류는 400, 권한 없음은 403, 범위 내 대상 없음은 404, 중복·동시 수정은 409로 응답한다. 유일성 위반을 내부 SQL 오류로 노출하지 않는다.
- PATCH/DELETE는 `id + project_id + workspace_id + version + deleted_at IS NULL`을 조건으로 수행하고 영향 행 수를 확인한다. 충돌 시 입력을 보존하고 최신 조회 후 재검토하도록 안내한다.
- 감사 resource는 `database_domain`을 제안한다. `lib/audit.ts`는 snapshot 허용 필드만 저장하므로 메타 상세는 기존 허용 키 `fields` 아래 넣고 `version`, `name` 등을 함께 기록하는 방안을 권장한다. 새 키를 최상위로 넘기기만 하면 감사 정보가 빠질 수 있다.
- 기존 `DB_LOGGING_ENABLED` 정책을 따른다. 도메인 전용 변경 이력 UI나 `artifact_revisions` 합류는 기본 범위에 포함하지 않는다. 사용자에게 메타의 모든 과거 버전 조회가 필요하면 별도 이력 테이블을 추가해야 한다.

## 6. 도메인 메타 기반 AI 테이블 생성

### 6.1 적용 흐름

```text
현재 프로젝트·DB 대상 권한 확인
  → readAiPage / read_page에서 RFP + 테이블 + 메타 catalog revision 조회
  → AI가 논리 컬럼명과 테이블 구조 제안
  → 서버 공통 resolver가 논리명 매칭·물리명/자료형/길이 결정
  → 컬럼 중복·PK/FK·기존 산출물 검증, 임시 검증 후 rollback
  → 정규화된 변경안과 적용 메타 revision을 pending에 보관
  → 최종 출력·가드레일 검사
  → 최종 트랜잭션에서 권한·메타 revision 재검사
  → 동일 규칙 재검증 후 산출물·연결·이력을 일괄 저장
```

공통 resolver는 `lib/database-domain-resolver.ts` 같은 순수 로직으로 분리하고 조회는 서버 서비스에서 담당한다. 단건·일괄 양쪽에 같은 사전 스냅샷과 규칙 버전을 전달한다. 일반 `prepareStructure()` 내부에 비동기 DB 조회를 숨기지 않는다.

### 6.2 명칭과 자료형 매칭 규칙 권장안

1. 논리 컬럼명을 정규화하고 활성 메타의 **복합 명칭 전체 일치**를 가장 먼저 찾는다. `작업_아이디` 자체가 등록되어 있으면 `작업`보다 우선한다.
2. 전체 일치가 없으면 공백·밑줄로 나뉜 용어 경계를 기준으로 가장 긴 등록 명칭부터 조합한다. `일괄작업` 안에 `작업`이 있다는 이유만으로 부분 매칭하지 않는다.
3. 사용자 예시를 지원하기 위한 기본 명칭 규칙으로 `아이디 → id`, 영문 `id → id`를 제안한다. 이는 물리명 접미어 규칙이며 별도의 자료형을 제공하지 않는다. 프로젝트 메타의 명시적 전체 일치가 기본 규칙보다 우선한다.
4. `작업 + 아이디`라면 물리 토큰 `job + id`를 `_`로 합친다. 자료형·길이는 `작업` 메타에서 상속한다. PK 여부·NULL·UNIQUE·기본값은 명칭이나 자료형 메타만으로 자동 지정하지 않고 AI가 제안한 구조와 기존 검증을 따른다.
5. 전체 일치 메타가 있으면 그 메타가 자료형의 출처다. 조합에서는 기준이 되는 업무 명칭 메타가 자료형을 제공한다. 서로 다른 자료형을 가진 메타가 여러 개 매칭되어 기준이 모호하면 임의 우선순위를 적용하지 않고 충돌로 반환한다. 정확한 복합 명칭 메타 등록을 안내한다.
6. 일부만 매칭되고 남은 한글 토큰을 해석할 수 없으면 임의 번역·붙이기를 하지 않는다. 예를 들어 `작업_담당자`에서 `담당자` 규칙이 없다면 해당 컬럼을 미해결로 반환한다. 단건은 저장을 보류하고 일괄 요청은 해당 배치를 전부 취소한다.
7. 어떤 메타도 매칭되지 않거나 사전이 비어 있으면 기존 AI 제안을 허용하되, 적용 메타가 없다는 결과를 명시하는 방안을 권장한다. 이 경우에도 유효한 물리명·자료형과 기존 검증을 통과해야 한다. 전체 컬럼의 사전 등록을 강제할지는 9절에서 결정한다.
8. 적용 후 물리명 최대 길이·대소문자 무시 중복·자료형·길이·PK/FK를 검증한다. 두 논리 컬럼이 같은 물리명으로 변환되면 숫자를 임의로 붙이지 않고 오류로 처리한다.

주요 사례:

| 메타/입력 조건 | 논리 컬럼명 | 기대 결과 |
| --- | --- | --- |
| `작업 → job / VARCHAR2 / 16` | `작업_아이디` | `name=job_id`, `dataType=VARCHAR2`, `length=16` |
| 같은 메타, 공백 구분자 정규화 허용 | `작업 아이디` | `job_id / VARCHAR2(16)` |
| `작업`과 `작업_아이디 → task_key / CHAR / 20` 등록 | `작업_아이디` | 전체 일치 우선: `task_key / CHAR(20)` |
| `작업`만 등록 | `일괄작업_아이디` | `작업` 부분 일치 금지. 사전 미매칭으로 보고 |
| `작업`만 등록, `담당자` 규칙 없음 | `작업_담당자` | 부분 미해결 오류, 임의 물리명 생성 금지 |
| 변환한 FK가 기존 참조 PK의 타입/길이와 다름 | `작업_아이디` | 기존 FK 검증 실패. 참조 테이블 타입을 함께 자동 수정하지 않음 |

`작업`이라는 업무 명칭의 자료형을 `작업명`, `작업일자`까지 모두 상속하면 부적절할 수 있다. 따라서 사용자의 `작업_아이디` 예시는 지원하되, 전체 일치 메타 우선 및 모호한 조합 차단을 기본으로 제안한다. 더 일반적인 표준용어/표준도메인 분리 모델이 필요하면 9절 결정 후 모델을 조정한다.

### 6.3 AI 조회 계약과 용량

- `readAiPage()`의 DB 대상 반환값에 `domainMeta: { catalogRevision, ruleVersion, items, total, truncated }`를 추가하는 안을 제안한다. 항목은 ID·version·논리/물리 명칭·자료형·길이 중심으로 제공한다.
- 초기 context와 `read_page` 재조회에서 같은 계약을 사용한다. RFP 부재·테이블 0건·메타 0건을 서로 구분한다. 다른 프로젝트의 메타나 삭제된 메타를 섞지 않는다.
- 메타 전용 budget을 두고, 잘린 사전을 전체 목록으로 오해하지 않게 한다. 사전 규모가 커지면 DB 전용 읽기 도구 `read_database_domains`로 논리명 검색·페이지 조회를 지원하는 방안을 포함한다. 검색 결과와 catalog revision을 함께 반환한다.
- 서버 resolver의 최종 매칭은 AI에게 전달된 일부 목록이 아니라 동일 프로젝트의 활성 사전 전체를 기준으로 한다. AI가 제시한 메타 ID나 타입을 그대로 신뢰하지 않는다.
- `logicalName`은 AI 신규 컬럼의 필수 계약으로 안내한다. 자유 설명만으로 임의 추출하지 않는다. 메타가 매칭되면 서버가 물리명·타입·길이를 정규화하고, AI 제안과 달라진 값을 도구 결과에 반환한다.
- 도구 결과에는 적용/미매칭/충돌 수와 정규화된 컬럼 결과를 제공한다. `pending=true`는 미저장 상태라는 현재 계약을 유지한다. 최종 설명이 AI의 원래 추측값이 아니라 서버 결과를 사용하도록 한다.
- 원래 DB 탭에 메타 CRUD 도구를 추가하지 않는다. 테이블 생성 요청으로 사전을 자동 생성·수정하는 기능은 별도 요구가 필요하다.

### 6.4 저장 직전 변경·취소·가드레일

- AI 요청이 사용한 catalog revision과 규칙 버전을 pending에 보관한다. 최종 write 트랜잭션에서 다시 확인한다. 삭제뿐 아니라 새 복합명 메타 추가와 길이 수정도 revision 차이로 감지한다.
- 버전이 달라졌다면 이번 pending 변경을 409로 취소하고 메타를 다시 조회하여 재생성하도록 한다. 최종 답변 검사 뒤에 새 메타로 조용히 다시 변환하면 검토한 내용과 저장 결과가 달라지므로 피한다.
- 단건은 `save_artifact`의 임시 검증과 `commit → mutateArtifact`에서, 일괄은 `save_database_tables → applyDatabaseBatch`의 임시 검증과 최종 commit에서 같은 resolver와 revision 검사를 적용한다.
- 일괄 등록은 모든 신규 테이블 컬럼을 먼저 정규화한 후 `@clientRef`·서버 ID 연결 및 전체 FK 검증을 수행한다. 컬럼 ID를 이름으로 대체하거나 재발급하지 않는다.
- 등록 명시 의도, 프로젝트별 CREATE 권한, 가드레일 허용 작업·변경 건수, 취소 checkpoint, 최종 출력 검사를 유지한다. 프롬프트만으로 메타 강제를 구현하지 않는다.
- 첫 구현의 자동 적용은 AI `CREATE`에 한정하는 것을 권장한다. AI UPDATE와 수동 저장은 기존 컬럼 값·ID·binding을 보존하고, 재적용을 요청한 별도 기능이 없으면 자동 재명명하지 않는다.
- 기존 API를 통해 클라이언트가 `domainBinding`을 위조하지 못하도록 저장 경계에서 서버 생성 정보임을 검증한다. 수동 편집의 일반 구조 검증과 AI 생성 전용 정규화 책임을 분리한다.

## 8. 검증 방법과 구현 순서

### 8.1 권장 구현 순서

1. 9절 정책을 확정하고 메타·컬럼·API 계약과 순수 정규화/매칭 로직을 구현한다.
2. 격리된 로컬 DB에서 신규 스키마·CRUD·권한·동시 수정을 검증한다.
3. 새 탭 ERD와 메타 화면, 테이블별 수정·삭제 모달을 연결한다. 공통 삭제 경로의 자기 참조 FK 검사를 보완하고 직접 진입·빈 상태·테마·재조회를 검증한다.
4. AI 조회와 단건·일괄 등록에 공통 resolver, pending revision 및 최종 검사를 연결한다.
5. 기존 CRUD·FK·RFP·가드레일·출력 회귀를 확인한 뒤 변경 내역을 정리한다.

| ERD 원래 영역 | DB설계에는 버튼과 테이블 목록만 두고 ERD 본문은 새 탭으로 이동 | 인라인 ERD도 유지하면 중복 표시·갱신 정책 필요 |
| 메타 진입 버튼 | `도메인 메타 관리`로 목록 진입, 새 화면에 `등록` 버튼 | 버튼을 `도메인 메타 등록`으로 고정하거나 등록 폼을 바로 열지 결정 |
| 사전 범위 | 프로젝트별 사전 | 팀 공통·프로젝트 override가 필요하면 추가 소속·우선순위·권한 모델 필요 |
| 도메인 개념 | 논리/물리 명칭과 타입을 한 항목에 보관해 사용자 예시 우선 지원 | 표준단어·표준용어·표준도메인을 분리하면 다중 테이블과 조합 규칙 재설계 필요 |
| `아이디 → id` 출처 | 내장 명칭 접미어 규칙, 전체 일치 프로젝트 메타 우선 | 내장 규칙을 원치 않으면 접미어 전용 사전 또는 `작업_아이디` 전체 메타 등록 필요 |
| 타입 상속 | `작업_아이디`는 작업 메타 타입 상속. 전체 일치 우선, 모호한 조합 차단 | 복합 컬럼 전반의 타입 제공자를 별도 역할로 나눌지 결정 |
| 미매칭 컬럼 | 완전 미매칭은 AI 제안 허용·명시, 부분 미해결은 차단 | 전체 사전 등록을 강제하면 사전이 없는 프로젝트의 기존 AI 등록도 막힘 |
| 수동/기존 AI 수정 | 신규 AI CREATE만 자동 적용, 기존 값 자동 변경 없음 | UPDATE·수동 재적용까지 포함하면 diff 미리보기·확인·FK 변경 처리 추가 필요 |
| 지원 DBMS·타입 | Oracle 예시 지원, 앱 저장소와 분리 | Oracle 외 타입, 예약어, 식별자 길이, 문자 길이 단위·사용자 정의 타입 허용 범위 확정 필요 |
| 메타 삭제·이력 | 논리 삭제와 컬럼 생성 스냅샷 유지, 감사는 기존 설정 준수 | 사용 중 삭제 금지, 전용 이력·복구·영구 보존이 필요하면 추가 저장/조회 설계 필요 |
| 메타 수정 권한 | 기존 database CRUD 권한 상속 | 설계자만 사전을 바꾸게 하려면 별도 권한 대상과 정책 migration 필요 |
| 독립 화면 셸·AI | 전용 넓은 화면, AI는 원래 DB 탭에서 사용 | 공통 셸·독립 화면 AI를 원하면 AI 위치 판정·컨텍스트 연계 범위 확대 |
| 논리명 출력 | 독립 논리명 필드 추가, 과거 설명 유지 | 워크북의 별도 논리명 열 추가 또는 기존 열 병합 표시 결정 필요 |

위 권장안은 구현 확정 사항이 아니다. 사용자 검토·수정 후 문서의 최종 정책을 기준으로 구현 범위와 API 계약을 확정한다.

추가로 요청한 **ERD 테이블명 오른쪽 수정·삭제 버튼, 모달 편집, FK가 남은 테이블 삭제 금지**는 확정 요구사항이다. 위 결정표는 이 기능의 구현 여부를 다시 결정하는 항목이 아니며, 기존 메타 정책과 화면 구성의 미확정 사항을 정리한 것이다.
