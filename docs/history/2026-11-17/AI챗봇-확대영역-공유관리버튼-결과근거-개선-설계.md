### 1.1 용어와 해석

- **외부 창**: `.matrix-ai-drawer`. 페이지 안 패널과 이동 가능한 팝업을 모두 포함한다.
- **대화 열**: `.matrix-ai-messages`가 표시하는 질문·답변·첨부·이전 대화 영역이다.
- **LLM 입력 패널**: `.matrix-ai-card` 전체다. 모델·AI 대상·프롬프트 textarea·첨부·생성/중지·오류·토큰 안내를 함께 취급한다.
- **100px 방향 권장안**: 현재 확대 버튼과 좌우분리 진입은 너비를 변경하므로 이번 추가분도 **너비 100px**로 해석한다. 요청에 방향이 명시되지는 않았으므로 높이 증가가 의도되었는지는 결정 사항 D1로 남긴다. R2의 height는 버튼 하단 정렬 기준이다.
- 상하 배치에서는 입력 카드와 대화 목록이 같은 너비를 공유한다. 외부 너비를 늘리면서 입력 카드만 100px 넓히고 대화 목록 너비를 고정할지는 D2에서 별도로 구분한다.
- 이 문서는 실제 브라우저 재현 결과가 아닌 정적 소스 분석이다. 현재 코드로 확인한 원인과 구현 후 확인할 시각적 결과를 구분한다.

## 3. 수정 방향: 외부 너비와 입력 열 100px 추가

### 3.1 적용 상태와 외부 너비 권장안

추가분은 `expanded || split`일 때 한 번만 적용한다. 기준 너비는 **이번 변경 전 동일 상태의 너비**다. 좌우분리에서 수동 축소하는 기존 기능도 유지한다.

| 창 상태 | 기존 기준 | 변경 후 목표 너비, 화면 공간이 충분한 경우 |
| --- | --- | --- |
| 상하·기본 패널 | 작업 영역 30% | 동일 |
| 상하·확대 패널 | 작업 영역 50% | `50% + 100px` |
| 좌우분리·확대 패널 | 작업 영역 50% | `50% + 100px` |
| 좌우분리·수동 축소 패널 | 작업 영역 30% | `30% + 100px` |
| 상하·기본 팝업 | 460px | 동일 |
| 상하·확대 또는 좌우분리·확대 팝업 | 760px | 860px |
| 좌우분리·수동 축소 팝업 | 460px | 560px |

- 데스크톱 패널의 본문 열은 늘어난 만큼 줄어든다. 전체 작업 영역을 초과하지 않도록 너비를 제한하고, 좁은 구간은 기존 반응형 패널 규칙을 우선한다.
- 960px 이하 패널은 기존 440px 및 viewport 제한을 우선하는 것을 권장한다. 팝업은 `viewport - 24px`가 우선한다. 이 경우 실제 추가분은 100px보다 작거나 0px일 수 있다.
- 위 예외는 화면 밖으로 밀리는 것을 방지하기 위한 권장 정책이며 D3에서 검토한다. 기본 높이·모바일 높이·팝업 드래그 동작은 유지한다.
- 좌우분리 진입 시 기본 확대, 모드별 마지막 확대 선택 복원, 닫기·재열기와 방 전환 시 창 상태 유지 정책을 보존한다. 확대와 좌우분리를 켤 때 200px가 누적되지 않아야 한다.
- 크기 상수/계산을 CSS와 창 훅에서 일치시키고 tooltip도 `패널 50% + 100px`, `팝업 최대 860px` 등 실제 상태에 맞춘다. 분리 상태에서 축소할 때의 560px 안내도 반영한다.

### 3.2 실제 추가분을 입력 열에 배분

외부 너비만 늘리고 내부 3:2 비율을 그대로 쓰면 추가분이 대화 60px·입력 40px로 나뉘므로 R1을 만족하지 못한다.

다음 값으로 내부 분배를 정의한다.

- `W0`: 기존 규칙의 외부 창 너비, `W1`: 새 규칙의 외부 창 너비.
- `Δ = max(0, W1 - W0)`: 화면 경계 제한을 적용한 실제 추가 너비. 목표는 100px다.
- `C1`: 변경 후 두 열에 쓸 수 있는 내부 너비. 테두리·좌우 padding을 제외한다.
- `C0 = C1 - Δ`, `G = 12px`: 기존 내부 너비와 열 간격이다.
- 최소 입력 너비 제약이 걸리지 않는 경우 대화 열은 `0.6 × (C0 - G)`, 입력 열은 `0.4 × (C0 - G) + Δ`로 배분한다.

충분한 너비에서 변경 전 대화 360px·입력 240px·간격 12px였다면 변경 후 대화 360px·입력 340px·간격 12px가 된다. 외부 창의 padding·border·gap은 그대로 두어 이 비교가 성립하도록 한다.

구현은 공통 CSS 사용자 속성에 기준 너비와 실제 추가분을 표현하고, 내부 grid가 추가분을 제외한 기준 너비로 왼쪽 열을 계산하도록 구성하는 방향을 권장한다. 실제 추가분 계산을 반응형 제한과 공유해야 하며 무조건 100px를 빼면 화면 경계에 걸린 창의 대화 열이 과도하게 줄어든다.

560px 컨테이너 경계와 입력 열 최소 240px는 우선 보존한다. 기존 규칙에서 이미 좌우 배치가 가능했던 너비는 대화 폭 유지와 입력 폭 증가를 비교한다. 확장으로 처음 경계를 넘은 경우에는 새로 좌우 배치가 가능해진 결과를 확인하되, 기존 상하 배치와의 열 너비 비교를 적용하지 않는다. 최소 열 너비나 가용 폭을 충족하지 못하면 상하 배치로 안전하게 표시한다.

상하 배치의 권장안은 전체 창과 전폭 콘텐츠를 함께 넓히는 것이다. 입력 카드도 100px 늘어나지만 대화 목록도 같은 폭을 사용한다. 상하 배치에서 대화 목록만 기존 폭으로 남길지는 D2에서 결정한다. textarea 높이를 100px 늘리는 변경은 이 너비 권장안에 포함하지 않는다.

## 4. 수정 방향: 공유 답변 관리 버튼 하단 정렬

공통 상단, 대화 열, 입력 열을 명시적으로 구분하여 자동 배치 행을 없앤다. 권장 DOM은 다음과 같다. 아래 클래스 이름은 구현 시 확정할 제안명이다.

```text
.matrix-ai-panel-content
├─ .matrix-ai-panel-heading                 공통 상단
│  ├─ AiConversationTitle
│  ├─ AiProjectPicker
│  └─ 이력 미저장 안내                      조건부
├─ .matrix-ai-conversation-pane             왼쪽 열
│  ├─ AiConversationMessages                flex:1, 자체 스크롤
│  └─ .matrix-ai-conversation-footer        축소되지 않는 하단 영역
│     └─ SharedAnswerControls               관리 버튼 한 개
└─ section.matrix-ai-card                   오른쪽 열, 자체 스크롤
   ├─ 기존 모델·대상·상태
   ├─ SharedAnswerCandidates               조건부, 입력 패널 안으로 이동
   └─ 기존 textarea·첨부·생성/중지·안내
```

1. 공통 상단은 두 열 전체 너비를 사용한다. 그 아래 grid의 한 행에 대화 pane과 입력 카드를 stretch로 배치한다.
2. 왼쪽 pane은 `min-height:0`의 세로 flex로 만들고 대화 목록에 남은 높이와 스크롤을 준다. footer는 `flex-shrink:0`으로 두어 목록 길이와 무관하게 접근 가능하게 한다.
3. 왼쪽 pane의 **목록+footer 전체 높이**와 오른쪽 입력 카드 높이를 맞춘다. 버튼의 개별 사각형과 카드 외곽선은 footer padding만큼 차이가 날 수 있다. 정렬 검증은 열 컨테이너 하단을 기준으로 한다.
4. 카드의 높이 제한과 스크롤을 유지하고, 공유 후보가 길어져도 바깥 grid에 새 행이 생기지 않게 한다. 후보는 입력과 관련된 내용이므로 입력 카드 안에서 함께 스크롤하는 것을 권장한다.
5. 상하 폴백에서도 같은 DOM을 유지한다. 공통 상단 → 대화와 관리 footer → 입력 카드 순서로 표시하고, 기존 대화 최소 높이와 입력 카드 65% 제한의 적용 대상을 재점검한다. 필요하면 대화 pane이 남은 높이를 받도록 flex 규칙을 옮긴다.
6. 답변별 `공유 답변으로 등록` 버튼은 기존 메시지 액션 영역에 둔다. 관리 버튼의 disabled 조건, 프로젝트 범위, 모달 생성 시점과 서버 권한 검증은 바꾸지 않는다.
7. 입력·첨부·생성 요청 상태를 옮기거나 같은 컴포넌트를 두 개 렌더링하지 않는다. CSS 배치 전환으로 textarea DOM, 방과 사용자 scope를 보존한다.

absolute/fixed bottom 배치는 카드·버튼 겹침과 짧은 화면에서의 잘림을 유발하므로 사용하지 않는 방향이다. 공통 상단이 화면 대부분을 차지하는 극단적인 낮은 높이에서는 기존처럼 내부 스크롤로 접근 가능한지 구현 검증이 필요하다.

## 5. 수정 방향: 결과 모달 관련근거 표시

### 5.1 동일 데이터와 공통 표시 컴포넌트

- 신규 표시 전용 `components/ai/ai-evidence.tsx`를 만들어 일반 대화와 결과 모달이 같은 목록 렌더링을 사용하도록 한다. 입력은 기존 `RagReference[]`와 펼침 여부 등 최소 표시 옵션으로 제한한다.
- 대화 목록은 현재처럼 접힌 details로 유지하고, 결과 모달에서는 답변 본문 아래의 근거 목록을 기본 펼침으로 표시하는 것을 권장한다. 제목은 기존 `프로젝트 근거 N건`을 유지한다.
- 각 항목은 현재 데이터의 title, version, section, href를 사용한다. 빈 title/section 등 과거 데이터의 누락 값은 레이아웃을 깨뜨리지 않도록 처리한다. chunkId를 추적 기준으로 보존하고 순서는 서버 배열을 유지한다.
- 링크는 기존 href를 사용한다. hash나 indexedAt을 본문에 무조건 노출하거나 추가 원문을 가져오지 않는다. 긴 제목·경로·다수 근거는 모달 본문 안에서 줄바꿈·세로 스크롤로 표시한다.
- references가 undefined 또는 빈 배열이면 빈 접이식 영역을 만들지 않는다. 데이터가 없는데 현재 프로젝트를 재검색해 과거 답변의 근거처럼 붙이지 않는다.
- 공통 근거 CSS는 `styles/ai-chatbot.css`로 소유권을 모으고 `styles/ai-project-rag.css`의 중복 규칙은 구현 시 함께 정리한다. 두 파일을 상충하는 규칙으로 유지하지 않는다.

### 5.2 기존 결과·공유 답변 동작 보존

- 결과 모달의 질문·첨부·본문 원문과 `결과 복사`는 보존한다. 복사는 계속 `result.result`를 그대로 복사하며 UI의 근거 목록을 덧붙이지 않는다.
- 본문 전체 Markdown 전환, 저장 문자열 재작성, HTML 삽입은 이 수정의 필수 범위가 아니다. `[근거:chunkId]`를 클릭 가능한 표식으로 바꿀지는 D5로 남긴다.
- 모달은 반드시 선택한 답변의 references만 사용한다. 다른 답변 열기, 방/프로젝트 변경, 재열기에서 이전 목록이 남지 않아야 한다. 열려 있는 모달의 데이터가 재조회로 마스킹되는 경우 오래된 선택 객체를 계속 노출하지 않는지도 점검한다.
- 공유 답변의 버전·현재 열람 불가·근거 변경 상태는 일반 대화와 같은 의미로 전달하는 것을 권장한다. 서버가 숨긴 본문과 references를 과거 클라이언트 캐시에서 복구하지 않는다.
- 공유 답변 관리의 evidence가 있는데 AiChat.references가 비어 있는 경우, 현 DTO에 없는 근거를 일반 모달에서 새로 보여주는 것은 별도 범위다. 최소 수정은 빈 배열을 정상 처리하는 것이다. 공유 근거까지 통합하려면 D6에 따라 API 계약·권한·이력 표시 정책을 먼저 정해야 한다.
- `closeResult`, Esc, 배경 클릭, 복사 성공 후 입력·첨부 초기화, 복사 실패 시 내용 보존, 포커스 복귀 동작은 유지한다. 근거 링크 이동 중 이 동작과 충돌하는지도 확인한다.

## 8. 검증 방법과 완료 조건

### 8.1 창 크기·분배·상태 보존

| 검증 항목 | 방법·기대 결과 |
| --- | --- |
| 데스크톱 패널 | 같은 viewport·메뉴 상태에서 기존 기준 50% 대비 +100px, 본문은 그만큼 감소. 분리 수동 축소는 30%+100px. 확대+분리 중복 추가 없음 |
| 팝업 | 충분한 화면에서 기본 460px, 확대/분리 기본 860px, 분리 수동 축소 560px. 화면 경계에서는 viewport-24px 우선 |
| 입력 열 배분 | 같은 기준 상태에서 외부 폭 +100px, 대화 열 폭 변화 0px, 입력 열 폭 +100px를 DOMRect로 비교. padding·border·gap을 포함해 약 2px 오차만 허용 |
| 제한된 추가분 | 화면 상한에 걸려 Δ가 0~99px인 경우에도 대화 열을 고정 100px 빼지 않고 실제 Δ만 오른쪽에 배분 |
| 배치 경계 | 실제 컨테이너 559/560/561px와 viewport 961/960/701/700/390px 확인. 폭 560px는 외부 창이 아니라 `.matrix-ai`의 내부 컨테이너 기준 |
| 상태 전환 | 상하·분리·확대·축소·팝업·패널·닫기/재열기·방 전환에서 기존 확대 선택과 입력/모델/대상/첨부/textarea DOM 보존 |
| 팝업 위치 | 오른쪽 끝에 둔 뒤 확대/분리, 분리 해제, viewport 축소. 최초 위치와 전환 후 위치가 12px 경계를 준수 |
| 생성 중 조작 | 레이아웃 전환이 요청 재시작·추가 생성·선택 대상 변경을 일으키지 않고 중지 버튼에 접근 가능 |

### 8.2 관리 버튼·조건부 콘텐츠

- 빈 대화와 긴 대화에서 왼쪽 pane과 입력 카드 하단 차이가 약 2px 이내인지 측정한다. 대화 목록 높이는 footer만큼 줄어드는 것이 정상이다.
- 왼쪽 목록 스크롤 중 관리 버튼 위치가 유지되고, 오른쪽 카드 스크롤은 왼쪽에 영향을 주지 않는지 확인한다.
- 긴 프로젝트명·이력 미저장 안내·공유 후보 표시·다수 첨부·오류·토큰 안내가 추가돼도 암시적 grid 행과 겹침/잘림이 없는지 확인한다.
- projectId 없음, 관리 버튼 disabled, 관리 모달 열기/닫기, 메시지의 등록 버튼을 각각 확인한다. 관리 버튼 위치 변경으로 승인·반려·철회 동작이 달라지지 않아야 한다.
- 낮은 높이, 모바일 상하 폴백, 라이트/다크, 키보드 Tab과 실제 브라우저 200% 확대에서도 관리·생성·중지에 접근 가능한지 수동 확인한다.

### 8.3 결과 모달 근거

| 데이터/조작 | 기대 결과 |
| --- | --- |
| 생성 직후 references 1건/다수 | 일반 대화와 모달의 건수·제목·버전·section·href가 일치, 모달은 기본 펼침 |
| 방 재진입·이전 대화 조회 | 저장된 references가 동일하게 표시되고 최신 프로젝트 검색 결과로 교체되지 않음 |
| references 없음/빈 배열 | 질문·첨부·답변은 표시되고 빈 근거 제목·오류가 생기지 않음 |
| 긴 제목·다수 항목 | 모달 본문 스크롤 안에 표시되고 헤더·복사/닫기 동작 접근 가능 |
| 서로 다른 답변 연속 열기 | 각 답변의 근거만 표시, 펼침 상태와 이전 DOM이 다른 답변에 잘못 잔존하지 않음 |
| 공유 답변 열람 제한/근거 변경 | 서버 마스킹과 상태 안내를 보존, 숨긴 본문·링크를 오래된 캐시에서 재노출하지 않음 |
| 근거 링크 클릭·키보드 활성화 | 해당 프로젝트 자료의 기존 접근 검증을 거쳐 이동. 잘못된 다른 프로젝트 링크가 만들어지지 않음 |
| Esc·닫기·배경 클릭·복사 성공/실패 | 기존 입력/첨부 초기화·오류 보존·포커스 복귀 정책 유지. 복사 내용은 원래 result 문자열 |

향후 구현 검증은 `pnpm typecheck`, 변경 파일 ESLint, `pnpm build`, `pnpm test:ai-targets-browser`, `pnpm test:shared-answers-browser`를 중심으로 수행한다. `check-ai-window-browser.mjs`는 독립 실행기가 아니라 기존 브라우저 검증에서 호출하는 함수이므로 기존 실행 흐름을 사용한다. 근거 데이터 fixture를 추가하여 모달이 표시하는 실제 DOM과 링크를 검사한다. 공유 표시 로직에 영향을 주면 `pnpm test:shared-answers`도 임시 DB에서 수행한다.

브라우저 통합 검증이 필요한 구현 단계에서는 합성 계정·모의 AI·임시 DB만 사용하고 운영 DB에 회귀 데이터를 넣지 않는다. 이번 설계 단계에서는 앱 서버·생성 요청·테스트·빌드·마이그레이션을 실행하지 않는다. 문서 경로·링크·HISTORY 기존 내용 보존과 소스 미변경만 확인한다.

## 9. 구현 순서 제안과 이번 단계 결과

1. 사용자가 검토·수정한 문서에서 D1~D7의 적용 정책을 확인한다.
2. 내부 공통 상단·대화 footer·입력 카드 배치를 명시해 자동 행을 제거한다.
3. 외부 너비와 실제 추가분의 입력 열 배분, 팝업 위치/tooltip을 함께 반영한다.
4. 공통 근거 표시를 일반 대화와 결과 모달에 연결한다.
5. 기존 geometry 검증을 새 규칙에 맞추고 모달 근거·footer 회귀를 검증한 후 구현 기록을 작성한다.

이번 단계는 현재 소스에 근거한 분석과 설계 문서 작성으로 한정한다. 기능 수정 완료나 브라우저 검증 통과를 의미하지 않는다. `HISTORY.md`에는 기존 목록을 보존하면서 이 문서의 상대 경로와 작성일만 추가한다.
