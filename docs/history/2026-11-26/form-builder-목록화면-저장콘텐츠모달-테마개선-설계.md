# Form Builder 목록 화면 및 저장 콘텐츠 모달 테마 개선 설계

- 작성일: 2026-11-26 (한국시간, Asia/Seoul)
- 상태: 현재 소스를 분석한 검토용 설계. 사용자가 검토·수정한 문서를 기준으로 별도 구현 요청 후 작업한다.
- 이번 작업: 이 문서 신규 작성과 `HISTORY.md` 링크 추가만 수행한다. 소스·설정·의존성·DB·마이그레이션은 수정하지 않는다.
- 조사 방식: 저장소의 소스와 기존 설계·구현 기록을 읽었다. 실제 화면 실행이나 DB 조회·변경은 수행하지 않았으며, 아래 검증 항목은 후속 구현 시 수행할 계획이다.
- 경로 기준: 별도 표시가 없으면 `hams-matrix/` 기준이다. 신규 파일과 URL은 구현 제안이며 현재 존재하는 기능이 아니다.

### 1.1 권고 범위와 제외 범위

권고 범위는 목록 조회·제목 검색·정렬·페이지 이동·신규 작성/편집 연결, 모달 테마 수정, 이 흐름에 필요한 초기화·미저장 변경 보호다. 삭제·복제·일괄 처리·배포·프로젝트 귀속·신규 테이블은 기본 범위에 추가하지 않는다. 기존 API가 삭제를 지원한다는 이유만으로 목록에 삭제 기능을 넣지 않는다.

목록과 모달의 시각적 일관성은 기존 `--builder-*` 테마 변수를 기준으로 한다. 독립 챗봇의 자체 테마를 폼 목록에 사용하지 않는다. 빌더 전체의 MUI 팔레트나 Matrix 전역 테마를 재설계하는 작업으로 확대하지 않는다.

## 2. 현재 구조와 확인 결과

### 2.1 진입 경로와 화면 구성

| 영역 | 현재 소스 | 현재 동작 및 분석 |
| --- | --- | --- |
| 폼 페이지 | `app/(builder)/form-builder/page.tsx` | `FormBuilder.tsx`를 바로 export하는 서버 page wrapper이며 `instant = false`를 선언한다. 독립 목록을 선택하는 분기가 없다. |
| 폼 편집기 | `app/(builder)/form-builder/FormBuilder.tsx` | 요소 팔레트·캔버스·속성·JSON·저장·불러오기 모달을 제공한다. URL의 `formId`를 읽어 상세를 조회하는 처리가 없다. |
| 빌더 메뉴/초기화 | `app/(builder)/providers/runtime.tsx` | 폼 메뉴가 `/form-builder`를 가리킨다. 사용자/workspace 변경 시 빌더 및 폼 store를 초기화한다. `Entry`의 URL 복원은 `scenarioId`·`versionId` 중심이다. |
| 폼 상태 | `app/(builder)/form-builder/stores/useFormEditorStore.ts` | `formId`, `revision`, 제목, 요소, 선택 상태를 보관한다. 데이터 소스 등 일부 설정은 편집기 로컬 상태에 있다. 시나리오 폼 노드와 같은 store를 공유한다. |
| 시나리오 목록 참고 | `app/(builder)/react-flow/scenario-list/ScenarioList.tsx` | 검색 영역과 카드 형태 목록을 제공한다. 조회 UI의 간격·밀도는 참고할 수 있지만, 이번 폼 목록은 요구대로 테이블을 사용한다. |
| 빌더 인증 셸 | `app/(builder)/layout.tsx` | 인증·온보딩·빌더 접근 검사 후 Query 경계, 개인 설정, `BuilderRuntime`을 제공한다. 신규 목록도 이 경계를 상속한다. |

`(builder)`는 URL에 포함되지 않는 route group이다. 현재 `/form-builder`는 목록 없이 편집기로 바로 진입하므로 “목록 화면이 없다”는 요구는 소스로 확인된다. 기존 구현 기록의 폼 “목록” 언급은 저장 콘텐츠 선택 모달의 목록과 구분해야 한다.

### 2.2 저장 콘텐츠 모달

대상은 `app/(builder)/form-builder/components/modals/SavedFormContentModal.tsx`와 같은 이름의 CSS Module이다.

현재 동작은 다음과 같다.

1. 열릴 때 `builderList("/forms")`로 현재 workspace의 폼을 조회한다.
2. API의 `id/title/elements/definition/revision`을 `SavedFormContent` 형식으로 변환한다.
3. 제목의 앞뒤 공백 제거·소문자 비교를 통해 입력 즉시 부분 검색하고, 10개씩 클라이언트 페이지를 나눈다.
4. 테이블 행을 더블클릭하면 `onSelect(id, formData)`를 호출한 뒤 닫는다.
5. 편집기는 `loadFormJson()`으로 내용을 적용하고, 시나리오 폼 노드는 `handleLoadSavedFormContent()`로 노드에 내용을 적용한다.

현재 테이블에는 생성자·수정자 열이 있지만, `repository.ts`의 폼 DTO는 작업자 필드를 반환하지 않고 모달의 변환 코드도 채우지 않는다. 따라서 이 열을 신규 목록에 그대로 복제하면 빈 값이 생긴다. 작업자 표시 확대는 8절의 별도 결정 사항이다.

### 2.3 테마 불일치의 원인

| 확인 위치 | 현재 코드/값 | 영향 |
| --- | --- | --- |
| 모달 `.searchPanel` | 배경 `#f8f9fb`, 테두리 `#e5e7eb` | 다크 모드에서도 검색 조건 카드가 밝게 남는다. |
| 모달 `.searchLabel` | 글자 `#444` | 검색 카드의 배경만 바꾸면 라벨 대비가 나빠질 수 있다. |
| 모달 `.searchInput` | 테두리 `#cfd4dc`, 자체 배경·글자색 지정 없음 | 부모의 입력 전역 규칙에 의존하며 호출 위치별 차이가 생긴다. |
| 모달 테이블·보조 UI | 헤더 `#f8f9fb/#555`, hover `#f6f8ff`, 경계 `#ddd/#eee`, 비활성 버튼 `#f3f4f6/#aaa` 등 | 검색 영역만 수정하면 바로 아래 목록·페이지 이동에 테마 불일치가 남는다. |
| `styles/builder.css` | `.builder-root, [data-builder-theme]`에 `--builder-*` 선언 | 변수는 해당 DOM과 하위 요소에 적용된다. `body`의 모든 자손에게 자동 제공되는 구조가 아니다. |
| `FormNodeController.tsx` | `createPortal(..., document.body)`로 모달 표시 | 모달 DOM이 `.builder-root` 밖으로 이동한다. 현재 모달 최상위에는 `data-builder-theme`가 없어 빌더 변수의 상속 경계를 벗어난다. |
| `providers/runtime.tsx` | MUI Dialog/Menu의 paper에 테마 속성 제공 | 대상 모달은 일반 `div` 기반이므로 이 MUI 설정의 적용 대상이 아니다. |

고정 색상 잔존과 portal의 CSS 변수 상속 문제는 서로 다른 원인이다. CSS 색상 교체와 모달 자체의 테마 경계 처리를 함께 설계한다. React context는 portal에서도 전달되지만 DOM 기반 CSS 상속은 portal의 실제 위치를 따른다. 화면별 실제 대비와 최종 계산 스타일은 후속 브라우저 검증으로 확인한다.

### 2.4 조회·저장 API와 데이터 계약

| 항목 | 현재 계약 |
| --- | --- |
| 목록 | `GET /api/builder/forms` → `{ items, nextCursor }` |
| 목록 파라미터 | `limit`·`cursor`. `limit` 기본 100, 최대 200, ID 오름차순 커서. 폼 제목 검색·수정일 정렬·전체 건수 파라미터는 현재 없다. |
| 폼 DTO | `id`, `title`, `elements`, `definition`, `createdAt`, `updatedAt`, `revision` |
| 상세 | `GET /api/builder/forms/[formId]` → `{ form }` |
| 생성/수정 | 컬렉션 POST/상세 PATCH. 수정은 `expectedRevision`을 검사하고 충돌 시 409를 반환한다. |
| 서버 처리 | `app/(builder)/server/repository.ts`의 `listResources/getResource/saveResource`. `builder_forms`를 사용하며 workspace와 논리 삭제 조건을 검사한다. |
| 전송 | `app/(builder)/services/transport.ts`의 `builderRequest/builderList`. 기존 사용자/workspace Query key와 정책을 사용하고 범위 종료 시 요청을 취소한다. 쓰기 후 빌더 Query를 무효화한다. |
| 전체 목록 수집 | `builderList()`는 한 번에 200개씩 `nextCursor`가 없어질 때까지 요청해 배열로 합친다. 첫 200개만 반환하는 함수가 아니다. |

목록 API는 이미 있으므로 기본안에서 API·DB 변경은 필요하지 않다. 현재 응답에는 요소와 전체 정의도 포함되므로, 대량 데이터에서의 전송 비용은 서버 검색·요약 DTO를 검토할 근거가 된다. 다만 실제 데이터 규모나 성능 저하를 이번 정적 분석으로 확정하지 않는다.

### 2.5 목록 연결 시 함께 다뤄야 하는 상태 문제

- 폼 편집기는 `registerDraftGuard()`를 등록하지 않는다. 현재 등록자는 시나리오 상세 편집기다. 새 목록 이동 버튼만 추가하면 폼의 미저장 변경을 보호하지 못한다.
- `BuilderNavigation`의 버리기 확인 후 초기화는 시나리오 상태 중심이다. 폼 제목·요소·revision과 편집기 로컬 설정을 일관되게 정리할 경로가 필요하다.
- `resetForm()`은 ID·제목·요소·선택을 초기화하지만 revision을 초기화하지 않는다. 신규 작성에서는 revision까지 초기화하도록 명시한다.
- `FormBuilder.tsx`의 `loadFormJson()`은 저장 리소스 ID와 정의 내부의 `data.id`를 따로 다룬다. 목록에서 전달하는 ID 하나로 둘을 대체하면 요소 참조나 저장 대상이 달라질 수 있다.
- 폼 노드도 같은 store를 사용하므로 목록을 여는 것만으로 store를 초기화하지 않는다. 편집기 진입 시 명시적으로 선택한 대상에 한해 초기화·복원한다.

## 3. 목록 화면 설계

### 3.1 URL과 진입 경로: 권고안

| URL/동작 | 제안 |
| --- | --- |
| `/form-builder/list` | 신규 독립 목록. 빌더 공통 상단의 `폼` 메뉴 목적지로 사용한다. |
| `/form-builder?mode=new` | 신규 작성 진입. 미저장 확인 이후 폼 ID·revision·내용·로컬 설정을 초기화한다. |
| `/form-builder?formId=<저장 리소스 ID>` | 기존 폼 편집. 상세 API로 최신 정의와 revision을 조회한다. |
| 기존 `/form-builder` | 기존 편집 주소를 유지한다. 같은 범위의 편집 초안이 있으면 보존하고, 없으면 신규 편집 상태를 표시한다. |
| 편집기의 `목록` 버튼 | 미저장 확인 후 목록으로 돌아간다. 목록의 검색·정렬·페이지는 목록 URL에서 복원한다. |

기존 `/form-builder`를 곧바로 목록으로 교체하면 기존 진입 주소의 의미와 브라우저 검증이 바뀐다. 주소를 보존하는 위 안을 권고하며, `/form-builder` 자체를 목록으로 하고 편집기를 하위 경로로 이동할지는 사용자 검토 항목으로 남긴다. `formId`와 `mode=new`가 동시에 있거나 잘못된 값인 경우에는 임의 저장 대상을 선택하지 않고 안내한다.

신규 페이지도 서버 wrapper와 클라이언트 컴포넌트를 분리한다. 기존 페이지와 동일하게 route config는 서버 wrapper에 둔다. 개인 설정·Query·인증 Provider를 목록 안에 중복 추가하지 않는다.

### 3.2 화면 배치

위에서 아래 순서로 화면 제목·신규 작성, 조회 조건 카드, 조회 건수·테이블, 페이지 이동을 배치한다. 검색 조건 카드는 목록 위에 항상 표시하고, 테이블은 남은 공간을 사용한다.

| 영역 | 기본 구성 | 동작 |
| --- | --- | --- |
| 제목/작업 | `Form Builder` 또는 `폼 목록`, `신규 작성` | 신규 작성 클릭 시 새 편집 상태로 이동한다. |
| 상단 조회 | 제목 입력, 정렬 선택, `조회`, `초기화` | 제목 입력의 Enter와 조회 클릭이 같은 적용 동작을 수행한다. |
| 정렬 | 최근 수정순 기본, 제목순 | 수정일 내림차순, 동일 값은 ID로 보조 정렬한다. 제목순은 한국어 기준 비교 후 ID로 순서를 고정한다. |
| 목록 정보 | 검색 결과 전체 건수, 현재 표시 구간 | 전체 커서 수집 완료 이후의 필터 결과로 계산한다. 불러오는 중에는 확정 건수로 표시하지 않는다. |
| 하단 | 테이블, 처음/이전/다음/마지막, 페이지 정보 | 페이지 크기는 기존 모달과 같은 10개를 기본으로 한다. |

조회 조건은 입력 중인 초안과 적용된 조건을 구분한다. 조회 시 앞뒤 공백을 제거하고 대소문자를 구분하지 않는 제목 부분 검색을 적용하며 1페이지로 이동한다. 초기화는 제목 없음·최근 수정순·1페이지로 복귀한다. 목록의 적용 조건은 `title`, `sort`, `page` 등 정해진 URL 파라미터로 보존하고 유효하지 않은 페이지는 범위 안으로 보정한다. 브라우저 뒤로 가기에서도 해당 조건을 복원한다.

| 테이블 열 | 데이터 및 표시 기준 |
| --- | --- |
| No | 검색·정렬 결과의 페이지를 반영한 순번. DB 식별자가 아니다. |
| Content ID | `form.id`. 길면 말줄임하되 전체 값을 확인할 수 있게 한다. |
| Content Title | `form.title`. 키보드로 접근 가능한 편집 링크로 표시한다. |
| Element | `elements`에서 요소 유형별 개수를 요약한다. 비어 있으면 `-`를 표시한다. |
| Updated | `updatedAt`. 표시 기준은 한국시간을 권고하며 잘못된 날짜는 `-`로 처리한다. |
| 작업 | 명시적인 `편집` 링크 또는 버튼. 더블클릭만을 유일한 진입 수단으로 사용하지 않는다. |

생성자·수정자와 revision 열은 기본 목록에서 제외한다. revision은 편집·저장 충돌 검사에 내부적으로 유지한다. 생성일 열 추가 여부는 검토 시 정할 수 있다.

### 3.3 데이터 처리와 상태 표시

기본안은 기존 모달처럼 `builderList("/forms")`를 재사용해 모든 커서를 수집한 뒤 클라이언트에서 검색·정렬·페이지를 적용한다. 미지원 검색 파라미터를 현재 API에 보내고 서버가 처리한다고 가정하지 않는다. 페이지 이동 때마다 전체 목록을 재요청하지 않는다.

목록 배열·필터·페이지는 목록 소유 상태이며 편집 store에 저장하지 않는다. 편집 대상은 URL의 리소스 ID로 식별하고, 진입 시 상세 API를 호출해 현재 내용을 확인한다. 쓰기 후 기존 Query 무효화와 목록 재진입 조회를 통해 최신 결과를 반영한다. 명시적 조회의 재조회·캐시 처리도 기존 workspace Query 정책을 따라 설계하며, 임의의 별도 fetch·전역 캐시·폴링을 추가하지 않는다.

로딩, 자료 없음, 검색 결과 없음, 조회 실패를 구분한다. 실패 시 재조회 동작을 제공한다. 이전 요청이 늦게 완료되어 새 조건이나 다른 사용자 범위의 화면을 덮지 않도록 unmount/요청 세대 검사를 적용한다. 401·403에서는 이전 목록을 숨기고, 편집 상세의 404는 찾을 수 없음과 목록 이동을 표시한다.

전체 정의를 받는 현 방식은 폼 수와 정의 크기에 비례해 전송량·메모리가 증가한다. 대량 폼이 예상되면 서버 제목 검색·수정일 정렬·요약 DTO·페이지 계약을 별도 확장하는 안을 선택한다. 이 경우 ID 기반 기존 커서를 수정일 커서처럼 사용하지 말고 정렬과 일치하는 커서를 별도로 설계해야 한다.

## 4. 편집기 연결과 데이터 보존

### 4.1 복원 경로 통합

빌더 내부 `services/forms.ts` 등 하나의 모듈에 폼 리소스 타입, API 응답을 편집 정의로 변환하는 함수, 요소 요약 함수를 둔다. 목록과 모달에서 변환 코드를 복제하지 않는다. 다음 값을 구분한다.

- 저장 리소스 ID: `form.id` → store의 `formId`, 상세 API 주소와 PATCH 대상.
- 요소 정의 ID: `definition.data.id` 등 기존 정의 내부 ID → 기존 캔버스·요소 참조에 사용. 누락 시에만 기존 호환 규칙을 적용한다.
- 저장 revision: 응답의 `form.revision` → store에 원자적으로 복원하고 다음 저장의 `expectedRevision`에 사용.
- 정의: `definition`을 보존하면서 현재 응답의 `title`과 `elements`를 반영한다. `dataSource`, `dataSourceType`, `enableExcelUpload`, 요소별 API 매핑·슬롯·그리드·옵션 정보를 누락하지 않는다.

목록의 상세 진입과 모달 선택은 같은 정규화·적용 경로를 거친다. 기존 요소 `normalizeElement()` 처리도 보존한다. 서버 정의에 편집기가 알지 못하는 필드가 있다면 로드 후 첫 저장에서 사라지지 않도록 원본 정의와 편집 결과를 병합하는 기준을 둔다. 정의와 요소 배열을 화면마다 새로 조립하면서 부가 설정을 잃는 회귀를 검증한다.

### 4.2 초기화·저장·미저장 변경

1. **상세 진입:** 대상 ID별 요청 상태를 관리한다. 로딩 중 이전 폼을 새 대상처럼 편집·저장할 수 없게 한다. 같은 대상의 단순 렌더나 테마 전환으로 편집 초안을 다시 덮지 않는다.
2. **신규 작성:** 승인된 이동 시에만 `formId=null`, `revision=0`, 기본 제목, 빈 요소·선택과 데이터 소스·Excel·JSON 로컬 상태를 함께 초기화한다. 목록을 조회하는 행위는 초기화를 일으키지 않는다.
3. **신규 저장 성공:** API가 반환한 ID·revision을 store에 반영하고 `router.replace`로 편집 URL을 `?formId=...`로 맞춘다. 이 URL 반영 때문에 방금 저장한 초안이 다시 초기화되지 않게 한다.
4. **수정 저장 성공:** 반환 revision을 반영하고 미저장 판정 기준을 갱신한다. 실패·409 시 현재 초안을 유지하고 재조회/재선택 안내를 제공하며 강제 덮어쓰기나 자동 저장 재시도를 하지 않는다.
5. **화면 이동:** 편집기의 목록·신규 작성·다른 폼 불러오기와 공통 빌더 메뉴에서 같은 미저장 확인을 사용한다. 사용자가 취소하면 URL·내용·선택을 유지한다. 목록 필터 URL 변경에는 이 확인을 걸지 않는다.
6. **브라우저 이탈:** 폼 편집기가 기존 `registerDraftGuard()`를 등록·해제해 새로고침/닫기 확인에 참여한다. 기본 판정에는 제목·요소뿐 아니라 데이터 소스·Excel·저장에 반영될 JSON 편집도 포함하고 단순 선택·탭 변경은 제외한다. 뒤로/앞으로 이동에 대한 확인·복원도 후속 브라우저 검증에 포함한다.

공통 draft guard는 단일 등록 구조이므로 시나리오 상세와 폼 편집기의 mount/unmount 시 등록 해제가 맞는지 확인한다. 공통 메뉴의 기존 시나리오 버리기 동작을 깨지 않으면서, 폼 편집기의 승인된 이탈에서는 폼 store와 로컬 상태도 정리하도록 연결한다.

## 5. 테마 수정 설계

### 5.1 목록과 모달의 색상 기준

| 역할 | 사용할 변수 |
| --- | --- |
| 화면 배경 | `--builder-canvas` |
| 테이블/모달 기본 표면 | `--builder-surface` |
| 검색 카드·테이블 헤더·보조 표면 | `--builder-muted-surface` 또는 `--builder-accent-soft` |
| 입력 배경/글자 | `--builder-input`, `--builder-text` |
| 경계·구분선 | `--builder-border` |
| 기본/보조/placeholder 글자 | `--builder-text`, `--builder-muted` |
| 주요 동작·focus 표시 | `--builder-accent`, 필요 시 `--builder-on-accent` |
| hover | `--builder-accent-soft`와 대비가 확보된 글자색 |
| 비활성 버튼 | 기존 표면·보조 글자 변수와 disabled 상태. hover와 구분한다. |

목록은 테마 변수 기반 CSS Module로 작성한다. 모달도 검색 카드, 라벨, 입력의 배경·글자·테두리·placeholder·focus를 각각 명시한다. `.builder-root input` 규칙의 상속만으로 색상을 맞추지 않는다. 주요 버튼에 `--builder-on-accent`를 쓰는 경우 실제 프리셋·커스텀 색상의 대비도 확인한다.

검색 영역 바로 아래의 표 머리·행 hover·경계·빈 상태·페이지 이동·닫기 버튼에도 고정 색상이 있으므로 같은 모달 범위에서 테마 변수로 정리하는 것을 권고한다. 불투명 오버레이·그림자처럼 테마 의미색이 아닌 값은 필요에 맞게 유지한다. 전역 `body`, 모든 input/table, Matrix 다른 페이지를 대상으로 선택자를 확장하지 않는다.

### 5.2 Portal에서의 테마 경계

`SavedFormContentModal` 최상위에 현재 빌더 appearance context의 밝기 값을 읽어 `data-builder-theme={theme}`를 부여하는 안을 권고한다. 그러면 기존 `.builder-root, [data-builder-theme]` 선언이 직접 적용되어 `document.body`로 portal되는 경우에도 `--builder-*` 변수를 사용할 수 있다. Matrix의 원본 `--surface/--ink/--primary` 등은 루트 설정을 그대로 따른다.

테마 속성은 모달을 열 때 한 번 복사하는 값이 아니라 context 갱신을 따라야 한다. `FormNodeController`의 portal 위치는 기본안에서 유지하며, 모달이 호출 위치와 무관하게 필요한 변수를 갖도록 한다. portal을 루트 내부로 옮기는 안은 clipping·z-index·스크롤 영향이 있어 우선 적용하지 않는다.

모달 CSS 클래스명을 유지하면 `.module.css.d.ts`를 수정할 필요는 없다. 신규 클래스를 추가하거나 삭제할 때만 선언 파일을 함께 갱신한다. 테마 외 모달 검색의 입력 즉시 필터·10개 페이지·더블클릭 선택·콜백 형식은 보존한다. 키보드 선택·Escape·포커스 복귀 보완은 별도 검토 항목으로 둔다.

### 7.1 이번 문서 작업의 검증

- 요구사항·현재 구조·수정 방향·변경 대상·검증·결정 사항의 누락 여부를 확인한다.

| 영역 | 주요 시나리오 | 기대 결과 |

| 조회/페이지 | 공백·영문 대소문자·한글 제목, Enter, 초기화, 0/1/10/11/201개 자료 | 전체 커서 수집 후 정확한 검색·건수·페이지. 200개 이후 자료도 누락되지 않음. |
| 정렬/복원 | 동일 수정일·제목, 잘못된 page, 편집 후 뒤로 가기 | 순서가 안정적이며 페이지가 보정되고 적용 조건이 복원됨. |
| 상세 진입 | 목록 선택, `?formId=` 직접 진입·새로고침, 삭제/없는 ID | 최신 상세·revision을 복원하거나 명확한 오류와 목록 이동 제공. |
| 신규/저장 | 기존 폼에서 신규 작성, 생성 후 새로고침, 수정 저장 | 새 상태의 ID/revision 초기화, 생성 ID가 URL에 반영, 수정 대상 유지. |
| 데이터 보존 | 데이터 소스·API 매핑·슬롯·그리드·Excel·요소 ID·추가 정의 필드 | 목록/모달에서 로드 후 수정·저장해도 부가 설정이 유실되지 않음. |
| 충돌 | 다른 편집자가 수정해 revision 불일치 | 409에서 초안을 보존하고 안내. 무조건 재저장하지 않음. |
| 미저장 보호 | 목록/신규/공통 메뉴/다른 폼 로드/뒤로 가기/새로고침 | 취소 시 현재 초안 유지. 승인된 버리기만 초기화하고 다른 화면에 초안이 섞이지 않음. |
| 비동기 경합 | 빠른 대상 전환, 모달 닫기 후 응답, 사용자/workspace 전환 | 오래된 응답이 현재 폼·목록을 덮거나 다른 범위 데이터를 표시하지 않음. |
| 공유 store | 시나리오 폼 노드 → 목록 → 신규/다른 폼 편집 | 목록 열기만으로 노드 내용이 변하지 않고 명시적 편집 대상과 revision이 일치함. |
| 권한/격리 | 미로그인·guest·비관리자·다른 workspace의 formId | 기존 서버 제한을 유지하고 이전 목록/상세를 숨김. |

### 7.3 테마·레이아웃 검증

- 라이트/다크 각각에서 주황·파랑·초록 프리셋과 커스텀 테마를 확인한다. 현재 테마 그대로 첫 진입·새로고침이 되는지도 확인한다.
- 목록, 편집기의 저장 콘텐츠 모달, 시나리오 폼 노드에서 body portal로 열린 같은 모달을 각각 검증한다. 열린 모달 상태에서 밝기와 강조색을 변경한다.
- 검색 카드·입력·라벨·placeholder·focus·테이블 헤더·hover·경계·빈 상태·disabled 페이지 버튼의 계산 스타일을 확인한다. portal에서도 `--builder-*` 값이 정의되는지 확인한다.
- 데스크톱과 좁은 화면에서 검색 조건 줄바꿈, 버튼 접근성, 테이블 내부 가로 스크롤을 확인한다. 기존 모달의 `min-width: 960px` 테이블이 화면 전체 가로 넘침을 만들지 않는지 검사한다.
- 키보드로 목록 제목/편집·조회·페이지 이동을 조작할 수 있고 focus가 식별되는지 확인한다. 긴 제목·ID·요소 요약이 레이아웃을 깨지 않는지 확인한다.
- 시나리오 목록·편집·버전 조회·기존 MUI Dialog/Menu와 독립 챗봇 테마가 이번 CSS 변경의 영향을 받지 않는지 확인한다.

### 7.4 후속 구현 시 실행할 검사

변경 파일 ESLint와 타입 검사를 먼저 수행하고 `pnpm build`, `node scripts/test-builder.mjs`, `node scripts/test-builder-browser.mjs`로 범위에 맞게 확인한다. DB/API·브라우저 검증은 기존 스크립트의 임시 DB·합성 계정 방식으로 수행하고 구성된 DB에 테스트 자료를 만들지 않는다. 의존성 설치·마이그레이션은 이 개선의 기본안에 필요하지 않다.

기존 브라우저 검증은 폼 편집기 표시·다크 새로고침 수준이며 독립 목록과 해당 모달의 검색 영역/portal을 구체적으로 검사하지 않는다. 따라서 기존 검사 통과만으로 이번 요구를 충족했다고 판단하지 않는다. 과거 구현 기록의 빌드/타입 실패는 당시 기록이고, 이후 기록에서는 통과 이력도 있으므로 후속 구현 당시 실제 결과와 구분한다.

## 8. 결정이 필요한 사항

다음은 검토 시 정할 항목이다. 현재 문서의 권고안을 구현 확정으로 간주하지 않으며, 검토 후 사용자가 수정한 문서를 우선한다.

| 항목 | 권고안 | 다른 선택 시 영향 |
| --- | --- | --- |
| 목록/편집 URL | `/form-builder/list` 추가, 기존 `/form-builder` 편집 주소 보존 | 루트를 목록으로 바꾸면 편집 하위 route와 기존 북마크·링크·브라우저 검증을 함께 변경해야 함. |
| 초기 목록 검색 | 제목만, 최근 수정순/제목순, 10개 페이지 | ID·기간·작업자 검색 추가 시 조건·날짜·조회 범위 계약 추가 필요. |
| 조회 처리 위치 | 기존 전체 커서 조회 후 클라이언트 처리 | 대량 폼 환경이면 서버 검색·요약 DTO·정렬 커서/건수 계약 설계 및 API 검증 범위 확대. |
| 생성자/수정자 열 | 신규 목록 기본 제외, 기존 모달은 현행 열을 보존하되 누락 문제 기록 | 표시하려면 실제 작업자 DTO·표시명·탈퇴 처리·workspace 범위를 정의하고 서버/모달 변환 추가. 임의 이름·현재 로그인 사용자로 채우지 않음. |
| 모달 수정 폭 | 검색 영역과 같은 모달의 표·페이지 이동까지 테마 정리 | 검색 영역만 고치면 테이블의 고정 밝은 색상이 남음. 전역 테마 개편으로는 확대하지 않음. |
| 모달 조작 개선 | 현재 즉시 검색·더블클릭 선택 유지 | 목록과 동일한 조회 버튼 방식, 키보드 선택·Escape·포커스 복귀까지 요구하면 모달 동작 및 접근성 검증 추가. |
| 추가 관리 작업 | 신규 작성/편집만 | 삭제·복제·다건 작업은 별도 요구사항과 확인/충돌/참조 정책 필요. |
