- 작성일: 2026-11-18 (한국시간, Asia/Seoul)
- 상태: 사용자 검토용 설계 초안. 검토 및 직접 수정 후 별도 구현 요청 시 적용한다.
- 분석 기준: 현재 작업 트리의 소스. 기존 `PROMPT.md` 수정은 이번 작업과 별개이며 보존한다.

### 1.1 용어와 적용 범위

- **창 모드**는 헤더의 「AI 채팅 팝업으로 전환」으로 활성화하는 `floating === true` 상태로 해석한다. 브라우저 별도 창이 아니라 같은 페이지 위의 비모달 팝업이다.
- **패널 모드**는 페이지 옆에 붙어 본문과 공간을 나누거나 좁은 화면에서 레이어로 표시되는 상태다. 패널 경계 드래그는 이번 요구 범위에 포함하지 않는 권장안이다.
- **너비 조절**은 외부 `.matrix-ai-drawer`의 가로 크기 변경이다. 높이와 대화/입력 열 사이의 내부 분할선은 대상이 아니다.
- 입력 내용·첨부·모델·대상·현재 방·생성 상태를 유지하고, 크기 변경만으로 AI 요청이나 권한 재조회가 발생하지 않아야 한다.
- 최소·최대 너비, 양쪽 가장자리 제공, 키보드 대체 조작 및 수동 너비 복원 정책은 요구사항을 구체화한 권장안이다. 7절에서 검토한다.

### 2.2 현재 크기 규칙

`useAiWindow`의 계산은 다음과 같다.

```text
expanded = split ? splitExpanded : stackedExpanded
widthGrowth = expanded || split ? 100 : 0
popupBaseWidth = expanded ? 760 : 460
popupWidth = popupBaseWidth + widthGrowth
```

| 상태 | 팝업의 요청 너비 | 비고 |
| --- | --- | --- |
| 상하 기본 | 460px | stackedExpanded 기본 false |
| 상하 확대 | 860px | 760 + 100 |
| 좌우 분리 진입 | 860px | 분리 진입마다 splitExpanded를 true로 설정 |
| 좌우 분리에서 축소 | 560px | 460 + 100 |

- 실제 팝업 너비는 CSS에서 `min(요청 너비, 100vw - 24px)`로 제한한다. 860px는 현재 확대 프리셋이며 별도 수동 조절 상한은 아직 없다.
- 팝업 위치는 fixed, 기본 y=88px, z-index=55이고 배경 차단막 없이 본문을 조작할 수 있다.
- 높이는 기본 `min(720px, calc(100dvh - 100px))`, 최대 `calc(100dvh - 24px)`다. 700px 이하에서는 `min(600px, 70dvh)`를 사용한다.
- 패널은 960px 초과에서 작업 영역 30% 또는 50%에 상태별 100px를 추가한다. 960px 이하에서는 최대 440px이며 사이드바와 모바일 헤더 경계 규칙을 따른다.
- 팝업·패널 전환과 닫기에서는 채팅을 제거하지 않는다. 창 상태는 로컬 메모리이며 전체 새로고침에서 초기화된다.

### 2.3 이동과 화면 경계 보정

- 제목의 Pointer Events는 주 버튼만 허용하고 `setPointerCapture`로 포인터를 추적한다. pointerup/cancel/lostpointercapture에서 종료한다.
- 이동 시 실제 `getBoundingClientRect()` 크기로 상하좌우 12px 여백 안에 위치를 제한한다. 제목 방향키는 10px, Shift+방향키는 40px 이동이다.
- 팝업 진입의 최초 위치 계산에는 `popupWidth`를 사용한다. 열린 팝업은 popupWidth 변경과 window resize 후 실제 DOM 크기로 위치를 다시 보정한다.
- 수동 너비를 CSS에만 적용하면 최초 위치 계산과 effect가 참조하는 popupWidth가 실제 너비와 달라진다. 너비 상태·CSS·위치 보정의 기준을 함께 연결해야 한다.

### 2.4 좌우 분리의 영향

- `.matrix-ai`는 `container: ai-chat / inline-size`를 사용한다. **내부 콘텐츠 너비 560px 이상**일 때만 split 선택이 실제 좌우 배치로 표시된다. 외부 창 560px와 같은 기준이 아니다.
- 분리 레이아웃은 기존 대화 열의 60% 배분과 입력 열 최소 240px을 기준으로 계산하고, `--ai-added-width`의 실제 추가분을 입력 열에 배분한다.
- 팝업의 `--ai-added-width`는 현재 viewport와 popupBaseWidth로 계산한다. 수동으로 창을 줄였는데 viewport가 넓으면, 실제 없는 추가분 100px을 계속 공제할 수 있다.
- 따라서 수동 너비를 반영한 **실제 추가분** 계산을 함께 수정해야 한다. 단순히 CSS width만 덮어쓰는 변경으로 끝내면 두 열 비율과 입력 가용 영역에 오차가 생길 수 있다.
- 기존 상단·대화 footer·입력 카드의 grid 배치 및 독립 스크롤은 유지한다. 좁아지면 container query가 상하 배치로 복귀하고 split 선택 자체는 유지한다.

## 3. 수정 방향

### 3.1 조작 UI 권장안

1. 열린 팝업의 왼쪽·오른쪽 테두리 안쪽에 너비 조절 영역을 둔다. 제목 이동 영역과 분리하고 패널 모드에서는 렌더링하지 않는다.
2. 조절 영역의 포인터 커서는 `ew-resize`, 실제 클릭 폭은 8px을 초안으로 한다. hover·focus·조절 중에는 테마 색으로 경계를 표시한다.
3. 조절 영역은 aside의 직접 자식으로 두어 대화/입력 스크롤과 분리한다. drawer의 `overflow:hidden` 때문에 바깥쪽 핸들이 잘리지 않도록 테두리 안쪽에 배치한다.
4. 헤더 버튼과 본문 컨트롤의 클릭을 가리지 않도록 내부 여백과 조절 영역의 겹침을 검증한다. 높이·모서리 대각선 조절은 추가하지 않는다.
5. 포커스를 받을 수 있는 세로 separator로 제공하고 「AI 채팅 창 왼쪽/오른쪽 너비 조절」 접근성 이름, `aria-controls="matrix-ai-panel"`, 현재/최소/최대 너비 값을 제공한다.
6. 키보드 좌우 방향키로 10px, Shift 조합으로 40px 조절한다. 왼쪽 핸들은 왼쪽 방향이 확대, 오른쪽 핸들은 오른쪽 방향이 확대다. Home/End는 해당 가장자리를 기준으로 최소/최대 너비를 적용하는 권장안이다.

### 3.2 너비 상태와 우선순위

`useAiWindow`에 상하용·분리용 사용자 지정 너비(`number | null`)와 조절 중 상태를 추가한다. 포인터 시작 정보는 ref로 관리하며 다음 값을 보관한다.

```text
pointerId, edge(left/right), startClientX,
startLeft, startRight, startWidth, startTop
```

- 현재 배치의 사용자 지정 너비가 있으면 프리셋보다 우선한다. 없으면 기존 popupBaseWidth + widthGrowth를 사용한다.
- 드래그 시작 너비는 프리셋 숫자가 아니라 현재 표시 중인 DOM의 border-box 너비로 읽는다. viewport 제한으로 작게 보이던 창이 첫 움직임에 커지는 현상을 방지한다.
- CSS에는 팝업 전용 요청/표시 너비 변수를 연결한다. 패널의 grid 너비와 `--ai-window-growth`를 사용자 지정 값으로 덮어쓰지 않는다.
- `popupWidth` 및 팝업 진입 위치 계산도 같은 유효 너비를 사용한다. 열린 상태의 보정 effect에는 사용자 지정 너비 변경이 반영되어야 한다.
- 확대 여부는 계속 기존 프리셋 선택 상태를 의미한다. 수동 너비가 프리셋과 다르면 tooltip과 접근성 안내에서 「사용자 지정 너비 · 현재 Npx · 확대/축소 시 프리셋 적용」을 알리고, aria-pressed만으로 현재 너비를 설명하지 않는다.
- 현재 상하 기본 상태에서 수동으로 900px까지 늘린 뒤 확대 버튼을 누르면 860px로 돌아갈 수 있다. 버튼은 프리셋 전환이라는 정책을 안내하고 7절에서 확정한다.

### 3.3 너비 제한과 가장자리별 계산

권장 최소 너비는 **360px**, 최대 너비는 **viewport 너비 - 24px**다. 화면이 작으면 화면 제한을 우선하며, 860px를 수동 조절의 최대치로 사용하지 않는 권장안이다.

```text
margin = 12
viewportMax = max(0, viewportWidth - 2 * margin)
minWidth = min(360, viewportMax)
deltaX = currentClientX - startClientX

오른쪽 핸들:
  maxWidth = viewportWidth - margin - startLeft
  width = clamp(startWidth + deltaX, minWidth, maxWidth)
  x = startLeft

왼쪽 핸들:
  maxWidth = startRight - margin
  width = clamp(startWidth - deltaX, minWidth, maxWidth)
  x = startRight - width
```

- 계산 전 현재 창이 화면 안에 있다는 조건을 보장한다. resize로 화면이 바뀌면 진행 중 조절을 먼저 끝내고 위치·너비를 정상화한다.
- 오른쪽 핸들은 왼쪽 경계를, 왼쪽 핸들은 오른쪽 경계를 고정한다. 오른쪽에 붙어 있는 창도 왼쪽 핸들로 넓힐 수 있다.
- 두 방향 모두 y와 높이는 유지한다. 범위를 넘어 드래그해도 창이 화면 밖으로 나가거나 반대쪽 경계가 갑자기 이동하지 않는다.
- viewport 축소에서는 표시 너비와 위치를 제한하되 메모리에 있는 사용자 희망 너비는 유지한다. viewport가 다시 넓어지면 복원하고 필요 시 x를 재보정한다.
- 화면이 좁아 너비 변경 여유가 없으면 조절 영역은 비활성화하고 키보드 조절도 막는다. viewport 기준과 CSS의 `100vw`가 일치하는지 스크롤바가 있는 화면에서도 확인한다.

### 3.4 포인터 이벤트와 종료 처리

- 기존 제목 이동과 같은 Pointer Events를 사용한다. CSS `resize:horizontal`은 반대편 경계 고정·React 상태 동기화·프리셋 복원 제어가 어려워 권장하지 않는다.
- pointerdown에서 열린 floating 상태와 주 버튼을 확인하고 현재 rect를 저장한다. 기본 선택 동작을 막고 포커스와 pointer capture를 설정한다.
- pointermove에서 시작 rect와 전체 이동량으로 x와 width를 함께 계산한다. 이전 이벤트의 React state에 누적하는 방식은 사용하지 않는다.
- 위치 이동과 너비 조절은 동시에 활성화하지 않는다. 공통 조작 종료 함수를 두거나 단일 조작 ref에 종류를 저장해 중복을 방지한다.
- pointerup/cancel/lostpointercapture에서 마지막 유효 크기를 유지하고 capture와 조절 중 상태를 해제한다.
- 닫기, 팝업→패널, 배치·프리셋 전환, viewport resize, window blur, 컴포넌트 unmount에도 조작을 정리한다. 열린 dialog가 Escape를 처리하는 기존 흐름과 충돌하지 않도록 별도 전역 Escape 동작은 추가하지 않는다.
- `touch-action:none`은 조절 영역에 한정하고 user-select 차단도 조작 중에만 적용한다. 종료 후 텍스트 선택과 입력이 복구되어야 한다.
- 드래그 중 width/left 전환 애니메이션은 넣지 않는다. 현재 opacity와 열림 전환 및 reduced-motion 정책은 유지한다.

### 3.5 실제 추가분과 내부 열 계산

팝업의 표시 너비를 W, 현재 popupBaseWidth를 B, widthGrowth를 G라 하면 다음 값을 기준으로 한다.

```text
effectiveAddedWidth = min(G, max(0, W - B))
```

- 기존 프리셋에서는 100px, 화면 제한에 걸리면 40px 또는 0px인 기존 배분을 유지한다.
- 사용자 지정 너비가 B보다 작아지면 추가분은 0px다. 100px보다 더 늘어난 수동 증가분은 기존 열 배분식에 따라 나누고, 기존 보너스 100px만 입력 열 전용으로 취급한다.
- 예: 상하 확대 프리셋을 선택한 상태에서 수동 너비 700px이면 B=760, G=100이므로 추가분은 0px이다. 사용자 지정 820px이면 60px, 1000px이면 100px다.
- CSS 변수 또는 훅 계산으로 이 값을 일관되게 전달한다. DOM 측정 시 border-box 단위를 통일하고 내부 콘텐츠 너비 560px query와 혼동하지 않는다.
- 수동 증가분 전체를 입력 열에 배분하고 대화 열을 계속 고정하는 요구는 현재 요청에 없으므로 별도 선택 사항으로 남긴다.

## 4. 모드 전환과 상태 유지 정책

아래는 기존 모드 동작과 사용자 지정 너비를 결합한 권장안이다.

| 동작 | 사용자 지정 너비 처리 | 기존 상태와의 관계 |
| --- | --- | --- |
| 팝업에서 직접 너비 조절 | 현재 상하/분리 슬롯에 저장 | expanded 선택은 자동 변경하지 않음 |
| 팝업의 확대/축소 버튼 | 현재 슬롯의 사용자 지정 값 해제 후 기존 프리셋 전환 | 상하 460/860px, 분리 560/860px 복원 |
| 상하→좌우 분리 | 분리 슬롯을 초기화하고 확대 프리셋으로 진입 | 기존 「분리 진입마다 확대」 유지, 상하 슬롯 보존 |
| 좌우 분리→상하 | 상하 슬롯이 있으면 복원, 없으면 상하 프리셋 복원 | 기존 stackedExpanded 보존 |
| 팝업→패널→팝업 | 같은 배치의 사용자 지정 값을 보관·복원 | 패널은 기존 비율 규칙 사용, 위치는 기존 진입 규칙으로 보정 |
| 패널에서 배치/확대 변경 | 관련 팝업 슬롯을 같은 전환 규칙에 따라 정리 | 다시 팝업으로 전환할 때 선택된 프리셋과 크기의 불일치 방지 |
| 닫기→재열기·방 전환 | 레이아웃 인스턴스가 유지되는 동안 보존 | 채팅 내용/방 scope의 기존 초기화 규칙은 그대로 적용 |
| 전체 새로고침·레이아웃 재마운트 | 사용자 지정 값 초기화 | localStorage·DB 저장은 도입하지 않음 |

프리셋·배치 조작을 위한 기존 네 개 헤더 버튼 순서는 유지한다. 너비 조절은 별도 가장자리 요소로 제공한다.

## 6. 검증 방법

### 6.1 구현 후 기능·회귀 시나리오

| 항목 | 방법과 기대 결과 |
| --- | --- |
| 양쪽 너비 조절 | 실제 pointerdown→move→up으로 좌우 확대·축소. 실제 rect 너비가 이동량만큼 바뀌고 반대편 경계/y/높이 유지 |
| 최소·최대 | 360px 이하 드래그와 viewport 밖 드래그. 최소 너비 및 각 방향의 12px 여백 제한 준수 |
| 포인터 추적 | 핸들 바깥으로 이동해도 capture로 조절 지속. 우클릭·비활성 패널에서 시작하지 않음 |
| 조작 종료 | cancel/lostcapture/blur/닫기/패널 전환/resize 뒤 커서·선택 차단·조작 ref가 정리되고 재조작 가능 |
| 이동 회귀 | 수동 너비에서 제목 드래그와 방향키 이동. 현재 실제 너비를 기준으로 12px 경계 보정 |
| 프리셋·복원 | 수동 조절→확대/축소→분리/상하→패널/팝업을 표 4의 정책대로 확인. 프리셋 상태에서 460/560/860px 유지 |
| viewport 변경 | 1440/961/960/701/700/390px에서 화면 안 표시. 축소 후 확대하면 희망 너비 복원, 좁은 화면에서는 허용 범위 우선 |
| 좌우 분리 경계 | 내부 콘텐츠 너비 559/560/561px에서 상하/좌우 배치 전환. 외부 창 너비와 구분하여 실측 |
| 추가분 계산 | 프리셋의 100/40/0px 배분과 사용자 지정 W<B, B<W<B+100, W>B+100을 검증. 입력 최소 240px·footer 정렬·독립 스크롤 유지 |
| 상태 보존 | textarea DOM identity, 입력값, 첨부, 모델, 대상, 선택 방이 동일하고 진행 중 생성/중지 조작 유지 |
| 네트워크 | 순수 너비 조절·프리셋·배치 변경에서 `/api/ai/*`와 프로젝트 access 호출 증가 없음. 기존 헤더 카운터 폴링과 구분 |
| 본문 조작 | 비모달 본문 버튼·입력·스크롤 및 메뉴 접기 정상. 팝업 너비 변경으로 본문 grid 공간을 차지하지 않음 |
| 시각·접근성 | light/dark, reduced-motion, 키보드 너비 조절 및 focus 표시 확인. 작은 화면에서 헤더 네 버튼과 입력/첨부/전송 접근 가능 |
| 낮은 화면 높이 | 1440×480 등에서 조절 핸들·헤더 버튼·전송 버튼에 접근 가능하고 대화/입력 스크롤 유지 |

기존 `scripts/check-ai-window-browser.mjs`는 실제 방과 미전송 입력·첨부를 준비한 AI 대상 브라우저 검증에서 호출된다. 프리셋 단언을 제거하지 않고 수동 조절 사례를 추가하며, 각 사례 이후 원래 배치로 복원해 후속 검증에 영향을 주지 않는다.

### 6.2 구현 후 실행 계획

- 타입·정적 검사: `pnpm typecheck`, 변경 소스 대상 ESLint.
- 빌드: `pnpm build`.
- 핵심 브라우저 회귀: 빌드 후 `pnpm test:ai-targets-browser`. `check-ai-target-browser.mjs` → `check-ai-window-browser.mjs` 실행 경로를 사용한다.
- 공유 관리 footer와 모달 상호작용까지 영향을 주는 변경이 생기면 `pnpm test:shared-answers-browser`를 추가한다.
- 브라우저 검증은 기존 스크립트의 임시 SQLite·합성 계정·모의 AI·별도 브라우저 프로필을 사용한다. 운영 DB나 실제 AI 호출로 검증하지 않는다.
- 실제 이벤트와 DOM 기하값을 검증하고, 구현 함수와 같은 계산을 복제한 테스트만으로 통과 판정을 내리지 않는다.

### 6.3 이번 문서 단계의 확인

- 소스·기존 README·관련 설계·브라우저 검증 코드를 읽어 현재 구조를 분석했다.
- 작성 문서의 필수 항목, 날짜/파일명, HISTORY 상대 링크 및 기존 목록 보존을 확인한다.
- git diff로 이번 변경이 이 문서와 HISTORY 추가에 한정되는지 확인하고 기존 `PROMPT.md` 변경과 구분한다.
- 구현·빌드·브라우저·DB 테스트는 실행하지 않는다. 위 검증표는 구현 완료 결과가 아닌 후속 검증 계획이다.
